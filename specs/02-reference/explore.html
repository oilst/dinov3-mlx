Step 2 Reference: Explore

Roadmap step 2. Status: decided. On 2026-11-06 the user chose the recommended option of each decision D1 to D7 (Table 1). Date: 2026-11-06.

1 Goal

Step 2 gives every later step a fixed reference output and the parity tests. The reference output comes from the Hugging Face backbone on torch-cpu in fp32. The parity tests compare torch-mps in fp32, fp16 and bf16 with it. Steps 4 and 5 run the same tests on mlx.

The task fixes these points. They are not options:

  • Model sizes: all six. Meta approved the access on 2026-11-06, and the Hugging Face cache holds all six model sizes. The converted weights of ViT-S/16 and ViT-H+/16 stay as a fallback. Their tensors are equal to the Hub tensors (specs/01-scope/verify.html, Section 11).
  • The weight loader reads the Hugging Face cache first and the converted folder second. A missing model size skips with a reason.
  • The reference outputs go into tests/fixtures/generated/. Git ignores this folder.
  • One heavy job at a time, the MPS watermarks, and a memory check before each model load.

This page has seven decisions. Table 1 gives the options and the recommendations. Section 3 gives the trade-offs and the measurements.

2 DINOv3 topic

The topic is the tokens and the two outputs. The token sequence has 1 CLS token, 4 register tokens and N patch tokens. The final layer norm acts on all tokens. The frame embedding is the CLS token after the final layer norm. The patch embeddings are the patch tokens after the final layer norm. No output includes the register tokens. The explainer docs/learn/02-tokens-and-outputs.html covers these parts.

The probe of Section 3.1 found a surprise for the explainer. Inside the backbone, one register token holds very large values. In ViT-H+/16 at 224 px, the register token at sequence position 2 holds values up to 130,689 from block 23 on. The largest fp16 value is 65,504. So ViT-H+/16 with fp16 weights gives NaN on torch-mps. The final layer norm removes the large values: the outputs stay below 13. Figure 1 and Table 2 show the values.

3 Design

3.1 The probe

We ran a probe on 2026-11-06 to get numbers for the decisions. The probe used the converted weights of ViT-S/16 and ViT-H+/16 and one image: COCO 000000039769 (640 × 480 px). This image is also the image of the conversion check of Step 1. The converted tensors are equal to the Hub tensors, so the results also apply to the Hub weights. The probe compared three preprocessing methods on torch-cpu in fp32. Then it compared torch-mps in five dtype modes with torch-cpu in fp32. Each model size ran in its own process, one after the other. The free memory was 15 GB (free and inactive pages) before each load. Table 3 gives the results.

Red marks a value below the frame threshold of Table 9 of docs/plan.html for the dtype of the row (0.9999 for fp32, 0.999 for fp16 and bf16). "Cast" puts all weights and inputs in the dtype. Four results drive the decisions:

  1. A resize of 8-bit pixels moves each pixel by up to 0.0039. For ViT-H+/16 at 224 px, this drops the patch minimum to 0.929. The preprocessing must be the same for all backends (D2).
  2. A Pillow resize of float pixels equals the torch float resize within 8.2e-6 per pixel. The outputs agree to 1.000000 (D2).
  3. fp16 with cast weights overflows in ViT-H+/16 at 224 px, but not at 512 px. The input resolution changes the token values (D3, D5).
  4. The patch minimum depends on one patch. For ViT-H+/16 in bf16 autocast it is 0.988567 at 224 px and 0.999913 at 512 px. The 1st percentile is 0.99785 and 0.99998 (D6).

3.2 D1: test images

The images must be public domain, so that the public repo can hold them. They must have at least two aspect ratios.

Option A: scikit-image sample images. For example astronaut (512 × 512 px, public domain, NASA), coffee (400 × 600 px, CC0) and rocket (427 × 640 px, public domain, SpaceX). The scikit-image documentation gives these licenses.

  • For: the licenses are documented. The files are small.
  • Against: the images are small (640 px or less), so the 512 px input resolution needs an upscale. All three are square or landscape. No image is 16:9 or portrait. CC0 is a public-domain dedication, not public domain by law.

Option B: public-domain photos from Wikimedia Commons. We pick three photos that are works of a US federal agency, for example NASA. One photo is 16:9 landscape, the shape of a video frame, with people and equipment indoors. One is 4:3 landscape with fine texture outdoors. One is 3:4 portrait. We store each one at 1024 px on the long side as JPEG with quality 95, about 200 KB. A file tests/fixtures/images/SOURCES.md names the page, the author and the license of each photo.

  • For: real image statistics. Enough pixels for every input resolution up to 768 px. The 16:9 photo has the shape of our video frames. The portrait photo and the 4:3 photo give the same patch grid with rows and columns swapped, so a swap of height and width fails a test.
  • Against: we must check the license page of each photo. About 600 KB in git.

Option C: synthetic images from code. Gradients, checkerboards and noise.

  • For: no license, no file.
  • Against: far from the training data. Table 2 shows that the token values depend on the input. A parity pass on noise says little about real images.

Option D: COCO images, downloaded at test time.

  • For: the Hugging Face converter uses COCO 000000039769, so we can compare with its published values.
  • Against: COCO images have Flickr licenses. They are not public domain, so the repo cannot hold them. The tests need the network once.

Recommendation: Option B. Three public-domain photos at 16:9, 4:3 and 3:4. The plan names the three files after a check of each license page. COCO 000000039769 stays only in the conversion check of Step 1, as now.

3.3 D2: preprocessing

The Hugging Face image processor DINOv3ViTImageProcessor (transformers 5.22.1) does three actions: it divides the 8-bit pixels by 255, it resizes the float pixels (bilinear, with antialiasing), and it normalizes with the ImageNet mean and standard deviation. It resizes to a fixed 224 × 224 px and ignores the aspect ratio. It needs torchvision. Our project does not install torchvision.

Option A: torch float resize. Pillow decodes the image to 8-bit RGB. We divide by 255 to get float32 values. torch.nn.functional.interpolate resizes with mode="bilinear" and antialias=True. Then we normalize.

  • For: the same math as the Hugging Face image processor. scripts/convert_meta_checkpoint.py already uses it.
  • Against: it needs torch. The MLX path of Step 6 needs its own resize.

Option B: Pillow float resize. We put each color channel into a float32 Pillow image (mode F) and resize it with BILINEAR. Pillow antialiases when it makes an image smaller.

  • For: NumPy and Pillow only, no torch. Table 3: at most 8.2e-6 per pixel from Option A, parity 1.000000.
  • Against: three resizes per image, one for each channel. A later Pillow version can move away from torch.

Option C: the Hugging Face image processor.

  • For: exactly what Hugging Face users get.
  • Against: one more pinned package (torchvision). It always resizes to a fixed size, so the own aspect ratio of D3 needs a second call.

Separate choice: store the pixel tensor. The reference script stores the normalized fp32 pixel tensor of each image and input resolution. Every backend reads these stored pixels. Then the parity tests measure only the backbone, and no preprocessing difference can hide in them. A separate test compares our preprocessing function with the stored pixels.

Recommendation: Option A, and store the pixel tensor. Option B stays a candidate for the MLX path of Step 6. A test then compares B with A, with a limit of 1e-5 per pixel.

3.4 D3: input resolutions

Table 9 of docs/plan.html asks for 224, 448 and 512 px, and one non-square input, for example 224 × 320 px. Section 7 of docs/plan.html names two priority configurations: ViT-S/16 with frame embeddings, and ViT-H+/16 and ViT-S/16 with patch embeddings at 512 px. Table 3 shows that the input resolution changes the token values. The counts below are for three images and one model size.

Option A: the Table 9 minimum. Every image at 224, 448 and 512 px square. The Hugging Face image processor also resizes to a square and ignores the aspect ratio. One image at 224 × 320 px. 10 configurations.

  • For: the least compute.
  • Against: one non-square grid in one orientation only.

Option B: square plus own aspect ratio. Every image at 224, 448 and 512 px square. Every image also at its own aspect ratio: the short side is 224 px, and the long side is rounded to the nearest multiple of 16. For example 224 × 400 px for 16:9, 224 × 304 px for 4:3 and 304 × 224 px for 3:4. 12 configurations.

  • For: non-square grids in both orientations. A swap of height and width in the RoPE tables or in the reshape of the patch embeddings fails a test.
  • Against: 2 more configurations than Option A.

Option C: Option B plus 768 px square. 15 configurations.

  • For: covers the largest crop of the high-resolution adaptation.
  • Against: Table 11 of docs/plan.html has no 768 px configuration. ViT-7B/16 at 768 px in fp32 on torch-cpu is slow and needs about 27 GB for the weights alone.

Recommendation: Option B. Step 6 can add 768 px when it studies the attention cost.

3.5 D4: storage format

For each configuration we store the input and the output:

  • The normalized fp32 pixel tensor (D2).
  • All tokens after the final layer norm, in fp32: the CLS token, the 4 register tokens and the patch tokens. The frame embedding and the patch embeddings are slices of these tokens.
  • Metadata: the versions of transformers, torch and Pillow, the SHA-256 of each image and of each weight file, the weight source (Hugging Face cache or converted folder), the preprocessing settings and the date.
  • For one configuration per model size (first image, 224 px square): the token sequence after each block. Step 4 then finds the first block that differs.

Size for D3 Option B: about 21 MB of pixels for all model sizes. Tokens: 11 MB for ViT-S/16, 36 MB for ViT-H+/16 and 114 MB for ViT-7B/16. Hidden states for one configuration: 34 MB for ViT-H+/16 and 135 MB for ViT-7B/16.

Option A: safetensors. One file inputs.safetensors for the pixels. One file per model size, for example reference-vith16plus.safetensors, with keys such as photo1/224x224/tokens. The metadata goes into the safetensors header as JSON text.

  • For: already a dependency. No pickle. torch, NumPy and mlx.core.load read it. A test loads one tensor without the full file. One file per model size lets a test skip a missing model size, and we can make one model size again alone.
  • Against: the header holds text only, so the metadata is a JSON string.

Option B: NumPy .npz plus a JSON file.

  • For: NumPy only. mlx.core.load reads it.
  • Against: two files per model size. No place for metadata inside the file.

Option C: torch .pt.

  • For: one line to write.
  • Against: pickle. The MLX tests of Step 4 then need torch to read the reference.

Recommendation: Option A, with all tokens and with the hidden states for one configuration per model size.

3.6 D5: fp16 and bf16 on torch-mps

PyTorch can run a backbone in half precision in two modes. Cast mode puts all weights and inputs in the dtype. Autocast mode keeps the weights in fp32: torch.autocast runs the matrix products in the dtype and keeps the layer norms and the residual stream in fp32. MLX in Step 5 works like cast mode. The reference fine-tuning setup uses fp16 autocast (Table 12 of docs/plan.html). bf16 has the range of fp32, so it does not overflow.

Option A: cast mode only.

  • For: the same mode as MLX. Half the weight memory.
  • Against: ViT-H+/16 in fp16 fails at 224 px (Table 3). The baseline then has no fp16 value for ViT-H+/16.

Option B: autocast mode only.

  • For: it works for both model sizes. It is the mode of the reference fine-tuning setup.
  • Against: an MLX result in fp16 has no partner in the same mode. The weights stay in fp32.

Option C: both modes. Four half-precision modes: fp16 cast, bf16 cast, fp16 autocast and bf16 autocast.

  • For: the full picture. The overflow becomes a recorded result, and Step 5 knows it before the MLX work.
  • Against: twice the half-precision runs on torch-mps. Each run takes about one second.

Recommendation: Option C. The parity test of ViT-H+/16 in fp16 cast mode records the overflow as an expected failure with its reason. Step 5 must solve the overflow for MLX, for example with an fp32 residual stream.

3.7 D6: patch threshold

Table 9 of docs/plan.html gives frame thresholds: 0.9999 for fp32, 0.999 for fp16 and bf16. The probe passes them with a margin (Table 3). Table 9 leaves the patch threshold to Step 2.

Option A: thresholds on the mean and the minimum.

  • For: the simplest rule. One wrong patch fails the test.
  • Against: one sensitive patch sets the minimum. For bf16, the minimum threshold must go down to about 0.98. Such a low limit lets real errors in other patches pass.

Option B: thresholds on the mean and the 1st percentile. The report also gives the minimum.

  • For: one sensitive patch does not set the limit. An error in one row or one column of patches still fails: at 224 px one row is 14 of 196 patches, which is 7 %.
  • Against: an error in less than 1 % of the patches passes the threshold. The minimum in the report still shows it.

Option C: one threshold for each model size and dtype, from the torch-mps values minus a margin.

  • For: the tightest limits.
  • Against: many numbers. A new torch version can move them. The mission asks for one threshold for each dtype.

Recommendation: Option B. The plan sets the numbers from the measurements on all test images. The frame thresholds of Table 9 stay, unless the full measurement shows a reason to change them.

3.8 D7: ViT-7B/16

The reference output comes from torch-cpu in fp32 (GLOSSARY.md). The weights of ViT-7B/16 need 26.9 GB in fp32 and 13.4 GB in fp16 or bf16. The run rules of CLAUDE.md say: run ViT-7B/16 in fp16, bf16 or with quantized weights. Step 2 of docs/plan.html allows one fp32 run for the reference output, after a memory check. On 2026-11-06 at 16:20, memory_pressure gave 57 % free memory, about 36 GiB.

Option A: fp32 reference on torch-cpu, half precision on torch-mps. The reference script runs ViT-7B/16 last, in its own process, after a memory check. The torch-mps tests of ViT-7B/16 run in fp16 and bf16 only. fp32 on torch-mps skips with a reason.

  • For: a true fp32 reference for all six model sizes. It follows docs/plan.html and the run rules.
  • Against: about 27 GB in one process. The peak of the load can be higher than the weights. The plan measures the load peak of ViT-H+/16 first and scales it to ViT-7B/16.

Option B: a bf16 reference for ViT-7B/16. torch-cpu in bf16 makes the reference output of ViT-7B/16.

  • For: half the memory.
  • Against: a bf16 output has its own error of about 1e-4 (Table 3, bf16 rows). The parity of the half-precision backends then measures two errors together.

Option C: Option A, plus fp32 on torch-mps.

  • For: a full fp32 row for ViT-7B/16.
  • Against: it breaks the run rule of CLAUDE.md. The MPS high watermark (0.8) leaves little room next to 27 GB of weights.

Recommendation: Option A. When the memory check fails, the script skips ViT-7B/16 and records the reason. The run of ViT-7B/16 in fp16 cast mode can show the same overflow as ViT-H+/16. The test then records it.

9 Open questions
