1 Goal and context

Step 5 extends the MLX backbone of Step 4 to all six model sizes and to fp16 and bf16. The step ends when all model sizes pass the parity tests on the backend mlx, or when verify.html explains each failure. Step 5 in Section 6 of docs/plan.html sets this condition. This page gives the decisions with real options, the trade-offs and one recommendation for each decision.

These points are fixed. They are not options:

  • The MLX backbone of Step 4: modules with the names of the safetensors file, the key map at load time, RoPE tables from NumPy fp32, the patch embedding as one matmul, mx.fast.scaled_dot_product_attention, and the fp32 dtype mode with TF32 off (ADR 0005). The target of the RoPE tables is the Hugging Face tables (ADR 0006).
  • The reference output: the reference files of Step 2 (torch-cpu, fp32) for five model sizes. The thresholds of ADR 0003 hold for every backend and model size: fp32 0.9999 / 0.9999 / 0.9999, fp16 0.999 / 0.999 / 0.99, bf16 0.998 / 0.995 / 0.96 (frame embedding, patch mean, patch 1st percentile).
  • RoPE stays in fp32 in every dtype mode, as the official code does (Step 5 in docs/plan.html). apply_rope already rotates in fp32 and casts the result back.
  • The run rules of CLAUDE.md: one heavy job at a time, a memory check before each model load, mx.set_memory_limit for MLX, and ViT-7B/16 in fp16, bf16 or with quantized weights only.
  • Versions: mlx 0.32.4, transformers 5.22.1, torch 2.15.0. Hardware: M5 Max with 64 GB of unified memory.
  • Later steps: Step 6 adds mx.compile, the mlx benchmark and quantized weights. Step 8a adds LoRA on q_proj and v_proj in fp16 autocast. Step 8b adds adapters on all linear layers and on the feed-forward activations. The Step 5 design must not block these steps.

Nine findings shape the decisions:

  1. Only D and FF change the shapes. All model sizes use the same tensor names. ViT-S+/16, ViT-H+/16 and ViT-7B/16 add layer.N.mlp.gate_proj.weight (FF, D) and layer.N.mlp.gate_proj.bias (FF). ViT-7B/16 has no q_proj.bias and no v_proj.bias. Its head dimension is 128, so its RoPE has 32 frequencies, not 16 (D1).
  2. The SwiGLU formula. DINOv3ViTGatedMLP.forward in transformers 5.22.1 computes down_proj(act_fn(gate_proj(x)) * up_proj(x)). Only gate_proj gets the activation. act_fn is SiLU: silu(z) = z · sigmoid(z), nn.silu in MLX. gate_proj, up_proj and down_proj each have a bias (D1).
  3. The port stops at SwiGLU. Block raises NotImplementedError for a gated config, and MLP raises it for hidden_act "silu" (src/dinov3_apple/mlx_model.py). block_parameter_names builds a probe block without a gate, so map_key raises UnknownWeightError for gate_proj. The hook "the key map already accepts mlp.gate_proj" in Table 5 of specs/04-mlx-port/plan.html is stale since the F4 fix (D1).
  4. One dtype for each mode. MLX_DTYPE_MODES maps each mode to one dtype. It cannot express fp16 or bf16 matmuls with an fp32 residual stream (D2).
  5. The official precision is bf16 autocast with RoPE in fp32. The official eval code runs torch.autocast with bf16 on fp32 weights. Every hub backbone sets pos_embed_rope_dtype="fp32". The backbone path of the official code never uses fp16. The Hugging Face code casts the RoPE tables to the dtype of the pixels. So in cast mode on torch-mps, the rotation runs in fp16 or bf16 (D2).
  6. The MLX kernels. The matmul kernels accumulate in fp32 and round once. The SDPA kernel computes the scores, the softmax and P · V in fp32 (Note after Verify (2026-11-07): measured on this Mac (Apple M5 Max, mlx 0.32.4), the half kernel does not compute in fp32 inside. See finding F3 of verify.html and ADR 0007.) The layer norm accumulates in fp32 and rounds twice. nn.silu and nn.gelu round after each operation (D2).

# src/dinov3_apple/mlx_model.py (shape of the code, not final)
class SwiGLU(nn.Module):
    """The feed-forward network of ViT-S+/16, ViT-H+/16 and ViT-7B/16."""

    def __init__(self, config: MlxConfig) -> None:
        super().__init__()
        if config.hidden_act != "silu":
            raise NotImplementedError(f"activation {config.hidden_act!r} of SwiGLU")
        self.gate_proj = nn.Linear(config.dim, config.ff, bias=config.mlp_bias)
        self.up_proj = nn.Linear(config.dim, config.ff, bias=config.mlp_bias)
        self.down_proj = nn.Linear(config.ff, config.dim, bias=config.mlp_bias)

    def __call__(self, x: mx.array) -> mx.array:
        """Return down_proj(silu(gate_proj(x)) * up_proj(x)). The product runs in fp32 (D2)."""
        gate = self.gate_proj(x).astype(mx.float32)
        up = self.up_proj(x).astype(mx.float32)
        return self.down_proj((nn.silu(gate) * up).astype(x.dtype))

self.mlp = SwiGLU(config) if config.gated else MLP(config)

3.2 D2: MLX dtype modes and their names

Step 5 must run fp16 and bf16 on mlx. On torch-mps there are two kinds of dtype mode. In cast mode, the weights, the inputs and the residual stream are in fp16 or bf16. In autocast mode, the weights and the residual stream stay in fp32, and torch.autocast runs the matmuls in fp16 or bf16. The question is which modes mlx gets, and their names.

Option A: cast modes only. fp16-cast and bf16-cast: the weights and all activations in half precision. RoPE stays in fp32.

Option B: cast modes and an autocast-like mode under the names fp16-autocast and bf16-autocast. The weights of the matmuls are in half precision. The residual stream, the layer norms, LayerScale, the CLS token and the register tokens stay in fp32. The SDPA kernel keeps the softmax in fp32. RoPE stays in fp32.

Option C: the same modes as B under new names, for example fp16-mixed and bf16-mixed.

Option D: a real autocast on mlx. fp32 weights, and a cast of each weight to half precision at each call.

3.3 D3: fp16 overflow of ViT-L/16 and ViT-H+/16

In fp16-cast, the residual stream is fp16. A register token of ViT-L/16 or ViT-H+/16 goes above 65,504 (Table 3). The value becomes infinite. The next layer norm or softmax then gives NaN. MLX rounds the matmul output to fp16 in the same way as torch-mps, so we expect the same failures: ViT-L/16 at every input resolution, ViT-H+/16 at the inputs with a 224 px short side. ViT-7B/16 is open: on torch-mps it gave finite fp16-cast output at 224 × 224 px for the three test images.

Option A: accept the overflow, as on torch-mps. fp16-cast is "not valid" for these model sizes. fp16-autocast and the bf16 modes give their fp16 and bf16 rows. This is risk R6 of docs/plan.html: "Use bf16 where fp16 fails".

Option B: an fp32 residual stream also in fp16-cast. Then fp16-cast equals fp16-autocast.

Option C: a scaled residual stream. Divide the residual stream by a power of two s, for example 4. The load divides the CLS token, the register tokens, the patch-embedding weight and bias, and each λ by s. The layer norms use eps / s². In exact arithmetic, LN(x / s, eps / s²) = LN(x, eps), so the outputs do not change. 157,130 / 4 = 39,283 fits in fp16. This is our own derivation. Nobody measured it.

Option D: no fp16 rows for ViT-L/16, ViT-H+/16 and ViT-7B/16. The tests skip fp16 for these model sizes.

def check_finite(tokens: np.ndarray, model_size: str, dtype_mode: str, note: Callable[[], None]) -> None:
    """Record and xfail an expected overflow. Fail any other non-finite output."""
    if np.isfinite(tokens).all():
        return
    note()  # writes the result line with the status "non-finite"
    if (model_size, dtype_mode) in EXPECTED_FP16_OVERFLOW:
        pytest.xfail(FP16_OVERFLOW)
    pytest.fail("non-finite output")

5.2 Terms for GLOSSARY.md

  • Matmul: one matrix multiplication of the backbone, for example in an nn.Linear module or in the patch embedding.
  • Autocast mode (changed): a dtype mode in which the matmuls run in fp16 or bf16, and the residual stream, the layer norms and LayerScale stay in fp32. On torch, the weights stay in fp32 and torch.autocast casts them at each matmul. On mlx, the load casts the weights of the matmuls once.
  • Residual stream: the token sequence that passes from block to block. Each branch of a block adds its output to it.
  • Matmul dtype: the dtype of the weights and the inputs of the matmuls in one dtype mode of mlx.
  • Stream dtype: the dtype of the residual stream, the layer norms, LayerScale, the CLS token and the register tokens in one dtype mode of mlx.
  • Branch output: the output of the attention branch or the feed-forward branch of a block, before LayerScale.
  • Token range: the largest absolute value in the token sequence before block 1 and after each block, for one configuration.
  • Streamed reference: a reference output computed on torch-cpu in fp32 with one block in memory at a time. ViT-7B/16 uses it.
  • Small model (changed): a Hugging Face backbone with 2 blocks and random weights (tests/small_model.py). It has the values of ViT-S/16 or of ViT-S+/16, or the shape of ViT-7B/16 at a small embedding dimension. The oracle of the part tests. It needs no gated weights.
  • Part test (changed): a test of one part of a block in mlx against the Hugging Face module on torch-cpu, with a small model.
  • Load peak: the largest MLX active memory (mx.get_peak_memory) during one model load. It does not include the MLX cache.
  • Default session: a pytest session without DINOV3_SLOW.
  • Slow session: a pytest session with DINOV3_SLOW=1.
