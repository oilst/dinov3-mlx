1 What Step 6 must do and the starting point

Step 6 makes the MLX backbone fast. Section 6 of docs/plan.html lists nine actions (Table 1). We measure each change against the previous result, so verify.html shows the gain of each change. The step ends when the speedup table covers all configurations. The explainer covers the attention cost at high input resolution and the effect of the batch size. mission.md asks for a speedup above 1 for each model size and dtype. If a speedup is not above 1, verify.html explains why.

These points are fixed. They are not options:

  • mlx 0.32.4 and mlx-metal 0.32.4 stay pinned during Step 6. A version change goes into its own commit (tech-stack.md).
  • The parity thresholds of ADR 0003. Only the user changes them. Quantized weights have no thresholds yet (Section 6, question 1).
  • The baseline row of ADR 0004: the fastest valid dtype mode of each dtype, with the median of its runs. At P1 and P2 the baseline is a compile row of torch.compile.
  • ADR 0005 (fp32 on mlx with TF32 off), ADR 0006 (Hugging Face RoPE tables), ADR 0007 (the mlx autocast modes keep fp16 or bf16 weights) and ADR 0008 (ViT-7B/16 never loads its fp32 weights).
  • The run rules of CLAUDE.md: one heavy job at a time, a memory check before each one, mx.set_memory_limit for MLX, the MPS watermarks for torch-mps.
  • Later steps: Step 7 writes embed_frames and embed_patches on top of the Step 6 forward pass. Step 8a puts LoRA on q_proj and v_proj in fp16 autocast. Step 6 must keep these module names.

1.4 The target: a compiled and quantized forward pass

Figure 1 shows the data flow that the recommended options give. One mx.compile function holds the whole forward pass. The weights enter it as inputs. The element-wise chains become fused kernels. 2 Measured facts and probe results

On 2026-11-07, research agents read the repo, the results of Steps 3 to 5 and the MLX 0.32.4 package. They ran small CPU probes without a model load. Then one agent ran the GPU probes outside the repo: 24 probe runs in 762 s (12.7 min) of wall time, one heavy job at a time, each after the wait loop and a memory check, with mx.set_memory_limit in each MLX worker. Later the same day, after the power adapter was connected, the seven probes that check the machine state ran on AC power (Section 2.9): 3.8 min for p1-compile-pairs and 11.3 min for the other six. No repo file changed. This section gives the results. A throughput ratio divides the throughput of the new form by the throughput of the old form; above 1 means faster. Tables 9 and 11 also give time ratios; above 1 means slower.

Limits of all probe values.

  • Battery power, then AC power. The first 24 probe runs ran on battery power (99 % down to 66 %, no adapter). Seven probes check the machine state and stopped at their first worker. They ran again on AC power and gave complete results (Table 4, Section 2.9).
  • Battery power did not lower the throughput. ViT-S/16 fp32 eager at P1 gave 891 img/s (batch size 8) and 367 img/s (batch size 1), against 830 to 852 and 351 to 360 img/s in Step 4 on AC power.
  • Thermal drift on battery power is large. On battery power, ViT-H+/16 bf16-cast eager at P2 took 434 ms per batch at the start of one process and 512 ms 40 s later (+18 %). Two minutes later, the next process took 650 to 690 ms. Step 5 on AC power measured 780 to 930 ms. So absolute values of the battery-power probes do not compare with other sessions. Only the paired values compare: the forms alternate in one process, in a rotated order, over 3 to 5 rounds.
  • On AC power the drift is small. The probe long-phase gave a last-third / first-third throughput ratio of 0.987 (ViT-S/16) and 0.981 (ViT-H+/16) over about 90 s, with no thermal warning. The probe paired-noise gave a spread inside one arm of 1.6 % (torch-mps) and 3.0 % (mlx) over 6 runs each. The spread between runs on different days stays about 20 % (F2).

Kernel nodes of one forward pass from a graph export (no evaluation), eager / compiled / compiled with the concat-free RoPE: 12-block MLP in fp32 292 / 220 / 172, bf16-cast 365 / 245 / 173, bf16-autocast 414 / 270 / 198; 32-block SwiGLU in fp32 836 / 612 / 484, bf16-cast 1061 / 677 / 485, bf16-autocast 1190 / 742 / 550.

  • New shapes. retrace (ViT-H+/16 bf16-autocast): a new batch size or input resolution costs one trace of 2 to 6 ms. A second process starts as fast as the first: the fused kernels come from the on-disk shader cache. The RoPE cache gets one small entry for each patch grid. The MLX buffer cache grows to 4.9 GB over five shapes; the active memory stays at 1.7 to 1.85 GB.
  • Hazards. After an in-place weight change, a compiled forward pass that captures the weights in a closure, and mx.compile(model), give the old output without an error. With inputs=model.state, the output follows the change. A compiled function stored on the model forms a reference cycle: 12.52 MiB of weights stayed after del model until gc.collect(). shapeless=True fails: "Slice cannot infer output shapes".

7 New terms

Terms for GLOSSARY.md. The Close stage adds the terms of the chosen options.

  • Eager forward pass: the forward pass of the MLX backbone without mx.compile. Each call builds the graph again.
  • Compiled forward pass: the forward pass of the MLX backbone wrapped by mx.compile, with the weights as inputs (inputs=model.state). It has one trace for each input shape and dtype.
  • Trace: the record of the operations of one call of a compiled function for one set of input shapes and dtypes. mx.compile makes it at the first call and replays it at later calls.
  • Fused kernel: one GPU kernel that mx.compile makes from a chain of element-wise operations.
  • Fusion barrier: an operation that mx.compile does not fuse with its neighbours, for example mx.fast.layer_norm, a matmul, slice and concatenate.
  • Concat-free rotation: the RoPE rotation x · cos2 + reversed(x) · sin2 on a (…, 2, head_dim / 2) view, with the sign of rotate_half in the sin table. It gives one fused kernel.
  • Change ratio: the throughput after a change divided by the throughput before it, both forms in one process, in alternation and in a rotated order. The median over the rounds.
  • NAX kernel: an MLX Metal kernel that uses the Neural Accelerators. Its name contains "nax", for example steel_attention_nax.
  • Neural Accelerators on / off: the state with and without the NAX kernels. MLX_METAL_GPU_ARCH=applegpu_g16s turns the NAX kernels off. The page does not use "NAX" alone.
  • Relaxed precision: the option of the NAX matrix operation that lets the hardware compute with less precision. MLX 0.32.4 turns it on in the NAX matmul and attention kernels.
  • Quantized weights: the weights of an nn.Linear module stored as 8-bit or 4-bit integers, with one scale and one offset for each group of weights (affine format). The scales and offsets have the matmul dtype.
  • Group size: the number of weights of one row that share one scale and one offset.
  • Preprocessing: the steps from an RGB image to the normalized fp32 pixels: resize (bilinear, antialiased), divide by 255, normalize with the ImageNet mean and standard deviation.
  • Separable resize: a resize as two matmuls with fixed weight matrices, one for the rows and one for the columns.
  • Best batch size: the batch size with the highest median throughput for one model size, input resolution and dtype mode.
  • Speedup table: the table with the speedup of each configuration of the benchmark matrix.
  • MLX peak: mx.get_peak_memory() after mx.reset_peak_memory(): the largest MLX allocation during one measured phase of one form. It is not the peak memory (the lifetime maximum of the process footprint).
  • Spread between runs: (largest run median − smallest run median) / smallest run median, over two or more runs of the same configuration at different times.
  • Load footprint peak: the lifetime maximum of the process footprint after a model load (the result field of F17). It differs from the load peak.
  • Fault bound: a loose parity bound that catches only faults, for example a wrong input cast. Not a threshold (only if the user picks D18 option A).
