Roadmap step 1. Status: decided. On 2026-11-06 the user chose Option A (scope) and Option B of R1 (MIT for our code, see ADR 0002). Date: 2026-11-06.

1 Goal

Step 1 makes sure that this repo adds value. This file compares the public MLX ports of DINOv3 with the plan of this repo. It lists the gaps that this repo fills. It gives three scope options and one recommendation. The user picks one option.

We read the code of each port on 2026-11-06. We did not run the ports. A port "has" a feature in Table 1 only when its code or its tests show the feature.

2 DINOv3 topic

The topic of Step 1 is what the other ports cover. The explainer docs/learn/01-prior-ports.html compares each port with the Hugging Face code: the token layout, the 2D RoPE, the feed-forward network and the two outputs.

The overlap is real for the small model sizes. mlx-image already gives ViT-S/16, ViT-S+/16 and ViT-B/16 in Python MLX. So a port of the small model sizes alone adds little. The value of this repo is in G1 to G6 together.

3.3 Option A: own Python package, full scope

We build a new Python MLX package, as docs/plan.html describes. We write the model from the Hugging Face code (Apache-2.0) and the paper. The package loads the weights from the Hugging Face cache. It covers all six model sizes, the parity tests, the benchmarks, the adapters and the explainers.

  • For: we control the API, the tests and the benchmark harness. Each part gets an explainer, so the learning goal is met. The fine-tuning step needs the model code in our hands.
  • Against: one more DINOv3 port. We must make the gaps visible in the README, or users see a duplicate.

3.4 Option B: contribute to mlx-image

We add ViT-L/16, ViT-H+/16, ViT-7B/16, parity tests and adapters to mlx-image. This repo keeps only the benchmarks, the explainers and the fine-tuning experiments.

  • For: one place for users, and 102 stars of reach.
  • Against: each change waits for the review of another maintainer. The mlx-image API fixes a 224 px config for each model and uses re-hosted weights that are not gated. The fine-tuning step needs changes deep inside the model code. Our steps lose their schedule.

3.5 Option C: benchmarks and explainers only

We use one existing port as the MLX backend. We add the parity tests, the benchmarks and the explainers. We do not write a port.

  • For: the least code.
  • Against: no port covers all six model sizes (G2). A fix of the port means that we own the port anyway. Goal 5 (fast adapter fine-tuning) has no base. The learning goal suffers, because we explain code that we did not write.

3.6 Recommendation

Option A, with a sharper focus. The README and the first release lead with the gaps G1 to G7, not with "a port of DINOv3". Concretely:

  1. Write the MLX model from the Hugging Face code and the paper. Do not copy the official Meta code. Section 4 explains how this choice touches the license.
  2. Load the gated weights from the Hugging Face cache with the Hugging Face key names. Do not re-host weights.
  3. Support all six model sizes, with sharded weights for ViT-7B/16.
  4. Publish parity for every model size and dtype, and the benchmark matrix against torch-mps on the M5 Max.
  5. Add LoRA and DoRA adapters in Step 8.
  6. Later, offer upstream fixes to mlx-image (for example the larger model sizes) where they help users. This is not a goal of this repo.

4 Effect on the license decision

Decision D6 (risk R1 in docs/plan.html) stays with the user. Table 1 gives three facts for it.

  • mlx_dinov3 ports the official Meta code and ships the DINOv3 License. This is Option A of R1.
  • MLXDINOv3 and mlx-image ship their code under MIT and state that the weights stay under the DINOv3 License. This is Option B of R1.
  • The Hugging Face model code is Apache-2.0. If we write the model from this code and from the paper, and not from the official Meta code, our code is less directly a derivative work of the official code. This is not a legal opinion.

The weights are DINO Materials in all cases. This repo never distributes them.
