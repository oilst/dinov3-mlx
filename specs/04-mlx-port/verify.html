Step 4 MLX port: Verify

Roadmap step 4. Status: verified. Date: 2026-11-07. Verifier: a separate agent, not the agent that built the step. Build commit: c212226 ("Step 4 build: ViT-S/16 in MLX, key map and fp32 parity").

1 Summary

This file checks the 19 acceptance criteria of specs/04-mlx-port/plan.html (Table 11) against build commit c212226. The verifier read the spec folder, the diff and the hand-over note of the build. The verifier ran ruff and both test sessions again. It ran the benchmark again into a scratch file and did six own checks (Section 5). The verifier did not change src/, scripts/, tests/ or results/.

Result: 16 rows pass, 1 row is partial (AC11), 0 rows fail, 2 rows are not in the scope of Verify (AC18, AC19).

  • Parity. On all 12 configurations, ViT-S/16 on mlx in fp32 with TF32 off agrees with the reference output to 1 − 3.1e-11 or better. This is the worst patch 1st percentile. The own parity code of the verifier gives the same values to the last digit. Five more inputs have odd input resolutions (16 × 16 px to 48 × 800 px). These inputs and two batches of three different images agree to 1 − 4.6e-10 or better.
  • Benchmark (report only). Median paired ratio mlx / torch-mps over the 6 rounds of two benchmark runs: batch size 8: 1.39 (range 1.36 to 1.44); batch size 1: 3.14 (range 2.84 to 3.24). The verifier run gives the same median as the build run within 2.1 %.
  • TF32. With TF32 on, 1 − cosine increases by a factor of about 1e6. The parity still passes the fp32 thresholds by a factor of 4 or more (Section 5.2).
  • Findings. Section 7 gives 11 findings: 1 medium, 6 low, 4 for information. F1 (medium): after nn.quantize, the pixel cast of Embeddings casts the pixels to uint32. This does not affect Step 4, but it breaks the quantized weights of Step 6 without an error message. A second check of the code confirmed F1 and F4 with the small model. AC11 is partial because the mlx benchmark workers do not log their memory check (F6).

7 Findings

The verifier did not change code. Each finding gives the place and a proposed fix. The user decides. A second check read the code again for F1 and F4 and ran both with the small model (Section 10). Both faults are real.

  1. F1 (medium): after nn.quantize, the pixel cast of Embeddings destroys the input.
    • Place: src/dinov3_apple/mlx_model.py:218 casts the pixels to self.patch_embeddings.weight.dtype. run_mlx and run_mlx_hidden_states both go through this cast (:343, :382).
    • Cause: the default predicate of nn.quantize replaces the patch embedding with a QuantizedLinear. Its input has 3 · 16 · 16 = 768 values, a multiple of the group size 64. The weight of a QuantizedLinear holds packed uint32 values. So the cast turns the normalized pixels into unsigned integers.
    • Failure scenario: nn.quantize(model, bits=8), then run_mlx(model, pixels, "fp32"). No error message comes. The tokens are float32 and finite, but wrong.
    • Check on ViT-S/16 with 8-bit weights: the cast pixels of forest/224x224 have 3 different values. The patch tokens of the patch embedding have a minimum cosine of 0.268 with the cast and 0.99984 without it. With all linear layers quantized, the frame embedding has the cosine 0.716 to the unquantized output. With only the blocks quantized, the cosine is 0.99986.
    • Check on the small model (2 blocks, random weights, mlx 0.32.4): the patch embedding becomes a QuantizedLinear with a uint32 weight. The cast pixels are uint32 with 5 different values. The minimum cosine of the patch tokens is 0.631 with the cast. With a cast to the dtype of the CLS token, it is 0.99999. run_mlx gives no error and returns finite float32 tokens.
    • Effect on Step 4: Step 4 does not quantize, so no criterion fails. But plan Table 5 names nn.quantize as the hook for the quantized weights of Step 6. The docstring of MlxBackbone (mlx_model.py:321 to :322) also names nn.quantize. Review fix R1 added the cast after the plan.
    • Proposed fix: cast the pixels to the dtype of a float parameter that nn.quantize does not change, for example pixels.astype(self.cls_token.dtype). Another option is the dtype of patch_embeddings.scales when this attribute exists. Add a part test in tests/test_mlx_parts.py that quantizes the small model with the default predicate. The test asserts that the embeddings stay floating point and stay close to the embeddings of the unquantized model.
  2. F2 (low): the plan has no recorded approval of the user. specs/04-mlx-port/plan.html:42 still gives the status "draft, for the approval of the user". The hand-over note says that the agent approved the plan on behalf of the user. CLAUDE.md ends the Plan stage when "the user approves the plan", and plan Section 9 starts the build only after this approval. The verifier cannot see a user approval. Proposed fix: the user confirms the approval (or not), and the Close stage sets the status line of plan.html.
  3. F3 (low): the benchmark table of the hand-over note is not the committed file. The note gives Table 7 from build run 1 at 01:11:48 to 01:14:45 local time. Examples are 840.7 img/s and the paired ratio 1.382 at batch size 8. The note also says that the benchmark did not run again after review fix R10. But results/bench-mlx-port.jsonl:1 to :12 come from build run 2 at 01:44:40 to 01:47:37 (driver.log). This run ended five seconds before the commit (01:47:42). It gives 846.9 img/s and 1.390. The two runs agree within 1 % at batch size 8 and within 2 % at batch size 1, so no conclusion changes. Proposed fix: the Learn and Close stages take the benchmark values from the committed file or from Section 4 of this file. They do not take them from the note.
  4. F4 (low): map_key accepts names that are not in a DINOv3 backbone, and two docstrings promise the opposite.
    • Place: the pattern BLOCK_KEY (src/dinov3_apple/mlx_weights.py:37) accepts any lower-case path between layer.{i}. and the suffix, and any block index. The Raises sections of map_key (:55) and mlx_weights (:80) promise UnknownWeightError for each name that is not a tensor of a DINOv3 backbone. So the two docstrings are not correct.
    • Failure scenario: map_key("layer.0.foo.weight") returns "layer.0.foo.weight". map_key("layer.12.norm1.weight") returns "layer.12.norm1.weight", but ViT-S/16 has blocks 0 to 11. Neither name raises UnknownWeightError.
    • Check: own check (c) (Table 7) and the check with mlx 0.32.4 give the same result. A name with a capital letter, for example layer.0.attention.q_proj.lora_A.weight, raises UnknownWeightError. The strict load then stops the two names with a ValueError (Table 7), so the load stays safe. No criterion fails.
    • Proposed fix: name the block parts in the pattern (norm1, norm2, attention.(q|k|v|o)_proj, layer_scale(1|2).lambda1, mlp.(up|down|gate)_proj). The pattern does not know the number of blocks, so the strict load still finds layer.12. Another option: change the two Raises sections. They then say that map_key checks only the form of the name and that load_weights(strict=True) finds the other unknown names.
  5. F5 (low): --results moves only the JSON lines. The per-batch files and driver.log still go to tests/fixtures/generated/bench/mlx-port/ (scripts/bench_mlx_port.py:64 to :65, :167, :263, :384 to :389). A verifier run overwrites the per-batch files of the build. The verifier had to copy the folder and put it back. Finding F7 of Step 3 is the same for profile_block.py. Proposed fix: when the user gives --results, put the per-batch files and the driver log next to the results file. Another option is a hidden --bench-dir option.
  6. F6 (low): the memory-check line of the load in an mlx worker goes nowhere. worker_main (scripts/bench_mlx_port.py:252) configures no logging. So Python drops the INFO line of check_free_memory (src/dinov3_apple/memory.py:75). The check itself runs and can stop the load. The driver writes its own line before each worker. This line has another label ("mlx ViT-S/16 fp32 224px b8") and the benchmark need (4.17 GB), not the load need (4.10 GB). So the 18 mlx worker loads of the three benchmark runs have no line "ViT-S/16 mlx fp32", and AC11 is partial. The torch-mps workers of Step 3 have the same gap (scripts/benchmark.py:80). The hand-over note reports it as deviation 5. Proposed fix: in worker_main, send the logger dinov3_apple.memory to stderr, and let run_worker_subprocess copy these lines to driver.log. Another option: record the available memory of the worker check in the result line.
  7. F7 (low): the TF32 probe test accepts any error below 1. tests/test_mlx_environment.py:127 asserts 0 <= error < 1 for both values. If a later MLX version ignored MLX_ENABLE_TF32, the test would stay green. The part tests catch TF32 in the fp32 path (plan Table 7), so the risk is small. Proposed fix: assert that the value with TF32 off is at most 1e-5 (measured 7.8e-7), and keep the value with TF32 on as report only.
  8. F8 (information): TF32 on passes the fp32 thresholds for ViT-S/16. Section 5.2: worst frame 1 − 2.5e-5, margin 4×. This is input for the decision of Step 6 on an fp32 row with TF32 on. The verifier did not measure the margin of the larger model sizes.
  9. F9 (information): the probe values are about 8 times the "about" values of the plan. Off 7.8e-7 against "about 1e-7"; on 7.2e-4 against "about 1e-4". The ratio is 919. The probe gives the largest difference divided by the largest reference value, so it is larger than one unit roundoff. Also, MLX_ENABLE_TF32=true turns TF32 off (Table 10). The explainer 04-3-attention.html can use both facts.

Another MLX version or another GPU can change the order of the sums. Proposed: no change now; Step 5 records the value again with each new MLX version.
