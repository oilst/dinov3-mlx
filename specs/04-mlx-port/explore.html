Step 4 MLX port: Explore

Roadmap step 4. Status: options and recommendations. The user asked the agent on 2026-11-06 to decide; the recommended options are the choice. Date: 2026-11-06.

1 Goal and context

Step 4 builds the ViT-S/16 backbone in MLX, one part at a time, with a test for each part. The step ends when ViT-S/16 on the backend mlx passes the parity tests in fp32 (Step 4 in Section 6 of docs/plan.html). This page gives the decisions with real options, the trade-offs and one recommendation for each decision.

These points are fixed. They are not options:

  • Source of the code: we write the MLX backbone from the Hugging Face file modeling_dinov3_vit.py (Apache-2.0) and the paper. We read the official Meta code only to check facts (ADR 0002).
  • Weights: the Hugging Face safetensors of facebook/dinov3-vits16-pretrain-lvd1689m in the Hugging Face cache. weights_dir finds them. The weights stay outside the repo.
  • Reference output: the Hugging Face backbone on torch-cpu in fp32, in the reference files of Step 2. The fp32 thresholds are 0.9999 for the frame embedding, the patch mean and the patch 1st percentile (THRESHOLDS["fp32"], ADR 0003).
  • Versions: mlx 0.32.4, transformers 5.22.1, torch 2.15.0. Hardware: M5 Max (GPU applegpu_g17s), macOS 26.5.2.
  • Run rules: one heavy job at a time. A memory check before each model load. mx.set_memory_limit for MLX.
  • Later steps: Step 5 adds SwiGLU, all six model sizes, fp16 and bf16. Step 6 adds mx.compile, the cache of the RoPE tables, the mlx benchmark and quantized weights. Step 8 adds LoRA on q_proj and v_proj. The Step 4 design must not block these steps.

Five findings shape the decisions:

  1. The linear weights in the file have the layout (out, in). mlx.nn.Linear uses the same layout. Only the patch embedding weight [384, 3, 16, 16] needs a new layout (D2, D4).
  2. mx.fast.rope cannot compute the DINOv3 RoPE in one call. This confirms risk R5 of docs/plan.html (D3).
  3. The Meta checkpoints store the RoPE periods in bf16. We read the pickle header of the ViT-S/16 Meta checkpoint again: rope_embed.periods is a BFloat16Storage of 16 values. The Hugging Face code computes exact fp32 frequencies. The two sets of angles differ by up to 0.0079 rad at 224 px. Table 1 of docs/learn/01-prior-ports.html says "same angles" for the Meta hub code. That row is wrong (D3, R11).
  4. MLX turns on TF32 by default: MLX_ENABLE_TF32 has the default value 1. mlx 0.32.4 ships fp32 matmul kernels for the Neural Accelerators that request relaxed precision. This can cost fp32 parity (D7, R10).
  5. No file in src/ imports mlx yet. The functions that read the stored pixels and the reference files are in reference.py, which imports torch (D6, R12).

3 Decisions

Seven decisions have real options. Each subsection gives the options, a table of trade-offs and a recommendation. Section 5 lists the chosen options.

3.1 D1: code structure

The MLX backbone needs a form. The form sets the converter, the tests and the hooks for Steps 5, 6 and 8.

Option A: mlx.nn.Module classes that mirror the Hugging Face module tree and names. An embeddings module, a list layer of 12 blocks and a final norm. Each block has norm1, attention (q_proj, k_proj, v_proj, o_proj), layer_scale1, norm2, mlp (up_proj, down_proj) and layer_scale2. The parameter names are the keys of the safetensors file.

Option B: functions over a dict of weights. One function forward(weights, pixels) reads each array by its name.

Option C: reuse or fork a prior MLX port. Step 1 found four ports (Table 1 of specs/01-scope/explore.html).

3.2 D2: weights

The MLX backbone reads the Hugging Face safetensors. Two changes are necessary. The patch embedding weight gets a new layout (D4). The mask token goes away, because only training uses it. Table 5 gives the key map. The question is when the key map runs, and if its result goes into a file.

Option A: convert at load time. mx.load reads each safetensors file of weights_dir. The read is lazy. The key map runs in memory. No new file.

Option B: a converted MLX file in a cache folder outside the repo, for example ~/.cache/dinov3-apple/mlx/<Hugging Face id>/<snapshot>/<dtype>.safetensors. A command writes it once. The loader reads only this file.

Option C: both. The first load converts and writes the file. The next loads read the file.

  1. Run the memory check: check_free_memory(load_bytes(…), "ViT-S/16 mlx fp32").
  2. Set mx.set_memory_limit to the need of the memory check.
  3. Read config.json and every *.safetensors file of weights_dir(model_size) with mx.load.
  4. Apply the key map of Table 5. Cast to the dtype of the dtype mode (only fp32 in Step 4).

3.3 D3: RoPE

Figure 2 shows the layout of RoPE in one head. RoPE needs four things: the patch-center coordinates (y, x) of each patch token, 16 frequencies, a cos table and a sin table. Then it computes q · cos + rotate_half(q) · sin, and the same for k.

Recommendation: Option C, variant C1.

  5. Leave RoPE-box jittering out of Step 4. The flag stays off. Step 8 decides.

# src/dinov3_apple/mlx_model.py (shape of the code, not final)
def rope_tables(grid_h: int, grid_w: int, head_dim: int, theta: float) -> tuple[np.ndarray, np.ndarray]:
    inv_freq = 1 / theta ** np.arange(0, 1, 4 / head_dim, dtype=np.float32)   # (head_dim / 4,)
    coord_h = np.arange(0.5, grid_h, dtype=np.float32) / grid_h
    coord_w = np.arange(0.5, grid_w, dtype=np.float32) / grid_w
    coords = np.stack(np.meshgrid(coord_h, coord_w, indexing="ij"), axis=-1).reshape(-1, 2)
    coords = 2.0 * coords - 1.0                                                  # (N, 2): y, x
    angles = (2 * np.pi * coords[:, :, None] * inv_freq[None, None, :]).reshape(len(coords), -1)
    angles = np.tile(angles, 2)                                                  # (N, head_dim)
    ones = np.ones((NUM_PREFIX_TOKENS, head_dim), np.float32)
    return np.concatenate([ones, np.cos(angles)]), np.concatenate([0 * ones, np.sin(angles)])


def apply_rope(x: mx.array, cos: mx.array, sin: mx.array) -> mx.array:
    """x: (B, heads, 5 + N, head_dim). cos and sin: (5 + N, head_dim), fp32."""
    half = x.shape[-1] // 2
    rotated = mx.concatenate([-x[..., half:], x[..., :half]], axis=-1)
    return (x * cos + rotated * sin).astype(x.dtype)

3.4 D4: patch embedding

The patch embedding is a convolution with kernel 16 and stride 16. So each patch token is a linear map of the 768 pixel values of its patch. The stored pixels are fp32 NumPy arrays in NCHW layout. MLX convolutions take NHWC input and a weight in the layout (out, kh, kw, in).

Option A: nn.Conv2d with NHWC input. Transpose the pixels to NHWC. Transpose the weight once at load: (384, 3, 16, 16) → (384, 16, 16, 3). Run the convolution. Reshape to (B, N, 384).

Option B: cut the image into patches, then one matmul. Reshape the NCHW pixels to (B, 3, Hp, 16, Wp, 16). Transpose to (B, Hp, Wp, 3, 16, 16). Reshape to (B, N, 768). Multiply by the weight, reshaped to (384, 768), and add the bias. An nn.Linear(768, 384) holds the weight. The weight needs no transpose.

3.7 D7: fp32 precision on the Apple GPU

The fp32 thresholds are 0.9999. On torch-mps, matmuls with a 10-bit mantissa (fp16-autocast) gave a worst patch 1st percentile of 0.999781 over five model sizes (Table 3 of docs/learn/02-tokens-and-outputs.html). That is below 0.9999. TF32 also keeps a 10-bit mantissa. Table 14 gives the evidence about TF32 in MLX.

Recommendation: Option B for the fp32 dtype mode, in all parity tests and benchmarks. Option C only as a diagnostic.

  1. Start the build with a probe, after the running benchmark ends: one small fp32 matmul in two subprocesses, with MLX_ENABLE_TF32=0 and with 1, each against NumPy float64.
  2. Record the two relative errors in verify.html. The expected values are about 1e-7 with TF32 off and about 1e-4 with TF32 on.
  3. If a configuration fails on the GPU with TF32 off, run it on mx.cpu. A pass on the CPU points to a kernel. A fail on the CPU points to the port.

5.2 New terms in GLOSSARY.md

  • MLX weights: the weights of one model size as MLX arrays, with the names and layouts of the MLX backbone. The key map makes them at load time from the Hugging Face safetensors.
  • RoPE tables: the cos and sin arrays of one patch grid, with one row for each token and one column for each value of a head.
  • TF32: a matmul mode that rounds the fp32 inputs to a 10-bit mantissa. MLX turns it on by default.
