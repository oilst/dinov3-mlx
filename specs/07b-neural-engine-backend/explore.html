Step 7b Neural Engine backend: Explore

Spec folder specs/07b-neural-engine-backend/. Written on 2026-11-15. Stage 1 of the spec loop: the user picks an option for each decision.

1 What Step 7b must do and the starting point

Step 7b adds the backend "mlx+ne" to Embedder. Core ML runs on the Neural Engine and compiled mlx runs on the GPU at the same time. mlx stays the default backend. The backend is for inference only.

Step 6d measured the two-stream run in two processes. Table 1 gives the result. The target of Step 7b is the same stream ratio through the public API, with valid outputs.

Facts that limit the options:

  • The conversion needs torch, transformers and coremltools==9.0 with the cast patch (ADR 0015). The core of the package has five dependencies and no torch (ADR 0020).
  • A Core ML package has one fixed input shape. Each model size, input resolution and batch size needs its own package. The conversion takes 3 to 76 s; the ViT-H+/16 package is 1.7 GB, and its conversion needs up to 5.6 GB.
  • The first load on the Neural Engine takes 1.7 to 119 s. A cached load takes about 0.04 s.
  • The Neural Engine gain is large only for small models at 224 px. At 512 px the Neural Engine gives 0.10 to 0.16 of the mlx throughput.
  • Step 6d ran the two streams in two processes. One process with two threads was not measured.

3.2 D2: How the two streams run at the same time

OptionWhat it doesForAgainst
D2 ATwo threads in the process of the user. One thread calls mx.eval, the other calls predict of Core ML.No copy of frames or outputs between processes. Simple life cycle.It works only if both calls release the Python GIL. Not measured: Step 6d used two processes.
D2 BOne worker process for Core ML. The frames go to it and the tokens come back through shared memory.The setup of Step 6d: it gave the stream ratios of Table 1.A process start, a copy of each batch, and the clean-up of a worker process when the user stops or the worker fails.

OptionWhat it doesForAgainst

4 Recommendation

D1 A, D2 C, D3 B, D4 A. The extra [ne] reuses the tested ne3 conversion and keeps the core free of torch. A short probe decides between threads and a worker process. A work queue keeps both streams busy and gives the outputs back in the input order. The backend accepts the same inputs as "mlx".

Decision of the user, 2026-11-15: D1 A, D2 C, D3 B, D4 A, as recommended.

With two threads, the mlx stream drops to about 17 % of its throughput, while the Neural Engine stream keeps its throughput. The likely cause: the predict call of Core ML holds the Python GIL, so the mlx thread cannot send its next batch. Two processes reach the stream ratio of Step 6d (1.32). The threads reach 0.39 of it, below the limit of 0.95. The plan uses a worker process for Core ML (D2 B).

The acceptance benchmarks of Step 7b are heavy jobs (P1, P3 and P2, each in two runs). The user stopped the heavy runs on 2026-11-15. The plan can be written now. The Build can run the light tests on ViT-S/16. The benchmarks wait for a free Mac and a yes from the user.

5 Questions for the user

  1. D1: Is an extra with torch acceptable, or must the backend work without torch (D1 B)?
  2. D2: May the light probe of D2 C run (ViT-S/16, 224 px, about 1 min, through the GPU lock and after a memory check)?
  3. D4: Do you want the full contract (D4 A) or only the configurations with a clear gain (D4 B)?

6 New terms

  • Work queue: the list of batches of one call, from which each stream takes the next batch when it is free.
  • Neural Engine extra: the optional dependency set dinov3-mlx[ne] that the conversion of the Core ML packages needs.

Both terms are in GLOSSARY.md since the decision of the user.
