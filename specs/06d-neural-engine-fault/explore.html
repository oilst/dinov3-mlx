Step 6d Neural Engine fault: Explore

Roadmap step 6d. Status: waiting for the user to pick an option (Section 4). Date: 2026-11-08.

1 What Step 6d must do and the starting point

Step 6c (finding V1 of specs/06c-neural-engine/verify.html) found that 13 of 15 Core ML packages of the Neural Engine rewrite ne2 give finite but wrong tokens on CPU_AND_NE. The same packages pass on CPU_AND_GPU and ALL (30 of 30). Only ViT-S/16 and ViT-S+/16 at 224 px and batch size 1 pass on CPU_AND_NE. In these two packages the compute plan keeps the first 46 ops on the CPU. The Step 6c Q3 probe found the first wrong tensor: the output of the embeddings (cosine 0.19 and 0.31). A matmul patch embedding (probe P) and an fp16 input (J3 probe) did not help.

Step 6d must find the cause, then fix it or bound it. Target of the roadmap row: Neural Engine parity for ViT-S/16 to ViT-H+/16 at 224 to 512 px, and the two-stream throughput again.

These points are fixed. They are not options: the fp16 thresholds of ADR 0003 (frame ≥ 0.999, patch mean ≥ 0.999, patch 1st percentile ≥ 0.99), the rewrite ne2 of ADR 0014, the fixed shapes and coremltools 9.0 of ADR 0015, the run rules of CLAUDE.md.

The two passing forms with two constants (c4, c1 and c3, c2) have no input and output cast in the compute plan, so the converter changed these programs in a different way. We did not find the exact rule for two or more constants.

Cause. The Neural Engine (macOS 26, coremltools 9.0, ML Program for macOS 15) writes a wrong result for a concat along the token axis when the concat has two or more constant inputs and its other input comes from the patch conv. Every concat with one constant input was right. The values are exact copies of other rows, so this is not an fp16 range fault: it is a fault of the row offsets in the concat. The Hugging Face embeddings have this form (CLS token and register tokens as two constants).

Why 2 of 15 packages passed. At 224 px and batch size 1 the compute plan of ViT-S/16 and ViT-S+/16 puts the input cast, the conv, the concat and the first attention branch on the CPU (46 ops). The CPU concat is right. Every other package runs the concat on the Neural Engine.

Why probe P and the J3 probe did not help. The matmul patch embedding and the fp16 input change the ops before the concat. The concat with two constants stays.

3 Options for the fix

Core ML has no setting for the device of one op. So "the embeddings off the Neural Engine" needs two packages in a chain (option B). All options keep the rewrite ne2 of ADR 0014 for the blocks.

3.1 Option A: one constant prefix in the concat (rewrite version ne3)

NeuralEngineBackbone.forward builds the embeddings itself and concats one constant of 5 rows with the patch tokens. The prefix holds the CLS token and the register tokens of the backbone. In fp32 the output is bit-equal to the Hugging Face embeddings.

def embed(emb: DINOv3ViTEmbeddings, pixels: torch.Tensor) -> torch.Tensor:
    patches = emb.patch_embeddings(pixels).flatten(2).transpose(1, 2)  # (B, N, D)
    prefix = torch.cat([emb.cls_token, emb.register_tokens], dim=1)    # (1, 5, D): one constant
    return torch.cat([prefix.expand(pixels.shape[0], -1, -1), patches], dim=1)

A guard test reads the converted MIL program and fails on a concat with two or more constant inputs. A part test converts the embeddings of ViT-S/16 at 448 px (a package of about 1 MB) and checks it on CPU_AND_NE, so a new macOS that changes the fault shows at once. The variants pad_add and cat_cf of Table 4 are also right; cat2 is the smallest change.

3.2 Option B: two packages in a chain

Package 1 (pixels to embeddings, divided by r) runs on CPU_ONLY. Package 2 (embeddings to tokens, the blocks and the final norm) runs on CPU_AND_NE. The worker calls both for each batch. CPU_ONLY keeps the GPU free for mlx in the two-stream run.

3.3 Option C: bound the fault, no fix

The Neural Engine path stays limited to ViT-S/16 and ViT-S+/16 at 224 px and batch size 1. The other 13 packages stay expected failures on CPU_AND_NE. Step 6d records the cause (Section 2.3) in an ADR and closes.

3.4 Not an option for Step 6d: the ml-ane-transformers layout

The layout of option D of Step 6c D2 ((B, C, 1, S) tensors, 1 × 1 convolutions, one attention for each head) is not needed for the parity: Table 5 shows parity without it. It can help the Neural Engine speed at 448 and 512 px (Table 6), but that is a second rewrite of every block. It is a candidate for a later step (Section 5, Q2).

4 Recommendation

Option A: one constant prefix in the concat, rewrite version ne3.

A is exact, it is one function, and the probes already show the parity for the smallest and the largest model sizes, for r = 1 and r = 8, at 224, 448 and 512 px and at batch size 8. B gives the same parity with more code, two loads and a cost for each call. C leaves 13 of 15 configurations wrong, and the fix is cheap.

For the plan: change the speed target of roadmap row 6d. Parity on CPU_AND_NE is reachable for every configuration. A two-stream gain is reachable at 224 px only (Table 6). The plan should set a two-stream target at P1 and one 224 px point of a larger model size (for example ViT-B/16 or ViT-L/16), and report P2 without a target.

The user picks the option. The agent does not decide.

  • Q1: Which option: A, B or C?
  • Q2: The Neural Engine runs at 5 to 15 % of the mlx speed at 448 and 512 px. Is a later step on the speed of the Neural Engine at high input resolutions worth it (for example the ml-ane-transformers layout)?
  • Q3: Do you want a bug report to Apple (Feedback Assistant) with the E6 graph? It is an external action, so the agent does not send it. The E6 script can serve as the minimal sample.

6 New terms

Terms for GLOSSARY.md. The build adds them when the code uses them.

  • Concat fault: the wrong token concat of the Neural Engine when the concat has two or more constant inputs (Section 2.3).
  • Constant prefix: the CLS token and the register tokens as one constant of 5 rows, in front of the patch tokens (option A).
