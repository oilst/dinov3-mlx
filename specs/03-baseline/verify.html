After this verification, F11 showed that the build ran on a 30 W power adapter; Section 14 gives the re-measurement on the 94 W adapter, which replaces the committed results.

5 Repeatability (AC5)

AC5 fails, as the build reported. The user accepted this on 2026-11-06. The verifier adds these facts:

  • The noise is in the GPU time. P1 takes 10.0 to 24.7 ms for each batch of 8 (median frame time), not 1.5 to 3 ms. The device time is 97.2 % or more of the frame time in every P1 run. So the change from run to run is in the forward pass on the GPU, not in the copy to the host and not in the Python launch cost.
  • Inside one run, the batch times are tight; between runs, the level moves. P2 in the build: inside each run, p90 / median of the batch times is 1.01 to 1.10, but the median batch time of fp16-autocast is 1.356 s in repeat 1 and 1.046 s in repeat 2 (4 minutes later). One P1 run changes its level in the middle: fp16-cast, main run, median 25.2 ms in the first half and 16.1 ms in the second half.
  • The P1 result depends on the run that holds it. The two B1 runs (build r0, verifier B1) and the three --priority runs (build r1 and r2, verifier) form two groups. In each of the five dtype modes the groups do not overlap, and the ranking of the modes flips: in the B1 runs fp32 and the autocast modes are fast and the cast modes are slow; in the --priority runs it is the opposite (Table 4). The verifier tested if the worker before P1 sets the level (Table 6). It does not: with the same worker before it as in B1, P1 fp16-cast gave 705.0 and 721.5 img/s, the level of the --priority runs, not 383 to 496 img/s. In these 14 workers over 4 minutes, P1 stayed within 8 % (fp16-cast) and 11 % (fp32). The cause of the two groups stays open.

Control in test 1: at fp32, 224 px, batch size 8, (12 × block + outer parts) / forward pass is 1.03; at fp32, 512 px, batch size 1, it is also 1.03.

Explanation:

  1. The isolation of one block is not the cause. The 12 blocks in sequence, the same work as in the forward pass, take as long per block as block 1 alone, or longer.
  2. At batch size 1, a part of the forward pass takes longer than the whole forward pass. The encoder alone, on stored inputs, takes 25 to 32 % longer than the full forward pass, which does more work (patch embedding, RoPE tables, final layer norm). Module hooks are not the cause: the model has 0 hooks, and layer.forward gives the same time as layer(...).
  3. The extra time comes after the CPU issues the work. The CPU issue time of the forward pass and of the encoder is about the same (2.9 to 3.6 ms). The difference is in the time until the GPU ends the queued work. The verifier did not find the mechanism inside torch-mps.
  4. The effect needs small kernels. At batch size 8, or at 512 px, the check is 1.03 in the own test. Each kernel then has more work, and a fixed cost for each kernel is a small part of it.
  5. The other gaps of the re-run come from the level change of Section 5. B5 times the 11 parts, the block, the outer parts and the forward pass one after the other, over 4 to 17 minutes for each model size and dtype mode. In test 2 the fp32 forward pass of one process went from 2.38 ms to 4.99 ms within about one minute; in test 1 at 512 px one trial gave 8.0 ms and the others 13.7 to 16.0 ms. The build values of the same configurations are within 15 %, and the block times of the re-run are 0.99× to 1.73× the build values.

Consequence. At batch size 1 the absolute block time of B5 is too high for the time of a block inside the forward pass: by about 30 to 70 % for ViT-S/16 at 224 px. The time shares are robust: between the build and the re-run, the largest difference of a time share is 0.6 to 6.2 percentage points for each configuration (median 2.2), and the largest part is the same part in 15 of 16 configurations. The explainer should use the time shares, and forward pass / L for the time of one block at batch size 1 (F4).

The claim of the build ("the fixed launch cost per call in the isolated loop is counted 12 times; the forward pass overlaps launches") is partly right: the gap is a fixed cost that matters only for small kernels. It is not specific to the isolated loop, and the CPU launch time does not differ.

9 Findings

The verifier did not change code. Each finding gives the place and a proposed fix. The user decides.

  1. F1 (high): the throughput level of one configuration changes by up to 2× between runs on this Mac. AC5 fails for this reason, and every B1 value is one sample of it. Evidence: Sections 4.1, 5 and 6. ViT-S/16 re-run: 15 of 45 configurations within 5 % of the build, ratios 0.846 to 1.518. P1: five runs, spread 32.3 to 74.8 %. Inside one process, a forward pass changed from 2.38 to 4.99 ms within about one minute. The change is in the GPU time. Free memory, power and thermal notes do not explain it. The worker before P1 does not explain it (Table 6). The Claude desktop app ran on this Mac during all runs of the build and of the verifier. Places: scripts/benchmark.py:146 (run_configs: one run for each configuration), src/dinov3_apple/bench.py:386 (baseline_rows: one line for each configuration). Proposed fix, for a decision before Step 6:
    • Step 6 measures each speedup with torch-mps and mlx workers in alternation in one session (for example three rounds of torch-mps, mlx), and reports the median of the paired ratios with their range. A stored B1 value alone is not a safe denominator.
    • Add a --rounds N option to benchmark.py that runs the configuration list N times in rotation, and let baseline_rows use the median of the rounds.
    • Add the measured spread to the header of baseline-torch-mps.md (scripts/baseline_table.py:377).
    • Look for the cause: run a P1 loop next to sudo powermetrics --samplers gpu_power (the user runs it, because it needs sudo) with the other apps closed.
  2. F2 (medium): the compile gain uses the main run only, and the table text is wrong for two rows. scripts/baseline_table.py:226 compares each compile row with the eager row of repeat 0. scripts/baseline_table.py:418 writes "The gains were above 10 %", but the same table gives −22.6 % (P1 fp32) and +9.4 % (P2 bf16-cast).
