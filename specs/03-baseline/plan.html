Step 3 Baseline: Plan

Roadmap step 3. Status: approved by the user on 2026-11-06. Date: 2026-11-06.

1 Goal

Step 3 builds the benchmark harness and measures the baseline: the throughput and the peak memory of the Hugging Face backbone on torch-mps. It also measures the time share of each part of one block for ViT-S/16 and ViT-H+/16. Step 6 runs the same harness on mlx. On 2026-11-06 the user chose the recommended option of each decision in explore.html:

  • D1: all five dtype modes of Step 2: fp32, fp16-cast, bf16-cast, fp16-autocast and bf16-autocast.
  • D2: the baseline row for a speedup is the fastest dtype mode of the same dtype that gives a valid output.
  • D3: host to host. One forward pass for each batch. The copy of the frame embeddings and the copy of the patch embeddings are timed separately, so one run gives both rows.
  • D4: a time budget. The two priority configurations run three times.
  • D5: the lifetime maximum of the macOS process footprint is the main peak memory number. The torch.mps counter and the load peak are also recorded.
  • D6: each part of a block alone in a micro-benchmark, plus a FLOP count for each part.
  • D7: the Hugging Face default (SDPA attention, no compile) is the baseline. Report-only rows with torch.compile for the priority configurations.
  • D8: ViT-7B/16 in a separate run, last, in cast modes only, after the user frees memory.

Step 2 is closed (commits 11fc2dd, 44d411e, 7f5dd59). Its last commit made the memory check stricter, so the large model sizes need the user to close apps first (Section 3.6).

2 DINOv3 topic

The topic is where the compute goes for each model size and input resolution. The explainer docs/learn/03-where-the-compute-goes.html covers it with three views:

  1. The FLOP count of each part of a block (Table 7). The attention share grows with the token count N and falls with the embedding dimension D: the ratio of attention-score FLOPs to linear-layer FLOPs is about N / (6 D) (Figure 1 of explore.html).
  2. The measured time share of each part (D6). Layer norms, RoPE, LayerScale, the activation function and the residual adds have almost no FLOPs, but they read and write every token.
  3. The measured throughput of each model size and input resolution, against its FLOPs. The ratio gives the reached TFLOP/s. A low value shows fixed costs, for example ViT-S/16 at batch size 1.

The explainer covers every function that Step 3 adds to src/.

3.3 The worker of one configuration

scripts/benchmark.py starts one worker subprocess for each configuration. The worker does these actions:

  1. Set the MPS watermarks 0.8 and 0.6 before the torch import.
  2. Read the footprint (base).
  3. Load the backbone with load_torch_backbone(model_size, "mps", dtype_mode). Record the load time.
  4. With --compile: wrap the backbone with torch.compile.
  5. Read the footprint (load peak = lifetime maximum now).
  6. Make the input batch from the stored pixels (Section 3.5).
  7. Time the first batch. Record it as the time of the first call.
  8. Check the validity of the first output (Section 3.5).
  9. Run warm-up batches until WARM_UP ends.
  10. Run timed batches until TIMED ends. After each batch, read torch.mps.driver_allocated_memory() and keep the maximum.
  11. Read the footprint (end).
  12. Print one JSON object to stdout. Write the per-batch times to tests/fixtures/generated/bench/.

The driver adds the configuration, the machine state and the versions, and appends one line to results/baseline-torch-mps.jsonl. A worker that exits with an error gives a line with status "error" and the last 20 lines of its stderr.

One timed batch records four times (D3):

TimeTaken afterUsed for
t0nothing; the batch is fp32 NumPy on the hoststart
t1pixels to the GPU, forward pass, torch.mps.synchronize()device time = t1 − t0
t2tokens[:, 0].cpu().numpy()frame time = t2 − t0
t3tokens[:, 5:].cpu().numpy()patch time = (t1 − t0) + (t3 − t2)

Table 4. The four times of one timed batch. The outputs stay in the dtype of the backend output: the dtype of the weights in cast mode, fp32 in autocast mode (the final layer norm runs in fp32 under autocast). The JSON line records the output dtype.

Throughput of one output = batch size × timed batches / sum of its batch times. Latency = the median and the p90 of the batch times at batch size 1. The JSON line gives the median and the p90 for every batch size.

Repeatability: B2 runs P1 and P2 two more times, each in a new subprocess. The spread is (largest − smallest) / median of the three throughputs, for the output of Table 3. If a spread is above 5 %, the build stops and asks the user. A longer budget is the first remedy.

3.5 Input batch and validity check

make_batch(inputs, side, batch_size) takes the square stored pixels of the three test images at the input resolution, in the order of TEST_IMAGES, and repeats them until the batch is full. The batch is fp32 NumPy, shape (B, 3, side, side). Every batch is the same array.

check_validity(tokens, reference, dtype_mode) takes the tokens of image 0 of the first batch, cast to fp32. The output is valid when all values are finite and measure_parity passes THRESHOLDS[dtype_mode] on the frame, the patch mean and the patch 1st percentile. ViT-7B/16 has no reference file yet. Its check is "finite only", and the JSON line says so. A configuration with an output that is not valid still runs its timed batches. Its line has "valid": false and the reason.

Expected: fp16-cast is not valid for ViT-L/16 at 224, 448 and 512 px and for ViT-H+/16 at 224 px (results/parity-torch-mps.md). All other configurations of B1 are valid.

3.6 Memory check and peak memory

The driver checks the free memory before it starts a worker. The need of one configuration is:

need = required_load_bytes(model_size, weights dtype)              # Step 2: 1.2 x weights + 4 GB
     + B x T x (8 D + 3 F) x a                                    # tokens and feed-forward activations
     + 2 x B x heads x T^2 x a                                    # attention scores and softmax
T = tokens (201, 789 or 1,029), F = feed-forward size, a = 2 bytes in cast mode, 4 bytes otherwise

The attention term assumes that SDPA on torch-mps keeps the full score matrix. This is the safe case. For ViT-H+/16 at 512 px, batch size 32, fp32 the need is about 17 GB. For ViT-7B/16 at 512 px, batch size 32, fp16 it is about 28 GB.

Rule: if a measured lifetime maximum footprint is above the need of its configuration, the build raises the activation factor until every measured configuration fits, and records the new factor. The build never lowers the factor alone.

The available memory comes from available_memory_bytes. Commit 7f5dd59 of Step 2 made it stricter: it counts the free, speculative and purgeable pages, plus the inactive pages up to the file-backed pages. It does not count memory that macOS must compress or swap first. On 2026-11-06 it gave about 7 GB and later 11.3 GB on this Mac, against about 20 GB with the old count. The largest needs: ViT-S/16 6.7 GB, ViT-B/16 9.7 GB, ViT-L/16 12.5 GB, ViT-H+/16 16.8 GB, ViT-7B/16 28.2 GB. P2 needs 7.1 GB in cast mode and 10.2 GB with fp32 weights. The 4 GB reserve of required_load_bytes is in every need.

So the build does not run B1 in one go. It does these actions:

  1. Run scripts/benchmark.py --dry-run. It prints the need of each configuration and the available memory, and it loads no model.
  2. Run ViT-S/16, ViT-S+/16 and ViT-B/16. These need 9.7 GB or less.
  3. Ask the user to close apps until the dry run shows at least 17 GB. Then run ViT-L/16 and ViT-H+/16.
  4. Run scripts/benchmark.py --only-skipped after the user frees more memory. It runs again only the configurations whose latest line is "skipped".

The results table uses the latest line of each configuration. A later "done" line replaces an earlier "skipped" line. The JSON file keeps both.

The worker records three footprint values and one counter:

  • footprint_base_bytes: the footprint before the load.
  • load_peak_bytes: the lifetime maximum after the load.
  • peak_bytes: the lifetime maximum at the end. This is the peak memory of the results table.
  • run_peak_bytes: peak_bytes if it is above load_peak_bytes, else null with the note "below the load peak".
  • mps_driver_max_bytes: the largest driver_allocated_memory() after a batch.

3.7 Baseline row (D2)

For each model size, input resolution, batch size, output and dtype (fp32, fp16, bf16), baseline_rows picks one result line:

  1. Take the lines of the dtype modes of that dtype: fp32 → fp32; fp16 → fp16-cast and fp16-autocast; bf16 → bf16-cast and bf16-autocast.
  2. Drop the lines with status "skipped" or "error", the lines with "valid": false and the compile rows.
  3. Take the line with the highest throughput of the output.
  4. If no line is left, the baseline row is empty, with the reason.

The results table names the dtype mode of each baseline row. The Close stage writes this rule as ADR 0004.

3.8 Machine state

The driver reads the machine state before each worker and adds it to the JSON line:

  • Power source, from pmset -g batt ("AC Power" or "Battery Power").
  • Low Power Mode, from the lowpowermode line of pmset -g. On this Mac the line is missing; then the value is "not reported".
  • Thermal notes, from pmset -g therm. On 2026-11-06 it gave "No thermal warning level has been recorded".
  • The free memory before the worker, from available_memory_bytes.
  • macOS, Python, torch and transformers versions, the chip name and the memory size (once per run, in each line).

check_machine_state raises MachineStateError on battery power or with Low Power Mode on. The driver then stops and writes no line for the configuration.

3.9 Compile rows (D7)

B3 runs P1 and P2 in all five dtype modes with --compile. The compile time is part of the time of the first call. A compile error gives a line with status "error" and the error text. If a compile row is more than 10 % faster than its non-compiled row, the build reports it to the user, who decides if the compile rows join the baseline.

3.10 ViT-7B/16 (D8)

B1 writes one line with status "deferred" for each ViT-7B/16 configuration: "ViT-7B/16 runs in its own session (D8)". B4 runs only on the user's command:

uv run python scripts/benchmark.py --model-size ViT-7B/16

The user closes other apps first. The same memory check applies. A configuration that does not fit gives a "skipped" line. The fp32, fp16-autocast and bf16-autocast modes never run for ViT-7B/16 (run rule). If B4 does not run before Verify, Step 3 closes with the deferred lines.

3.11 Block profile (D6)

block_parts splits block 1 (model.model.layer[0]) into the parts of Table 6. run_parts runs the parts in order with the Hugging Face modules and functions. A test checks that their result equals the output of the block. profile_block captures the input of each part from one run, then times each part alone: a loop with one synchronize at the end, until at least 20 calls and 0.5 s, five times; the result is the median of the five loops. It times the whole block the same way, and also the parts outside the blocks: patch embedding, RoPE tables and the final layer norm.

3.13 Run order and run rules

  1. Wait until the user approves this plan. (Step 2 is closed: commits 11fc2dd, 44d411e, 7f5dd59.)
  2. Run B1 from the smallest to the largest model size, in the order of Section 3.6. One worker at a time.
  3. Run B2, then B3. P2 needs at least 10.2 GB available.
  4. Run B5, one subprocess for each model size and dtype mode.
  5. Ask the user for B4. Run it only after the user frees memory.

Each worker runs alone. The driver waits for a worker to end before it checks the memory for the next one. The driver sets the MPS watermarks in the environment of each worker. ViT-7B/16 never loads fp32 weights.

# src/dinov3_apple/bench.py
@dataclass(frozen=True)
class TimeBudget:
    """When a phase of batches ends (Table 5)."""

    min_batches: int
    min_seconds: float
    max_seconds: float | None = None
    floor_batches: int = 0


WARM_UP = TimeBudget(min_batches=3, min_seconds=2.0)
TIMED = TimeBudget(min_batches=30, min_seconds=10.0, max_seconds=60.0, floor_batches=10)


def keep_going(budget: TimeBudget, batches: int, elapsed_s: float) -> bool:
    """Return True while the phase needs another batch."""
    if budget.max_seconds is not None and elapsed_s >= budget.max_seconds:
        if batches >= budget.floor_batches:
            return False
    return batches < budget.min_batches or elapsed_s < budget.min_seconds
# src/dinov3_apple/torch_bench.py
@torch.inference_mode()
def time_batch(model: DINOv3ViTModel, batch: np.ndarray, mode: DtypeMode) -> tuple[float, float, float]:
    """Return the device time, the frame time and the patch time of one batch (Table 4)."""
    t0 = time.perf_counter()
    pixels = torch.from_numpy(batch).to("mps", mode.weights)
    with autocast_or_null("mps", mode.autocast):
        tokens = model(pixel_values=pixels).last_hidden_state
    torch.mps.synchronize()
    t1 = time.perf_counter()
    tokens[:, 0].cpu().numpy()
    t2 = time.perf_counter()
    tokens[:, NUM_PREFIX_TOKENS:].cpu().numpy()
    t3 = time.perf_counter()
    return t1 - t0, t2 - t0, (t1 - t0) + (t3 - t2)
# src/dinov3_apple/footprint.py
class _RusageInfoV4(ctypes.Structure):
    _fields_ = [("ri_uuid", ctypes.c_uint8 * 16)] + [(name, ctypes.c_uint64) for name in _V4_FIELDS]


def read_footprint(pid: int | None = None) -> Footprint:
    """Return the current physical footprint and its lifetime maximum, in bytes.

    The footprint includes the GPU memory of torch-mps and mlx on unified memory.

    Raises:
        OSError: If proc_pid_rusage fails.
    """
    info = _RusageInfoV4()
    if _libc.proc_pid_rusage(pid or os.getpid(), RUSAGE_INFO_V4, ctypes.byref(info)) != 0:
        raise OSError(ctypes.get_errno(), "proc_pid_rusage failed")
    return Footprint(info.ri_phys_footprint, info.ri_lifetime_max_phys_footprint)
# src/dinov3_apple/bench.py
DTYPE_OF_MODE = {"fp32": "fp32", "fp16-cast": "fp16", "fp16-autocast": "fp16",
                 "bf16-cast": "bf16", "bf16-autocast": "bf16"}


def baseline_rows(lines: list[dict], output: str) -> dict[tuple, dict | None]:
    """Pick the fastest valid non-compiled line for each configuration and dtype (Section 3.7)."""
    best: dict[tuple, dict | None] = {}
    for line in lines:
        key = (line["model_size"], line["side"], line["batch_size"], DTYPE_OF_MODE[line["dtype_mode"]])
        best.setdefault(key, None)
        if line["status"] != "done" or not line["valid"] or line["compile"]:
            continue
        if best[key] is None or line[output]["throughput_ips"] > best[key][output]["throughput_ips"]:
            best[key] = line
    return best

6 Tests

Each test is written first and must fail first (red). Tests that need weights, stored files or torch-mps skip with a reason when these are missing. Tests that load a model use ViT-S/16 only, on the default run.

  1. test_keep_going_small_batches_reach_30_and_10_s, test_keep_going_stops_at_60_s_after_10_batches, test_keep_going_slow_batches_run_10, test_warm_up_needs_3_batches_and_2_s: Table 5 with a fake clock (3 ms, 2.5 s and 40 s per batch give 3,334, 24 and 10 timed batches).
  2. test_summarize_throughput_median_p90: known batch times give the throughput of Section 3.3 and the median and p90 of NumPy.
  3. test_bench_configurations_counts: B1 has 225 configurations; ViT-7B/16 has 18, all in cast mode; --priority gives P1 and P2 in five modes.
  4. test_required_bench_bytes_grows_with_batch_and_side and test_required_bench_bytes_examples: at least required_load_bytes; ViT-H+/16, 512 px, batch size 32, fp32 between 15 and 19 GB.
  5. test_make_batch_cycles_test_images: batch size 8 gives images 0, 1, 2, 0, 1, 2, 0, 1 with shape (8, 3, side, side), fp32.
  6. test_check_validity_flags_nan, test_check_validity_passes_reference, test_check_validity_without_reference_is_finite_only.
  7. test_baseline_rows_pick_fastest_valid, test_baseline_rows_skip_invalid_and_compile, test_baseline_rows_empty_with_reason: synthetic lines.
  8. test_machine_state_parses_pmset (stored pmset texts for AC power, battery power and a lowpowermode 1 line), test_check_machine_state_refuses_battery, test_check_machine_state_refuses_low_power_mode.
  9. test_read_footprint_counts_mps_tensor: a 256 MB tensor on torch-mps raises the footprint by at least 230 MB; the lifetime maximum is at least the current value.
  10. test_part_flops_match_explore_table_2: image_flops gives the GFLOP values and the attention shares of Table 2 of explore.html within 0.5 %.
  11. test_run_parts_equals_block_output: ViT-S/16 and ViT-S+/16 on torch-cpu in fp32, 224 px: the parts in order give the output of block 1 with a largest difference of 1e-5 or less. It covers the MLP and SwiGLU.
  12. test_worker_writes_all_fields: ViT-S/16, 224 px, batch size 1, fp32, with a short budget: the result has every field of Table 7, valid is true.
  13. test_baseline_table_from_lines: synthetic lines give a Markdown table with the dtype mode of each baseline row and a skip section.
