Step 3 Baseline: Explore

Roadmap step 3. Status: decided. On 2026-11-06 the user chose the recommended option of each decision D1 to D8 (Table 1). Date: 2026-11-06.

1 Goal

Step 3 measures the baseline: the throughput and the peak memory of the Hugging Face backbone on torch-mps. Every later speedup divides by these numbers. Step 3 also measures where the time goes inside one block, for ViT-S/16 and ViT-H+/16. Step 6 runs the same harness on mlx.

These points are fixed by docs/plan.html, CLAUDE.md and Step 2. They are not options:

  • Backbone: DINOv3ViTModel of transformers 5.22.1, loaded with load_torch_backbone from the Hugging Face cache. The memory check runs before each load.
  • Model sizes: all six. Input resolutions: 224, 448 and 512 px square. Batch sizes: 1, 8 and 32, or smaller when the memory check fails (Table 11 of docs/plan.html).
  • Input: the stored pixels of tests/fixtures/generated/reference/inputs.safetensors. The three test images fill each batch in turn. Then each worker can check its first output against the reference output (D2).
  • Metrics: throughput, median and p90 latency at batch size 1, peak memory, load time and the time of the first call.
  • Run rules: one subprocess for each configuration, one heavy job at a time, a memory check first, and the MPS watermarks 0.8 and 0.6. ViT-7B/16 never runs with fp32 weights on torch-mps.
  • Output files: one JSON line for each configuration or skip, and a Markdown table in results/.

2 DINOv3 topic

The topic is where the compute goes for each model size and input resolution. The explainer docs/learn/03-where-the-compute-goes.html covers it. It starts from a FLOP count and ends with the measured time shares of D6.

A block has two kinds of matrix products. The linear layers (query, key, value and output projections, and the feed-forward network) cost about 2 × weights × N FLOPs for N tokens. The attention scores (Q·KT and the product with V) cost 4 × N2 × D FLOPs in each block. For an MLP with ratio 4, the ratio of the two is about N / (6 D). So the attention share grows with the token count and falls with the embedding dimension. Figure 1 and Table 2 show the shares.

FLOPs for one image, from the weight shapes of each model size (dinov3_mlx.flops.image_flops): the patch embedding, plus in each block 2 × N × (4 D2 + 2 D F) for the linear layers (3 D F for SwiGLU) and 4 × N2 × D for the attention scores. Corrected in the build on 2026-11-06: the first version used 2 × parameters × N with the rounded parameter counts of the model card (21M, 29M, 86M, 300M, 840M, 6,716M), which moved the values by up to 4 % and the shares by up to 0.5 points. N is 201, 789 or 1,029 tokens (Table 4 of docs/plan.html). One multiply-add counts as 2 FLOPs. The count leaves out the layer norms, RoPE, LayerScale, the activation function and the softmax.

The FLOP count is not the time. Two effects move the time away from it, and Step 3 measures both:

  • The parts without FLOPs in Table 2 (layer norms, RoPE, LayerScale, GELU or SiLU, the residual adds) read and write every token. Their cost is memory traffic. In small model sizes, their share of the time can be much larger than their share of the FLOPs.
  • Each operation has a fixed cost to start on the GPU. The probe of Section 3.1 measured about 170 µs for each extra synchronize after a small operation. ViT-S/16 at 224 px with batch size 1 has only 9 GFLOP. So fixed costs can set its throughput. This is risk R8 of docs/plan.html.

Four results drive the decisions:

  1. The macOS process footprint includes the memory of torch-mps. Its lifetime maximum catches short peaks. MLX memory also counts in it. So one measure works for both backends (D5).
  2. torch.mps.driver_allocated_memory() grows in steps of about 1 GB. A 256 MB tensor and a 1 GB tensor give the same value. It is too coarse for the small model sizes (D5).
  3. Each extra synchronize costs about 170 µs: (2,382 − 817) / 9 = 174 µs. A hook with a synchronize around each part of a block adds more time than some parts take (D6).
  4. torch.compile works on torch-mps for an MLP. It gave no gain for this MLP (D7).

3.2 D1: dtype modes in the baseline

Table 11 of docs/plan.html names three dtypes: fp32, fp16 and bf16. Step 2 found five dtype modes on torch-mps (Table 5 of specs/02-reference/plan.html). fp16-cast gives NaN for ViT-L/16 at every input resolution and for ViT-H+/16 at 224 px (results/parity-torch-mps.md). The reference fine-tuning setup uses fp16-autocast. MLX in Step 5 works like cast mode.

Option A: fp32, fp16-cast and bf16-cast. The three dtypes of Table 11, in cast mode, as MLX runs them.

  • For: the fewest configurations. Each MLX row has a partner in the same mode.
  • Against: ViT-L/16 and ViT-H+/16 have no valid fp16 row. The mode of the reference fine-tuning setup is not measured. A user who switches to autocast does not know the cost.

Option B: all five dtype modes.

  • For: the full picture. D2 can pick the best valid mode. The cost of autocast against cast becomes a measured number. Step 2 already tests the same five modes.
  • Against: 5/3 of the run time of Option A (Table 4).

Option C: five dtype modes for ViT-S/16 and ViT-H+/16, three for the others. These two model sizes are in the priority configurations of Section 7 of docs/plan.html.

  • For: the full picture where it matters most. Less run time than B.
  • Against: ViT-L/16 has no valid fp16 row, because fp16-cast overflows there at every input resolution.

3.3 D2: baseline row for the speedup

The glossary defines the speedup as the throughput of mlx divided by the throughput of the baseline, for the same configuration. With five dtype modes, "fp16" has two baseline rows. The rule must be fixed before Step 6 measures, so that nobody picks the row after the result.

Option A: the same dtype mode as mlx. MLX runs in cast mode, so the baseline is fp16-cast or bf16-cast.

  • For: the same arithmetic on both sides.
  • Against: ViT-L/16 and ViT-H+/16 have no valid fp16-cast row. A fast row with a wrong output can be the baseline. A user of PyTorch picks the faster valid mode, so the speedup overstates the gain.

Option B: the fastest dtype mode of the same dtype with a valid output. For fp16, the faster of fp16-cast and fp16-autocast. For bf16, the faster of bf16-cast and bf16-autocast. A row is valid when its output is finite and the first image passes the parity thresholds of its dtype mode. Each worker checks this on its first batch.

  • For: MLX must beat the best that PyTorch does with a correct output. It is the strictest fair rule. Every configuration has a baseline row.
  • Against: the arithmetic can differ (autocast keeps the residual stream in fp32). The results table must name the mode of each baseline row.

Option C: fp16-autocast only, the mode of the reference fine-tuning setup.

  • For: the number that matters for our own pipeline.
  • Against: no bf16 baseline. ViT-7B/16 has no autocast row, because its weights cannot be fp32 on torch-mps.

Recommendation: Option B. The results table also lists every other dtype mode, so a reader can compute the speedup against any row. The rule goes into an ADR in the Close stage, because Step 6 depends on it.

3.4 D3: timed region and the two outputs

The backbone computes all tokens for both outputs. The frame embedding and the patch embeddings differ only in the slice and in the copy to the host: B × D values or B × N × D values. For ViT-H+/16 at 512 px and batch size 32 in fp16, the patch embeddings are 84 MB. The frame embeddings are 82 KB.

Option A: device only. The pixels are already on the GPU. The timer stops after torch.mps.synchronize(). The output stays on the GPU. One row serves both outputs.

  • For: it measures only the backbone. The least noise.
  • Against: a user gets the output on the host. The copy of the patch embeddings is not measured. MLX on unified memory can avoid a copy, and Option A cannot show that gain.

Option B: host to host, one configuration for each output. The timer starts with the fp32 pixels in NumPy and stops with the output in NumPy. The frame run and the patch run are two configurations, as Table 11 lists them.

  • For: exactly what a user sees, for each output.
  • Against: twice the run time (Table 4). The two runs do the same forward pass.

Option C: host to host, one forward pass for each batch, the copy of each output timed separately. Each timed batch records four times:

t0 = perf_counter()
pixels = torch.from_numpy(batch).to("mps", dtype)    # pixels to the GPU
tokens = model(pixel_values=pixels).last_hidden_state
torch.mps.synchronize(); t1 = perf_counter()          # forward pass ends
frame = tokens[:, 0].cpu().numpy(); t2 = perf_counter()
patch = tokens[:, 5:].cpu().numpy(); t3 = perf_counter()

frame_time = t2 - t0                   # frame embedding row
patch_time = (t1 - t0) + (t3 - t2)     # patch embeddings row
device_time = t1 - t0                  # also recorded
  • For: one run gives the frame row, the patch row and the device time. Half the run time of Option B.
  • Against: the frame copy runs before the patch copy, so a cache effect can favor the patch copy a little. The copy is a few milliseconds against a forward pass of up to seconds.

Recommendation: Option C. The outputs stay in the dtype of the backend, with no cast to fp32 in the timed region. Step 6 uses the same four times for mlx, with mx.eval in place of the synchronize and np.array for the copy.

3.5 D4: timing procedure

The plan sets 5 warm-up batches and 30 timed batches, and lets Step 3 change them with a reason. One batch takes from about 3 ms (ViT-S/16, 224 px, batch size 1) to about 40 s (ViT-7B/16, 512 px, batch size 32, estimated). This Mac is an M5 Max. A long run can heat it and lower the clock.

Option A: 5 warm-up and 30 timed batches.

  • For: simple. The same count for every configuration.
  • Against: 30 batches of 3 ms are 0.1 s. The GPU clock can still ramp up in that time. 35 batches of 40 s are 23 minutes for one ViT-7B/16 configuration.

Option B: a time budget. Warm-up: at least 3 batches and at least 2 s. Timed: at least 30 batches and at least 10 s. Stop at 60 s when at least 10 batches are done.

  • For: small configurations get thousands of batches and a stable clock. Large configurations stop after a fixed time. The median and the p90 latency at batch size 1 always have at least 30 values.
  • Against: the count of timed batches differs between configurations. Each JSON line records it.

Option C: Option A with 3 repeats in new subprocesses. The median of the three runs is the result.

  • For: the spread of the repeats shows the noise.
  • Against: three times the run time, and the small configurations stay too short.

Recommendation: Option B, plus 3 repeats for the two priority configurations (ViT-S/16 frame embedding at 224 px, ViT-H+/16 patch embeddings at 512 px, batch size 8, the fp16 baseline row of D2). If their spread is above 5 %, the plan makes the budget longer. Each JSON line also records the machine state: power source, Low Power Mode, the CPU speed limit of pmset -g therm and the free memory before the load. The harness stops when the Mac runs on battery.

3.6 D5: peak memory

The glossary defines the peak memory "as the backend reports it". torch.mps has no peak counter. It has current_allocated_memory() and driver_allocated_memory(). MLX has mx.get_peak_memory(). The two backends count differently, so a ratio of their numbers can mislead.

Option A: the torch.mps counters. Read driver_allocated_memory() after each batch and keep the largest value.

  • For: no extra code. It is what the backend reports.
  • Against: it misses peaks inside a batch. It grows in steps of about 1 GB (Table 3). It does not include the CPU memory of the process. It cannot be compared with mx.get_peak_memory().

Option B: the process footprint of macOS. proc_pid_rusage gives the current footprint and its lifetime maximum. Each configuration runs in a new subprocess, so the lifetime maximum belongs to one configuration.

  • For: the same measure for torch-mps and mlx. It catches short peaks. It is the memory that the out-of-memory crash of this Mac depends on.
  • Against: it includes the load peak. The footprint does not fall after empty_cache() (Table 3), so the run peak can hide under the load peak. It needs ctypes and a fixed struct layout (rusage_info_v4).

Option C: both, with the load peak and the run peak apart. The worker reads the lifetime maximum after the load and again after the timed batches. It also records the largest driver_allocated_memory().

  • For: the footprint gives a fair comparison. The backend counter shows the share of the GPU heap. The load peak shows the cost of the load.
  • Against: when the run peak stays below the load peak, the run peak is unknown. The JSON line then records "below the load peak" and the current footprint after the run.

Recommendation: Option C. The lifetime maximum of the footprint is the main number in the results table. The glossary entry "peak memory" changes in the Close stage to name this measure.

3.7 D6: time share of each part of the block

Step 3 of docs/plan.html asks for the time share of each part of the block for ViT-S/16 and ViT-H+/16. The parts are: the first layer norm, the query, key and value projections, RoPE, SDPA, the output projection, the first LayerScale, the second layer norm, the feed-forward network and the second LayerScale.

Option A: profiler traces. torch.profiler or torch.mps.profiler, which writes signposts for Instruments.

  • For: the real kernels of one forward pass, with no change to the code.
  • Against: the MPS signposts need Instruments, a manual step. The CPU-side profiler shows the launch time, not the GPU time. A script cannot read the shares.

Option B: forward hooks with a synchronize before and after each part.

  • For: one forward pass of the real model. Easy to write.
  • Against: each synchronize costs about 170 µs (Table 3). A ViT-S/16 block at 224 px has about 10 parts. The hooks then add more time than the block takes. The GPU cannot overlap the parts.

Option C: each part alone, in a micro-benchmark. The harness takes the real weights of block 1, makes an input of the right shape and runs each part many times in a loop with one synchronize at the end. It also times the whole block the same way. A check compares the sum of the parts with the whole block.

  • For: no distortion from synchronizes. A script reads the shares. Step 4 and Step 6 can run the same split on mlx, so the explainer can show both backends side by side.
  • Against: a part alone can run faster or slower than inside the block (cache, launch overlap). The sum check shows the size of this error.

Option D: FLOP count only. Table 2, extended to every part.

  • For: no run. Exact.
  • Against: it misses the memory-bound parts and the fixed costs (Section 2).

Recommendation: Options C and D. C gives the measured share and D gives the FLOP share. The gap between them is the main lesson of the explainer. The sum of the parts must be within 15 % of the whole block, or verify.html explains the gap. Batch sizes 1 and 8, input resolutions 224 and 512 px, fp32 and the valid fp16 mode.

3.8 D7: software settings of the baseline

The baseline must be the backbone that a user of PyTorch gets. transformers uses SDPA attention by default on torch-mps, and Step 2 recorded it (attn_implementation: sdpa). transformers marks DINOv3 as ready for a full-graph torch.compile.

Option A: the Hugging Face default. SDPA attention, eager mode, no compile.

  • For: the same code as Step 2 and as most users. No compile time.
  • Against: a tuned PyTorch can be faster. Then the speedup overstates the gain over the best PyTorch.

Option B: Option A with torch.compile for every configuration.

  • For: the strongest baseline.
  • Against: a compile for each subprocess, about 4 s for one MLP (Table 3), more for a full backbone. The probe showed no gain. The MPS backend of torch.compile is new, so an error can block a configuration.

Option C: Option A as the baseline, plus report-only rows with torch.compile. Only for the two priority configurations, in the dtype modes of D1.

  • For: the baseline stays simple. The extra rows show if a tuned PyTorch is faster, at small cost.
  • Against: the other configurations have no compile row.

Recommendation: Option C. If a compile row is more than 10 % faster than its baseline row, the plan asks the user if the compile rows join the baseline.

3.9 D8: ViT-7B/16

ViT-7B/16 runs on torch-mps in fp16-cast and bf16-cast only. Step 2 measured a need of 20.1 GB for that load and found 14.7 GB free. The weights take 13.4 GB in fp16. At 512 px and batch size 32, the activations add a few GB more. Step 2 deferred its reference file for the same reason.

Option A: in the normal run. The memory check of each configuration decides.

  • For: no extra step.
  • Against: with about 15 to 23 GB free, most or all ViT-7B/16 configurations skip. The run gives no number.

Option B: a separate run, last. The harness takes a model size argument. The user closes other apps. Then the harness runs ViT-7B/16 alone, in cast mode, with the same memory check. A configuration that does not fit still skips with a recorded reason.

  • For: the best chance of a ViT-7B/16 baseline, inside the run rules. It can share the session with the deferred ViT-7B/16 reference file of Step 2.
  • Against: it needs the user. About 0.7 h of run time (Table 4).

Option C: leave out ViT-7B/16.

  • For: no risk for the memory of this Mac.
  • Against: goal 3 of mission.md asks for every model size. The MLX run of ViT-7B/16 in Step 6 then has no speedup.

Recommendation: Option B. The normal run records ViT-7B/16 as "deferred to the separate run". Step 3 can close with recorded skips for ViT-7B/16 (the done condition of Step 3 accepts a recorded skip).

3.10 The design with all recommendations

The new code reuses Step 2: check_free_memory, load_torch_backbone, DTYPE_MODES, read_inputs, read_reference, measure_parity and THRESHOLDS. The worker does not use run_torch in the timed region, because run_torch casts the output to fp32 and copies all tokens. The plan names the new modules, for example src/dinov3_mlx/bench.py for the timing loop and the footprint reader.

9 Open questions

  • D1 to D8: decided on 2026-11-06. The user chose the recommendation of each decision.
  • When does Step 3 run its first heavy job? The build starts after the user confirms that Step 2 is closed, because a Step 2 Verify agent can still run tests now.
  • Batch sizes: Table 12 of docs/plan.html sends up to 120 frames of ViT-S/16 through the backbone in one batch. Should Step 3 add batch size 64 or 128 for ViT-S/16? The recommendation is no: Step 6 searches the best batch size for both backends.
  • Low Power Mode and the power source: the harness records them. Should it also refuse to run when Low Power Mode is on? The recommendation is yes.
  • The rates in Table 4 are assumptions. The first ViT-S/16 and ViT-H+/16 runs of the build measure them. If the full run takes more than 4 h, the plan splits it by model size.
