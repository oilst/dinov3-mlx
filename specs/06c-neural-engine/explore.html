Step 6c Neural Engine: Explore

Roadmap step 6c. Status: options picked. The user asked the agent to decide (night of 2026-11-07): each decision takes the recommended option of Table 12. Date: 2026-11-07.

1 What Step 6c must do and the starting point

Step 6c explores Core ML on the Apple Neural Engine, alone and in parallel with the GPU, against mlx. mission.md allows Core ML when a profile shows that MLX cannot reach a goal. The Step 6 matrix shows this: compiled mlx is about as fast as torch.compile, and both backends reach about 29 TFLOP/s at ViT-L/16, the limit of the GPU matmul units. The Neural Engine is a second matrix accelerator next to the GPU. If it gives correct outputs, it can add throughput to the GPU.

These points are fixed. They are not options:

  • The reference output and the fp16 thresholds of ADR 0003: frame ≥ 0.999, patch mean ≥ 0.999, patch 1st percentile ≥ 0.99.
  • The Hugging Face DINOv3ViTModel is the source graph (our reference model). Its weights come from the Hugging Face cache.
  • ADR 0004: a speedup comes from paired runs, and two runs at different times. Step 6c measures our compiled mlx again in the same paired runs.
  • ADR 0008 and the run rules of CLAUDE.md: one heavy job at a time through the GPU lock, a memory check before each load, ViT-7B/16 never with the fp32 weights of the whole model.
  • Converted .mlpackage files live outside the repo, in ~/.cache/dinov3-mlx/coreml/.

The Step 6b probes (shared note of 2026-11-07, 22:40) found that the public fp16 Core ML exports of DINOv3 break on CPU_AND_NE (patch mean 0.66 and −0.03), and pass on CPU_AND_GPU (≥ 0.999992). Section 2.3 gives the cause.

2.2 coremltools 9.0 with the versions of this repo

coremltools 9.0 (PyPI, 2025-11-10) is the newest release; 9.1.dev1 is a development build. It has a wheel for Python 3.12 on arm64. It imports with torch 2.15.0 and numpy 2.5.4, and it warns: "Torch 2.7.0 is the most recent version that has been tested." MLComputePlan is in coremltools.models.compute_plan.

The first conversion failed in the torch frontend: _cast (the op aten::Int) calls int() on a constant array with one value, and numpy 2.5 refuses this ("only 0-dimensional arrays can be converted to Python scalars"). A replacement of coremltools.converters.mil.frontend.torch.ops._cast that calls .item() fixes it (15 lines). With it, every probe converted. uv add --group coreml coremltools==9.0 adds 5 packages (attrs, cattrs, coremltools, protobuf, pyaml) and changes no version of the repo (commit d9bb890).

2.3 Why the Neural Engine breaks the fp16 graph

ViT-S/16 converts in 2.0 s (trace 0.4 s). On CPU_AND_NE it runs at 593 img/s at batch size 1, but its output is wrong: frame cosine 0.035, patch mean 0.148. The same package on CPU_AND_GPU passes (frame 0.999996, patch 1st percentile 0.999993). The output on the Neural Engine is finite, so a check for non-finite values does not catch the fault.

The hidden states (probe p2) show the place: before block 1 the token sequence agrees (cosine 1.0). After block 1 it is infinite, although its largest true value is only 47.5. A layer norm that divides each token by its largest value first (p3) does not help. Probe p4 returns each intermediate value of block 1:

Finding F1. The attention scores of DINOv3 are far outside the fp16 range: 2.4 million in block 1 of ViT-S/16, 36 times the largest fp16 value. The Neural Engine stores the scores in fp16 before the softmax, so they become inf, and the softmax gives inf or NaN. The GPU path of Core ML, mlx and torch-mps keep the scores inside a fused attention kernel with fp32 accumulation, so the same fp16 graph passes there. This is the cause of the failure of the public fp16 exports on CPU_AND_NE that Step 6b found. In the full model the inf values later turn into finite but wrong tokens (frame 0.035).

2.5 The fix: an exact rewrite before the conversion

Two changes to the torch graph before the trace keep every value inside fp16. Each change is exact in real numbers. The weights do not change except for one power of two in two projections of each block.

  1. Score scaling. The attention multiplies q by (1/√d) / s with s = 256 (a power of two, so the division adds no rounding error). Then z = q·kᵀ is 256 times smaller than the true score. The softmax gets (z − max z) · s, clipped at −60,000. The maximum subtraction comes before the multiplication, so no value above 0 enters the softmax. softmax((z − max z) · s) = softmax(true scores).
  2. Residual-stream scale. The embeddings (CLS token, register tokens, patch tokens) are divided by r, and the weights and the bias of o_proj and down_proj are multiplied by 1/r. LayerScale stays a separate multiplication. The whole residual stream and each branch output are r times smaller, so the branch output of ViT-L/16 before LayerScale (52,019) also drops. Each layer norm and the final layer norm remove the factor, because a layer norm does not change when its input is scaled (except for its ε). r is a power of two: 1 for ViT-S/16 to ViT-B/16, 8 for ViT-L/16 and ViT-H+/16 (158,177 / 8 = 19,772).

Four facts follow:

  • Batch size 8 does not help the Neural Engine. ViT-S/16 runs at 540 img/s at batch size 1 and 452 img/s at batch size 8 (17.7 ms a batch). The GPU gains 3 times from batch size 8.
  • The Neural Engine is slow at 512 px and for large model sizes. ViT-H+/16 at 512 px batch size 8 takes 2.93 s a batch (2.7 img/s), 7 times slower than Core ML on the GPU. Its first load (the Neural Engine compile) takes 114 s.
  • Core ML on the GPU is close to compiled mlx: faster at P2 in this short loop (19.7 against 16.3 img/s), slower at P1 (1,476 against 1,842 to 2,040 img/s). Step 6b found 0.94 to 1.09 in paired checks. Step 6c measures it in paired runs (D7).
  • Finding F2: the LayerScale fold is wrong in fp16. The LayerScale factors of DINOv3 go down to 3.6e-8 (median 2.6e-4 in block 1 of ViT-S/16). Folded into the weights of o_proj, they make 94 % of the weights of block 1 of ViT-S/16 subnormal in fp16 (below 6.1e-5), and 63 to 78 % in block 1 of ViT-L/16 and ViT-H+/16; without the fold 0.1 to 9 %. With the fold, ViT-L/16 and ViT-H+/16 fail also on the GPU (frame 0.990, patch 1st percentile 0.985). So the rewrite keeps LayerScale as a multiplication and moves only the power of two 1/r into o_proj and down_proj (D2).

One question is open at the time of writing: the ViT-S/16 package with the fold passes on the Neural Engine at batch size 1 (p11: frame 0.99986) but fails at batch size 8 (p7). At batch size 1 the compute plan put the patch embedding and the first attention on the CPU (46 ops, 24.6 % of the estimated cost); at batch size 8 every op ran on the Neural Engine. Probe chain 2 (p12 to p17: the compute plans, block 1 with score scaling at batch size 1 and 8, ViT-S/16 batch size 8 without the fold, ViT-L/16 and ViT-H+/16 with the power-of-two scale) answers it. Section 2.10 gives its result.

2.9 What the compute plan shows

MLComputePlan (coremltools 9.0, coremltools.models.compute_plan) gives for each op the preferred device, the supported devices and an estimated cost (a share of the total). It answers the explore question "which ops run on the Neural Engine" without a profiler.

  • ViT-S/16, 224 px, batch size 1, score scaling (p5), CPU_AND_NE: 525 ops on the Neural Engine, 46 on the CPU, with 75.4 % and 24.6 % of the estimated cost. The CPU ops are the input cast, the patch embedding (conv), one layer_norm, 4 linear, 2 matmul, 1 softmax and the ops around them: the size of one attention branch.
  • ViT-S/16, 224 px, batch size 8 (p7), CPU_AND_NE: every op on the Neural Engine except 3 reshape.
  • With ALL, the plan puts every op on the GPU (p1). ALL is not a mix of GPU and Neural Engine for this graph. Step 6b found the same speed for ALL and CPU_AND_GPU.
  • The Neural Engine runs linear, matmul, softmax, layer_norm, gelu, silu, reduce_max and clip. The converter writes no scaled_dot_product_attention op: the Hugging Face SDPA path becomes matmul, softmax, matmul. A fused attention op on the Neural Engine is not available from this graph.

Finding F4. At batch size 8 the Neural Engine gives wrong input tokens: cosine 0.133 before block 1, with the right largest value (10.66). The 8 images of the batch are equal, so the fault is in the order of the values inside the patch embedding (conv, reshape, transpose, concat), not a mix of images. At batch size 1 the compute plan keeps the input cast, the conv and the ops up to the first attention on the CPU (p12: 46 ops, 24.6 % of the estimated cost), and the output is right. At batch size 8 the plan puts all of them on the Neural Engine (p12: 4 ops on the CPU, 1.3 % of the cost). The ViT-S/16 package at batch size 8 without the fold (p15) gives frame 0.385, the same as with the fold (p7): the fold did not cause the P1 failure.

Score scaling works on the Neural Engine: at batch size 1 the scores of block 1 have cosine 0.999999 and a largest value of 9,344 (true 9,335), and the block output has cosine 0.999992. The softmax output has cosine 0.952 (rows close to one-hot, rounded to fp16), but the attention output has 0.99937.

ViT-L/16 at 224 px batch size 1 with the power-of-two scale (r = 8, no fold, p16) still fails: on CPU_AND_NE frame 0.092, and on CPU_AND_GPU frame 0.990 and patch 1st percentile 0.943. The same graph with the fold gave nearly the same values (p10). So ViT-L/16 has a second fp16 limit that the rewrite does not remove, also on the GPU. Step 5 could not show it, because ViT-L/16 in fp16-cast overflows at block 1 there. A candidate cause is the layer norm ε: with r = 8 the ε of each layer norm acts as 64 · ε on the unscaled tokens. The plan sets ε to ε / r², and the build runs the block probe on the first wrong block of ViT-L/16 (plan Q3).

Consequences for the plan (amended after the approval, with this evidence): the coreml-ne rows at batch size 8 use the batch-size-1 package with the batch API of Core ML (predict on a list of 8 inputs), which is also the faster form (540 against 452 img/s); the batch-size-8 package runs on CPU_AND_NE once at P1 as F4 evidence. The layer norm ε becomes ε / r². ViT-L/16 and ViT-H+/16 may be expected failures in AC4 and AC5 with the evidence of a block probe.

3.3 D3: Compute precision and the name of the dtype mode

The Neural Engine computes in fp16 only. A package with fp32 compute precision runs on the CPU or the GPU, not on the Neural Engine (Step 6b: the FP32 SharpAI export on CPU_AND_NE kept parity 1.0 at 157 img/s). Recommendation: fp16 compute precision (ct.precision.FLOAT16) for every package. The input stays fp32 (a cast op in the package) and the output is fp32. The weights, the residual stream and every activation are fp16, so the rows get the dtype mode fp16-cast and the fp16 thresholds of ADR 0003. Options: A. one package for each model size, input resolution and batch size (fixed shapes); B. one package with ct.EnumeratedShapes; C. a flexible range (ct.RangeDim). 3.6 D6: The model sizes and configurations

Recommendation: ViT-S/16, ViT-S+/16, ViT-B/16, ViT-L/16 and ViT-H+/16; input resolutions 224, 448 and 512 px for parity (batch size 1, the 3 test images); 224 and 512 px at batch size 1 and 8 for speed. The own-aspect configurations of the reference files need one package each; they stay out. ViT-7B/16 stays out: the trace needs the torch model in fp32 (27 GB, against ADR 0008), and its fp16 weights (13.6 GB) are far above the size of the other packages. The plan records it as "deferred" with this reason. The user asked the agent to decide (night of 2026-11-07).

3.7 D7: The measurement protocol

Recommendation: the protocol of Step 6 (ADR 0004): each configuration runs in its own subprocess, with the time budget of bench.py (warm-up 2 s, timed 10 s). The Core ML workers and the compiled mlx workers of one configuration run in alternation, in a rotated order. The mlx side takes the fastest valid fp16 dtype mode of the configuration (fp16-cast or fp16-autocast). P1 and P2, at batch size 8 and 1, get 5 paired rounds; the Verify stage runs a second paired run at another time. The other configurations get 2 paired rounds. The user asked the agent to decide (night of 2026-11-07).

3.8 D8: The two-stream run

Options: A. two processes (Core ML on CPU_AND_NE, compiled mlx on the GPU) with a common start time; each counts its batches in the same time window; the combined throughput is the sum. B. Two threads in one process. C. One Core ML package with ALL. C does not split the work (Section 2.9). B shares one Python interpreter and its lock between the two loops. Recommendation: A, in the order alone, alone, both, rotated over the rounds, so each round has its own reference. The user asked the agent to decide (night of 2026-11-07).

3.9 D9: Where the code goes

Recommendation: new files only: src/dinov3_mlx/coreml.py (the rewrite, the conversion, the _cast patch, the load and the run), scripts/bench_coreml.py (the driver, its own result file results/coreml.jsonl), tests/test_coreml.py. coremltools stays in the dependency group coreml; the tests skip without it. The shared modules (bench.py, speedup.py, mlx_bench.py) do not change; bench_coreml.py calls their public functions. Step 6b works in parallel on its own new files. 7 New terms

Terms for GLOSSARY.md. The build adds them when the code uses them.

  • Core ML package: one converted backbone for one model size, input resolution and batch size (.mlpackage), in ~/.cache/dinov3-mlx/coreml/.
  • Compute unit: the Core ML setting that names the devices a package may use: CPU_ONLY, CPU_AND_GPU, CPU_AND_NE or ALL.
  • Compute plan: the device and the estimated cost of each op of a compiled package, from MLComputePlan.
  • Neural Engine rewrite: the two exact changes to the Hugging Face backbone before the conversion that keep every value inside fp16: score scaling and residual-stream scale.
  • Score scale: the power of two (256) that divides the query before q·kᵀ. The softmax gets (z − max z) · 256.
  • Residual-stream scale: the power of two r that divides the embeddings and the weights and bias of o_proj and down_proj. The layer norms remove it.
  • Two-stream run: Core ML on the Neural Engine and compiled mlx on the GPU at the same time, in two processes with a common start time. Its throughput is the sum of the two.
