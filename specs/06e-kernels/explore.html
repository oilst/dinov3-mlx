Step 6e Kernels: Explore

Roadmap step 6e. Status: option picked. On 2026-11-11 the user picked "A, then C1": option A (A1 and A2), then the probe C1 (Section 4). Date: 2026-11-10.

1 What Step 6e must do and the starting point

The roofline of 06-5 shows where the time of one block goes. The configuration is P2: ViT-H+/16, 512 px, batch size 8, compiled mlx, on the M5 Max. The five matmul parts are compute-bound. They reach 60 to 85 % of the matmul roof. The six element-wise parts are memory-bound, and mx.compile already fuses their chains.

Step 6e must find out which change of the kernels, or of the way the port calls them, makes the block faster. Then it must measure the gain with a paired run. Target of the roadmap row: a paired gain at P2 that is above the noise, with the parity of the fp16 and bf16 thresholds.

These points are fixed. They are not options:

  • The thresholds of ADR 0003. A faster kernel that fails parity does not count.
  • The compiled forward pass is the path of the parity tests and the API (ADR 0010).
  • The measurement protocol of Step 6: paired rounds, two runs, the pooled median (ADR 0004, ADR 0009, D7 and D21 of specs/06-speed/plan.html).
  • Third-party code runs outside the repo, in its own venv, and only with the user's permission (ADR 0013).
  • The module names q_proj, k_proj, v_proj, gate_proj and up_proj stay. The strict load, nn.quantize and the LoRA targets of Step 8 use them.
  • The run rules of CLAUDE.md.

2.3 What the numbers say

  • If all matmul parts ran at the roof, the block would be 1.25 times faster in fp16-cast and 1.27 times in bf16-cast. If the grey part also went to zero, it would be 1.49 and 1.47 times. These are upper limits, not targets.
  • The roof itself is the best rate of an MLX kernel (scripts/probe_roofs.py). It is not the hardware peak. A better kernel can also raise the roof.
  • The rate of a matmul depends on its shape on this Mac. In fp16, one 1,280 → 3,840 layer reaches 53.6 TFLOP/s, but one 1,280 → 1,280 layer reaches only 43.0 TFLOP/s (Table 1 of 06-5). In bf16 the 1,280 → 10,240 layer reaches only 45.1 TFLOP/s, against 56.3 TFLOP/s for 1,280 → 5,120.
  • The layout matters: x @ W.T (the nn.Linear layout) reached 59.3 TFLOP/s, a plain a @ b only 41.4 TFLOP/s.
  • Step 6 already measured the fused projections (D6 of specs/06-speed/explore.html): 7 to 8 % at batch size 1 eager, 0 to 2 % compiled, at 224 px. It kept separate projections. The estimate at P2 is 8.5 % in fp16-cast and 2.5 % in bf16-cast (Table 5 of 06-5), but that estimate compares two processes.

3 Options

3.1 Option A: call the MLX kernels in a better way

No kernel code changes. The port gives the existing kernels better shapes and layouts. Two changes:

  • A1 Fused projections at P2. The compiled path joins the weights of q, k and v into one 1,280 → 3,840 matmul, and the weights of gate and up into one 1,280 → 10,240 matmul. The modules and their names stay; a function builds the joined weights once after the load (D6 b). It costs a second copy of these weights in memory, or a second load path. For ViT-H+/16 in a half dtype the copy is 1.15 GB: 32 blocks × 18.0 M values × 2 bytes, about 69 % of all weights.
  • A2 Shape and layout sweep. A probe of the other layouts of the same arithmetic: the layout of q, k and v at the input of the attention kernel, and the gate and up matmul as one or two layers per dtype mode (the bf16 result of Section 2.3 says that two layers can be faster).

Gain: at most the gap of qkv_proj and ff_in, 1.16 ms (9.7 % of the block) in fp16-cast. The estimate is 8.5 % in fp16-cast and 2.5 % in bf16-cast.

3.2 Option B: our own fused kernels with mx.fast.metal_kernel

mx.fast.metal_kernel (MLX 0.32.4) compiles Metal source code from Python at run time. The port can call the kernel like any other MLX operation. Two uses:

  • B1 Epilogue fusion. One kernel for the matmul and the element-wise operations after it: o_proj with the bias, LayerScale and the residual add; ff_out with the same. The intermediate values do not go to memory.
  • B2 Layer norm with its next operation. mx.fast.layer_norm is a fusion barrier (06-1). One kernel for the layer norm and the cast of the autocast modes.

Gain: at most the grey part of Figure 1, 1.51 ms (13 %) in fp16-cast. At the memory roof the element-wise bytes still need 1.12 ms, so the real gain is smaller. Risk: for B1 our matmul must be as fast as the NAX matmul kernel of MLX, which uses the Neural Accelerators of the M5. The MLX wheel ships the headers of these kernels (steel/gemm/gemm_nax.h, steel/attn/nax.h), but it is not known if a custom kernel can use them. The custom kernel also needs its own vjp for the training of Step 8.

3.3 Option C: tune the MLX kernels in a source build

MLX selects the tile sizes of a matmul and of the attention kernel from the device and the shape. A source build of MLX lets us change these values for the shapes of Table 1 on the M5 Max, and measure each change.

  • C1 Probe. A clone of the MLX repo outside our repo, its own venv, a build with the Xcode command line tools. A sweep of the tile sizes for three shapes: 1,280 → 1,280 (o_proj and q, k, v), 1,280 → 10,240 in bf16, and the attention kernel at T = 1,029 and head dimension 64.
  • C2 Upstream. If C1 finds a gain, a pull request to MLX. Only an upstream change reaches the users of our package: the package cannot depend on a private build of MLX.

Gain: at most the whole gap, 2.40 ms (20 % of the block time, 1.25 times the block speed) in fp16-cast, and more if a new tile size raises the roof. Cost: the largest of the three options. It needs C++ and Metal work, a build of MLX for each change, and a review by the MLX maintainers that we cannot plan.

3.4 Not an option for Step 6e

  • The Neural Engine. Steps 6c, 6d and 7b cover it.
  • Lower precision (8 bits, 4 bits). Step 6 found that quantized weights save memory, not time (ADR 0011).

4 Recommendation

Option A first, then the probe C1. No option B in Step 6e.

  • A1 is cheap, and a paired run at P2 (5 rounds, two runs) decides the open question of D6 at a large configuration. If the pooled median of both runs is above 1.03 in fp16-cast, the compiled path takes the joined weights for the SwiGLU model sizes.
  • C1 measures whether other tile sizes close the gap of o_proj and SDPA. It is a probe only: our package keeps the released MLX. A gain of C1 goes to MLX as a proposal, which the user sends (C2).
  • B has the smallest ratio of gain to work: most of the grey part is already fused, and an epilogue kernel must first match the NAX matmul.

5 Questions for the user

  • Q1: Which options: A, B, C, or a mix? The recommendation is A, then C1.
  • Q2: C1 needs a clone of the MLX repo (MIT license) in ~/.cache/dinov3-mlx/mlx-src/, its own venv and a build with the Xcode command line tools. Under ADR 0013 this needs your yes. Do you allow it?
  • Q3: A pull request to MLX is an external action. The agent prepares the change and the numbers; you send it. Do you want this, if C1 finds a gain?
  • Q4: Target for A1: a paired gain of 3 % or more at P2 in fp16-cast (pooled median, both runs above 1.03). Is this the right limit? D6 of Step 6 set 10 % at batch size 1 as the condition to reopen the question.
  • Q5: Order: does Step 6e come before Step 7b (the Neural Engine backend) and Step 8 (fine-tuning)?

6 New terms

Terms for GLOSSARY.md. The build adds them when the code uses them.

  • Joined projection: one matmul with the weights of q, k and v (or of gate and up) joined along the output axis (option A1).
  • Epilogue fusion: one kernel that runs a matmul and the element-wise operations after it (option B1).
  • Tile size: the size of the block of the output that one group of GPU threads computes in a matmul or attention kernel (option C).
  • Source build: a build of MLX from its source code, outside the repo, in its own venv (option C1).
