1 Why compare the ports

Four public projects run DINOv3 in MLX: MLXDINOv3 (Swift), mlx_dinov3 (Python), the DINOv3 part of mlx-image (Python) and mlx-dinov3 (Python, not complete). specs/01-scope/explore.html compares what each project gives. This explainer compares how each project computes the backbone, part by part, against the Hugging Face DINOv3ViTModel. Our parity tests compare with that model (see "reference output" in GLOSSARY.md).

The ports come from two code bases. MLXDINOv3 follows the Hugging Face code. mlx_dinov3 and mlx-image follow the official Meta code. Both code bases compute the same function, but they use different weight names and different defaults.

2 The token layout

All four ports and the Hugging Face model use this layout. The patch embedding is a 16 × 16 convolution with stride 16. MLX convolutions use the channels-last layout NHWC, so every port moves the axes of the convolution weight from (out, in, 16, 16) to (out, 16, 16, in). In the Hugging Face code, the variable num_prefix_tokens holds the 5 tokens before the patches.

3 The 2D RoPE

DINOv3 has no learned position embedding. Each block rotates the queries and keys of the patch tokens by angles that come from the patch position. The Hugging Face code computes the angles in four steps:

# transformers, modeling_dinov3_vit.py (Apache-2.0), shortened
coords_h = torch.arange(0.5, num_patches_h) / num_patches_h    # patch centers in (0, 1)
coords_w = torch.arange(0.5, num_patches_w) / num_patches_w
coords = 2.0 * stack(meshgrid(coords_h, coords_w)) - 1.0        # (H*W, 2) in (-1, 1)
inv_freq = 1 / base ** torch.arange(0, 1, 4 / head_dim)        # head_dim / 4 values, base = 100
angles = 2 * pi * coords[:, :, None] * inv_freq[None, None, :] # (H*W, 2, head_dim / 4)
angles = angles.flatten(1, 2).tile(2)                           # (H*W, head_dim)
  • Each axis gets one quarter of the head dimension, and the tile doubles the result for the rotate-half form.
  • Each axis has its own scale (Meta calls this "separate" normalization). A non-square image therefore still spans (-1, 1) on both axes.
  • The prefix tokens get no rotation. apply_rotary_pos_emb splits q and k after the prefix tokens.
  • Hugging Face computes the tables in fp32 and then casts them to the dtype of the input.

4 The feed-forward network

ViT-S/16, ViT-B/16 and ViT-L/16 use an MLP: up projection, GELU, down projection. ViT-S+/16, ViT-H+/16 and ViT-7B/16 use SwiGLU: down(silu(gate(x)) * up(x)). The width of the SwiGLU hidden layer looks strange in the Hugging Face config:

Model sizeMeta ffn_ratioEmbedding dimensionMeta hidden widthHugging Face intermediate_size
ViT-S+/166384384 × 6 × 2/3 = 15361536
ViT-H+/16612801280 × 6 × 2/3 = 51205120
ViT-7B/16340964096 × 3 × 2/3 = 8192, aligned to 648192

Table 2. SwiGLU width. Meta multiplies the ratio by 2/3, so the three matrices of SwiGLU have about the same parameter count as the two matrices of an MLP with the full ratio.

mlx_dinov3 has no factory for ViT-S+/16 or ViT-H+/16. Its converter computes the ratio back from the weight shape. mlx-image sets ffn_ratio=6 and ffn_layer="swiglu" for ViT-S+/16, as Meta does.

MLXDINOv3 reads the Hugging Face names and changes only the axes of the convolution weight. mlx_dinov3 and mlx-image keep the Meta names and read .pth files. ADR 0002 makes us follow the Hugging Face side.

8 The code of Step 1

8.1 src/dinov3_apple/hub.py

  • MODEL_IDS maps each model size to its Hugging Face id. A test compares it with tech-stack.md, so the code and the docs cannot drift apart.
  • check_free_disk(required_bytes, keep_free_bytes, path) raises InsufficientDiskError when a download would leave less free disk than the limit. The download script keeps 50 GB free.
  • download(model_id) calls snapshot_download with WEIGHT_PATTERNS. The patterns get the config, every safetensors shard and the shard index, and nothing else.

8.2 scripts/convert_meta_checkpoint.py

  • check_checksum(checkpoint): Meta puts the first 8 hex digits of the SHA-256 in each file name, for example …-08c60483.pth. The function computes the hash in chunks of 16 MB and compares.
  • convert_state_dict(meta_state_dict) applies Table 3.
  • load_test_image() resizes the COCO test image to 224 × 224 px on float pixels with antialiasing, then normalizes it with the ImageNet mean and standard deviation.
  • check_outputs(model, model_size) compares 5 values of the frame embedding and 5 values of the first patch embedding with the Hugging Face converter (tolerance 1e-3).
def convert_state_dict(meta_state_dict):
    converted = {}
    for key, tensor in meta_state_dict.items():
        if ".qkv." in key:  # one fused matrix -> three matrices

                converted[key.replace("qkv", name)] = part

            converted[key] = tensor

9 Surprises

  1. The k bias is always zero. Meta trains with one fused qkv bias, but a mask (mask_k_bias=True, bias_mask) sets the k part to zero. So the Hugging Face model has no k_proj.bias (key_bias=False). ViT-7B/16 has no q bias and no v bias either.
  2. 8-bit pixels change the output. Our first conversion check resized the 8-bit image with Pillow and missed the expected values by 0.004. A resize on float pixels, as torchvision does, missed by 0.0004 or less. The preprocessing must be fixed before the parity tests of Step 2 can mean anything.
  3. bf16 RoPE tables by default. Both Python ports build the RoPE tables in bf16 unless the caller changes a default. Meta's hub code and Hugging Face use fp32.
  4. SwiGLU width. intermediate_size is 4 × the embedding dimension for ViT-S+/16 and ViT-H+/16, but Meta's ratio is 6 (Table 2).
  5. Shards break a simple converter. MLXDINOv3 downloads only model.safetensors. ViT-7B/16 has six shards and an index, so the converter cannot read it.
  6. The converted file has the same size as the Hub file. Our converted ViT-S/16 and ViT-H+/16 files have exactly the byte count of the files on the Hub. After the downloads, a test showed that each converted tensor is equal to the Hub tensor.
