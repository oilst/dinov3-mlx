1 Why this explainer

Up to Step 5, the MLX backbone ran as an eager forward pass. Each call builds the graph again, and most operations become their own GPU kernel. nn.gelu and nn.silu are compiled functions in MLX already, so each of them is one kernel also in the eager forward pass (D1, specs/06-speed/explore.html). Each kernel reads its inputs from memory and writes its output to memory. Step 6 wraps the whole forward pass in one mx.compile function. mx.compile records a trace at the first call and joins each chain of element-wise operations into one fused kernel. Step 6 also changes the RoPE rotation, so that the rotation of q and the rotation of k each become one fused kernel.

This page covers the functions of row 06-1-compiled-forward-pass.html in Table 5 of specs/06-speed/plan.html, and the surprises of that row. Table 1 lists the functions. The line numbers are those of commit 2567808, the last commit of the Step 6 build. "(new)", "(changed)" and "(removed)" compare with commit 11a45b1, the last commit before the build. Each code quote is an exact copy of the file, except where the quote says "shortened". The first line of each quote, a comment with the file name, belongs to this page. The notes under each quote explain the code.

The agent that wrote this page ran no test, no model and no GPU job. It read the numbers from the committed result files with a small CPU-only Python script. Section 12 names each file. A number marked "probe" comes from the Explore stage (specs/06-speed/explore.html), before the build. Every other number comes from a result file of the build.

P1 and P2 are the two priority configurations: P1 is ViT-S/16 at 224 px, batch size 8, frame embedding. P2 is ViT-H+/16 at 512 px, batch size 8, patch embeddings.

The result in three numbers:

  • The compiled forward pass (change ratio C1) gives 1.250 to 1.305 times the throughput of the eager forward pass in the four fp16 and bf16 dtype modes, and 1.037 to 1.051 times in fp32 (median of 5 rounds at P1 and P2, results/speed-changes.jsonl).
  • The concat-free rotation (change ratio C2) adds 1.040 to 1.089 in the four fp16 and bf16 dtype modes and 1.010 to 1.012 in fp32. The product of the two medians is 1.303 to 1.408 in the fp16 and bf16 dtype modes (Section 10).
  • The compiled forward pass gives the same bits as the eager forward pass: 348 of 348 configurations of the six model sizes have a largest difference of 0 (Table 6 of results/parity-mlx.md). The first batch of each of the 20 C1 and C2 processes was also bit for bit equal.

3 One code path for eager and compiled

# src/dinov3_mlx/mlx_model.py, lines 471 to 497 (shortened: lines 472 and 473 of MlxBackbone.__init__ are left out)
        self.rope_cache = RopeCache(config.head_dim, config.rope_theta)

    def forward_with_rope(self, pixels: mx.array, cos: mx.array, sin: mx.array) -> mx.array:
        """Return all tokens after the final layer norm, (B, 5 + N, D), with the given RoPE tables.

        The eager and the compiled forward pass share this code path (D1 of
        specs/06-speed/plan.html).
        """
        x = self.embeddings(pixels)
        for block in self.layer:
            x = block(x, cos, sin)
        return self.norm(x)

    def __call__(self, pixels: mx.array) -> mx.array:
        """The eager forward pass: all tokens after the final layer norm, (B, 5 + N, D), of NCHW
        pixels, with the RoPE tables of the patch grid from the cache."""
        p = self.config.patch_size
        return self.forward_with_rope(
            pixels, *self.rope(pixels.shape[2] // p, pixels.shape[3] // p)
        )
  • forward_with_rope (lines 480–489). In Step 5, __call__ held this loop and read the cache itself. Step 6 moves the loop into its own method, with the RoPE tables as arguments. The method has no Python branch on array values. It uses only the shapes. So mx.compile can record it as a trace.
  • __call__ (lines 491–497). This is the eager forward pass. It computes the patch grid (H / 16, W / 16) from the shape, reads the tables and calls forward_with_rope. The eager and the compiled forward pass thus run the same block code. They cannot drift apart.
  • rope (lines 475–478). The method now only asks the RopeCache. The tables have the layout of the concat-free rotation (Section 6). In Step 5 the method filled a dict _rope_cache on the module (04-2, Section 9). Section 7 explains why the dict had to go.
  • Who still runs eager. The part tests, run_mlx_hidden_states, run_mlx_token_range and the stored-state tests of Step 5 run the eager forward pass (Section 3.4 of the plan). run_mlx without forward also runs it (Section 8.1).

4 compile_backbone and the trace

4.1 The code

# src/dinov3_mlx/mlx_model.py, lines 500 to 522
def compile_backbone(model: MlxBackbone) -> Callable[[mx.array], mx.array]:
    """Return the compiled forward pass of one backbone (D1 of specs/06-speed/plan.html).

    One trace for each input shape (B, H, W). The weights enter as implicit inputs
    (inputs=model.state), so the output follows a later weight change (R35). The RoPE tables enter
    as arguments; Python reads them from the cache, outside the trace. Call it after the last
    weight change (the load, nn.quantize). The caller holds the function: a function stored on the
    model keeps the weights until gc.collect() (R36).

    Args:
        model: A loaded backbone.

    Returns:
        forward(pixels) -> tokens, with the contract of model(pixels).
    """
    traced = mx.compile(lambda p, c, s: model.forward_with_rope(p, c, s), inputs=model.state)
    patch = model.config.patch_size

    def forward(pixels: mx.array) -> mx.array:
        cos, sin = model.rope(pixels.shape[2] // patch, pixels.shape[3] // patch)
        return traced(pixels, cos, sin)

    return forward
  • Line 515: the trace. The lambda takes three arrays: the pixels and the two RoPE tables. inputs=model.state tells mx.compile that each array in the module tree is an input of the trace too. MLX reads these arrays again at each call. So a later weight change reaches the output (R35). T35 adds 0.01 to layer.0.attention.q_proj.weight after one compiled call. The next compiled call equals the eager output of the changed model bit for bit.
  • The first call for a shape. At the first call with a new input shape (B, 3, H, W) or a new dtype, mx.compile runs the lambda once with placeholder arrays and records the operations: the trace. Then it fuses each element-wise chain. Later calls with the same shapes replay the trace. T37 calls forward at (1, 224, 224), (2, 224, 224), (1, 448, 448), (1, 224, 224) and (2, 224, 224). It counts 3 traces and 2 cache entries.
  • Lines 518–520: Python at each call. forward is a plain function. It runs at each call, outside the trace. It reads the tables of the patch grid from the RoPE cache. The tables are arguments of the trace, not constants inside it. So one trace serves all calls of one shape, and a new patch grid needs a new trace only because the shape changes.
  • No shapeless=True. One shapeless trace for all shapes fails at the first call: "Slice cannot infer output shapes" (option C of D1, explore.html). The retrace that it would save costs only milliseconds (Section 4.4).
  • Compile after the last weight change. load_mlx_backbone returns a model with all weights set, also after nn.quantize (06-3). The caller compiles after the load: for example forward: Forward = compile_backbone(model) if config.compile else model in mlx_bench.py, line 182.

5 Fused kernels and fusion barriers

A fused kernel is one GPU kernel for a chain of element-wise operations. Without fusion, each operation reads its full input tensor from memory and writes its full output tensor. With fusion, the chain reads its inputs once and writes its output once. The values between the operations stay in GPU registers. At P2 the feed-forward hidden values of one block are 8 × 1,029 × 5,120 = 42,147,840 values (T = 1,029 tokens at 512 px, Table 4 of the plan; ff = 5,120 for ViT-H+/16 in MODEL_SHAPES of src/dinov3_mlx/flops.py). In fp32 that is 168.6 MB. A cast of 256 M fp32 values to fp16 takes 3.14 ms (514 GB/s, probe, Table 7 of explore.html). So each avoided memory pass saves time at P2.

Some operations stop a fusion. They are fusion barriers: mx.fast.layer_norm, a matmul, the SDPA, slice and concatenate. A barrier stays its own kernel, and an element-wise chain before a barrier cannot fuse with an element-wise chain after it.

6 The concat-free rotation

RoPE rotates each pair (x[d], x[d + head_dim / 2]) of a query or a key by one angle (the half-split layout, 04-2, Section 5). Step 4 and Step 5 computed the rotation with rotate_half. Step 6 keeps the tables of rope_tables (ADR 0006). It changes the form of the rotation, and rope_layout gives the tables a new layout.

# tests/rope_oracle.py, lines 7 to 16 (the Step 5 form, now the oracle of T38)
def rotate_half(x: mx.array) -> mx.array:
    """Return (-x2, x1) for the halves x1 and x2 of the last axis (the half-split layout)."""
    half = x.shape[-1] // 2
    return mx.concatenate([-x[..., half:], x[..., :half]], axis=-1)


def apply_rope_step5(x: mx.array, cos: mx.array, sin: mx.array) -> mx.array:
    """Rotate queries or keys with the tables of rope_tables, (T, head_dim), in fp32 (Step 5)."""
    xf = x.astype(mx.float32)
    return (xf * cos + rotate_half(xf) * sin).astype(x.dtype)

rotate_half needs two slices, a negation and mx.concatenate. Slice and concatenate are fusion barriers. So the compiled Step 5 form still needs 4 kernels for q and 4 for k; the eager form needs 7 each in the fp16 and bf16 dtype modes (option R1 of D2, explore.html). Figure 3 shows the new form.

# src/dinov3_mlx/mlx_model.py, lines 181 to 219
def rope_layout(cos: np.ndarray, sin: np.ndarray) -> tuple[np.ndarray, np.ndarray]:
    """Return the RoPE tables in the layout of the concat-free rotation (D2 of
    specs/06-speed/plan.html).

    Args:
        cos: The cos table of rope_tables, (T, head_dim), fp32.
        sin: The sin table of rope_tables, (T, head_dim), fp32.

    Returns:
        cos2 and sin2, each (T, 2, head_dim / 2), fp32. sin2 holds -sin in its first half: the
        sign of rotate_half moves into the table, so the rotation needs no join.
    """
    t, head_dim = cos.shape
    half = head_dim // 2
    signed = np.concatenate([-sin[:, :half], sin[:, half:]], axis=-1)
    return cos.reshape(t, 2, half), signed.reshape(t, 2, half)


def apply_rope(x: mx.array, cos2: mx.array, sin2: mx.array) -> mx.array:
    """Rotate queries or keys with the RoPE tables, without a join (D2, option R2).

    out = x · cos + (x2, x1) · (−sin1, sin2). The pair (x2, x1) is a reversed view of an axis of
    size 2, so mx.compile fuses the rotation into one kernel. The rotation runs in fp32 and the
    result has the dtype of x. In IEEE arithmetic (−x2) · s equals x2 · (−s), so the result
    equals the Step 5 form with rotate_half bit for bit. The identity rows of the prefix tokens
    give x · 1 + r · 0 = x.

    Args:
        x: Queries or keys with shape (B, heads, 5 + N, head_dim).
        cos2: The cos table, (5 + N, 2, head_dim / 2), fp32.
        sin2: The signed sin table, (5 + N, 2, head_dim / 2), fp32.

    Returns:
        The rotated values with the shape and the dtype of x.
    """
    b, h, t, d = x.shape
    xr = x.reshape(b, h, t, 2, d // 2).astype(mx.float32)
    out = xr * cos2 + xr[..., ::-1, :] * sin2
    return out.astype(x.dtype).reshape(b, h, t, d)
  • Lines 193–196: rope_layout. The function runs in NumPy, once for each patch grid, inside RopeCache.tables. It negates the first half of the sin table and reshapes both tables to (T, 2, head_dim / 2). The concatenate here runs on the CPU, outside the trace, so it costs no kernel.
  • Line 217: the view. x.reshape(b, h, t, 2, d // 2) splits the last axis into the two halves. Row 0 holds x1, row 1 holds x2. Then the values go to fp32, as in Step 5 (04-2, Section 8).
  • Line 218: the rotation. xr[..., ::-1, :] reverses the axis of size 2. It is a view with a negative stride: it swaps the halves without a copy and without a join (R48). The broadcast of cos2 and sin2 over B and heads works because the tables have the shape (T, 2, head_dim / 2) and x has (B, heads, T, 2, head_dim / 2). Two products and one sum: one fused kernel.
  • A slice, but one fused kernel. Section 5 names slice as a fusion barrier, and the Step 5 form stays at 4 kernels for q. Here the probe counted one kernel for q and one for k (option R2 of D2, explore.html): the fused kernel reads the reversed view directly. A new MLX version can add a copy kernel here (R48). T38 then still guards the bits, but not the speed; C2 measures the speed.
  • Line 219. The result rounds once to the dtype of x and goes back to (B, heads, T, head_dim).
  • Why the bits are the same. Step 5 computes x1 · c + (−x2) · s. Step 6 computes x1 · c + x2 · (−s). A negation in IEEE arithmetic is exact, and the product of two numbers has the same magnitude with either sign placement. So both products round to the same value, and the two sums see the same operands. T38 checks this bit for bit: 3 dtypes × 2 head dimensions (64, 128) × 3 patch grids (14 × 14, 32 × 32, 14 × 25), on the GPU and on the CPU stream (tests/test_mlx_rope.py). The C2 worker also compares both forms on its first batch before it times them (R56). All 10 C2 processes recorded frame_equal and patches_equal true (results/speed-changes.jsonl).
  • The prefix tokens. Rows 0 to 4 of the tables are identity rows (cos 1, sin 0, 04-2, Section 6). The minus sign of rope_layout gives −0 there. x · 1 + r · (−0) = x for each finite x, so the prefix tokens do not change.

Page 04-2 shows the Step 4 form with rotate_half in its Sections 5 and 8. The code of src/ now uses the concat-free rotation of this section. rotate_half lives on only in tests/rope_oracle.py, as the oracle of T38.

    model.state and the inputs of the compiled forward pass would change with each new grid (R43).
    """

    def __init__(self, head_dim: int, theta: float) -> None:
        self.head_dim = head_dim
        self.theta = theta
        self._tables: dict[tuple[int, int], tuple[mx.array, mx.array]] = {}

    def tables(self, grid_h: int, grid_w: int) -> tuple[mx.array, mx.array]:
        """Return (cos2, sin2) of one patch grid. The first call computes them in NumPy."""
        key = (grid_h, grid_w)
        if key not in self._tables:
            cos, sin = rope_tables(grid_h, grid_w, self.head_dim, self.theta)
            cos2, sin2 = rope_layout(cos, sin)
            self._tables[key] = (mx.array(cos2), mx.array(sin2))
        return self._tables[key]

    def __len__(self) -> int:
        return len(self._tables)

Why a plain object and not a dict on the module? mlx.nn.Module is itself a dict. Its __setattr__ stores each value of type mx.array, dict, list or tuple as an item of that dict. It stores other values as ordinary Python attributes. Module.state returns the module itself, so it holds every dict item. Module.parameters() leaves out the keys that start with "_" (mlx/nn/layers/base.py of MLX 0.32.4).

  • Step 5. The dict _rope_cache was not a parameter, so load_weights(strict=True), set_dtype and nn.quantize did not see it (04-2, Section 9, T19). But it was an item of model.state. The probes found it there (Section 3.4 of the plan).
  • The problem with inputs=model.state. The cached tables were then implicit inputs of the trace. A new patch grid adds an entry, so the set of implicit inputs changes. The first call at a new grid can then trace twice (R43, Table 38 of explore.html).
  • Step 6. A RopeCache is not an array, a dict, a list or a tuple. So Module.__setattr__ stores it as an ordinary attribute, outside the module tree. T39 flattens model.state and finds no name that contains "rope". It also finds as many leaves in model.state as in model.parameters(). T37 counts 3 traces for 5 calls at 3 shapes: the new grid does not retrace the old shapes.
  • Lines 235–245: tables and __len__. The first call for a patch grid runs rope_tables and rope_layout in NumPy and makes two mx.array objects. Later calls return the same two arrays. __len__ gives the number of patch grids in the cache. T37 and T39 read it with len(model.rope_cache).
  • The key is the patch grid. A batch of 1 and a batch of 8 at 224 px share one entry. T39 asserts that a second call returns the same two arrays (is). One pair of tables is about 0.53 MB at 512 px with head dimension 64 (Section 3.2 of explore.html).

8.1 run_mlx: the parity tests run the compiled forward pass

# src/dinov3_mlx/mlx_model.py, lines 551 to 580 (shortened: the docstring, lines 557 to 574, is left out)
def run_mlx(
    model: MlxBackbone,
    pixels: np.ndarray,
    dtype_mode: str,
    forward: Callable[[mx.array], mx.array] | None = None,
) -> np.ndarray:
    if dtype_mode != model.dtype_mode:
        raise ValueError(f"the model runs in {model.dtype_mode}, not in {dtype_mode}")
    tokens = (forward or model)(mx.array(pixels))
    tokens = tokens.astype(mx.float32)  # a bf16 mx.array does not convert to NumPy
    mx.eval(tokens)
    return np.array(tokens)
  • Line 577: (forward or model). With forward, the function runs the compiled forward pass. Without it, it runs the eager forward pass, as in Step 5. The docstring says: "None runs the eager forward pass (part tests, diagnostics)". T40 wraps a compiled function in a counter and checks one call, and the same tokens as the eager call.
  • D4. The parity tests of Step 5 (test_parity, test_batch_consistency) pass the compiled forward pass of the backbone slot. So the tests check the forward pass that the benchmark and the Step 7 API run.
  • W1. The test runs the 12 configurations of each model size and dtype mode twice: compiled and eager. Table 6 of results/parity-mlx.md gives 29 rows with 12 configurations each: 348 of 348 bit for bit equal, largest difference 0. The ViT-7B/16 fp32 row has 0 configurations: its fp32 weights alone need about 27 GB (run rule).
  • The CPU stream. On the GPU the compiled and the eager forward pass give the same bits. On the CPU stream they differ: up to 2.0e-6 in fp32 (probe, R37). So T34 uses a tolerance of 1e-5 in fp32 on the CPU stream. In the four fp16 and bf16 dtype modes the worst measured CPU values are 0.0059 (fp16-cast), 0.047 (bf16-cast), 0.0024 (fp16-autocast) and 0.017 (bf16-autocast). The comment in tests/test_mlx_parts.py (lines 743–747) gives the reason: the compiled CPU kernel rounds once for each fused chain; the eager CPU path rounds after each operation. A decision of 2026-11-07 (a deviation from AC1) applies on the CPU stream: T34 only reports the difference of these four modes and asserts a fault bound of at least 5 times the worst value (CPU_FAULT_BOUND, lines 748–753). On the GPU, T34 asserts bit equality in all five dtype modes.

8.2 mlx_embeddings: fp16 patch embeddings on the host

# src/dinov3_mlx/mlx_model.py, lines 583 to 611
def patch_dtype(dtype_mode: str, patch_fp32: bool = False) -> mx.Dtype:
    """Return the host dtype of the patch embeddings of one dtype mode (D13 of
    specs/06-speed/plan.html): fp16 in the four fp16 and bf16 dtype modes, else fp32."""
    half = MLX_DTYPE_MODES[dtype_mode].matmul != mx.float32
    return mx.float16 if half and not patch_fp32 else mx.float32


def mlx_embeddings(
    tokens: mx.array, dtype_mode: str, patch_fp32: bool = False
) -> tuple[np.ndarray, np.ndarray]:
    """Return the frame embeddings and the patch embeddings of one batch on the host (D13 of
    specs/06-speed/plan.html).

    The frame embeddings are fp32. In the four fp16 and bf16 dtype modes the patch embeddings are
    fp16: half the host bytes for at most 3e-8 of parity (probe fp16-output). NumPy has no bf16,
    so the bf16 modes cast to fp16 on the GPU; after the final layer norm no value is above 18.

    Args:
        tokens: All tokens after the final layer norm, (B, 5 + N, D).
        dtype_mode: The dtype mode of the backbone.
        patch_fp32: True for fp32 patch embeddings in every dtype mode.

    Returns:
        The frame embeddings (B, D) and the patch embeddings (B, N, D).
    """
    frame = tokens[:, 0].astype(mx.float32)
    patches = tokens[:, NUM_PREFIX_TOKENS:].astype(patch_dtype(dtype_mode, patch_fp32))
    mx.eval(frame, patches)
    return np.array(frame), np.array(patches)
  • Line 608: the frame embedding. Token 0 is the CLS token after the final layer norm. It goes to the host in fp32 in every dtype mode.
  • Line 609: the patch embeddings. They skip the 5 prefix tokens. In the four fp16 and bf16 dtype modes they go to the host in fp16: half the bytes. For one P2 batch that is 21.0 MB in place of 42.0 MB (Figure 1 of the plan). NumPy has no bf16, so a bf16 mode casts to fp16 on the GPU. bf16 to fp16 is exact for normal values up to 65,504, and after the final layer norm no value is above 18 (Table 10 of the plan). Only very small values below the normal range of fp16 can lose bits. This is the small extra loss of bf16-cast in Table 8 of results/parity-mlx.md (below).
  • Line 610: one mx.eval for both. The casts run on the GPU after the forward pass. The function is not part of the trace.
  • The parity cost. Table 8 of results/parity-mlx.md gives the extra loss of the fp16 patch embeddings: the parity of the fp32 output minus the parity of the fp16 output, for the patch mean and the patch 1st percentile. The largest extra loss of a row is 0 in fp16-cast, at most 3.7e-15 in bf16-cast, and 5.3e-8 to 1.3e-6 in the two autocast modes. In fp16-cast the tokens are fp16 already, so the cast changes nothing. In an autocast mode the tokens are fp32, so the cast rounds. The largest value, 1.3e-6, is ViT-H+/16 in bf16-autocast. W4 bounds the extra loss at 1e-7 for the patch mean and 5e-6 for the patch 1st percentile (FP16_EXTRA_LOSS, tests/test_mlx_parity.py, line 352). The docstring of mlx_embeddings still names the probe value "at most 3e-8"; the build measured more (Table 8). The frame embeddings do not change in any row.
  • The benchmark worker. time_batch_mlx (mlx_bench.py, lines 70–101) does the same two casts with patch_dtype, but it times the frame and the patch transfer on their own. The change ratio C4 compares fp32 and fp16 patch embeddings. At P2 (patch output) it gives 1.004 to 1.042 (Table 4 of results/speedup-table.md). At P1 that table gives the frame output, and the frame time does not hold the patch transfer. The patch ratio of the same P1 rows is 0.964 to 1.031 (field ratio of the C4 rows of results/speed-changes.jsonl). So the smaller transfer gives little or no speed gain at P1 and P2.

9 R30: the casts of the autocast modes

In an autocast mode the matmuls run in fp16 or bf16, and the residual stream, the layer norms and LayerScale stay in fp32. So each block has extra work at the dtype borders:

  • After each layer norm, a cast to the matmul dtype. Block.attention_branch (line 439) and Block.ff_hidden (line 443) call .astype(self.dtypes.matmul) on the fp32 output of norm1 and norm2. In a cast mode the norm output has the matmul dtype already, and the cast does nothing.
  • After each branch, a promotion. The branch output in fp16 or bf16 times the fp32 LayerScale factor gives fp32, then the residual add follows.

Eager, this gives 37 kernels per SwiGLU block against 33 in the cast modes (probe). Step 5 measured the autocast modes on mlx at P2, eager, at 0.953 to 0.973 times the throughput of the cast modes (R30; Table 7 of specs/05-all-sizes/verify.html). Compile fuses the promotion with the LayerScale multiply and the residual add. The cast after the layer norm stays, because mx.fast.layer_norm is a fusion barrier: 17 kernels against 15 (probe). Step 6 accepts the 2 remaining casts (D3, option a). The other options change the numerics of the autocast mode (round the residual stream before the norm) or need a custom kernel (a non-goal of mission.md).

10 The measured change ratios C1 and C2

A change ratio is the throughput after a change divided by the throughput before it. Both forms run in one process, in alternation and in a rotated order, for 5 rounds. Each form gets 3 warm-up batches and 20 timed batches per round at P1, and 3 warm-up batches and 4 timed batches at P2. The worker run_change_worker (mlx_bench.py, lines 363–457) builds the forms with change_forms (lines 327–360):

  • E: the eager forward pass with the Step 5 rotation (_apply_rope_step5, lines 301–309, swapped in by the context _Step5Rope, lines 312–324).
  • The context _Step5Rope. __enter__ (lines 315–319) keeps the module attribute mlx_model.apply_rope in self.saved and sets _apply_rope_step5 in its place. Attention.__call__ reads apply_rope from the module at each call, so the forward pass inside the with block uses the Step 5 rotation. __exit__ (lines 321–324) sets self.saved back, also after an exception. The concat-free rotation stays the rotation of all code outside the block.
  • A: mx.compile(..., inputs=model.state) with the Step 5 rotation and its tables (T, head_dim) as arguments. The inner function compiled5 (lines 348–350) calls this trace inside _Step5Rope. mx.compile records a trace at the first call and at each new input shape, and the trace reads apply_rope at that time. Without the context, the trace would record the concat-free rotation apply_rope with the Step 5 tables (T, head_dim). apply_rope needs tables (T, 2, head_dim / 2), so the trace would stop with a shape error.
  • R: compile_backbone(model), with the concat-free rotation.

C1 is A / E (build step 2a), C2 is R / A (build step 2b). Before the timed batches, the worker asserts that both forms give the same tokens bit for bit (R56). All 20 C1 and C2 rows recorded frame_equal and patches_equal true.

11 Surprises

  1. A closure or mx.compile(model) keeps the weights of the first trace. After a weight change, both give the old output without an error (probe, R35). Only inputs=model.state makes the weights implicit inputs that MLX reads at each call. T35 guards this.
  2. A function stored on the model keeps the weights until gc.collect(). The model, the function and the trace form a reference cycle. In the probe 12.52 MiB of weights stayed after del model (R36). So only the caller holds the compiled forward pass. T36 checks that the memory goes free without gc.collect().
  3. A dict on a module joins the compiled inputs (R43). The "_" in _rope_cache kept the RoPE tables out of parameters(), but not out of model.state. With inputs=model.state, each new patch grid changed the implicit inputs. A plain object (RopeCache) stays out of the module tree.
  4. shapeless=True fails. The first call stops with "Slice cannot infer output shapes". The first compiled call of a new shape, with its trace, costs only 1.8 to 13.4 ms before mx.eval (Table 3), so Step 6 uses one trace for each shape.
  5. Kernel counts 1,190 → 550 for 32 SwiGLU blocks in bf16-autocast. Compile removes 448 kernels (14 per block); the concat-free rotation removes another 192 (6 per block). The matmuls and the SDPA do not change: 8.8 ms of a 13.8 ms block at P2.
  6. The layer norm is a fusion barrier: 2 casts stay. Compile fuses the promotion of the autocast modes into LayerScale and the residual add, but not the cast after mx.fast.layer_norm. At P2 the autocast modes stay at 0.939 to 0.969 times the cast modes (Table 6).
  7. The concat-free rotation is bit for bit equal to the Step 5 form, although it moves the minus sign from the value into the table. The reason: (−x2) · s and x2 · (−s) give the same IEEE result. T38 covers 18 cases on each device.
  8. The SwiGLU activation gains most from compile: 3.16 → 0.66 ms per block at P2. In eager mode each cast of the one rounding of Step 5 writes a full tensor. Compile removes this cost and keeps the bits.
  9. On the CPU stream, compiled and eager differ; on the GPU they do not. The compiled CPU kernel rounds once for each fused chain. The difference reaches 0.047 in bf16-cast. On the GPU all 348 configurations of W1 are bit for bit equal.
  10. Two kernel counts disagree. The probe counted 365 → 173 kernels for 12 MLP blocks in bf16-cast. The P1 profile counted 841 → 637 nodes for ViT-S/16 (12 MLP blocks) in bf16-cast. The two counters count different graph nodes, and the eager form of the profile already uses the concat-free rotation.
  11. At P1 the autocast frame ratio of C3 is not below 1. bf16 gives 1.034 in the median of 5 rounds. The paired runs, with more rounds, give 0.951. Five rounds of separate subprocesses at P1 do not resolve a cost of a few percent.
  12. Page 04-2 still shows rotate_half. Its Sections 5 and 8 describe the Step 4 form, and it has no link to this page yet. Section 6 of this page (anchor #concat-free) holds the current form.
  13. Compile does not show a gain on R30 against Step 5. The probe in one process gave autocast / cast 0.917 eager and 0.976 compiled. The build gives 0.939 to 0.969 at P2, and Step 5 gave 0.953 to 0.973 eager at P2 (Section 9).
