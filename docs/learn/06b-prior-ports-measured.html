1 Why measure the ports

Step 1 read the code of four MLX ports of DINOv3, but did not run them. Step 6 made our compiled forward pass about as fast as torch.compile on torch-mps. Step 6b asks two questions: how fast are the other public ports and Core ML exports with our harness, and what does each change of a port cost in parity?

Two kinds of candidates exist. Core ML exports (C7 to C9) are model files: Apple's coremltools runs them, and no code of the candidate runs. Python MLX ports (C1, C2) are code. The permission system of the agent sessions refused to run that code, so their rows wait for the user (question Q1, ADR 0013). To answer the parity question without their code, we put each change of a port into our own backbone, one at a time: the port-change variants V1 to V5.

3 The Core ML exports and the spec-array input

C7 (SharpAI) and C8 (rinpatch) take an 8-bit RGB image. Core ML scales and normalizes it inside the program. Our stored pixels are fp32, normalized, and not on the 8-bit grid: a round to 0..255 moves each pixel by up to 0.5 / 255 / std. That alone drops the patch 1st percentile to about 0.999, below the fp32 threshold 0.9999. To measure the backbone and not the interface, the worker changes the input feature of the loaded spec to a FLOAT32 multiArray. The 0..255 values go in without a round. The package on disk does not change.

def load_export(path, input_kind, units):          # scripts/prior_art_coreml_worker.py
    import coremltools as ct                           # only inside the function: venv-coreml
    unit = getattr(ct.ComputeUnit, units)              # CPU_AND_GPU for the paired rows (D4)
    if input_kind != "spec-array":
        return ct.models.MLModel(str(path), compute_units=unit)
    spec = ct.utils.load_spec(str(path))
    feature = spec.description.input[0]                # imageType in the package
    height, width = feature.type.imageType.height, feature.type.imageType.width
    feature.type.multiArrayType.shape[:] = [1, 3, height, width]   # the oneof moves to multiArray
    feature.type.multiArrayType.dataType = ct.proto.FeatureTypes_pb2.ArrayFeatureType.FLOAT32
    weights = path / "Data" / "com.apple.CoreML" / "weights"       # the weights stay on disk
    return ct.models.MLModel(spec, weights_dir=str(weights), compute_units=unit)

The exports give their outputs in three layouts. export_outputs maps each to a frame embedding (or none) and patch embeddings (N, D). grid_tokens turns the grid (1, D, h, w) of C7 into (h · w, D) in row-major order, the token order of our backbone. export_parity then builds a token sequence as check_validity does: the frame embedding (or the reference CLS row), the 4 reference register rows and the patch embeddings. The cosine does not depend on the length of a vector, so the L2-normalized outputs of C7 and C8 need no change.

4 The paired cell and the prior-art ratio

The Explore found that one export run of less than 1 s is noise on this Mac: the same pair gave ratios from 0.65 to 1.12. So each cell runs as the paired runs of Step 6 do (ADR 0012): one driver holds the GPU lock, each worker runs in its own subprocess with the full time budget of bench.py (2 s warm-up, at least 10 s and 30 batches timed), and the cell runs in 5 rounds.

def cell_row(ours, other, fields=None):                 # src/dinov3_apple/prior_art.py
    by_round = {line["round"]: line for line in ours if _done(line)}
    pairs = [(by_round[line["round"]], line)              # a failed side drops only its round
             for line in other if _done(line) and line["round"] in by_round]
    ratios = [a["patch"]["throughput_ips"] / b["patch"]["throughput_ips"] for a, b in pairs]
    median = _lower_median(ratios)                       # ADR 0004
    return PriorArtRow(ratios, median, (max(ratios) - min(ratios)) / min(ratios),
                       single_verdict(median), len(ratios), ...)   # inside the noise: 1 ± 0.03

The same function gives the change ratios of the variants (J4): there the first side is the variant and the second side is V0, so a ratio above 1 means the change is faster.

5 The port-change variants

A port mixes several changes. A variant puts exactly one of them into our backbone, so its cost in parity and speed has one cause. variant_forward(model, variant) builds the compiled forward pass of a variant: it replaces the attention module of each block where the variant needs it, selects the RoPE tables, and compiles model.forward_with_rope with inputs=model.state, as compile_backbone does. forward_with_rope passes the tables to each block without a look, so V1 can use the table layout of the port.

5.1 V1: the RoPE of C1 and C2

def port_rope_tables(grid_h, grid_w, head_dim, base):     # src/dinov3_apple/port_variants.py
    bf16 = mx.bfloat16                                      # pos_embed_rope_dtype="bf16" of the ports
    periods = base ** (2 * mx.arange(head_dim // 4, dtype=bf16) / (head_dim // 2))
    coords_h = mx.arange(0.5, grid_h, dtype=bf16) / grid_h  # every step rounds to bf16
    coords_w = mx.arange(0.5, grid_w, dtype=bf16) / grid_w
    mesh = mx.stack(mx.meshgrid(coords_h, coords_w, indexing="ij"), axis=-1).reshape(-1, 2)
    mesh = 2.0 * mesh - 1.0
    angles = 2 * math.pi * mesh[:, :, None] / periods[None, None, :]   # up to about 2π
    angles = mx.tile(angles.reshape(angles.shape[0], -1), (1, 2))
    return mx.cos(angles), mx.sin(angles)                   # (N, head_dim): no prefix rows

def port_rotate(x, cos, sin):
    prefix = x.shape[-2] - cos.shape[0]                     # the 5 prefix tokens: no rotation
    patches = x[..., prefix:, :]
    half = x.shape[-1] // 2
    rotated = mx.concatenate([-patches[..., half:], patches[..., :half]], axis=-1)  # rotate_half
    return mx.concatenate([x[..., :prefix, :], patches * cos + rotated * sin], axis=-2)

class Bf16RotationAttention(Attention):
    def __call__(self, x, cos, sin):
        q, k, v = self.qkv(x)
        # all tokens go to bf16, also the prefix tokens, also in the fp32 dtype mode
        q, k = (port_rotate(t.astype(mx.bfloat16), cos, sin).astype(t.dtype) for t in (q, k))
        a = mx.fast.scaled_dot_product_attention(q, k, v, scale=self.scale, mask=None)
        return self.output(a)

A NumPy oracle (test T6) rounds to bf16 after each step, with round to nearest even. The GPU agrees with it within one bf16 step: the GPU and NumPy compute cos and sin with other code, so a value next to a rounding boundary can round the other way.

5.2 V2 and V3: the tables only

V2 takes the bf16 tables of V1, casts them to fp32, adds identity rows for the prefix tokens and gives them to our fp32 rotation (variant_tables with rope_layout). So V1 minus V2 is the cost of the bf16 rotation, and V2 is the cost of the bf16 tables. V3 keeps every step in fp32 but uses the periods of the Meta checkpoints: meta_periods rounds 100^(k / 16) to bf16 (1.0, 1.3359375, 1.78125, 2.375, …), as C9 and the Meta hub code do. Its largest angle difference to the Hugging Face tables is 0.00791 rad at 14 × 14 and 0.00825 rad at 32 × 32 (test T7, the values of Step 4).

5.3 V4: the unfused attention

class UnfusedAttention(Attention):
    def __call__(self, x, cos, sin):
        q, k, v = self.qkv(x)
        q, k = apply_rope(q, cos, sin), apply_rope(k, cos, sin)     # our fp32 rotation
        scores = mx.matmul(q, k.swapaxes(-1, -2)) * self.scale        # (B, heads, T, T) in memory
        return self.output(mx.matmul(mx.softmax(scores, axis=-1), v))

5.4 V5: the 8-bit input

def eight_bit_pixels(pixels):                                  # src/dinov3_apple/prior_art.py
    levels = np.clip(np.rint((pixels * std + mean) * 255), 0, 255)  # what an RGB image keeps
    return ((levels / 255 - mean) / std).astype(np.float32)         # moves ≤ 0.5 / 255 / std

5.5 Build one variant

def variant_forward(model, variant):
    attention = {"V1": Bf16RotationAttention, "V4": UnfusedAttention}.get(variant)
    if attention is not None:
        for block in model.layer:
            replacement = attention(model.config)
            replacement.update(block.attention.parameters())   # the same weights, a new __call__
            block.attention = replacement                       # the backbone keeps the variant
    traced = mx.compile(lambda p, c, s: model.forward_with_rope(p, c, s), inputs=model.state)
    ...
    def forward(pixels):
        if grid not in tables:
            tables[grid] = variant_tables(model, variant, *grid)   # V1: (N, head_dim) bf16
        if variant == "V5":
            pixels = mx.array(eight_bit_pixels(np.array(pixels.astype(mx.float32))))
        return traced(pixels, *tables[grid])

6 Why the bf16 RoPE costs parity

bf16 keeps 8 significant bits. Near an angle of 2π (the angles of the shortest period at the edge of the grid) one bf16 step is 2−5 = 0.031 rad. The tables of the ports differ from the fp32 tables by up to 0.0314 at 14 × 14 (test T6). That is four times the angle error of the Meta periods (0.0079 rad, V3). The rotation of V1 adds a second error: q and k of every token, also of the prefix tokens, round to bf16 before the attention, in every dtype mode. In the fp32 dtype mode this throws away 16 of the 24 bits of q and k in each of the 12 or 32 blocks.

Job J3 measured each variant on the 12 configurations of Step 2 at batch size 1 (Table 3 in Section 7). In the fp32 dtype mode:

  • V1, the RoPE of the ports, drops the worst patch 1st percentile from 1.000000 to 0.999530 (ViT-S/16) and 0.998381 (ViT-H+/16). Only 3 of 12 and 1 of 12 configurations pass the fp32 thresholds.
  • V2, the bf16 tables with our fp32 rotation, gives 0.999619 and 0.998675. So the tables cause most of the cost; the bf16 rotation of q and k adds the rest.
  • V3, the Meta periods, gives 0.999998 and 0.999990 and passes 12 of 12. A bf16 period with fp32 angles is close enough; bf16 angles are not.

In the bf16-cast dtype mode the backbone rounds its activations to bf16 anyway. There V1 lowers the worst patch 1st percentile from 0.999560 to 0.999283 (ViT-S/16) and from 0.986725 to 0.974840 (ViT-H+/16), and every configuration still passes the bf16 thresholds. The cost of the bf16 RoPE grows with the model size: ViT-H+/16 has 32 blocks, ViT-S/16 has 12.

8.3 Scripts

  • scripts/bench_prior_art.py: the driver. Subcommands coreml (J1, J2), variants (J3, J4), ports (J5, gated by --allow-third-party-python), table. One GPU lock, a memory check before each worker, other_heavy_jobs_seen before and after each worker, MLX_ENABLE_TF32=0 for every mlx worker.
  • scripts/prior_art_coreml_worker.py: runs in venv-coreml with -I; standard library, NumPy, safetensors, coremltools and Pillow only.
  • scripts/prior_art_port_worker.py: runs in venv-mlx with -I, only after the user's yes to Q1.
  • scripts/prior_art_meta_names.py: our ViT-H+/16 weights in the Meta names for C2, from the safetensors files (no pickle).

9 Surprises

  1. The probes lied by up to 1.8 times. Single Core ML runs of 10 batches were 1.4 to 1.8 times faster than the paired runs with the full time budget. On this Mac, a run below 1 s does not measure throughput.
  2. The 8-bit input, not the port, costs the parity. With float input every FP32 export reproduces our reference output to 6 decimals. The interface of an image-input export alone drops the patch 1st percentile below the fp32 threshold.
  3. The bf16 tables are 4 times further off than the Meta periods. The plan expected at most 0.02 between the bf16 and the fp32 tables; the measured value is 0.0314, one bf16 step at 2π.
  4. The 8-bit input hurts the large model more. V5 drops the worst patch 1st percentile to 0.998996 on ViT-S/16 but to 0.923926 on ViT-H+/16 in fp32 (Table 3): an input change of at most 0.5 / 255 / std grows through 32 blocks. A user who feeds 8-bit frames to ViT-H+/16 gets this cost before any port change.
  5. Core ML in fp16 beats our fp16-cast on the small model at many tokens. E3 and the DINOv2 export E7 are 6 to 15 % faster than our compiled forward pass, while every FP32 export is slower. Our host transfer is not the reason (at most 1.0 % of the batch time). The gap follows the attention share of the compute; Step 6c looks at Core ML in more detail.
  6. The variant parity runs in seconds. Job J3 ran 24 workers in 25 s: ViT-H+/16 in fp32 loads from the page cache in 0.3 s, and the 12 configurations at batch size 1 take about 1 s.
