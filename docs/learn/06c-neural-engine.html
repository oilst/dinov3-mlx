DINOv3 on the Neural Engine

Explainer for roadmap Step 6c. Date: 2026-11-08. It explains how the Apple Neural Engine runs the attention and the feed-forward network of DINOv3, the numeric range of DINOv3 in fp16, and every function that Step 6c adds to src/dinov3_apple/coreml.py.

1 Why this explainer

Step 6 found that compiled mlx runs at the matmul limit of the GPU. The Apple Neural Engine is a second matrix accelerator on the same chip. Core ML is the only public way to run a model on it. Step 6c converts the Hugging Face backbone into Core ML packages and measures them on three compute units: CPU_AND_NE (coreml-ne), CPU_AND_GPU (coreml-gpu) and ALL (coreml-all).

The Neural Engine computes in fp16 only. DINOv3 has two value ranges far above the largest fp16 value, 65,504. So the step is mostly a lesson in numeric range. The result in four points:

  • The plain fp16 package gives finite but wrong tokens on the Neural Engine (frame cosine 0.035 for ViT-S/16). The attention scores reach 2.5 million.
  • The Neural Engine rewrite (score scale 256, residual-stream scale r, ε / r²) is exact in real numbers. With it, every model size from ViT-S/16 to ViT-H+/16 passes the fp16 thresholds on CPU_AND_GPU and ALL.
  • On CPU_AND_NE the rewritten packages pass only where the compute plan keeps the first ops (input cast, patch embedding, first attention branch) on the CPU: ViT-S/16 and ViT-S+/16 at 224 px, batch size 1. Every other package gives wrong tokens. The fault shows first in the output of the embeddings. Its cause is open.
  • Where the Neural Engine output is right (ViT-S/16 at 224 px), the Neural Engine and mlx on the GPU add up: 2,503 img/s together against 1,984 for mlx alone at P1 (stream ratio 1.26). At 512 px the Neural Engine is 7 times slower than the GPU and adds nothing.

The values come from results/coreml.jsonl, results/coreml-table.md, specs/06c-neural-engine/explore.html (probes p1 to p17) and the Q3 probes of the build (Section 6).

2 From the torch backbone to the Neural Engine

A Core ML package is one converted backbone for one model size, input resolution and batch size. The conversion has five stages (Figure 1). The rewrite is the only new arithmetic.

Three details of the conversion matter:

  • The _cast patch. coremltools 9.0 calls int() on a constant array with one value in the torch op aten::Int. numpy 2.5.4 refuses this. patch_coremltools_cast points the torch frontend at _cast_with_item, which calls .item() first. It never edits the installed package, and it raises CoremltoolsVersionError for any version other than 9.0 (ADR 0015).
  • Fixed shapes. The trace makes the RoPE tables constants of one input shape. So each package has one batch size and one input resolution, and the name holds both, plus the rewrite version, the score scale, r and the coremltools version.
  • fp32 at the edges. The input pixels is fp32 and the output tokens is fp32. The converter adds a cast to fp16 at the start and one to fp32 at the end. Every op between them runs in fp16.
# src/dinov3_apple/coreml.py: _cast_with_item (the one changed line is marked)
x = torch_ops._get_inputs(context, node, expected=1)[0]
if x.can_be_folded_to_const():
    value = x.val.item() if isinstance(x.val, np.ndarray) else x.val   # changed: .item()
    res = x if isinstance(x.val, dtype) else mb.const(val=dtype(value), name=node.name)

4 Attention on the Neural Engine

The GPU path of Core ML, mlx and torch-mps keep the scores inside a fused attention kernel with fp32 accumulation. The converter writes no fused attention op for the Neural Engine: the Hugging Face attention becomes matmul, softmax, matmul. So the score matrix is a stored fp16 tensor. In block 1 of ViT-S/16 a score reaches 2,389,737; in fp16 it becomes inf, and the softmax gives inf or NaN (finding F1). Later blocks turn this into finite but wrong tokens.

# src/dinov3_apple/coreml.py: ne_attention (registered as "coreml-ne" in transformers.AttentionInterface)
s = SCORE_SCALE                                                 # 256.0, a power of two
z = torch.matmul(query * (scaling / s), key.transpose(2, 3))    # at most 9,877 for ViT-S/16
z = z - z.amax(-1, keepdim=True)                                # every value at most 0
probs = torch.softmax(torch.clamp(z, min=SCORE_FLOOR / s) * s, dim=-1)   # SCORE_FLOOR = -60,000
return torch.matmul(probs, value).transpose(1, 2).contiguous(), None

Code 3. ne_attention. softmax(z) = softmax((z / s − max(z / s)) · s), so the function is exact in real numbers. The clip keeps (z − max z) · 256 above −60,000; exp(−60,000) is 0 in any dtype. Tests: T1 (fp64, scores up to 1e7, difference ≤ 1e-6 relative), T2 (fp16: eager attention gives a non-finite value, ne_attention stays finite with cosine ≥ 0.999).

The division does not cost precision. fp16 keeps a relative precision of 2⁻¹¹ at every scale, so z has the same relative error as the true score would have. The MIL program of a package keeps the order: mul by 2⁻¹¹ (that is 1/8/256 for head dimension 64), matmul, reduce_max, sub, clip, mul by 256, softmax. The converter does not move the scale behind the matmul. Probe p13 of the explore stage shows that score scaling works on the Neural Engine: the output of block 1 of ViT-S/16 at 224 px, batch size 1, has cosine 0.999992 there. On the GPU the Q3 probe of the build gives cosine 0.99999997 for the scores of block 1.

5 The residual stream, LayerScale and the feed-forward network

In ViT-L/16 and ViT-H+/16 a register token reaches 158,433 in the residual stream (05-3). The stream is the sum x + λ₁·attention + λ₂·FF over all blocks. The rewrite divides the whole stream by a power of two r:

  • the embeddings get 1 / r (NeuralEngineBackbone.forward);
  • the weights and the bias of o_proj (end of the attention branch) and down_proj (end of the feed-forward branch) get 1 / r, so each branch output is r times smaller;
  • LayerScale (λ) stays a separate multiplication;
  • each layer norm gets ε / r². A layer norm does not change when its input is scaled, except for ε: LN(x / r) with ε equals LN(x) with ε r². So ε / r² gives exactly the old output.
# src/dinov3_apple/coreml.py: rewrite_for_neural_engine
for module in model.modules():                   # the layers share model.config; set each config
    config = getattr(module, "config", None)
    if config is not None:
        config._attn_implementation = NE_ATTENTION
    if isinstance(module, torch.nn.LayerNorm):
        module.eps = module.eps / residual_scale**2     # norm1, norm2 of each block, final norm
with torch.no_grad():
    for layer in model.model.layer:
        for proj in (layer.attention.o_proj, layer.mlp.down_proj):
            proj.weight.mul_(1.0 / residual_scale)      # exact: r is a power of two
            if proj.bias is not None:
                proj.bias.mul_(1.0 / residual_scale)
return NeuralEngineBackbone(model, residual_scale)       # embeddings / r, RoPE, blocks, final norm

# residual_scale: the smallest power of two with (largest token value) / r <= 32,768
value = largest_token_value(model_size, table)   # fp32 row of results/token-range-mlx.md
scale = 1
while value / scale > MAX_STREAM_VALUE:          # 32,768: half of the fp16 range
    scale *= 2

Code 4. The rewrite of the residual stream. residual_scale gives 1 for ViT-S/16, ViT-S+/16 and ViT-B/16 and 8 for ViT-L/16 and ViT-H+/16; ViT-7B/16 raises RunRuleError (its conversion would trace fp32 weights). Tests: T3 (the rewritten small models give the Hugging Face tokens within 1e-6 relative, r = 1 and 8), T4 (LayerScale unchanged, the projections divided by r bit for bit, ε / r²), T5.

5.1 Why no LayerScale fold

A first form folded λ into the weights of o_proj and down_proj. The LayerScale factors of DINOv3 go down to 3.6e-8. Folded, 94 % of the o_proj weights of block 1 of ViT-S/16 became subnormal in fp16 (below 6.1e-5), and 63 to 78 % in ViT-L/16 and ViT-H+/16. A subnormal fp16 value has fewer than 11 bits of precision, and some hardware flushes it to 0. The fold broke the parity also on the GPU (finding F2). With only the power of two in the weights, a weight changes only when it is already near 6.1e-5 · r.

5.2 ε / r²: the GPU failure of the first run

The first conversion of the build kept the Hugging Face ε (1e-5) and divided the stream by r = 8. Then each layer norm acted as if ε were 64 times larger. For a token with a small variance this changes the output. The effect is in the GPU rows of the first J2 run: ViT-L/16 frame 0.974 to 0.888, ViT-H+/16 patch 1st percentile 0.829 to 0.985, also on CPU_AND_GPU and ALL. With ε / r² (the plan amendment of 2026-11-08) every block of ViT-L/16 on CPU_AND_GPU has cosine ≥ 0.9999998 (Q3 probe), and every ViT-L/16 and ViT-H+/16 package passes on the GPU (frame ≥ 0.99999). A larger r does not help: with r = 64, ViT-L/16 on the GPU drops to frame 0.997 and patch 1st percentile 0.980, because λ · (branch / 64) goes below the normal fp16 range.

5.3 The feed-forward network

On the Neural Engine the feed-forward network is layer_norm, linear (up), gelu or silu with a mul (SwiGLU), linear (down), mul by λ₂ and add. Its hidden values stay below 6,620 (Table 1). Its branch output in ViT-L/16 block 1 reaches 52,019 before LayerScale, 79 % of the fp16 range; with r = 8 it is 6,502. The compute plan puts all these ops on the Neural Engine.

6 The first ops: where the Neural Engine still breaks

With the rewrite, CPU_AND_GPU passes for every model size. CPU_AND_NE passes only for 2 of 15 parity packages (Table 2). The compute plan explains the pattern: the two that pass are the only ones where Core ML keeps the first ops on the CPU.

The Q3 probe of the build returns the token sequence after each block as an output. On CPU_AND_NE the first wrong value is the output of the embeddings, the input of block 1: cosine 0.19 for ViT-S/16 at 448 px and 0.31 for ViT-L/16 at 224 px, with the right largest value (16.3 and 1.9). Every later value of the block probe is wrong too, but it starts from this wrong input. So the first fault is in the embeddings or before them: the input cast, the 16 × 16 convolution with stride 16, the flatten and the concatenation with the CLS and register tokens. On the GPU the same probe gives cosine ≥ 0.9999998 for the block input.

Two tests narrowed it down, and neither fixed it:

  • The patch embedding as reshape + matmul (exact; probe P of the build). The output stays wrong (ViT-S/16 448 px frame −0.01 to 0.71, ViT-L/16 224 px 0.16), and for iss-conference at 448 px the parity is identical to the convolution package. So the convolution itself is not the cause. The build removed this change again.
  • An fp16 input without the cast at the start (job J3 of the build). The output stays wrong with nearly the same values (ViT-S/16 448 px frame 0.0097 to 0.71). So the cast is not the cause either.

The explore stage first named this fault F4, "batch size 8 breaks the patch embedding". The build data show that batch size is not the cause: at 448 and 512 px, batch size 1 fails in the same way. The batch size changes only the compute plan.

output_validity is the important line. A wrong Neural Engine output is finite (risk R53), so every Core ML worker checks the parity of its first output. A check for non-finite values would pass every failing row of Table 2.

8 The compute plan

MLComputePlan (coremltools 9.0) gives for each op of a compiled package the preferred device, the supported devices and an estimated cost. compute_plan_report sums them: ops for each device, the cost share of each device, and a list of the ops off the Neural Engine with position, name, op type and cost. Constants have no device; the report counts them apart. _device_name turns "MLNeuralEngineComputeDevice" into "NeuralEngine".

  • Every rewritten package puts 99.1 to 99.8 % of the estimated cost on the Neural Engine, except ViT-S/16 and ViT-S+/16 at 224 px batch size 1 (75 %).
  • The 4 CPU ops of the other packages are 3 reshape ops in block 1 (the split into heads) and one add.
  • With ALL, Core ML puts every op on the GPU. ALL is not a mix of GPU and Neural Engine for this graph, so coreml-all gives the parity and the speed of coreml-gpu.

10 Surprises

  1. A wrong output that looks fine. The plain fp16 package on the Neural Engine gives finite tokens of normal size (largest value 4.0) with frame cosine 0.035.
  2. The CPU saved the two passing packages. ViT-S/16 and ViT-S+/16 at 224 px batch size 1 pass on CPU_AND_NE only because Core ML runs their first 46 ops on the CPU. A larger input or batch size moves these ops to the Neural Engine, and the output breaks.
  3. Not the convolution. The same wrong numbers come out when the patch embedding is a matmul.
  4. ε matters at r = 8. The layer norm ε, 1e-5, looks too small to matter. Multiplied by 64 it broke ViT-L/16 on the GPU (frame 0.888 at 512 px).
  5. The LayerScale fold makes weights subnormal. λ goes down to 3.6e-8. A fold that is exact in real numbers is not exact in fp16.
  6. ALL means GPU. For this graph Core ML never splits the work between the GPU and the Neural Engine. The two-stream run needs two processes.
  7. Batch size 8 does not help the Neural Engine. ViT-S/16 runs at about 540 img/s at batch size 1 and 450 img/s at batch size 8 (explore probes); the GPU gains 3 times from batch size 8.
