1 Why this explainer

The backbone takes normalized fp32 pixels with shape (B, 3, H, W). Up to Step 5, only preprocess.py made these pixels. It runs in torch, in fp64, on the CPU, one image at a time. An mlx user then needs torch only for the preprocessing. Step 6 adds a second path: preprocess_frames in src/dinov3_mlx/mlx_preprocess.py. It takes a batch of uint8 RGB frames and makes the pixels on the GPU with MLX. It imports no torch (decision D12, option c of specs/06-speed/explore.html).

The core of the new path is the separable resize: two matmuls with fixed weight matrices, one for the rows and one for the columns. NumPy computes the weights in fp64 with the antialias rule of torch. This page explains that rule, the code and the measurements. It also explains the fp16 patch embeddings of decision D13, because they are the other end of the same data path: D12 changes what enters the backbone, D13 changes what leaves it.

This page covers the row 06-4-preprocessing.html of Table 5 of specs/06-speed/plan.html: resize_weights, preprocess_frames, IMAGENET_MEAN_VALUES and IMAGENET_STD_VALUES. Table 1 lists them. It adds the private helper _resize_matrices and the new public function patch_dtype of mlx_model.py. Table 6 of the plan does not list patch_dtype. The build added it for the fp16 output. 06-1 explains mlx_embeddings in the compiled forward pass. This page quotes it only for its output dtype.

The line numbers are those of commit 2567808. The last change to mlx_preprocess.py, stored.py, preprocess.py and mlx_model.py is commit 6ef6c81, so both commits give the same lines. Each code quote is an exact copy, or the text marks it as "shortened".

The agent that wrote this page ran no test, no model, no benchmark and no GPU work. It read the numbers from the committed files of Section 11. It computed Table 2 and Figure 2 with a NumPy copy of the formula of resize_weights on the CPU. It computed the times per image of Table 7 as 1 / throughput from results/speed-pairs.jsonl.

2 Preprocessing in one picture

Preprocessing has three steps: divide by 255, resize (bilinear, antialiased), normalize with the ImageNet mean and standard deviation. The Hugging Face image processor of DINOv3 does the same three steps in this order (specs/02-reference/explore.html, Section 3.3). Both paths of Figure 1 do them. They differ in the place, the dtype and the batch.

3 The antialias filter widens when the image shrinks

A bilinear resize computes each output pixel as a weighted sum of input pixels. One axis at a time is enough: the 2-D weight of an input pixel is the product of its row weight and its column weight. So one (n_out, n_in) weight matrix for each axis describes the whole resize.

The weights of one output pixel come from a triangle filter. Its peak is at the center of the output pixel. Its half-width is the support. A tap is one input pixel with a weight above zero. Two numbers set the filter:

  • scale = n_in / n_out: the width of one output pixel, in input pixels.
  • support = max(scale, 1): the half-width of the triangle, in input pixels.

When the image grows (scale ≤ 1), the support is 1. Each output pixel then mixes the two nearest input pixels: plain bilinear interpolation. When the image shrinks (scale > 1), the support grows with the scale. Each output pixel then takes a weighted mean over a window of 2 · support input pixels, the width of two output pixels. The weight falls linearly from the center of the output pixel to zero at the edge of the window. This is the antialias rule. Without it, a shrink from 1920 to 224 px reads only 2 input pixels for each output pixel and skips the other 6 or 7. Fine detail then turns into false patterns (aliasing).

4 The code

4.1 resize_weights

# src/dinov3_mlx/mlx_preprocess.py, lines 19 to 39
@cache
def resize_weights(n_in: int, n_out: int) -> np.ndarray:
    """Return the (n_out, n_in) fp64 weights of the bilinear antialiased resize of torch.

    The rule of upsample_bilinear2d_aa: a triangle filter whose support grows with the scale when
    the image shrinks. Each row sums to 1.

    Args:
        n_in: The number of input pixels along one axis.
        n_out: The number of output pixels along the same axis.
    """
    scale = n_in / n_out
    support = max(scale, 1.0)
    weights = np.zeros((n_out, n_in))
    for i in range(n_out):
        center = scale * (i + 0.5)
        lo = max(int(center - support + 0.5), 0)
        hi = min(int(center + support + 0.5), n_in)
        taps = np.maximum(0.0, 1.0 - np.abs((np.arange(lo, hi) - center + 0.5) / support))
        weights[i, lo:hi] = taps / taps.sum()
    return weights
  • Line 19. functools.cache keeps the fp64 matrix of each (n_in, n_out) pair. The Python loop runs once for each pair, for example 224 times for 1920 → 224.
  • Lines 30 and 31. The two numbers of Section 3. support = max(scale, 1.0) is the antialias rule: the filter widens only when the image shrinks.
  • Line 32. The matrix is dense and fp64. np.zeros gives fp64 by default.
  • Line 34. The center of output pixel i, in input coordinates. Pixel j of the input covers [j, j + 1], so its center is at j + 0.5. This is the half-pixel rule of F.interpolate with align_corners=False.
  • Lines 35 and 36. The window [lo, hi) holds the input pixels inside the support. int(… + 0.5) rounds, as the torch kernel does. The window stops at 0 and at n_in, so it is shorter at the border.
  • Line 37. np.arange(lo, hi) - center + 0.5 is the distance d from the center of each input pixel to the center of the output pixel. The triangle is 1 − |d| / support. np.maximum(0.0, …) sets a negative value to 0.
  • Line 38. The division by the sum makes each row sum to 1. This keeps a flat image flat, also at the border, where the window is shorter. It also lets the resize and the normalization change places: for each channel, resize(a · x + b) = a · resize(x) + b when the weights of each row sum to 1. T51 checks the sum within 1e-12.

4.2 _resize_matrices

# src/dinov3_mlx/mlx_preprocess.py, lines 42 to 47
@cache
def _resize_matrices(h: int, w: int, size: tuple[int, int]) -> tuple[mx.array, mx.array]:
    """The fp32 matrices of the rows (H, h) and of the columns (w, W) of one size pair."""
    rows = mx.array(resize_weights(h, size[0]).astype(np.float32))
    columns = mx.array(resize_weights(w, size[1]).T.astype(np.float32))
    return rows, columns
  • Line 45. The row matrix keeps the shape (H, h). It multiplies from the left.
  • Line 46. .T transposes the column matrix to (w, W). It multiplies from the right. So the resize is rows · image · columns.
  • The cast to fp32. NumPy computes in fp64. The matmuls on the GPU run in fp32, so the weights round once to fp32 here.
  • The second cache. It keeps the MLX arrays, so a new batch of the same frame size does not copy the matrices again. For the C6 frames the two matrices hold (224 · 1080 + 1920 · 224) · 4 bytes = 2.69 MB at 224 px and (512 · 1080 + 1920 · 512) · 4 bytes = 6.14 MB at 512 px (computed by the agent). The cache never frees them. A process that sees many frame sizes keeps one pair for each size.

4.3 preprocess_frames

# src/dinov3_mlx/mlx_preprocess.py, lines 50 to 73
def preprocess_frames(frames: np.ndarray, size: tuple[int, int]) -> mx.array:
    """Return normalized fp32 pixels (B, 3, H, W) from uint8 RGB frames (B, h, w, 3).

    The uint8 frames go to the GPU: a quarter of the fp32 bytes. The resize matmuls run in fp32.

    Args:
        frames: The RGB frames as uint8 values, all of one size.
        size: The input resolution as (H, W).

    Returns:
        The pixels, divided by 255, resized and normalized, on the GPU.

    Raises:
        TF32ModeError: If TF32 is on: the resize matmuls run in fp32 (ADR 0005).
    """
    if tf32_enabled():
        raise TF32ModeError("set MLX_ENABLE_TF32=0: the resize matmuls run in fp32")
    _, h, w, _ = frames.shape
    rows, columns = _resize_matrices(h, w, tuple(size))
    x = mx.array(frames).astype(mx.float32).transpose(0, 3, 1, 2) / 255.0
    x = rows @ x @ columns
    mean = mx.array(IMAGENET_MEAN_VALUES).reshape(1, 3, 1, 1)
    std = mx.array(IMAGENET_STD_VALUES).reshape(1, 3, 1, 1)
    return (x - mean) / std
  • Lines 65 and 66. The TF32 check is the first action. It runs in every dtype mode. Section 6 explains why.
  • Line 67. All frames of one batch have one size. The channels are last, as a decoder gives them.
  • Line 68. tuple(size): functools.cache needs arguments that it can hash. A list, for example from a JSON spec, would raise TypeError.
  • Line 69. mx.array(frames) copies the uint8 values into MLX memory. Then the cast to fp32, the transpose to channels first (B, 3, h, w) and the division by 255 run on the GPU. The uint8 values are a quarter of the fp32 bytes: 49.8 MB against 199.1 MB for the 8 frames of C6 (8 · 1080 · 1920 · 3 bytes, computed by the agent).
  • Line 70. Python reads rows @ x @ columns as (rows @ x) @ columns. The first matmul broadcasts the (H, h) matrix over the batch and the channels: each (h, w) channel becomes (H, w). The second matmul makes (H, W). These two matmuls are the separable resize. The matrices are more than 98 % zeros (Table 2). A gather form with mx.take has the same math (Table 26 of explore.html). The build kept the dense form of the probe.
  • Lines 71 to 73. The constants become (1, 3, 1, 1) arrays. They broadcast over the batch, the height and the width. The result is fp32, because all inputs are fp32.
  • The return value is lazy. MLX records the operations and runs them at the next mx.eval. C6 calls mx.eval on the result, so its time includes the copy to the GPU and all operations (Section 8).

4.4 The ImageNet constants: one source

# src/dinov3_mlx/stored.py, lines 27 to 30

  • The same fp32 values as before. Before Step 6, preprocess.py made the tensors with torch.tensor([0.485, 0.456, 0.406], dtype=torch.float32) (commit 11a45b1). The fp32 values are the same, so the stored pixels do not change. test_imagenet_constants_have_one_source checks that the two NumPy arrays are fp32 and that the torch tensors hold the same values as the arrays (np.array_equal).
  • .copy(). torch.from_numpy shares the memory of the array. The copy gives the tensor its own memory. A change of the tensor in place then cannot change the constant of stored.py.
  • Both paths use the fp32 value, not the decimal value. 0.485 has no exact fp32 value. The CPU path widens the fp32 value to fp64 (Section 4.5). The MLX path computes with the fp32 value. So the two paths normalize with the same number.

4.5 The CPU path for comparison

# src/dinov3_mlx/preprocess.py, lines 42 to 57, shortened: the docstring is left out
def preprocess(image: np.ndarray, size: tuple[int, int]) -> torch.Tensor:
    pixels = torch.from_numpy(image).permute(2, 0, 1).unsqueeze(0).to(torch.float64) / 255.0
    resized = F.interpolate(pixels, size=size, mode="bilinear", antialias=True)
    mean = IMAGENET_MEAN.to(torch.float64).view(1, 3, 1, 1)
    std = IMAGENET_STD.to(torch.float64).view(1, 3, 1, 1)
    return ((resized - mean) / std).to(torch.float32)
  • fp64 from end to end. The module docstring of preprocess.py gives the reason: an fp32 antialiased resize in torch is off by up to 2.3e-5 for each pixel. In fp64 the error is below 1e-7. So other resize code can match the stored pixels.
  • One image. The function takes (h, w, 3) and gives (1, 3, H, W). C6 calls it 8 times for a batch of 8 frames.
  • The MLX path differs in three places. It computes in fp32, not fp64. It runs the resize as two matmuls, not as one call of F.interpolate. It takes a batch. The T52 target of 2e-6 allows for the fp32 rounding (Section 9).

5 Why the resize runs on float values

Many image libraries resize 8-bit pixels and round the result back to 8 bits. Step 2 measured the effect of this rounding on the output of the backbone (Table 3). Pillow resized the 8-bit image, and the backbone ran in fp32 on torch-cpu. The comparison is with the torch float resize, the method of preprocess.py.

The 8-bit resize moves each pixel by at most 0.0039, about one step of 1/255. This is small for the eye. But for ViT-H+/16 at 224 px it drops the patch minimum to 0.929. A parity test with this preprocessing would measure the preprocessing, not the backbone. So the project fixed the rule in Step 2: divide by 255 first, then resize the float values.

The MLX path keeps this rule. Line 69 sends uint8 values to the GPU, because they need only a quarter of the bytes. But the same line casts them to fp32 before the resize of line 70. No line rounds the resized values back to 8 bits. The uint8 values are exact input data; only the resize output must stay in float.

6 Why TF32 must be off

MLX turns TF32 on by default. With TF32, an fp32 matmul rounds its inputs to a 10-bit mantissa. ADR 0005 gives the size of the effect: for one fp32 matmul against NumPy float64, the TF32 probe of Step 4 gave a largest difference of 7.8e-7 with TF32 off and 7.2e-4 with TF32 on. The T52 target for the pixels is 2e-6. A resize with TF32 on would miss it by far.

ADR 0005 turns TF32 off for the fp32 dtype mode of the backbone. Step 6 adds a second reason. The two resize matmuls of line 70 run in fp32 in every dtype mode, because the pixels are always fp32: the backbone casts them later. So preprocess_frames refuses to run when TF32 is on, also in bf16-cast, where the backbone itself runs no fp32 matmul. T53 checks the refusal with a monkeypatched tf32_enabled.

# src/dinov3_mlx/mlx_model.py, lines 64 to 81, shortened: the docstring is left out
def tf32_enabled(environ: Mapping[str, str] | None = None) -> bool:
    value = (os.environ if environ is None else environ).get("MLX_ENABLE_TF32")
    if value is None:
        return True
    match = re.match(r"\s*([+-]?\d+)", value)
    return bool(match and int(match.group(1)))
  • The check reads the variable, not the state of MLX. MLX reads MLX_ENABLE_TF32 once, at its first use. The docstring warns: a process that changes the variable after its first mlx matmul defeats the check. So a caller sets MLX_ENABLE_TF32=0 before the first mlx import, as tests/conftest.py does (ADR 0005).
  • No variable means TF32 on. MLX uses the default 1. So a process without the variable gets TF32ModeError at the first call of preprocess_frames.
  • The benchmark workers. worker_env of scripts/bench_speed.py sets MLX_ENABLE_TF32=0 for each worker, also for the C6 process.
  • Step 7. The API of Step 7 (embed_frames) must decide on TF32 for the preprocessing; it must be off (Section 3.20 of the plan).

7 The fp16 patch embeddings

Decision D13 changes the output side. In the four fp16 and bf16 dtype modes, the patch embeddings reach the host in fp16. This page calls these four modes the half dtype modes. The frame embeddings stay fp32. The fp32 dtype mode gives fp32 for both. A caller who wants fp32 patch embeddings in a half dtype mode sets patch_fp32=True. So fp16 is the default of the half dtype modes, and fp32 is the opt-in (option B of Table 27 of explore.html; the recommendation of its Section 3.13 adds "a parameter for an fp32 output").

# src/dinov3_mlx/mlx_model.py, lines 583 to 587
def patch_dtype(dtype_mode: str, patch_fp32: bool = False) -> mx.Dtype:
    """Return the host dtype of the patch embeddings of one dtype mode (D13 of
    specs/06-speed/plan.html): fp16 in the four fp16 and bf16 dtype modes, else fp32."""
    half = MLX_DTYPE_MODES[dtype_mode].matmul != mx.float32
    return mx.float16 if half and not patch_fp32 else mx.float32

# src/dinov3_mlx/mlx_model.py, lines 608 to 611 (the body of mlx_embeddings)
    frame = tokens[:, 0].astype(mx.float32)
    patches = tokens[:, NUM_PREFIX_TOKENS:].astype(patch_dtype(dtype_mode, patch_fp32))
    mx.eval(frame, patches)
    return np.array(frame), np.array(patches)
  • Line 586. A dtype mode is "half" when its matmul dtype is not fp32. This holds for fp16-cast, bf16-cast, fp16-autocast and bf16-autocast.
  • fp16 also for the bf16 modes. NumPy has no bf16. bf16 has 7 stored mantissa bits, fp16 has 10. So each bf16 value inside the normal fp16 range converts to fp16 exactly. A bf16 value below the normal fp16 range (below 2−14, about 6.1e-5) can lose bits, because fp16 keeps fewer bits there. After the final layer norm no value is above 18 (docstring of mlx_embeddings; Table 27 of explore.html), far below the fp16 maximum of 65,504.
  • The cast runs on the GPU. astype runs before np.array, so only the fp16 bytes cross to the host. For a P2 batch: 21.0 MB against 42.0 MB in fp32 (Table 13 of explore.html).
  • The same rule in the benchmark worker. time_batch_mlx of mlx_bench.py (lines 93 to 101) uses patch_dtype in the same way. It stops the clock of the frame embeddings before the patch cast. So the patch dtype cannot change the frame time.

In the cast modes the tokens are already fp16 or bf16, so the cast to fp16 loses nothing or almost nothing. In the autocast modes the tokens are fp32, and the cast rounds them once. The plan target was an extra loss of at most 1e-7, from a probe value of at most 3e-8 (AC15). The comment of FP16_EXTRA_LOSS in tests/test_mlx_parity.py gives the measured values: the patch mean stays at or below 5.6e-8, below 1e-7. The patch 1st percentile, a tail value, reaches 1.27e-6 for ViT-H+/16 in bf16-autocast. On 2026-11-07 a decision changed W4: the patch mean keeps 1e-7, the patch 1st percentile gets a fault bound of 5e-6 (FP16_EXTRA_LOSS and its comment in tests/test_mlx_parity.py). The gate stays: each finite configuration passes THRESHOLDS[mode] with the fp16 patch embeddings.

8 C6: the MLX path against the CPU path

C6 is the change ratio of D12 (Table 23 of the plan). As for each change ratio, one process runs both paths in alternation. The process imports torch for the CPU path, so it is not an mlx worker (Table 23 of the plan). run_preprocess_worker of scripts/bench_speed.py (lines 805 to 858) does these actions:

  1. It makes 8 frames of 1080 × 1920 px from the three test images with a Pillow resize.
  2. For each input resolution (224 and 512 px), it calls preprocess_frames once and evaluates it. This first call builds the matrices.
  3. It runs 5 rounds. In rounds 1, 3 and 5 the CPU path runs first; in rounds 2 and 4 the MLX path runs first.
  4. CPU path: preprocess on each of the 8 frames, one at a time. MLX path: mx.eval(preprocess_frames(batch, …)) on the batch of 8 uint8 frames. The copy to the GPU is part of the time. The pixels stay on the GPU.
  5. It divides each time by 8 and records the milliseconds per frame. The ratio of a round is the CPU time divided by the MLX time.

Neither path decodes a JPEG file. The JPEG decode stays on the CPU in both paths (D12).

Two more facts of the build concern preprocess_frames. The benchmark matrix does not use it: it keeps the stored pixels, so the backbone throughput stays comparable with Step 3 (Section 3.6 of the plan). The Learn data at 768 and 1024 px uses preprocess_frames of the three test images (_learn_batch of scripts/bench_speed.py, lines 736 to 749). All 12 throughput lines of that data are finite (results/speed-learn.jsonl; Table 9 of results/speedup-table.md).

The plan says that the worker of the Learn data needs no torch (Section 3.6 of the plan). The build does not reach this. _learn_batch reads the test images with load_image of preprocess.py (line 742), and preprocess.py imports torch. The 14 lines of results/speed-learn.jsonl at 768 and 1024 px (12 throughput lines and 2 token-range lines) record torch_imported: true. The 8 lines at 224 and 512 px use the stored pixels and record false. mlx_preprocess.py itself imports no torch (T54); the torch import comes from the caller.

10 Surprises

  1. The antialias filter widens when the image shrinks. support = max(scale, 1). For a 1080p frame to 224 px, each output pixel reads 7 to 10 input pixels along the rows and 13 to 18 along the columns (Table 2). For an enlargement, it reads 2: the filter is then plain bilinear interpolation. A resize without the antialias reads 2 input pixels in every case and skips the rest.
  2. A resize of 8-bit pixels moves the patch minimum of ViT-H+/16 to 0.929. The pixels move by only 0.0037 (Table 3, Step 2). So the resize runs on float values. The MLX path still sends uint8 values to the GPU, for a quarter of the bytes. It casts them to fp32 before the resize and never rounds back to 8 bits.
  3. The resize matmuls need TF32 off in every dtype mode. This holds also in bf16-cast, where the backbone runs no fp32 matmul. ADR 0005 turns TF32 off only for the fp32 dtype mode. preprocess_frames extends the rule to each process that calls it.
  4. At P1 the CPU preprocessing costs more than one image of the forward pass. One 1080p frame needs 1.74 ms on the CPU path. One image of the P1 forward pass needs 0.69 to 0.73 ms in the half dtype modes: the CPU path costs 2.4 to 2.5 images. The MLX path (0.93 ms) also costs more than one image: 1.3. At P2 both paths are below 3 % of one image (Table 7).
  5. The build measured the MLX path slower than the probe. At 224 px: 0.93 ms against 0.65 ms in the probe. The CPU path stayed at 1.74 ms (probe 1.7). The ratio still meets AC14 in each of the 10 rounds.
  6. Round 1 is the slowest in all four series of C6 (2.246, 1.020, 2.110 and 1.503 ms). The CPU path gets no warm-up call before the rounds. The MLX path gets one, and its round 1 at 512 px is still 31 % above the median (1.503 against 1.151 ms, computed). The median hides this.
  7. Each resize matrix is more than 98 % zeros. The non-zero share is 0.39 to 1.99 % (Table 2). The dense matmul multiplies every zero. It is still 1.78 to 1.90 times as fast as the CPU path (the median ratios of C6, Table 6).
  8. The fp16 patch embeddings save bytes, not time. C4 is 0.991 to 1.042 in the speedup table. At P1 the patch ratio drops to 0.964 and 0.965 in the autocast modes, where the fp16 output adds a cast, and rises to 1.031 in fp16-cast, where the fp32 output needs the cast (Table 4).
  9. The fp16 output loses nothing in the cast modes, but more than the probe in the autocast modes. fp16-cast: 0. bf16-cast: at most 3.7e-15. Each bf16 value in the normal fp16 range converts exactly, so the loss is almost 0. It is not exactly 0, so some values changed. A likely reason: values below the normal fp16 range lose bits; no test isolates them. bf16-autocast: up to 1.3e-6 for ViT-H+/16, more than 40 times the probe value of 3e-8 and above the plan target of 1e-7 (computed from Table 5). The docstring of mlx_embeddings still says "at most 3e-8". W4 now uses a fault bound of 5e-6 for the patch 1st percentile.
  10. Table 6 of the plan does not list patch_dtype. The build added it as a new public function of mlx_model.py, so that mlx_embeddings and time_batch_mlx share one rule. This page covers it (Section 7).
  11. The worker of the Learn data imports torch. The plan wanted a worker without torch at 768 and 1024 px. _learn_batch calls preprocess_frames, but it reads the images with load_image of preprocess.py, which imports torch. The 14 lines at 768 and 1024 px record torch_imported: true (results/speed-learn.jsonl; Section 8). T54 does not see this, because it imports only the modules, not the driver.
