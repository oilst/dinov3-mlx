1 Why this explainer

Step 4 ports ViT-S/16 to MLX, one part at a time. Five explainers describe the parts. This page is the last of the five:

  1. Patch embedding, prefix tokens and the weights
  2. RoPE
  3. Attention and TF32
  4. LayerScale and the block
  5. The MLP, the final layer norm, the two outputs and the first speed result (this page)

The feed-forward network of ViT-S/16 is an MLP: a matrix product from 384 to 1,536 channels, an exact GELU, and a matrix product back to 384 channels. The MLP has 61 % of the FLOPs of a block at 224 px. It also has the one numeric trap of this part: MLX has three GELU functions, and only nn.gelu gives the reference output in fp32.

After the last block, the final layer norm makes the output tokens. run_mlx turns them into a NumPy array, and the Step 2 code cuts the frame embedding and the patch embeddings from it. With all parts in place, Step 4 ran its first benchmark: mlx against torch-mps in fp32, in alternation on the same Mac.

The values on this page come from the Step 4 build of 2026-11-07: the part tests (tests/fixtures/generated/mlx/report.jsonl, which git ignores), results/parity-mlx.md and results/bench-mlx-port.jsonl. The agent that wrote this page ran no test, no model and no GPU work. It computed the GELU curves, the FLOP counts and one estimate in NumPy. The text marks the estimate.

2 The MLP in one block

A block has two branches (04-4). The feed-forward branch is the second one. It runs norm2, the MLP, layer_scale2 and the residual add. The MLP works on each token alone. It does not mix information between the tokens; the attention branch does that.

The MLX code has the names and the structure of DINOv3ViTMLP of Hugging Face (lines 353 to 364 of modeling_dinov3_vit.py):

# src/dinov3_apple/mlx_model.py, lines 283 to 296
class MLP(nn.Module):
    """The feed-forward network of ViT-S/16, ViT-B/16 and ViT-L/16: up_proj, exact GELU,
    down_proj."""

    def __init__(self, config: MlxConfig) -> None:
        super().__init__()
        if config.hidden_act != "gelu":                                         # line 289
            raise NotImplementedError(f"activation {config.hidden_act!r} of the MLP")
        self.up_proj = nn.Linear(config.dim, config.ff, bias=config.mlp_bias)   # 384 -> 1536
        self.down_proj = nn.Linear(config.ff, config.dim, bias=config.mlp_bias) # 1536 -> 384

    def __call__(self, x: mx.array) -> mx.array:
        """Return down_proj(gelu(up_proj(x))). nn.gelu is the erf form, not nn.gelu_approx."""
        return self.down_proj(nn.gelu(self.up_proj(x)))                        # line 296
  • Line 289. The MLP accepts only hidden_act "gelu", the value in config.json of ViT-S/16, ViT-B/16 and ViT-L/16. A config with another activation stops with NotImplementedError. So a wrong activation cannot run without a message.
  • Lines 291 and 292. config.ff is intermediate_size (1,536) and config.mlp_bias is mlp_bias (true) of config.json. MlxConfig.from_hf reads both (lines 102 and 112). The code fixes no width and no bias flag. So ViT-B/16 (768 → 3,072) and ViT-L/16 (1,024 → 4,096) need no new code.
  • Line 296. nn.gelu is the exact form. Section 3 explains why the choice matters.

3 Exact GELU and the tanh form

GELU multiplies each value x by the probability Φ(x) that a standard normal value is below x (Hendrycks and Gimpel, 2016). Two formulas are in use:

exact (erf) form:  GELU(x) = x · Φ(x) = 0.5 · x · (1 + erf(x / √2))
tanh form:         GELU(x) ≈ 0.5 · x · (1 + tanh(√(2/π) · (x + 0.044715 · x³)))

DINOv3 uses the exact form. The Meta code builds its Mlp with nn.GELU of PyTorch, whose default is the exact form. In Hugging Face, hidden_act "gelu" selects GELUActivation, which calls torch.nn.functional.gelu: also the exact form. MLX has both forms:

nn.gelu_fast_approx(x), nn.GELU(approx="fast")x · σ(1.702 x)No. The MLX docstring gives an error below 0.015 on [−6, 6].

3.1 Why the tanh form fails the fp32 targets

The fp32 targets of the part tests come from the fp32 rounding (Table 7 of the plan). One unit in the last place of fp32 is 2.4e-7 near 2.7 and 4.8e-7 near 6. The target of the activation part is 2e-6: about four units in the last place at 6. A port with the exact form must stay inside this band. The tanh form misses it by a different formula, not by rounding: its difference of 4.73e-4 is about 2,000 units in the last place near 2.7.

  • Activation part (T10, part activation). Target 2e-6. The tanh form gives up to 4.73e-4: 237 times the target.
  • MLP part (T14). Target 2e-5. We estimated the effect in NumPy float64. The estimate uses the random weights and biases of the small model (Section 6.1 of the plan). It also uses normal tokens after a layer norm, 2 × 201 tokens and four seeds. The tanh form moves the MLP output by up to 6.1e-4 to 9.4e-4: 30 to 47 times the target. Each activation value differs by about 1.5e-4 (root mean square). down_proj adds 1,536 of these differences with weights of about 1 / √1,536. So each output value also differs by about 1.5e-4, and the largest of the 154,368 output values reaches 6e-4 to 9e-4. The MLP with the exact form differs from the reference by only 8.8e-6 (Table 5). So the tanh form gives a difference that is about 70 to 110 times larger.
  • Block part (T16) and the small model (T18). Targets 3e-5 and 5e-5. The same difference enters the residual stream in each block.

So the part tests fail, and the build stops (rule of Table 11 of the plan). explore.html lists this risk as R15 ("fails fp32"). The test test_mlx_part_gelu_is_exact_form (T15) checks both directions. nn.gelu must agree with ACT2FN["gelu"] within 2e-6 on 200,001 values in [−6, 6]. nn.gelu_approx must differ by 1e-4 or more, so the test can see the wrong form. Measured: 7.2e-7 and 4.74e-4.

The cosine thresholds alone would probably not see the tanh form. In the same NumPy estimate, the tanh form changes the cosine of each MLP output token by only 1.7e-8 to 2.0e-8 (1 − min token cosine). The fp32 parity threshold allows 1e-4. The estimate uses random weights, not the ViT-S/16 weights, so it is a guide only. The tight targets of the part tests are the guard against a wrong formula of this size.

4 The FLOP share of the MLP

Each matrix product of the MLP costs 2 · T · D · F FLOPs for one image: 2 × 201 × 384 × 1,536 = 237.1 MFLOP at 224 px. The two products of one block cost 474.2 MFLOP, and the 12 blocks cost 5.69 GFLOP. part_flops of Step 3 counts the GELU and the biases as 0 FLOPs. The GELU still reads and writes B · T · F values: 9.9 MB each way at batch size 8 in fp32.

5 The final layer norm and the two outputs

After block 12, MlxBackbone applies the final layer norm to each token over its 384 channels, with a learned weight and bias (eps 1e-5). The result is all tokens, (B, 5 + N, 384). Hugging Face returns the same tensor as last_hidden_state (lines 546 and 549 of modeling_dinov3_vit.py). The frame embedding is row 0. The patch embeddings are rows 5 to 5 + N − 1 (02, Section 4).

# src/dinov3_apple/mlx_model.py, lines 343 to 350 (MlxBackbone.__call__)
x = self.embeddings(pixels)                                       # (B, 5 + N, D)
p = self.config.patch_size
cos, sin = self.rope(pixels.shape[2] // p, pixels.shape[3] // p)  # one table pair per grid (04-2)
for block in self.layer:                                          # layer.0 to layer.11
    x = block(x, cos, sin)
return self.norm(x)                                               # the final layer norm

# lines 366 to 369 (run_mlx)
tokens = model(mx.array(pixels).astype(MLX_DTYPE_MODES[dtype_mode]))
tokens = tokens.astype(mx.float32)  # a bf16 mx.array does not convert to NumPy
mx.eval(tokens)
return np.array(tokens)

# lines 384 to 393 (run_mlx_hidden_states)
x = model.embeddings(mx.array(pixels[:1]).astype(model.norm.weight.dtype))
...
states = [x[0]]                                                   # state 0: before block 1
for block in model.layer:
    x = block(x, cos, sin)
    states.append(x[0])                                           # one state after each block
hidden = mx.stack(states).astype(mx.float32)                      # (L + 1, 5 + N, D)
mx.eval(hidden)
return np.array(hidden)
  • Line 26: MLX_DTYPE_MODES = {"fp32": mx.float32}. Step 4 has one dtype mode. Each key is also a key of THRESHOLDS and DTYPE_OF_MODE, so the parity tests and the parity table need no new code (T4). The dict lives in mlx_model.py, because run_mlx needs it and mlx_weights.py imports mlx_model.py. Step 5 adds the fp16 and bf16 dtype modes.
  • Line 366. run_mlx casts the pixels to the dtype of the dtype mode. Embeddings casts them again, to the dtype of the CLS token (line 220, 04-1). The CLS token has the dtype of the model weights, also when nn.quantize packs the patch embedding weight into uint32. So a dtype mismatch cannot promote the residual stream.
  • Line 367. run_mlx returns fp32 in every dtype mode, as run_torch does. NumPy has no bf16 dtype, so np.array of a bf16 mx.array does not work. The cast to fp32 comes first. Step 4 runs only fp32, so this line protects Step 5.
  • Lines 368 and 392. MLX is lazy. mx.eval runs the whole graph once. Without it, np.array would also run the graph. The benchmark worker does not call run_mlx: time_batch_mlx in scripts/bench_mlx_port.py calls mx.eval itself, so it can separate the device time from the copy to NumPy.
  • Lines 384 to 391. pixels[:1] keeps image 0 only. x[0] removes the batch axis of each state. mx.stack joins the 13 states in one array, and one mx.eval computes all of them.
  • MlxBackbone.__init__, lines 327 to 334. The tree has embeddings, the list layer (names layer.0 to layer.11) and norm: 210 parameters for ViT-S/16. The name _rope_cache starts with "_", so the cache is not a parameter (04-2). rope_box_jitter is False; Step 8 decides about RoPE-box jittering.

7 The first speed result

With all parts in place, Step 4 ran one small benchmark (Section 7 of the plan). It is report only and has no target. It compares mlx with torch-mps in the same session. Reason: the throughput of one configuration on this Mac can change by up to 2× from one run to the next (finding F1 of Step 3). The result is the paired ratio: the throughput of mlx divided by the throughput of torch-mps in the same round.

  • ViT-S/16, fp32, 224 px, the stored pixels of the 3 test images, batch sizes 8 (priority configuration P1) and 1.
  • mlx: the Step 4 backbone, TF32 off, no mx.compile. torch-mps: the Hugging Face backbone, eager, no torch.compile.
  • 3 rounds. The order of the two workers alternates from round to round. Each worker runs in its own subprocess after a memory check, with the time budget of Step 3.
  • Apple M5 Max with 64 GB of unified memory, macOS 26.5.2, on the 94 W adapter, battery 100 %. mlx 0.32.4, torch 2.15.0. 2026-11-07, 00:44 to 00:47 UTC.
  • All 12 workers finished and gave valid output. No mlx worker had torch in sys.modules.

What the numbers show:

  • mlx has the higher throughput at both batch sizes. The median paired ratio is 1.39 at batch size 8 and 3.12 at batch size 1. The spread over the rounds is small: 1.36 to 1.44 and 3.11 to 3.16.
  • The gap is larger at batch size 1. torch-mps needs 9.25 ms for 1 image and 13.03 ms for 8 images. mlx needs 2.80 ms and 9.43 ms. So torch-mps has a large fixed cost for each forward pass, and mlx has a small one. With 9.40 GFLOP per image, mlx reaches 3.36 TFLOP/s at batch size 1 and 7.96 TFLOP/s at batch size 8. torch-mps reaches 1.07 and 5.74 TFLOP/s.
  • The frame embedding and the patch embeddings cost almost the same. Their throughputs differ by 0.1 to 0.6 %. The copy to NumPy costs about 1 % of the batch time: without it, mlx gives 851.9 img/s at batch size 8 and 362.4 img/s at batch size 1.
  • The peak memory is mixed. At batch size 1, mlx needs 410 MB and torch-mps needs 565 MB. The main reason: the torch-mps worker starts at 300 MB before the load, for the imports of torch and transformers. At batch size 8, mlx needs more: 828 MB against 637 MB. Its own counter shows 606 MB of MLX memory, against 171 MB of MPS memory for torch-mps. Section 10 lists this as a surprise.

The paired ratio is not the speedup. A speedup divides by the baseline row of ADR 0004. At P1 in fp32 this is a compile row of torch-mps: 642.3 img/s in results/baseline-torch-mps.md, measured in another session. Step 6 measures the speedup, with mx.compile and the full benchmark matrix.

8 Step 5: SwiGLU

ViT-S/16, ViT-B/16 and ViT-L/16 have the MLP of this page. ViT-S+/16, ViT-H+/16 and ViT-7B/16 have SwiGLU, a gated feed-forward network: down_proj(silu(gate_proj(x)) * up_proj(x)) (DINOv3ViTGatedMLP, lines 367 to 380 of modeling_dinov3_vit.py). It has three matrices instead of two. For ViT-S+/16, gate_proj and up_proj have the shape (1536, 384), and down_proj has the shape (384, 1536). So at the same hidden width, SwiGLU has 1.5 times the FLOPs of the MLP.

Step 4 stops at SwiGLU on purpose, with a message:

# src/dinov3_apple/mlx_model.py, lines 305 and 306 (Block.__init__)
if config.gated:                                   # use_gated_mlp of config.json
    raise NotImplementedError("SwiGLU comes in Step 5")

The hooks for Step 5 are in place. MlxConfig reads use_gated_mlp into gated, and it reads hidden_act (lines 87, 88, 113 and 114). Block builds its feed-forward network from the config. So Step 5 replaces the two lines above with a SwiGLU class that has the names gate_proj, up_proj and down_proj. Today the test test_mlx_config_from_hf (T5) checks the NotImplementedError.

The key map does not accept mlp.gate_proj yet. map_key accepts a block name only if the part after layer.{i}. is a parameter name of the MLX block (mlx_weights.py, line 99). block_parameter_names (lines 48 to 74) takes these names from a Block with gated=False, so it gives the names of the MLP only. map_key raises UnknownWeightError for layer.{i}.mlp.gate_proj.weight. So Step 5 also adds the SwiGLU names to block_parameter_names.

10 Surprises

  1. Two GELU curves that look the same differ by 2,000 units in the last place. The tanh form is up to 4.73e-4 away from the exact form, at |x| = 2.70. Near x = −2.7 this is 5 % of the value. The test of the activation part allows 2e-6.
  2. "precise" in MLX means the tanh form. nn.GELU(approx="precise") and its alias approx="tanh" call gelu_approx. Only nn.gelu, or nn.GELU() with the default approx="none", gives the exact form of DINOv3.
  3. The cosine thresholds would probably not catch the wrong GELU. Our NumPy estimate gives 1 − cosine of about 2e-8 for one MLP with the tanh form. This is far inside the fp32 threshold of 1e-4. Only the tight part targets catch it.
  4. nn.gelu is already compiled. MLX wraps nn.gelu and nn.gelu_approx in mx.compile(shapeless=True). So the GELU is a compiled function, also without mx.compile around the backbone. It still agrees with torch within 7.2e-7.
  5. A bf16 mx.array does not convert to NumPy. NumPy has no bf16 dtype. run_mlx casts the tokens to fp32 before np.array. So Step 5 can add bf16 without a change to the output contract.
  6. The first paired ratio is 3.12 at batch size 1, without mx.compile. At batch size 8 it is 1.39. The difference comes from the fixed cost of each forward pass: 9.25 ms for 1 image on torch-mps, 2.80 ms on mlx.
  7. mlx needs more memory than torch-mps at batch size 8. MLX counts a peak of 606 MB: 86 MB of weights and about 520 MB of other arrays. One hidden tensor of the MLP is only 9.9 MB at batch size 8. torch-mps counts 171 MB of MPS memory. We do not know the cause yet. Step 6 measures where the memory of the mlx forward pass goes, also with mx.compile.
