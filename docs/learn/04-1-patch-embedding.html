1 Why this explainer

Step 4 ports the ViT-S/16 backbone to MLX. This explainer covers the start of the forward pass: the patch embedding. The patch embedding is the input layer before block 0. It cuts the image into patches and maps each patch to one patch token. Then it puts the 5 prefix tokens in front. On this page, "patch embedding" (singular) is always this layer. "Patch embeddings" (plural) is the output of the backbone: the patch tokens after the final layer norm. This explainer also covers the code that brings the weights into MLX: the MLX config, the key map, the load with its memory check, and the readers of the stored files.

Table 1 of specs/04-mlx-port/plan.html gives each new function of src/ to one explainer. This page explains patchify, Embeddings, MlxConfig, map_key, mlx_weights, UnknownWeightError, required_mlx_load_bytes, load_mlx_backbone and the readers in stored.py. It also explains two functions that Table 1 of the plan does not name: own_aspect_size, which moved from preprocess.py to stored.py, and reference_tokens, which moved from torch_bench.py to bench.py (Section 9). The fixes after the verification (commit ea82d58) added three functions to src/. This page explains them too: block_parameter_names of mlx_weights.py (Section 8.1), and send_checks_to and replay_checks of memory.py (Section 8.4). MlxBackbone and run_mlx are on page 5. tf32_enabled and TF32ModeError are on page 3.

The measured values come from the Step 4 build of 2026-11-07: the test report of the build (tests/fixtures/generated/mlx/report.jsonl, which git ignores), results/parity-mlx.md and results/bench-mlx-port.jsonl. The values of the fixes after the verification come from the test report of the fix session and from driver.log of the benchmark run after the fix of F6 (2026-11-07, 01:38 to 01:41 UTC). For this page, nobody loaded a model, ran a test or ran a benchmark. Sections 2, 4, 9.2 and 11 add small computations of our own (NumPy, and Pillow for the image sizes).

2 The convolution is one matmul

The Hugging Face model uses nn.Conv2d(3, 384, kernel_size=16, stride=16) as its patch embedding. The kernel and the stride are both 16. So each output position of the convolution sees exactly one patch, and the patches do not overlap. Each patch token is therefore a linear map of the 768 values of its patch (3 colors × 16 rows × 16 columns): patch token = W · patch + b, with a weight W of 384 × 768 and a bias b of 384.

The port uses this fact (option B of D4 in explore.html). patchify cuts the pixels into patches with a reshape and a transpose. Then one nn.Linear(768, 384) does the matmul and adds the bias. The port has no convolution. Three reasons decided this:

  • The patch embedding uses the matmul kernel of all other linear maps. The TF32 setting of the fp32 dtype mode covers it (page 3). No convolution kernel needs a check.
  • The weight needs only a reshape, not a transpose (Section 4).
  • An input resolution that is not a multiple of 16 gives a clear error. The torch convolution drops the rest of the pixels without a message.

The prior ports use nn.Conv2d of MLX. MLX convolutions use the channels-last layout NHWC, so these ports move the axes of the weight from (out, in, 16, 16) to (out, 16, 16, in) (01-prior-ports.html).

Our NumPy check of the equivalence: 2 images of 224 × 224 px with normal random values, a random weight of (384, 3, 16, 16) and a random bias. A convolution with stride 16, written from its definition in float64, and patchify plus one matmul in float64 differ by at most 1.1e-14. So the two paths do the same math. Only the order of the sums can differ.

3 patchify: from NCHW pixels to patches

patchify changes only the order of the values. It does no arithmetic.

173def patchify(pixels: mx.array, patch_size: int) -> mx.array:
  ⋮
189    b, c, h, w = pixels.shape
190    if h % patch_size or w % patch_size:
191        raise ValueError(f"input resolution {h} x {w} is not a multiple of {patch_size}")
192    hp, wp = h // patch_size, w // patch_size
193    x = pixels.reshape(b, c, hp, patch_size, wp, patch_size).transpose(0, 2, 4, 1, 3, 5)
194    return x.reshape(b, hp * wp, c * patch_size * patch_size)

Listing 1. src/dinov3_apple/mlx_model.py, lines 173 and 189–194 (without the docstring).

  • Lines 190–191. An input resolution that is not a multiple of 16 raises ValueError. Test T12 gives pixels of 224 × 230 and expects the message "multiple of 16". The glossary term input resolution says that both sides are multiples of 16.
  • Line 193, reshape. The reshape splits H into (Hp, 16) and W into (Wp, 16). The order of the values in memory does not change.
  • Line 193, transpose. The axes go from (B, C, Hp, 16, Wp, 16) to (B, Hp, Wp, C, 16, 16). The two patch axes (Hp, Wp) come first. The three axes inside one patch (color, row, column) come last.
  • Line 194. The reshape merges (Hp, Wp) into one axis of N = Hp · Wp patches, in row-major order: patch (i, j) is row n = Wp · i + j. It merges (C, 16, 16) into 768 values: value (c, r, s) is column 256 c + 16 r + s. After the transpose the values are not in this order in memory, so MLX copies them here: 150,528 values for each image at 224 px.

The Hugging Face code gets the same order in another way. The convolution gives (B, 384, Hp, Wp). Then flatten(2).transpose(1, 2) gives (B, Hp · Wp, 384), also row-major. The test test_patchify_order (added in the build) checks the order with the pixels 0, 1, 2, … of shape (2, 3, 32, 48). Patch (1, 2) of image 1 must be row 3 · 1 + 2 = 5, and its 768 values must equal pixels[1, :, 16:32, 32:48] in the order color, row, column. The test passes with exact values.

4 The weight reshape of the key map

The file stores the patch embedding weight as (384, 3, 16, 16). This is the layout OIHW of a torch convolution weight: output channel, input channel (the color), kernel row, kernel column. The key map changes it to (384, 768) with one reshape.

121    pairs = []
122    for name, array in tensors.items():
123        if (key := map_key(name)) is None:
124            continue
125        if key == PATCH_WEIGHT:
126            array = array.reshape(array.shape[0], -1)
127        pairs.append((key, array.astype(dtype)))
128    return pairs

Listing 2. src/dinov3_apple/mlx_weights.py, lines 121–128: the loop of mlx_weights.

  • Line 126. array.reshape(array.shape[0], -1) keeps the output axis and merges (3, 16, 16) into 768. Value (d, c, r, s) of the file goes to column 256 c + 16 r + s of row d. This is the column order of the patches of Listing 1. So the weight needs no transpose.
  • Why the layout (out, in) works. nn.Linear of MLX stores its weight as (out, in) and computes mx.addmm(bias, x, weight.T), that is x · Wᵀ + b. nn.Linear of torch also uses (out, in). So all other linear weights of the file load without a change. Only the patch embedding weight needs the reshape, because it is a convolution weight in the file.
  • Line 127. astype(dtype) casts each array to the dtype of the dtype mode. In Step 4 this is fp32, the dtype of the file. The arrays from mx.load are lazy, and the reshape and the cast keep them lazy (Section 8).
  • The strict load checks the shape. Without line 126, load_weights(…, strict=True) stops with "Expected shape (384, 768) but received shape (384, 3, 16, 16)".

An MLX convolution would need another order. nn.Conv2d of MLX takes NHWC pixels and a weight of (out, kernel row, kernel column, in). This needs one transpose of the weight at the load and one transpose of the pixels at each call.

A wrong order inside a patch gives tokens with the right shape and a normal size, but with wrong values (risk R16 of explore.html). Our NumPy example: we take the 768 values of each patch in the order row, column, color (the NHWC order) and multiply them by the reshaped OIHW weight. With normal pixels, a weight with standard deviation 1/√768 and a bias with standard deviation 0.5 (the values of the small model in tests/small_model.py), the cosine similarity of each patch token to the correct token is 0.20 on average and 0.04 at the minimum. The shared bias gives almost all of this value. Without the bias, the mean is about 0. The part test T11 and the check W1 against the stored hidden states catch this error (Section 10).

5 The prefix tokens and the token order

Embeddings holds the patch embedding and the two prefix parameters. Its call gives the token sequence that block 0 reads.

204    def __init__(self, config: MlxConfig) -> None:
205        super().__init__()
206        self.patch_size = config.patch_size
207        self.cls_token = mx.zeros((1, 1, config.dim))
208        self.register_tokens = mx.zeros((1, config.num_register_tokens, config.dim))
209        self.patch_embeddings = nn.Linear(config.num_channels * config.patch_size**2, config.dim)
  ⋮
211    def __call__(self, pixels: mx.array) -> mx.array:
  ⋮
220        pixels = pixels.astype(self.cls_token.dtype)
221        patches = self.patch_embeddings(patchify(pixels, self.patch_size))
222        prefix = mx.concatenate([self.cls_token, self.register_tokens], axis=1)
223        prefix = mx.broadcast_to(prefix, (pixels.shape[0], *prefix.shape[1:]))
224        return mx.concatenate([prefix.astype(patches.dtype), patches], axis=1)

Listing 3. src/dinov3_apple/mlx_model.py, lines 204–209, 211 and 220–224: Embeddings (without the docstrings).

  • Lines 207–208. cls_token (1, 1, 384) and register_tokens (1, 4, 384) are parameters. Their names are the keys of the file: embeddings.cls_token and embeddings.register_tokens. The zeros are only start values. The load replaces them.
  • Line 209. nn.Linear(3 · 16², 384), that is 768 → 384. It holds the weight (384, 768) and the bias (384). Its name patch_embeddings keeps the key embeddings.patch_embeddings.weight of the file.
  • Line 220. The pixel cast to the dtype of the CLS token (Section 6).
  • Line 221. patchify, then the matmul: the patch tokens (B, N, 384).
  • Line 222. The CLS token comes first, then the 4 register tokens: positions 0 to 4.
  • Line 223. broadcast_to gives the prefix to each image of the batch. A broadcast copies no memory.
  • Line 224. The prefix tokens come before the patch tokens: positions 5 to 4 + N. astype(patches.dtype) keeps one dtype in the token sequence.

The prefix rows are copies of the parameters, with no arithmetic. So they are bit-exact: the part test T11 and the check W1 find no difference in rows 0 to 4. DINOv3 has no learned position embedding: the patch tokens get their position only from RoPE in each block. The RoPE tables have identity rows (cos 1, sin 0) at positions 0 to 4, so RoPE does not change the prefix tokens (page 2). The RoPE tables use the same row-major order as patchify. A different order in one of the two moves each patch token to the angles of another patch.

Table 2. Positions in the token sequence. Hp and Wp are the numbers of patch rows and patch columns. The inputs of 224 × 304 px and 304 × 224 px have the same number of tokens, but patch (1, 0) has another position. So the part tests use both shapes: a swap of height and width fails them. 02-tokens-and-outputs.html shows which rows give the frame embedding and the patch embeddings.

The mask token. The Hugging Face module DINOv3ViTEmbeddings also has a parameter mask_token (1, 1, 384). It replaces the patch tokens of masked patches when the call gives bool_masked_pos. Only training uses it, for the iBOT loss. The file contains it, but the inference never reads it. Our Embeddings has no mask token, and the key map drops it (Section 8).

6 The pixel cast

The stored pixels are fp32. The weights can have another dtype: Step 5 adds fp16 and bf16. The Hugging Face code casts the pixels to the dtype of the patch embedding weight, two times:

  ⋮

 90        embeddings = torch.cat([cls_token, register_tokens, patch_embeddings], dim=1)
  ⋮
541        pixel_values = pixel_values.to(self.embeddings.patch_embeddings.weight.dtype)

Listing 4. Hugging Face transformers 5.22.1, models/dinov3_vit/modeling_dinov3_vit.py (Apache-2.0), lines 77, 80–81 and 88–90 (DINOv3ViTEmbeddings.forward) and line 541 (DINOv3ViTModel.forward).

Line 220 of mlx_model.py casts the pixels to the dtype of the model weights too, but it reads this dtype from another array: pixels = pixels.astype(self.cls_token.dtype). Without quantized weights, the CLS token and the patch embedding weight have the same dtype, so the result is the same as in Hugging Face. In MLX, an operation on an fp32 array and a bf16 array gives an fp32 array. Without the cast, fp32 pixels and bf16 weights give fp32 patch tokens. Then every block runs on an fp32 residual stream, and no message shows it. The code of Section 5 of the plan had no cast. The build added the cast and the test test_mlx_forward_casts_the_pixels_to_the_weight_dtype. The test sets the small model to bf16 with set_dtype and gives fp32 pixels. The token sequence must be bf16 and equal to the result with bf16 pixels. The output of the full small model must be bf16. set_dtype also casts the CLS token, so the test stays green with the new source of the dtype.

Why the CLS token and not the patch embedding weight. The build took the dtype from self.patch_embeddings.weight, as Hugging Face does. The verification found that this cast breaks after nn.quantize (F1 of specs/04-mlx-port/verify.html, Section 11, last surprise). nn.quantize replaces the patch embedding with a QuantizedLinear, and its weight holds packed uint32 values. nn.quantize replaces only modules, so the CLS token, an array of Embeddings, keeps its float dtype.

Two more casts touch the pixels. run_mlx casts the stored pixels to the dtype of the dtype mode (line 366), and run_mlx_hidden_states casts them to the dtype of the final layer norm weight (line 384). Page 5 explains these functions. In Step 4 the only dtype mode is fp32, so no cast changes a value on this page.

Table 4. The rules of map_key. Each block has 17 tensors: 2 layer norms with weight and bias, 4 projections with weight and bias except k_proj (no bias), 2 LayerScale factors, and up_proj and down_proj with weight and bias. Test T3 reads the header of the ViT-S/16 file and confirms the counts.

  • Two spellings. The file uses layer.{i}.…. transformers 5 renames the tree in memory to model.layer.{i}.… (conversion_mapping.py, line 1135). The small model of the part tests gives its state dict in the second spelling, with the mask token. So every part test also runs the key map.
  • UnknownWeightError is a KeyError. A name that has no place in the MLX backbone stops the load at once, with the name in the message. rope_embeddings.inv_freq is a buffer with persistent=False, so it is not in the file and not in the state dict. The rule guards against a future file that contains it.
  • block_parameter_names, lines 48–74. The function builds one Block from a small MlxConfig with every bias on (embedding dimension 8). tree_flatten of its parameters gives 18 names, for example norm1.weight, attention.k_proj.bias and layer_scale1.lambda1. The names come from the Block module itself, so the key map and the module cannot differ. The arrays of the small block stay lazy, and MLX never computes them. @cache builds the block one time for each process. Its random start values advance the global key of mx.random one time, as each MlxBackbone does.
  • Line 99, the parameter check. BLOCK_KEY cuts a block key into the block index and the parameter name. The name must be in block_parameter_names(), or map_key raises UnknownWeightError. Before this fix, the pattern accepted any lower-case path, for example layer.0.foo.weight (F4 of specs/04-mlx-port/verify.html). The test test_map_key_rejects_a_block_name_that_is_not_a_parameter gives five wrong names, for example layer.3.attention.q_proj.base_layer.weight (the name of a PEFT LoRA wrapper) and layer.3.layer_scale1.gamma. Each raises UnknownWeightError. The test also sends each of the 18 names through map_key as model.layer.7.{parameter} and expects layer.7.{parameter}.
  • The block index and the biases go to the strict load. map_key does not know the number of blocks or the bias settings of the config. So layer.12.norm1.weight passes map_key, and so does attention.k_proj.bias, which ViT-S/16 does not have. load_weights(strict=True) then stops these names with a ValueError. The test test_map_key_leaves_the_block_index_to_the_strict_load adds layer.2.norm1.weight to the state dict of the small model (blocks 0 and 1) and expects this ValueError.
  • Step 5. block_parameter_names builds a block with gated=False. So mlp.gate_proj.weight of SwiGLU now raises UnknownWeightError. When Step 5 adds SwiGLU to Block, block_parameter_names must also give the names of a gated block.

8.2 mlx_weights

mlx_weights(tensors, dtype) applies map_key to each tensor, skips the dropped tensor, reshapes the patch embedding weight and casts each array to dtype (Listing 2). It returns a list of (name, array) pairs, not a dict and not a path. Module.load_weights of MLX reads only a str as a path. A pathlib.Path fails (risk R18).

8.3 required_mlx_load_bytes

The memory check asks for the memory of the load before the load starts. The formula is the formula of the torch loader of Step 2:

148    return load_bytes(parameter_count(model_size) * MLX_DTYPE_MODES[dtype_mode].size, ratio)

Listing 7. src/dinov3_apple/mlx_weights.py, line 148. load_bytes in memory.py gives round(ratio × weight bytes) + LOAD_RESERVE_BYTES.

For ViT-S/16 in fp32: parameter_count reads 21,596,544 values from the safetensors header, the mask token included. 4 bytes each give 86,386,176 bytes (86.4 MB). The need is round(1.2 × 86,386,176) + 4,000,000,000 = 4,103,663,411 bytes, 4.10 GB. Test T7b checks this exact value.

9 The readers of the stored files

stored.py holds the readers of the stored pixels and of the reference files. The build moved these names without a change from reference.py and preprocess.py. 11 Surprises

  1. A convolution with stride = kernel is one matmul, and its weight needs only a reshape. The prior ports use nn.Conv2d of MLX and transpose the weight to (out, 16, 16, in). The OIHW layout of the file, flattened, already has the order color, row, column of patchify. So the port needs no convolution kernel and no transpose (Sections 2 and 4).
  2. The file holds a tensor that the inference never reads. embeddings.mask_token serves only the masked patches of the iBOT loss in training. The file has 211 tensors and the MLX backbone has 210 parameters. Without the drop in the key map, the strict load stops with "Received 1 parameters not in model".
  3. The load is lazy until mx.eval. mx.load reads only the header, and the random start values of nn.Linear are lazy too. Test T3 sends the 211 names of the file through the key map and compares the 210 results and their shapes with the parameter tree. MLX computes no array. mx.eval(model.parameters()) puts the read into the load. The whole load takes 12 ms. Without it, the first forward pass would pay the read (R14).
  4. The code of the plan had no pixel cast. In MLX, fp32 pixels and bf16 weights give fp32 patch tokens. A bf16 model would then run its whole residual stream in fp32, without a message. The Hugging Face code casts the pixels two times (Listing 4). The build added the cast and a test (Section 6). After the verification, the cast takes the dtype of the CLS token (line 220, last surprise).
  5. The memory need of ViT-S/16 is 47.5 times its weights. The need is 4.10 GB for 86.4 MB of weights, because the reserve of 4 GB holds for every model size. The mlx load used only 1.05 times the weight bytes above the footprint before the load. So LOAD_RATIO = 1.2 holds for mlx. The torch-mps load used 2.57 times.
  6. The margin of the part test T11 is small, but its value is normal. The largest difference is 8.8e-6 against a target of 1e-5. The CPU-stream probe of explore.html gave 1.4e-6 to 1.9e-6 on other values. Our NumPy computation on the same shapes and similar values (largest output 5.4) gives 5.3e-6 between an fp32 matmul and float64. T11 compares two fp32 results, each with its own rounding, so a difference up to about two times this value is normal. With TF32 on, the difference would be about 100 times larger (Table 7 of the plan).
  7. Verify found a fault of the pixel cast with quantized weights (F1). The cast of the build took the pixel dtype from patch_embeddings.weight. With its default predicate, nn.quantize of mlx 0.32.4 quantizes every module that has to_quantized, so every nn.Linear, the patch embedding too (768 inputs, a multiple of the group size 64). QuantizedLinear stores its weight as packed uint32 values. So the cast turned the pixels into unsigned integers, and no error message came. The verification of Step 4 found this fault (F1 of specs/04-mlx-port/verify.html). It measured ViT-S/16 with 8-bit weights: the patch tokens of the patch embedding have a minimum cosine of 0.268 with the old cast and 0.99984 without it. The fix (commit ea82d58) casts the pixels to the dtype of the CLS token (line 220). nn.quantize does not change this array. The test test_mlx_quantized_patch_embedding_gets_float_pixels quantizes the small model with 8 bits and the default predicate. The minimum token cosine of the patch tokens against the unquantized model is 0.999986 for the embeddings and 0.999983 for run_mlx (target ≥ 0.999). With the old cast, the small model gives about 0.63.
