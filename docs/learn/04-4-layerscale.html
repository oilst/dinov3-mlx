1 Why this explainer

Step 4 ports ViT-S/16 to MLX (commit c212226). Five explainers cover the port, one for each part of the backbone (Table 1 of specs/04-mlx-port/plan.html):

  1. Patch embedding, prefix tokens and the MLX weights
  2. RoPE
  3. Attention and TF32
  4. LayerScale and the block (this page)
  5. MLP, final layer norm and the two outputs

This page shows how the parts become one block: the two residual branches, the layer norms norm1 and norm2, LayerScale and the order of the operations. It also shows the final layer norm, which turns the token sequence into the frame embedding and the patch embeddings. Then it gives the evidence that the block matches the Hugging Face block: the part tests, the checks against the stored hidden states (AC3, AC4) and the end-to-end parity (AC1, AC2).

The trained LayerScale factors of ViT-S/16 are far from their initial value 1e-5 and far from 1. They span −7.6 to 10.0. Almost half of them are negative. One channel has the largest absolute factor in 21 of the 24 LayerScale vectors. Section 4 gives the values.

This page counts the blocks from 0, as the weight keys layer.0 to layer.11 and the test ids block-0 to block-11 do. 02-tokens-and-outputs.html and 03-where-the-compute-goes.html count from 1: "after block 1" there is the output of layer.0. Hidden state i is the token sequence before block i; hidden state 0 is the output of the embeddings.

2 The block at 224 px

A block reads the token sequence x and writes a sequence of the same shape. It has two branches. The attention branch mixes information between the tokens. The feed-forward branch changes each token alone. Each branch has the same structure:

  1. A layer norm normalizes a copy of each token (pre-norm).
  2. The branch computes its output from the normalized copy.
  3. LayerScale multiplies each channel of the output by a trained factor.
  4. The residual add adds the result to the input of the branch.

The input of the block flows through both residual adds without a change. This path is the residual stream. The branches only add updates to it. Figure 1 shows the block for one image at 224 × 224 px.

3 The layer norms norm1 and norm2

Each block has two layer norms: norm1 before the attention and norm2 before the MLP. A layer norm works on each token alone, over its 384 channels. It subtracts the mean of the channels, divides by the standard deviation and applies a trained scale (weight) and shift (bias) for each channel:

y[t, c] = (x[t, c] − mean(x[t, :])) / sqrt(var(x[t, :]) + eps) · weight[c] + bias[c]

The MLX code uses nn.LayerNorm of MLX. Its __call__ calls mx.fast.layer_norm, one fused GPU kernel. Its parameters have the names weight and bias, the same names as the keys layer.{i}.norm1.weight and layer.{i}.norm1.bias of the weights file. So the key map needs no rename rule for the layer norms. map_key keeps the name, because norm1.weight and norm1.bias are parameter names of the MLX block (block_parameter_names, page 04-1, Section 8).

# src/dinov3_apple/mlx_model.py, lines 307 and 310 (Block.__init__)
self.norm1 = nn.LayerNorm(config.dim, eps=config.eps)   # eps from config.json: layer_norm_eps
self.norm2 = nn.LayerNorm(config.dim, eps=config.eps)

# line 106 (MlxConfig.from_hf)
eps=config["layer_norm_eps"],                            # 1e-05 for ViT-S/16

eps. The value of eps is 1e-5 for ViT-S/16. It comes from layer_norm_eps in config.json. The official DINOv3 code has two layer-norm types. The type "layernorm" uses eps 1e-6. The type "layernormbf16" uses eps 1e-5. The hub constructors of the released model sizes select "layernormbf16" (dinov3/hub/backbones.py). So a port that takes the default type of the Meta code gets the wrong eps.

Table 2 shows the effect of a wrong eps. We computed it for this explainer in NumPy fp64, with the stored hidden states of iss-kibo-lab at 224 × 224 px and the ViT-S/16 weights. The effect is large where a token has a small variance. Before block 0, the register token R2 has a variance of only 0.0155. After block 11, the smallest variance is 153.

4 LayerScale: one factor for each channel

LayerScale multiplies the output of a branch by a trained vector λ with one factor for each of the 384 channels. Touvron et al. introduced it in CaiT (2021) to train deep vision transformers. The factor broadcasts over the batch axis and the token axis: all tokens of all images get the same factor in channel c.

# src/dinov3_apple/mlx_model.py, lines 271–280
class LayerScale(nn.Module):
    """A learned factor for each channel."""

    def __init__(self, dim: int) -> None:
        super().__init__()
        self.lambda1 = mx.ones((dim,))        # the name of the key: layer.{i}.layer_scale1.lambda1

    def __call__(self, x: mx.array) -> mx.array:
        """Return x · lambda1."""
        return x * self.lambda1               # (B, T, 384) · (384,): broadcast over B and T

The parameter has the name lambda1 in both LayerScale modules of a block. The Hugging Face class DINOv3ViTLayerScale uses this name (lines 344–350 of modeling_dinov3_vit.py), and the key map keeps it. The key map also checks it. block_parameter_names (mlx_weights.py, lines 48–74) reads the parameter names from Block itself, for example layer_scale1.lambda1. map_key (lines 77–101) raises UnknownWeightError for a block key with another parameter name, for example layer.3.layer_scale1.gamma (page 04-1, Section 8). The official code calls the same vector gamma and the modules ls1 and ls2. The value mx.ones is only a placeholder: load_weights(strict=True) replaces it with the trained values.

Initial values. The training configs of the official code set the initial value of each factor to 1e-5 (layerscale: 1.0e-05). So each branch starts almost closed, and the residual stream starts as an identity path. config.json of the Hugging Face model has layerscale_value: 1.0. Hugging Face uses this value only to initialize a new model. The weights file overwrites it.

Trained values. We read the 24 LayerScale vectors of ViT-S/16 from the weights file. Figures 2 and 3 and Table 3 show them. The values are far from 1e-5 and far from 1.

Five facts follow from the data:

  • The branches open with the depth. The median |λ1| grows from 0.00026 in block 0 to 7.0 in block 11. The median |λ2| grows from 0.063 to 3.7 (block 10).
  • Block 0 almost closes its attention branch. 361 of the 384 factors of layer.0.layer_scale1 are below 0.01 in absolute value, and 330 are below 0.001. Only channel 369 (−0.804) and channel 341 (0.104) are above 0.1.
  • Both signs. 4,542 of the 9,216 factors (49 %) are negative. A negative factor reverses the update of a branch in its channel. A LayerScale is not a damper with values in (0, 1).
  • Channel 369. Channel 369 has the largest absolute factor in 21 of the 24 vectors: in all 12 λ2 vectors and in 9 of the 12 λ1 vectors. Channel 369 is also the channel of the large register value. In the stored hidden states of iss-kibo-lab at 224 × 224 px, the largest absolute value of the sequence sits in channel 369 after 10 of the 12 blocks, in register token R1 or R2. After block 10 it is −1,708 in R1. After blocks 6 and 7 the largest value sits in channel 10 of R2 (968 and 966).
  • Most of the large updates go to channel 369. The largest change of the residual stream that a block makes sits in channel 369 in 10 of the 12 blocks. Example: block 10 changes channel 369 of R1 by −704. Its λ1[369] is −6.80 and its λ2[369] is 10.03.

The DINOv3 paper and Darcet et al. (2024) describe tokens and channels with very large values (page 02, Section 5). The LayerScale factors show one part of the mechanism in ViT-S/16: the training gave channel 369 the largest factors, so the branches write their largest updates into this channel. We did not study the cause further.

The dtype in Step 5. In Step 4 every array is fp32. In MLX, an fp16 array times an fp32 array gives fp32. So the dtype of lambda1 sets the dtype of the residual stream after each LayerScale. mlx_weights casts lambda1 to the dtype of the dtype mode at load time, so an fp16 model keeps an fp16 residual stream. An fp32 lambda1 would move the residual stream to fp32. Section 3.6 of the plan keeps an fp32 residual stream open as an option for Step 5, because of the register values above the fp16 maximum in ViT-L/16 and ViT-H+/16 (page 02, Section 6).

5 The order of the operations in a block

The MLX block uses the order of the Hugging Face block: pre-norm, branch, LayerScale, residual add. It does this twice. The second branch reads the output of the first residual add, not the block input.

MLX (mlx_model.py, lines 314–317)

def __call__(self, x, cos, sin):
    # attention branch: norm1, attention,
    # LayerScale, residual add (parts 1–6)
    x = self.layer_scale1(
        self.attention(self.norm1(x), cos, sin)
    ) + x
    # feed-forward branch (parts 7–11)
    return self.layer_scale2(
        self.mlp(self.norm2(x))
    ) + x

Hugging Face (modeling_dinov3_vit.py, lines 433–450)

residual = hidden_states
hidden_states = self.norm1(hidden_states)
hidden_states, _ = self.attention(hidden_states, ...)
hidden_states = self.layer_scale1(hidden_states)
hidden_states = self.drop_path(hidden_states) + residual

residual = hidden_states
hidden_states = self.norm2(hidden_states)
hidden_states = self.mlp(hidden_states)
hidden_states = self.layer_scale2(hidden_states)
hidden_states = self.drop_path(hidden_states) + residual

Four details make the two versions equal:

  • No drop path. drop_path_rate is 0.0 in config.json, so Hugging Face sets self.drop_path to nn.Identity(). The MLX block has no drop path. Step 8 must decide if fine-tuning needs it.
  • The RoPE tables come from outside. MlxBackbone makes the tables once for each patch grid and gives the same tables to all 12 blocks (page 04-2). Only the attention reads them.
  • The operands of the add. MLX writes branch + x, Hugging Face writes branch + residual, and the official code writes x + self.ls1(...). IEEE 754 addition is commutative, so all three give the same bits.
  • No in-place operation. The official LayerScale has an option inplace (x.mul_(gamma)). MLX arrays are immutable, so the port has no such option. The result is the same.

A block with the wrong order still runs and gives the right shapes. Two examples: a post-norm block (norm after the add) or a feed-forward branch that reads the block input x in place of x2. Only a comparison of values finds such an error. The block test of Section 7 does this on the small model, and the isolated block checks of Section 8 do it for each of the 12 trained blocks.

6 The final layer norm and the two outputs

After the last block, MlxBackbone applies one more layer norm to all tokens. Then run_mlx returns all tokens as fp32 NumPy, with the contract of run_torch. Page 04-5 gives the details of run_mlx and the dtype modes.

# src/dinov3_apple/mlx_model.py, lines 343–350
def __call__(self, pixels: mx.array) -> mx.array:
    """Return all tokens after the final layer norm, (B, 5 + N, D), of NCHW pixels."""
    x = self.embeddings(pixels)                                   # hidden state 0
    p = self.config.patch_size
    cos, sin = self.rope(pixels.shape[2] // p, pixels.shape[3] // p)
    for block in self.layer:                                     # layer.0 to layer.11
        x = block(x, cos, sin)                                   # hidden states 1 to 12
    return self.norm(x)                                          # norm.weight, norm.bias, eps 1e-5

The final layer norm has the same form as norm1 and norm2, with its own weights. Its scale norm.weight spans 0.28 to 4.43. It brings every token to a similar size. Before it, the register token R1 holds −1,475 after block 11. After it, no output value of this test image is above 9.2 in absolute value (page 02, Section 4).

The two outputs are slices of the normalized sequence. split_tokens of Step 2 makes them:

  • The frame embedding is row 0, the CLS token: shape (1, 384).
  • The patch embeddings are rows 5 to 200, reshaped to the patch grid: shape (1, 14, 14, 384).
  • Rows 1 to 4, the register tokens, are not part of either output.

run_mlx_hidden_states (lines 372–393) gives a third, diagnostic output: the sequence before block 0 and after each block, before the final layer norm. Its shape is (13, 201, 384) for one image at 224 px. It runs the same blocks in the same loop and keeps each result:

# src/dinov3_apple/mlx_model.py, lines 384–392
x = model.embeddings(mx.array(pixels[:1]).astype(model.norm.weight.dtype))
...
states = [x[0]]                     # hidden state 0: the embeddings
for block in model.layer:
    x = block(x, cos, sin)
    states.append(x[0])             # hidden state i + 1: the output of block i
hidden = mx.stack(states).astype(mx.float32)
mx.eval(hidden)                     # one evaluation for all 13 states

The reference file of each model size stores the L + 1 hidden states (13 for ViT-S/16) for iss-kibo-lab at 224 × 224 px. Section 8 uses them.

7 The part tests

A part test runs one part of the MLX block and the same part of the Hugging Face block on the same inputs. The Hugging Face side is the small model: DINOv3ViTModel on torch-cpu in fp32 with the values of ViT-S/16, 2 blocks and random weights (tests/small_model.py). It needs no gated weights. The MLX side gets the same weights through the key map, so each part test also tests the key map.

Why random factors. The Hugging Face initialization sets each LayerScale factor to 1.0 and each bias to 0. With these values, a port that forgets LayerScale, applies it to the wrong axis or drops a bias gives the same output. So small_hf_model draws new values for every parameter. Each factor gets a standard deviation of 0.3:

# tests/small_model.py, lines 52–55 (_std_and_mean)
if "norm" in name:
    return 0.1, 1.0 if name.endswith("weight") else 0.0   # layer norms: weight mean 1, bias mean 0, std 0.1
if name.endswith("lambda1"):
    return 0.3, 0.0                                       # LayerScale: std 0.3

How the 11 part tests get their inputs. run_parts of Step 3 runs the 11 parts of block 0 of the small model on torch-cpu and keeps every intermediate tensor. Each MLX part gets the Hugging Face inputs of its part and must give the Hugging Face outputs. So an error in one part does not move into the next part. The MLX parts carry the names of block_parts:

The LayerScale parts are bit-equal. The plan set the target 0 for layer_scale1 and layer_scale2, and the build measured 0. Each part does one multiply and one add for each value. IEEE 754 rounds each result of a multiply and of an add correctly, so both sides get the same bits from the same inputs. Two conditions must hold: no side may fuse the multiply and the add into one fused multiply-add (one rounding in place of two), and no side may change the order of the operations. MLX without mx.compile runs the multiply and the add as two kernels (Table 7 of the plan), and eager torch does the same.

The block is closer than its largest part. The block test gives 3.6e-6. The part ff_out alone gives 8.3e-6. A probable cause: LayerScale multiplies the error of each branch by its factor, and the random factors of the small model have a standard deviation of 0.3. So the branch errors shrink before the residual add. The two tests also use different inputs: the part test gets the Hugging Face input of ff_out, the block test gets only the block input.

8 The stored hidden states (AC3, AC4)

The part tests use random weights. The trained weights have other value ranges: register values up to 1,708, LayerScale factors up to 10. So the build also compares the MLX backbone with the 13 hidden states of the reference file, which torch-cpu made with the trained ViT-S/16 weights. There are two kinds of check (Figure 4).

The isolated checks (AC3) use a stricter limit than the fp32 threshold: a minimum token cosine of 0.99999, so 1 − cosine ≤ 1e-5. The reason (Table 8 of the plan): an isolated block has no error from the blocks before it. The cosine runs in fp64 over all 201 tokens, the prefix tokens included. The cosine of a token does not depend on its size, so the register values of up to 1,708 do not hide an error in a small token.

Three observations:

  • The largest difference follows the size of the values. It grows from 1.2e-5 (state 0) to 1.2e-3 (state 12), because the largest stored value grows from 10.7 to 1,475. fp32 rounds relative to the size of a value. The largest relative difference stays between 7e-8 and 8e-6.
  • The chain adds up, but slowly. In the chain, 1 − min cosine is 3.03e-11 after block 0 and 1.07e-10 at most (state 11). That is about 6 times the worst isolated value (1.68e-11). The error does not grow with each block: state 12 gives 7.46e-12.
  • Block 0 has the largest isolated error. Its 1 − min cosine (1.68e-11) and its relative difference (3.7e-6) are the largest of the 12 blocks. Block 0 also has the smallest input values (largest 10.7), and its attention branch writes almost only channel 369 (Section 4). We did not study the cause.

9 End-to-end parity (AC1, AC2)

AC1 runs run_mlx on the stored pixels of the 12 configurations and compares all tokens after the final layer norm with the reference file. 10 The cost of LayerScale

LayerScale has no matrix product, so the FLOP count of Step 3 gives it 0 FLOPs. It still takes time: it reads every token and writes every token (page 03, Section 4). The block profile of Step 3 measured it on torch-mps. Step 4 has no MLX block profile; Step 6 makes one.

Table 8. Time of the LayerScale parts and the layer-norm parts of block 0 (layer.0, "block 1" in the 1-based count of the block profile of Step 3) (results/block-profile-torch-mps.md). Each LayerScale part includes its residual add. The shares use the sum of the 11 parts.

A LayerScale part takes 1.4 times as long as a layer norm on the same tokens at batch size 1, and 3.3 to 5.3 times as long at batch size 8. A layer norm does more arithmetic. The cause is the number of kernels. A layer norm is one fused kernel: it reads x and writes h. A LayerScale part in eager mode is two kernels: the multiply writes the product to memory, and the add reads it back with x. That is about 5 BTD of memory traffic in place of the 3 BTD that part_bytes counts (B images, T tokens, D channels). At 224 px and batch size 8, one BTD in fp32 is 2.5 MB.

Two options for Step 6, not decisions:

  • mx.compile. It can fuse the multiply and the add into one kernel. The kernel can then use a fused multiply-add, which rounds once. So the result can differ in the last bit from the eager result, and the target 0 of the LayerScale part tests needs a review.
  • Fold LayerScale into the weights at load time. LayerScale follows a linear layer in both branches: λ ⊙ (W h + b) = (diag(λ) W) h + λ ⊙ b. So mlx_weights can multiply row c of o_proj.weight and of down_proj.weight, and entry c of their biases, by λ[c]. Then the 24 LayerScale parts disappear from the forward pass. Costs: the rounding changes, the parameter tree loses the 24 lambda1 keys, and an adapter on o_proj or down_proj needs the unfolded weights. Without lambda1 in Block, block_parameter_names does not give layer_scale1.lambda1, and map_key raises UnknownWeightError for the 24 lambda1 tensors of the weights file. So the fold must read these tensors before map_key. The LoRA target modules of Step 8 are q_proj and v_proj (Table 5 of the plan), so folding does not touch them.

12 Surprises

  1. The trained LayerScale factors are large and have both signs. The official training starts each factor at 1e-5. In ViT-S/16 the factors span −7.62 to 10.03, and 49 % of them are negative. The median |λ1| grows from 0.00026 in block 0 to 7.0 in block 11.
  2. One channel gets the largest absolute factor almost everywhere. Channel 369 has the largest absolute factor in 21 of the 24 LayerScale vectors. The same channel holds the largest value of the residual stream after 10 of the 12 blocks (−1,708 in register token R1 after block 10).
  3. Block 0 almost closes its attention branch. 361 of its 384 factors λ1 are below 0.01 in absolute value. The attention of block 0 writes almost only channel 369 (factor −0.804).
  4. LayerScale is bit-equal, as the plan predicted. Both LayerScale part tests measured a difference of 0. One multiply and one add round the same way on both sides. mx.compile in Step 6 can change this.
  5. The default eps of the Meta code is the wrong eps. The type "layernorm" of the official code uses 1e-6, but the released models use "layernormbf16" with 1e-5. A wrong eps changes norm1 of block 0 by up to 0.0039, but the token cosine only by 3.7e-9. Only a test of the largest difference sees it.
  6. LayerScale costs more than a layer norm. On torch-mps at batch size 8, a LayerScale part with its residual add takes 3.3 to 5.3 times the time of a layer norm (Step 3 data), because eager mode runs it as two kernels. Together the two LayerScale parts take 6.0 % to 6.6 % of the block at batch size 8, for 0 FLOPs.
  7. The block is closer to the oracle than its largest part. The block test gives 3.6e-6, the part ff_out alone 8.3e-6. A probable cause: LayerScale scales the branch errors by the factors before the residual add.
