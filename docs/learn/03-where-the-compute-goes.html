1 Why this explainer

Step 3 measures the baseline: the throughput and the peak memory of the Hugging Face backbone on torch-mps. Step 6 divides the throughput of mlx by these values to get each speedup. To make the backbone faster, we must know where its time goes. This explainer shows it in three views. The FLOP view covers each model size and input resolution. The time view covers ViT-S/16 and ViT-H+/16 at 224 and 512 px. The throughput view covers the five model sizes of B1.

  1. FLOPs. The FLOP count of each part of a block (Section 3). The attention scores take a larger share of the FLOPs when the token count T grows, and a smaller share when the embedding dimension D grows.
  2. Time. The measured time share of each part (Section 6). Layer norms, RoPE, LayerScale, the activation function and the residual adds have almost no FLOPs. They read and write every token, so they take time.
  3. Throughput against FLOPs. The throughput of a configuration times the FLOPs of one image gives the reached TFLOP/s (Section 7). A low value shows a fixed cost, for example ViT-S/16 at batch size 1.

Sections 5, 8 and 9 explain how Step 3 measures: the host-to-host time of one batch, the time budget, the process footprint, the memory need, the noise of this Mac and the rule for the baseline row. Section 10 annotates the code. Section 11 lists the surprises.

All measured values come from the committed results files results/baseline-torch-mps.md and results/block-profile-torch-mps.md and their JSON lines. The verifier measured them on the 94 W power adapter on 2026-11-06, from 22:43 to 01:00 local time (Section 14 of specs/03-baseline/verify.html). These results replace the first results, which ran on a 30 W adapter (Section 9.1). The machine is an Apple M5 Max with 64 GiB unified memory, macOS 26.5.2, torch 2.15.0 and transformers 5.22.1 with SDPA attention. The FLOP counts come from src/dinov3_mlx/flops.py. 2 The parts of one block

Each branch starts with a layer norm and ends with LayerScale and a residual add. block_parts in src/dinov3_mlx/block_profile.py splits block 1 of the Hugging Face backbone into 11 parts. It uses the Hugging Face modules and functions (Figure 1, Table 2). A test runs the 11 parts in order and compares the result with the output of the block. On torch-cpu in fp32 the largest difference is 0.0 for ViT-S/16 and ViT-S+/16 (AC11).

3 The FLOP count

A product of an (M, K) matrix and a (K, N) matrix has M · K · N multiply-adds, so 2 · M · K · N FLOPs. For one image (B = 1), one block has these FLOPs:

linear parts:  qkv_proj 6 T D²  +  o_proj 2 T D²  +  ff_in 2k T D F  +  ff_out 2 T D F
sdpa:          Q Kᵀ 2 T² D  +  softmax(Q Kᵀ) V 2 T² D  =  4 T² D

sdpa / linear  =  4 T² D / (8 T D² + 2 (k + 1) T D F)  =  2 T / (4 D + (k + 1) F)

The heads do not change the count. Each head has D / heads channels, and all heads together have D channels. The linear parts grow with T. The attention scores grow with T². So the sdpa share of the FLOPs grows with T and falls with D:

  • ViT-S/16, ViT-B/16 and ViT-L/16 have an MLP with F = 4 D and k = 1. The ratio is T / (6 D). Section 2 of the plan writes N / (6 D), with N for the token count.
  • ViT-S+/16 and ViT-H+/16 have SwiGLU with F = 4 D and k = 2. The ratio is T / (8 D).
  • ViT-7B/16 has SwiGLU with F = 2 D and k = 2. The ratio is T / (5 D).

Example: ViT-S/16 at 224 px has T = 5 + 14² = 201 tokens. The ratio is 201 / (6 × 384) = 0.087. So sdpa has 8.0 % of the block FLOPs.

image_flops adds the patch embedding to L blocks. The patch embedding is a 16 × 16 convolution from 3 color channels to D channels: 2 × 3 × 16 × 16 × D FLOPs for each patch. The count leaves out the final layer norm. Table 4 gives the FLOPs of one image for each model size and input resolution.

4 The parts without FLOPs

Six of the 11 parts have no matrix product: norm1, rope, layer_scale1, norm2, activation and layer_scale2. The residual adds are inside layer_scale1 and layer_scale2. part_flops counts these six parts as 0 FLOPs. They still take time. Each of them reads every token from memory and writes a result back. So their time depends on the bytes that they move and on the number of GPU kernels that they start, not on FLOPs.

part_bytes estimates the bytes (Table 2). Example: ViT-S/16 at 224 px, batch size 8, fp32. One (B, T, D) tensor has 8 × 201 × 384 = 617,472 values. norm1 reads x and writes h1: 2 × 617,472 × 4 bytes = 4.9 MB. RoPE reads q and k and writes qr and kr: 4 × 617,472 values. cos and sin are small: 196 × 64 values each, the same for all 8 images and all 6 heads. part_bytes counts 6 BTD for RoPE, so its estimate is 6 × 617,472 × 4 bytes = 14.8 MB. In B5, this RoPE takes 190.9 µs, so part_bytes / time is about 78 GB/s.

RoPE is the largest part without FLOPs. The Hugging Face function rotates only the patch tokens. It splits q and k into the prefix tokens and the patch tokens, rotates the patch tokens and joins the two pieces again:

# transformers 5.22.1, models/dinov3_vit/modeling_dinov3_vit.py (Apache-2.0)
q_prefix_tokens, q_patches = q.split((num_prefix_tokens, num_patches), dim=-2)
k_prefix_tokens, k_patches = k.split((num_prefix_tokens, num_patches), dim=-2)
q_patches = (q_patches * cos) + (rotate_half(q_patches) * sin)   # rotate_half: slice, negate, cat
k_patches = (k_patches * cos) + (rotate_half(k_patches) * sin)
q = torch.cat((q_prefix_tokens, q_patches), dim=-2)
k = torch.cat((k_prefix_tokens, k_patches), dim=-2)

For each of q and k, this is a chain of element-wise operations: two products, a negation and a concatenation in rotate_half, a sum and the concatenation with the prefix tokens. Each operation reads and writes the full tensor. Section 6.3 gives the measured cost.

5 How Step 3 measures time

5.1 One worker for each configuration

scripts/benchmark.py is the driver. For each configuration it does these actions:

  1. Read the machine state. Stop on battery power, in Low Power Mode or on a power adapter below 90 W.
  2. Compute the memory need and do the memory check. A configuration that does not fit gets a "skipped" line.
  3. Start one worker subprocess with the MPS watermarks 0.8 and 0.6.
  4. Write one JSON line with the result, the machine state and the versions.

The worker runs run_worker of src/dinov3_mlx/torch_bench.py. It loads the backbone, times the first batch, checks the validity of the first output, runs the warm-up batches and the timed batches, and reads the process footprint. Only one worker runs at a time. So the lifetime maximum of the footprint belongs to one configuration, and no other job uses the GPU.

5.2 Host to host: time_batch

A user of the backbone starts with pixels on the host and needs the output on the host. So time_batch times one batch from host to host (D3). The forward pass runs once for the two outputs. The copy of the frame embeddings and the copy of the patch embeddings have separate times, so one worker gives the throughput of both outputs.

t0 = time.perf_counter()
pixels = torch.from_numpy(batch).to("mps", mode.weights)    # stored fp32 pixels to the GPU
with _autocast(mode):                                       # autocast modes only
    tokens = model(pixel_values=pixels).last_hidden_state
torch.mps.synchronize()                                     # wait for the GPU
t1 = time.perf_counter()
frame = tokens[:, 0].cpu()                                  # frame embeddings, (B, D)
t2 = time.perf_counter()
patches = tokens[:, NUM_PREFIX_TOKENS:].cpu()               # patch embeddings, (B, N, D)
t3 = time.perf_counter()
return (t1 - t0, t2 - t0, (t1 - t0) + (t3 - t2)), frame, patches

summarize turns the batch times of one output into three numbers. The throughput is batch size × timed batches / sum of the batch times. The median and the p90 of the batch times give the latency. On unified memory the copy to the host is cheap. Over the 255 "done" lines of the 94 W results, the throughput of the patch embeddings is 0.994 to 1.006 times the throughput of the frame embedding (own count from results/baseline-torch-mps.jsonl). So Section 7 uses the frame embedding rows only.

5.4 The input batch and the validity check

make_batch fills a batch with the stored pixels of the 3 test images at the input resolution, in the order of TEST_IMAGES, again and again. Batch size 8 gives the images 0, 1, 2, 0, 1, 2, 0, 1. Every timed batch is the same array.

check_validity takes the frame embedding and the patch embeddings of image 0 of the first batch. The output is valid when all values are finite and the parity passes THRESHOLDS for the frame, the patch mean and the patch 1st percentile. A configuration with an output that is not valid still runs its timed batches. Its line has "valid": false and the reason, and it never becomes a baseline row. On 94 W, 12 lines are not valid, all with "non-finite output" (Surprise 5).

5.5 The block profile: time_part

A synchronize after each part costs about 170 µs on torch-mps. Some parts take less (docstring of block_profile.py). So profile_block does not time a part between two synchronizes. It runs block 1 once and keeps the input tensors of each part. Then time_part runs each part alone in a loop with one synchronize at the end:

def loop(n: int) -> float:
    _synchronize(device)
    start = time.perf_counter()
    for _ in range(n):
        fn()                         # the GPU queues n calls; the CPU does not wait
    _synchronize(device)             # one wait for all n calls
    return time.perf_counter() - start

n, elapsed = 1, loop(1)
while n < min_calls or elapsed < min_seconds:    # at least 20 calls and 0.5 s; also the warm-up
    n = max(min_calls, math.ceil(1.2 * n * min_seconds / max(elapsed, 1e-9)), n + 1)
    elapsed = loop(n)
return statistics.median(loop(n) / n for _ in range(loops))   # median of 5 loops

profile_block times the whole block, the parts outside the blocks (patch embedding, RoPE tables, final layer norm) and the forward pass the same way. It times the forward pass before and after the parts (finding F4). A change between the two shows that the Mac ran faster or slower during the profile.

Two checks guard the split. The sum of the 11 part times must be within 15 % of the block time: 16 of 16 configurations pass (0.926 to 1.065). L × block time + the parts outside the blocks must be within 15 % of the forward pass: 11 of 16 configurations pass. The 5 others have small kernels: ViT-S/16 at 224 px, batch size 1 in fp32 (1.611) and fp16-cast (1.690), ViT-S/16 fp16-cast at 224 px, batch size 8 (1.342) and at 512 px, batch size 1 (1.252), and ViT-H+/16 fp16-cast at 224 px, batch size 1 (1.170). Surprise 3 explains them.

6 The measured time share of each part

B5 profiles block 1 of ViT-S/16 and ViT-H+/16 in fp32 and fp16-cast, at 224 and 512 px and at batch size 1 and 8: 16 configurations. B5 uses fp16-cast, not the fp16 baseline row. In block 1 the largest token value is below 100 for both model sizes, so fp16-cast does not overflow there. MLX has no autocast, so a cast mode is the direct match for the fp16 and bf16 dtype modes of mlx in Step 5. Step 4 has only the fp32 dtype mode of mlx.

The time share of a part is its time divided by the sum of the 11 part times. The FLOP share is its share of the block FLOPs, without the patch embedding. Figure 3 puts the 11 parts into five groups. Tables 7 and 8 give each part.

8 Peak memory and the memory need

8.1 The process footprint

Peak memory is the lifetime maximum of the process footprint of the worker (D5). macOS charges the process footprint to one process. On unified memory it includes the GPU memory of torch-mps and mlx, so one measure serves both backends. read_footprint reads it with proc_pid_rusage, which fills the rusage_info_v4 struct of sys/resource.h:

info = _RusageInfoV4()                         # a 16-byte uuid, then 35 uint64 fields
if _libc.proc_pid_rusage(pid or os.getpid(), RUSAGE_INFO_V4, ctypes.byref(info)) != 0:
    raise OSError(ctypes.get_errno(), "proc_pid_rusage failed")
return Footprint(info.ri_phys_footprint, info.ri_lifetime_max_phys_footprint)

The footprint does not fall after torch.mps.empty_cache(). A test puts a 256 MB tensor on torch-mps and checks that the footprint grows by at least 230 MB. run_worker reads the footprint three times and records five memory values:

  • footprint_base_bytes: the footprint before the load (0.30 GB in the largest configurations).
  • load_peak_bytes: the lifetime maximum after the load.
  • peak_bytes: the lifetime maximum at the end. This is the peak memory of the results table.
  • run_peak_bytes: the peak memory when it is above the load peak, else null with the note "below the load peak" (14 lines on 94 W).
  • mps_driver_max_bytes: the largest torch.mps.driver_allocated_memory() after the warm-up and after each timed batch.

8.2 The memory need

The driver does the memory check before each worker. required_bench_bytes gives the need of one configuration:

need = load_bytes(weights)                    # 1.2 × weight bytes + 4 GB (Step 2)
     + B × T × (8 D + 3 F) × a                # tokens and feed-forward activations
     + 2 × B × heads × T² × a                 # attention scores and softmax
a = 2 bytes in cast mode, 4 bytes otherwise; activation factor 1.0

The attention term assumes that SDPA on torch-mps keeps the full score matrix and its softmax. This is the safe case. The build may raise the activation factor when a peak memory is above the need. It may never lower the factor alone.

9 Noise, the power adapter and the baseline row

9.1 The power adapter

The build and the first verifier runs ran on a 30 W USB-C power adapter (finding F11). system_profiler reported the adapter, and the battery charge fell from 10 % to 8 % while pmset reported "AC Power". An M5 Max draws much more than 30 W under GPU load, so it took the missing power from the battery. The machine state did not record the adapter, so no check caught it.

On the 96 W adapter of the Mac (it reports 94 W), the verifier measured all of Step 3 again (Section 14 of verify.html). The frame throughput of 94 W / 30 W for each B1 configuration has a median of 1.30 and a range of 0.89 to 3.47. 210 of 225 configurations are faster. By model size, the median ratio is 1.52 (ViT-S/16), 1.30 (ViT-S+/16), 1.29 (ViT-B/16), 1.27 (ViT-L/16) and 1.35 (ViT-H+/16). A speedup against the 30 W baseline would have been about 30 % too high.

The fix (commit a1e7d4e): the machine state now records adapter_watts and battery_percent, and check_machine_state refuses an adapter below MIN_ADAPTER_WATTS = 90 W. All 273 lines of the 94 W results record 94 W, with a battery charge of 22 to 89 %.

9.3 The baseline row (ADR 0004)

A speedup divides the throughput of mlx by the throughput of the baseline row. baseline_rows picks one baseline row for each model size, input resolution, batch size, output and dtype:

  1. Take the lines of the dtype modes of the dtype: fp32 → fp32; fp16 → fp16-cast and fp16-autocast; bf16 → bf16-cast and bf16-autocast. A compile row counts as its own configuration.
  2. Drop the lines that are not "done" and the lines with "valid": false.
  3. For each configuration, take the run with the median throughput of its runs: the main run, the repeats and the rounds. For an even number of runs, take the lower of the two middle runs.
  4. Take the configuration with the highest median throughput. The row names its dtype mode, "+ compile" for a compile row, and its number of runs.

Two decisions changed the first rule of the plan. Median of the runs: one run can be far off (F1), and the fastest run would depend on luck. Compile rows join the baseline: the user decided this on 2026-11-06, so that a speedup does not count a gain that torch.compile also gives. Only P1 and P2 have compile rows. So at P1 and P2 the baseline is compiled torch: 6 of the 135 baseline rows of each output are compile rows (fp32, fp16 and bf16 of P1 and P2). The other rows are eager torch, and most of them have 1 run. Step 6 therefore measures each speedup again with torch-mps and mlx runs in alternation in one session.

def _median_run(runs: list[dict], output: str) -> tuple[dict, int]:
    ordered = sorted(runs, key=lambda line: line[output]["throughput_ips"])
    return ordered[(len(ordered) - 1) // 2], len(ordered)   # lower middle run for an even count

10 The code of Step 3

Step 3 adds six modules to src/dinov3_mlx/ and adds names to three modules of Step 2: hub.py, memory.py and parity.py (Section 10.7). bench.py and flops.py do not import torch, so the mlx harness of Step 6 can use them without the memory of torch in its process footprint. A test checks this (test_bench_module_does_not_import_torch).

10.1 flops.py: FLOPs and bytes, pure Python

  • PART_NAMES: the 11 part names in the order of the forward pass (Table 2).
  • ModelShape: dim (D), blocks (L), heads, ff (F, the intermediate_size) and gated (True for SwiGLU). MODEL_SHAPES maps each model size to its shape (Table 3). A test compares it with the config.json of each model size.
  • tokens(side): T = 5 + (side / 16)², the prefix tokens plus the patch tokens.
  • part_flops(shape, batch_size, num_tokens): the FLOPs of each part. The six parts without FLOPs stay 0.
  • part_bytes(shape, batch_size, num_tokens, bytes_per_value): the approximate bytes that each part reads and writes, with the activations and the weight matrices (Table 2).
  • image_flops(shape, side): the FLOPs of one square image (patch embedding + L blocks) and the sdpa share. A test checks the values against Table 2 of explore.html within 0.5 %.

10.2 block_profile.py: the block profile

  • Part: one part of a block, with its name, its computation fn, and the names of its inputs and outputs in a state dict.
  • block_parts(layer): the 11 parts of one block with the Hugging Face modules and functions. It checks for gate_proj to choose between SwiGLU (two ff_in matrices, silu(gate) * up) and the MLP (one matrix, GELU).
  • run_parts(parts, state): runs the parts in order and returns a new state with every input and output.
  • time_part(fn, device, min_calls=20, min_seconds=0.5, loops=5): the median time of one call (Section 5.5).
  • profile_block(model, pixels, dtype_mode, **timing): the forward pass before the parts, the 11 parts, the whole block, the three parts outside the blocks and the forward pass after the parts. It returns the times and the number of blocks L.

11 Surprises

  1. The first baseline ran on a 30 W power adapter. pmset reported "AC Power", but the battery charge fell from 10 % to 8 % (F11). On the 94 W adapter, P2 fp32 gave 3.17, 3.97 and 3.46 img/s against 2.40 to 2.62 img/s, and P1 fp16-cast gave 811 to 847 img/s against 383 to 784 img/s (Table 16). Over all B1 configurations the median gain was 1.30 times. The adapter made the baseline too slow, but it is not the only cause of the noise. The driver now refuses an adapter below 90 W.
  2. One run is one sample. On 30 W, the throughput of one configuration changed by up to 2 times between runs (F1). P1 had five runs with a spread of 32.3 to 74.8 %, and only 15 of 45 ViT-S/16 configurations of the verifier re-run were within 5 % of the build (ratios 0.846 to 1.518). Inside one process, a forward pass changed from 2.38 to 4.99 ms within about one minute. On 94 W the largest ratio of the fastest to the slowest run is 1.3, but the fp32 rows still miss 5 %. The cause stays open. So the baseline row takes the median of the runs, and Step 6 measures each speedup in pairs.
  3. At batch size 1, a block alone is slower than a block inside the forward pass. For ViT-S/16 at 224 px, batch size 1, block 1 alone takes 0.36 ms (fp32) and 0.29 ms (fp16-cast), but forward pass / L is only 0.23 and 0.18 ms. The verifier tested this on 30 W (Section 6 of verify.html). The 12 blocks in sequence, the same work as in the forward pass, also took as long as 12 × block 1 alone (6.95 against 6.24 ms in fp32). All blocks, called on stored inputs without the patch embedding, took 25 to 32 % longer than the full forward pass, which does more work. The CPU time to issue the work was the same (2.9 to 3.6 ms). The effect needs small kernels: in the verifier test on 30 W, batch size 8 or 512 px gave 1.03. On 94 W the GPU is faster, so more configurations show the effect, for example ViT-S/16 fp16-cast at 224 px, batch size 8 (1.342). So the time shares of B5 are robust, but the absolute block time at batch size 1 is too high. Use forward pass / L for the time of one block (F4).
  4. RoPE has 0 FLOPs and takes up to 30.5 % of the block time. It takes 10.9 to 30.5 % of the block time of ViT-S/16 and 4.1 to 14.2 % of ViT-H+/16 (Table 10). part_bytes / time is only 15 to 90 GB/s: the Hugging Face chain runs 12 small kernels and moves about four times the bytes that part_bytes counts. fp16 makes it only 0.95 to 1.35 times faster. On 30 W, F9 found that RoPE was slower in fp16-cast than in fp32 for ViT-S/16 at 224 px, batch size 8 (250 against 208 µs). On 94 W this does not hold: 176 µs in fp16-cast against 191 µs in fp32. RoPE is a candidate for one fused kernel in Step 6.
  5. fp16-cast overflows for ViT-L/16 and for ViT-H+/16 at 224 px. The 12 lines that are not valid are exactly ViT-L/16 fp16-cast (9) and ViT-H+/16 fp16-cast at 224 px (3), all with "non-finite output". Their register values are above the fp16 maximum of 65,504 (Section 6 of docs/learn/02-tokens-and-outputs.html). So the fp16 baseline row there is fp16-autocast, which keeps fp32 weights and an fp32 residual stream. At batch sizes 8 and 32 it reaches 12.4 to 16.6 TFLOP/s, while bf16-cast reaches 15.3 to 20.5 TFLOP/s in the same configurations. The block profile can still use fp16-cast for ViT-H+/16 at 224 px, because block 1 has values below 100.
  6. The small frame copy costs as much as the large patch copy. The frame copy runs first and copies B × D values. The patch copy copies B × N × D values: 84 MB against 82 KB for ViT-H+/16 at 512 px, batch size 32 in fp16 (explore.html). Over the 255 "done" lines of 94 W, the frame copy has a median of 0.31 ms and the patch copy 0.39 ms. In 91 of 255 lines the median frame time is longer than the median patch time, by 0.67 % or less (on 30 W: 93 of 254 lines, 0.8 % or less). explore.html expected this order effect: the first copy can make the second copy a little faster. The effect is real but below 1 %. A copy costs mostly a fixed time, not a time for each byte. (Own count from results/baseline-torch-mps.jsonl.)
  7. torch.compile gives large gains at P1. Against the median of the three eager runs, the compile rows of P1 are 24.5 to 126.7 % faster, and those of P2 are 9.5 to 30.0 % faster. P1 fp16-cast goes from 820.7 to 1,860.0 img/s. 9 of 10 compile rows are more than 10 % faster; P2 fp32 is +9.5 %. The first call with compile took 1.0 to 3.2 s on 94 W (4.3 to 12.7 s on 30 W), because the compile cache on disk was warm. The gain is largest where small kernels dominate. Step 3 did not profile the compiled graph. A likely cause is that torch.compile joins small element-wise operations into fewer kernels.
  8. Batch size 32 is mostly slower than batch size 8. The throughput ratio is 0.79 to 0.93 for most configurations, and 0.69 for ViT-S/16 at 224 px in fp16. Only five configurations gain, four of them by 10 % or more. Step 3 did not look for the cause.
  9. A batch has a fixed cost of about 5 ms. ViT-S/16 at 224 px, batch size 1 needs about 8 ms for each batch in fp32 and in fp16. The same forward pass takes 2.13 to 2.75 ms in a loop without a synchronize between the calls (Table 13). The cost is in the device time, not in the copy to the host.
  10. The memory need is 1.6 to 7.3 times the peak memory. The need formula assumes two full score matrices. For ViT-H+/16 at 512 px, batch size 32, fp32, the score term alone (5.42 GB) is larger than the measured growth above the load peak (4.51 GB). The formula is safe, but it skips configurations that fit. On 30 W, the verifier ran the one skipped configuration: it fitted with a peak memory of 8.70 GB against a need of 16.83 GB (F3).
