1 Why this explainer

Step 5 extends the MLX backbone to all six model sizes. Three model sizes use SwiGLU as their feed-forward network: ViT-S+/16, ViT-H+/16 and ViT-7B/16. The other three use the MLP of 04-5. Step 4 stopped at SwiGLU with a NotImplementedError (04-5, Section 8). Step 5 adds the class SwiGLU. It gives the MLP and SwiGLU the same three methods. It also extends the key map, so that map_key accepts gate_proj.

This page covers the functions of row 05-1-swiglu.html in Table 1 of specs/05-all-sizes/plan.html. Table 1 below lists them. Each section quotes the code with its line numbers. The line numbers are those of the working tree after the fixes of the Verify stage (Sections 9 and 10 of specs/05-all-sizes/verify.html). The fixes did not change mlx_model.py, so its line numbers equal commit 01cc631. In mlx_weights.py the fixes added one line to the module docstring (F4), so each line number after the docstring is 1 higher than in commit 01cc631. For example, block_parameter_names starts at line 79 here and at line 78 in 01cc631. Some comments in the quotes are annotations of this page.

The agent that wrote this page ran no test, no model and no GPU work. It computed the FLOP counts with flops.py of Step 3 on the CPU. It took all other values from the files of Section 10.

The result in three numbers:

  • SwiGLU matches DINOv3ViTGatedMLP within 9.1e-6 (small model vits16plus) and 5.5e-6 (small model vit7b16-shape). The target is 2e-5.
  • In fp16 and bf16 the activation computes in fp32 and rounds once. For SwiGLU, and for GELU at x ≥ −2.5, at most 0.082 % of the T23 values then differ from the float64 value rounded once, each by at most 1 unit in the last place. At x < −2.5 the GELU output equals nn.gelu in fp32, rounded once (Section 6). The MLX activation in the half dtype differs in 32 to 36 % of the values.
  • ViT-S+/16 and ViT-H+/16 pass the parity tests on mlx in all five dtype modes. In fp16-cast, 6 configurations of ViT-H+/16 are expected failures (fp16 overflow). ViT-7B/16 passes 48 of 48 configurations (4 rows of 12) in the four half modes against its streamed fp32 reference (path D4-Y). Its fp32 rows on mlx skip by the run rule.

2 SwiGLU in one picture

Figure 1 shows the feed-forward branch of one SwiGLU block. The input x2 is the residual stream after the attention branch. Block.ff_hidden runs norm2, casts the result to the matmul dtype and calls SwiGLU.hidden. SwiGLU.hidden runs the two input matmuls and calls SwiGLU.activation. Then Block.__call__ runs down_proj, LayerScale and the residual add.

3 Only gate_proj gets the activation

SwiGLU has three matrices. Two of them read the same input x. Only the output of gate_proj goes through the activation SiLU. The output of up_proj stays linear. An element-wise product joins the two paths:

gate = gate_proj(x)                    # (B, T, FF)
up   = up_proj(x)                      # (B, T, FF)
hidden = silu(gate) · up               # the feed-forward hidden values, (B, T, FF)
out  = down_proj(hidden)               # (B, T, D)

silu(z) = z · σ(z),   σ(z) = 1 / (1 + e^(−z))

Hugging Face writes the same formula in one line (DINOv3ViTGatedMLP.forward, lines 378 to 380 of modeling_dinov3_vit.py, transformers 5.22.1):

down_proj = self.down_proj(self.act_fn(self.gate_proj(x)) * self.up_proj(x))

act_fn is ACT2FN[config.hidden_act]. The config.json of ViT-S+/16, ViT-H+/16 and ViT-7B/16 sets hidden_act to "silu" and use_gated_mlp to true. The official DINOv3 code computes F.silu(x1) * x2 with x1 = w1(x) and x2 = w2(x) (SwiGLUFFN in dinov3/layers/ffn_layers.py). So the Meta name w1 is gate_proj, w2 is up_proj and w3 is down_proj. scripts/convert_meta_checkpoint.py maps the names in this way (lines 122 to 124).

Three facts follow:

  • The order of gate and up is part of the function. silu(up_proj(x)) · gate_proj(x) has the same shapes but other values. gate_proj and up_proj have the same shape, so the strict load cannot see a swap. Only a comparison of values can see it: the part test T17 compares SwiGLU with DINOv3ViTGatedMLP, whose gate_proj and up_proj have different random weights.
  • The hidden values can be large. The exact GELU of the MLP is never larger in magnitude than its input. In SwiGLU, two linear outputs multiply. For large positive gate values, silu(gate) · up is about gate · up. Section 8 gives the largest measured feed-forward hidden values: 7,257 for ViT-S+/16, against 300 for ViT-S/16 with the same embedding dimension (Table 8).
  • SiLU in MLX and in torch agree in fp32. The part test T18 compares nn.silu with ACT2FN["silu"] on 200,001 values in [−8, 8]. The largest difference is 9.5e-7. The target is 4e-6, four units in the last place at 8.

4 The hidden width: the 2/3 rule

The hidden width FF is intermediate_size in config.json. MlxConfig.from_hf reads it into ff (line 134). The port uses no formula for FF. But the values in the configs come from a rule in the official code, and this rule gives a surprise.

The official block computes a width from the Meta ratio ffn_ratio: int(dim * ffn_ratio) (SelfAttentionBlock in dinov3/layers/block.py). SwiGLUFFN then keeps 2/3 of this width and rounds it up to a multiple of align_to:

# official DINOv3 code, dinov3/layers/ffn_layers.py, SwiGLUFFN.__init__
d = int(hidden_features * 2 / 3)
swiglu_hidden_features = d + (-d % align_to)

Shazeer (2020) uses this factor 2/3 for the GLU variants. With 2/3 of the width, three matrices have the same number of weights as the two matrices of an MLP with the full width. The hub functions of the official code set ffn_ratio 6 for ViT-S+/16 and ViT-H+/16, but 3 for ViT-7B/16. So FF is 4 D for ViT-S+/16 and ViT-H+/16, but only 2 D for ViT-7B/16 (Figure 2).

5 The code

5.1 SwiGLU

# src/dinov3_apple/mlx_model.py, lines 349 to 372
class SwiGLU(nn.Module):
    """The feed-forward network of ViT-S+/16, ViT-H+/16 and ViT-7B/16 (D1 of
    specs/05-all-sizes/explore.html). Three nn.Linear modules with the Hugging Face names."""

    def __init__(self, config: MlxConfig) -> None:
        super().__init__()
        if config.hidden_act != "silu":                                          # line 355
            raise NotImplementedError(f"activation {config.hidden_act!r} of SwiGLU")
        self.gate_proj = nn.Linear(config.dim, config.ff, bias=config.mlp_bias)  # D -> FF
        self.up_proj = nn.Linear(config.dim, config.ff, bias=config.mlp_bias)    # D -> FF
        self.down_proj = nn.Linear(config.ff, config.dim, bias=config.mlp_bias)  # FF -> D

    def activation(self, gate: mx.array, up: mx.array) -> mx.array:
        """Return silu(gate) · up. It computes in fp32 and rounds once to the dtype of gate."""
        product = nn.silu(gate.astype(mx.float32)) * up.astype(mx.float32)     # line 363
        return product.astype(gate.dtype)                                       # the one rounding

    def hidden(self, x: mx.array) -> mx.array:
        """Return the feed-forward hidden values silu(gate_proj(x)) · up_proj(x)."""
        return self.activation(self.gate_proj(x), self.up_proj(x))

    def __call__(self, x: mx.array) -> mx.array:
        """Return down_proj(silu(gate_proj(x)) · up_proj(x)), as DINOv3ViTGatedMLP."""
        return self.down_proj(self.hidden(x))
  • Three separate nn.Linear modules (D1, Option A of explore.html). The attribute names are the Hugging Face names. So the key map stays the identity, and load_weights(strict=True) checks each name and each shape. A fused matmul of gate and up (Option B) is a Step 6 question. With separate modules, nn.quantize of Step 6 and the adapters of Step 8 find each matrix by its own name.
  • Line 355. SwiGLU accepts only "silu". MLP accepts only "gelu" (line 326). So a config with the wrong pair stops with NotImplementedError. T6 checks both directions: a gated config with "gelu" and an MLP config with "silu".
  • Lines 357 to 359. config.mlp_bias is true for all six model sizes. ViT-7B/16 has no q, k and v biases, but it has the feed-forward biases. Each SwiGLU block of ViT-S+/16 and ViT-H+/16 has 13 parameters in the matmul dtype; each block of ViT-7B/16 has 11 (Table 4 of the plan).
  • Lines 363 and 364. The activation casts gate and up to fp32, computes the SiLU and the product in fp32 and rounds once. Section 6 explains why. The method takes two arguments, so the part test can feed it the gate and up values of the Hugging Face block: block_parts of Step 3 gives the part activation the inputs (gate, up) when the module has gate_proj.
  • hidden and __call__. hidden gives one tensor: the feed-forward hidden values. The token range of Step 5 and the adapters of Step 8b use this tensor (Section 3.2 of the plan). __call__ exists for the part test T17. The backbone does not call it (Section 5.3).

5.2 MLP.activation and MLP.hidden

The MLP of Step 4 gets the same three methods. Its formula does not change.

# src/dinov3_apple/mlx_model.py, lines 331 to 346 (class MLP)
    def activation(self, up: mx.array) -> mx.array:
        """Return gelu(up). It computes in fp32 and rounds once to the dtype of up.

        nn.gelu is the erf form, not nn.gelu_approx. In half precision the MLX activations round
        after each operation (Table 8 of specs/05-all-sizes/explore.html). In fp32 the casts do
        nothing.
        """
        return nn.gelu(up.astype(mx.float32)).astype(up.dtype)                 # line 338

    def hidden(self, x: mx.array) -> mx.array:
        """Return the feed-forward hidden values gelu(up_proj(x))."""
        return self.activation(self.up_proj(x))

    def __call__(self, x: mx.array) -> mx.array:
        """Return down_proj(gelu(up_proj(x))), as DINOv3ViTMLP."""
        return self.down_proj(self.hidden(x))
  • Line 338. In Step 4, MLP.__call__ called nn.gelu(self.up_proj(x)) directly. Now the GELU computes in fp32 and rounds once, as the SiLU of SwiGLU does. In fp32 mode both casts keep the dtype. The part test of the activation gives 7.2e-7 for vits16, the same value as in Step 4 (04-5, Table 5).
  • The same interface. MLP and SwiGLU both have activation, hidden, __call__ and down_proj. Block uses only hidden and down_proj, so it needs no branch on the type of its feed-forward network. Only activation differs: one argument for the MLP, two for SwiGLU.

6 One rounding in half precision

In fp16 and bf16, the MLX activations round after each operation (finding 6 of explore.html). nn.silu(x) is x * mx.sigmoid(x): two operations. nn.gelu(x) is x * (1 + mx.erf(x / math.sqrt(2))) / 2: five operations (mlx/nn/layers/activations.py, MLX 0.32.4). The SwiGLU product with up adds one more. With half inputs, each of these operations gives a half result. Figure 3 counts the roundings.

The MLX agent of the Explore stage measured the effect of the extra roundings on 100,001 evenly spaced points in [−8, 8] (Table 3). The reference is "compute in fp32, then round once".

On the 33,282 finite bf16 values in [−8, 8], the bf16 shares are only 3.7 % (silu) and 3.0 % (gelu); the largest differences stay the same. The bf16 parity thresholds have a headroom of only 1.04 to 1.29 (finding F2 of specs/02-reference/verify.html). So extra roundings can move a bf16 row below its threshold.

So the Step 5 methods compute in fp32 and round once (D2 of explore.html). The test T23 test_mlx_activation_rounds_once checks this for both networks in fp16 and in bf16:

  • Input. 100,001 evenly spaced values in [−8, 8], rounded to the half dtype. For SwiGLU, gate is these values and up is the same values in reverse order.
  • Oracle. The float64 function of the same half values, rounded once to the half dtype by torch.
  • The GELU tail. At x < −2.5, the sum 1 + erf(x / √2) cancels in fp32: erf is near −1, so the sum loses digits. Then even a correct fp32 GELU differs from the float64 oracle. A NumPy emulation of the plan gives 7.3 % of the fp16 values (all at x ≤ −2.95) and 21.2 % of the bf16 values (all at x ≤ −4.44), and 0 differences at x ≥ −2.5. So at x < −2.5 the oracle is nn.gelu on the fp32 values, rounded once. There the test asks for exact equality.
  • Targets. At most 0.1 % of the values differ, and each by at most 1 unit in the last place of the half dtype. A second assertion shows that the activation in the half dtype misses this target, so the test can see a regression.

7 The key map for gate_proj

The key map maps each Hugging Face tensor name to the MLX parameter name. A block name passes only if its part after layer.{i}. is a parameter name of the MLX block. In Step 4, block_parameter_names built one probe block without a gate. So map_key raised UnknownWeightError for layer.{i}.mlp.gate_proj.weight (04-5, Section 8). Step 5 takes the union of two probe blocks (D1 of explore.html).

# src/dinov3_apple/mlx_weights.py, lines 79 to 109 (the config values abbreviated)
@cache
def block_parameter_names() -> frozenset[str]:
    """Return the parameter names of an MLP block and of a SwiGLU block, both with all biases.

    The union has 20 names. The names come from the Block module itself, so the key map and the
    module cannot differ. map_key stays without the config; load_weights(strict=True) stops a
    gate_proj key of an MLP model size. The probe blocks have a small width. Their arrays stay
    lazy and are never computed; their random init advances the global key of mx.random.
    """
    mlp = MlxConfig(dim=8, heads=1, blocks=1, ff=8, ..., mlp_bias=True, gated=False, hidden_act="gelu")
    gated = dataclasses.replace(mlp, gated=True, hidden_act="silu")              # line 106
    return frozenset(
        name for config in (mlp, gated) for name, _ in tree_flatten(Block(config).parameters())
    )

# lines 134 and 135 (map_key)
    if (match := BLOCK_KEY.fullmatch(name)) and match.group("parameter") in block_parameter_names():
        return match.group(1)                                                     # layer.{i}.{parameter}
  • Why a union and not the config. explore.html compared three ways: the union of two probe blocks, a probe from the config of the model size, and a fixed list. A probe from the config would give map_key a config argument. A fixed list can differ from the module. The union keeps map_key without the config, and the strict load still stops a gate_proj key of an MLP model size.
  • Line 106. The SwiGLU probe is the MLP probe with gated=True and "silu". The pair must be valid: Block raises NotImplementedError for a gated config with "gelu".
  • All biases. Both probes set every bias flag to true. So the union also has attention.k_proj.bias, although no model size has a bias on k_proj. map_key asks only whether the probe has a name. It does not ask for every name of the probe. So ViT-7B/16, without q, k and v biases, needs no special code.
  • @cache. The function builds the two probe blocks once per process. Their random init advances the global key of mx.random at the first call.

9 Surprises

  1. Only gate_proj gets the activation. up_proj has the same shape and the same input, but its output stays linear. The strict load cannot see a swap of the two weights; only a comparison of values can (T17 and the parity tests).
  2. FF is 4 D for ViT-S+/16 and ViT-H+/16, but 2 D for ViT-7B/16. SwiGLU keeps 2/3 of the Meta width. The Meta ratio is 6 for ViT-S+/16 and ViT-H+/16, but 3 for ViT-7B/16. So the feed-forward network of ViT-7B/16 has 60.0 % of the block weights, less than the 66.6 % of an MLP block. ViT-S+/16 and ViT-H+/16 have 74.9 % and 75.0 %.
  3. The MLX activations round after each operation in half precision. nn.gelu has five operations and nn.silu two, plus the product with up. In the half dtype 21 to 35 % of the values differ from one rounding (Table 3). The port computes the activation in fp32 and rounds once. Then, for SwiGLU and for GELU at x ≥ −2.5, at most 0.082 % of the T23 values differ from the float64 value rounded once, each by at most 1 unit in the last place. At x < −2.5 the GELU output equals nn.gelu in fp32, rounded once.
  4. A correct fp32 GELU is not correct at x < −2.5. The sum 1 + erf cancels in fp32. So T23 cannot use the float64 oracle there. It uses nn.gelu in fp32, rounded once, and asks for exact equality.
  5. The T23 target holds only for its own input grid. 1,000,000 values from N(0, 3²) give 0.117 % for GELU in fp16, above the 0.1 % of T23.
  6. The SwiGLU hidden values are 24 times those of the MLP at the same embedding dimension. ViT-S+/16 reaches 7,257.1, ViT-S/16 only 300.1 (Table 8). Two linear outputs multiply. The finite values stay at 11.1 % of the fp16 maximum or less.
  7. The backbone does not call SwiGLU.__call__. Block.__call__ calls ff_hidden and mlp.down_proj. Only the part tests call MLP.__call__ and SwiGLU.__call__. So the token range sees the hidden values with the same calls as the forward pass.
  8. map_key accepts gate_proj for every model size. It does not know the config. The strict load stops a gate_proj key of an MLP model size (T3). The union also holds attention.k_proj.bias, a name that no model size has.
  9. The official block gives nn.GELU to SwiGLU. SelfAttentionBlock passes act_layer=nn.GELU to each feed-forward layer. SwiGLUFFN accepts the argument, does not use it and calls F.silu. config.json correctly says "silu".
  10. The smallest parity margin of Step 5 is a SwiGLU row. ViT-S+/16 in bf16-autocast uses 97.3 % of its patch-mean budget on mlx. torch-mps gives about the same value, 0.995177 against 0.995136.
