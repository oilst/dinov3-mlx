1 Why this explainer

DINOv3 has no learned position embedding. RoPE gives each patch token its position. Each block rotates the queries and the keys of the patch tokens by angles that come from the 2D position of the patch. The tensor v does not rotate. The prefix tokens do not rotate.

Step 4 ported ViT-S/16 to MLX (commit c212226). This page explains the RoPE part of the port. It covers four functions of src/dinov3_apple/mlx_model.py and two attributes of MlxBackbone (Table 1). Each section quotes the code with its line numbers. The line numbers are those of commit ea82d58, which fixed the findings of the verification. That commit did not change the RoPE code, but it added 2 lines to the docstring of Embeddings.__call__. So each line after this docstring moved down by 2. The RoPE functions come before it and kept their line numbers. Some comments in the quotes are annotations of this page. Section 12 gives the measured results.

The result in three numbers:

  • The MLX RoPE tables differ from the Hugging Face tables by at most 1.2e-7 on all six patch grids (acceptance criterion AC5, target 1e-6).
  • The rotation is bit-equal to the Hugging Face rotation: the part test rope gives a difference of 0.
  • The Meta tables differ from the Hugging Face tables by up to 0.0083 rad, because the Meta checkpoint stores the periods in bf16 (AC6, report only).

2 RoPE in one picture

Figure 1 shows the path at 224 × 224 px. The input resolution gives the patch grid: 224 / 16 = 14 rows and 14 columns. MlxBackbone.rope looks up the grid in the cache. On the first call for a grid, rope_tables makes the two tables in NumPy. Each table has 5 + 196 = 201 rows and 64 columns: one row for each token and one column for each value of a head. All 12 blocks use the same two tables. In each block, apply_rope rotates q and k. The tables broadcast over the batch and over the 6 heads.

The backbone finds the patch grid from the shape of the pixels and gets the tables once for the whole forward pass:

# src/dinov3_apple/mlx_model.py, lines 345–349 (MlxBackbone.__call__)
x = self.embeddings(pixels)
p = self.config.patch_size
cos, sin = self.rope(pixels.shape[2] // p, pixels.shape[3] // p)   # (H // 16, W // 16)
for block in self.layer:
    x = block(x, cos, sin)                                          # the same tables in every block

# line 266 (Attention.__call__)
q, k = apply_rope(q, cos, sin), apply_rope(k, cos, sin)             # v is not rotated

3 Patch-center coordinates: y, then x

RoPE puts the patch grid into a box from −1 to 1 on each axis. Each patch gets the coordinates of its center:

  • Row i of Hp rows: y = (2i + 1) / Hp − 1.
  • Column j of Wp columns: x = (2j + 1) / Wp − 1.

At 224 px, the 14 centers of an axis are at −13/14, −11/14, …, 13/14. The spacing is 2/14 = 0.143. No center is at −1 or at 1. On a grid with an even number of rows, no center is at 0. Each axis has its own scale: a 224 × 304 px input has 14 rows and 19 columns, and both axes still span the full box (Figure 2, middle). The Meta code calls this "separate" normalization. So the angles depend on the relative position of a patch in the image, not on its position in pixels. A patch near the image center has a coordinate near 0 at 224 px and at 512 px.

The order is y, then x. Token n = 5 + Wp · i + j gets the pair (yi, xj). This is the row-major order of the patch embedding (04-1).

# src/dinov3_apple/mlx_model.py, lines 139–142 (rope_tables)
coord_h = np.arange(0.5, grid_h, dtype=np.float32) / grid_h    # (i + 0.5) / Hp, in (0, 1)
coord_w = np.arange(0.5, grid_w, dtype=np.float32) / grid_w    # (j + 0.5) / Wp
coords = np.stack(np.meshgrid(coord_h, coord_w, indexing="ij"), axis=-1).reshape(-1, 2)  # (N, 2), row-major
coords = 2.0 * coords - 1.0  # (N, 2): y, x in [-1, 1]

indexing="ij" makes the row index the slow index. So row n of coords belongs to token 5 + n, and column 0 holds y. Table 2 gives the six patch grids of the parity tests.

4 Sixteen frequencies from base 100

One head of ViT-S/16 has 64 values. RoPE rotates them in 32 pairs. Each axis gets 16 pairs. Pair k of an axis has the frequency fk = 100−k/16, for k = 0 to 15. Its period is pk = 1 / fk = 100k/16, from 1 to 75. The angle of the pair is θ = 2π · c · fk, with c the y or the x coordinate of the patch. The base 100 is rope_theta in config.json. All six model sizes use 100.

# src/dinov3_apple/mlx_model.py, line 138 and lines 143–144 (rope_tables)
inv_freq = 1 / theta ** np.arange(0, 1, 4 / head_dim, dtype=np.float32)  # 100^(-k/16): 16 frequencies for head_dim 64
angles = (2 * np.pi * coords[:, :, None] * inv_freq[None, None, :]).reshape(len(coords), -1)
                                                                       # (N, 2, 16) -> (N, 32): 16 y angles, then 16 x angles
angles = np.tile(angles, 2)                                            # (N, 64): column d and column d + 32 hold the same angle
  • np.arange(0, 1, 4 / 64) gives the 16 exponents 0, 0.0625, …, 0.9375, so k/16. For ViT-7B/16 (head dimension 128), the same line gives 32 frequencies.
  • The reshape puts the 16 y angles of a token first and its 16 x angles second.
  • The tile doubles the 32 angles to 64 columns. Section 5 shows why.

The operations and their order follow DINOv3ViTRopePositionEmbedding of Hugging Face, in fp32. NumPy 2 keeps a Python float "weak" (NEP 50): 2.0 * coords and 2 * np.pi * coords stay fp32. A float64 computation with a cast to fp32 at the end (variant C2 of explore.html) differs from the fp32 order (variant C1) by up to 5.4e-7. The reference output uses the fp32 order, so the port uses it too (decision D3).

The fastest pair (k = 0) has a period of 1, half the width of the box. At 224 px its angle goes from −5.83 to 5.83 rad, 1.86 turns. Two patches 7 rows apart have a coordinate difference of exactly 1, so they get the same angle in this pair. The slower pairs tell them apart. The slowest pair (k = 15) turns by only 0.025 of a turn across the box. Its angle changes little inside one image.

5 The half-split layout and rotate_half

RoPE rotates pairs of values. In the half-split layout, value d pairs with value d + 32. Pairs 0 to 15 (values 0–15 with values 32–47) rotate by the y angles. Pairs 16 to 31 (values 16–31 with values 48–63) rotate by the x angles. Figure 3 shows the layout. The other common layout, the interleaved layout, pairs value 2d with value 2d + 1. The DINOv3 weights expect the half-split layout. The interleaved layout has the same shapes, so it gives wrong attention scores and no error.

# src/dinov3_apple/mlx_model.py, lines 149–152
def rotate_half(x: mx.array) -> mx.array:
    """Return (-x2, x1) for the halves x1 and x2 of the last axis (the half-split layout)."""
    half = x.shape[-1] // 2                                         # 32 for head_dim 64
    return mx.concatenate([-x[..., half:], x[..., :half]], axis=-1)

# lines 169–170 (apply_rope)
xf = x.astype(mx.float32)
return (xf * cos + rotate_half(xf) * sin).astype(x.dtype)

Why the rotation encodes the position: after the rotation, the score q · k of two tokens depends, for each pair, on the angle difference θq − θk. The angle difference depends only on the coordinate difference of the two patches. So RoPE gives the attention the relative position of two patches, separately for y and for x (RoFormer, Section 3).

6 Identity rows for the prefix tokens

The sequence has 5 prefix tokens in front of the patch tokens: the CLS token and the 4 register tokens. RoPE must not rotate them. Hugging Face splits q and k, rotates the patch tokens and joins the two pieces again:

# transformers 5.22.1, models/dinov3_vit/modeling_dinov3_vit.py, apply_rotary_pos_emb (Apache-2.0), shortened
q_prefix_tokens, q_patches = q.split((num_prefix_tokens, num_patches), dim=-2)
q_patches = (q_patches * cos) + (rotate_half(q_patches) * sin)
q = torch.cat((q_prefix_tokens, q_patches), dim=-2)                 # the same three lines for k

The MLX port puts 5 identity rows on top of the tables: cos 1 and sin 0. Then apply_rope gives x · 1 + rotate_half(x) · 0 = x for each prefix token. The result is exact for finite values, because a product with 1 and a sum with 0 do not round.

# src/dinov3_apple/mlx_model.py, lines 145–146 (rope_tables)
prefix = np.ones((NUM_PREFIX_TOKENS, head_dim), np.float32)        # NUM_PREFIX_TOKENS = 5 (outputs.py)
return np.concatenate([prefix, np.cos(angles)]), np.concatenate([0 * prefix, np.sin(angles)])
  • The port has no split and no join. The rotation is one expression on all 5 + N rows.
  • The extra work is 5 rows: 2.5 % of 201 rows at 224 px, 0.5 % of 1,029 rows at 512 px.
  • The Hugging Face tables have N rows; the MLX tables have 5 + N rows. The part test rope therefore gives the MLX code the Hugging Face tables plus 5 identity rows. So it tests the rotation alone (tests/test_mlx_parts.py, _rope_tables).

The MLX rotation is still a chain of element-wise operations: a negation, a concatenation, two products and a sum, plus the two casts. Without mx.compile, each operation reads and writes a full q or k tensor. On torch-mps, Step 3 measured RoPE at 15.0 % of the block time of ViT-S/16 in fp32 at 224 px, batch size 8. In fp16-cast, the RoPE share went up to 30.5 % (Table 10 of 03-where-the-compute-goes.html). Step 4 did not time RoPE on mlx. Step 6 profiles the mlx block and can fuse the chain.

7 Why mx.fast.rope cannot do it in one call

MLX has a fused RoPE kernel, mx.fast.rope. explore.html checked it against the needs of DINOv3 (Table 6 there). Table 4 gives the result.

An exact workaround exists. It puts each patch token in its own batch entry (axis 0) with T = 1. A vector offset then gives each token its own integer offset m = 2i + 1 − Hp. The workaround uses freqs = Hp · pk / 2π. Then the angle is m / freqs = 2π · ((2i + 1)/Hp − 1) / pk. The workaround needs one call for the y pairs and one call for the x pairs, plus gathers, transposes and a join. Only the CPU stream checked it (largest error 3e-7). Step 4 uses the tables instead (decision D3). This confirms risk R5 of docs/plan.html. If the mlx block profile of Step 6 shows a large RoPE share, Step 6 can try the two-call form.

8 The rotation in fp32

apply_rope casts x to fp32, rotates it with the fp32 tables and casts the result back to the dtype of x (lines 169–170, Section 5). In Step 4 the only dtype mode of mlx is fp32, so both casts change no value. They prepare Step 5, which adds fp16 and bf16. The three codes treat the dtype in three ways:

Table 5. Dtypes of RoPE in the two official codes and in the port. The port follows the Meta code. In fp32 all three give the same dtypes.

  • In MLX, a bf16 array times an fp32 array gives fp32. Without the last cast, the fp32 tables would turn q and k into fp32, and the attention would run in fp32. .astype(x.dtype) keeps the dtype of the dtype mode.
  • In bf16-cast mode, Hugging Face rotates in bf16 and the port rotates in fp32. The reference output is fp32, so the fp32 rotation is closer to it. Step 5 measures the effect on parity.
  • The tables stay fp32 in every dtype mode. They are not parameters, so set_dtype does not cast them (Section 9).

9 The cache by patch grid

# src/dinov3_apple/mlx_model.py, line 333 (MlxBackbone.__init__) and lines 336–341
self._rope_cache: dict[tuple[int, int], tuple[mx.array, mx.array]] = {}

def rope(self, grid_h: int, grid_w: int) -> tuple[mx.array, mx.array]:
    """Return the RoPE tables (cos, sin) of one patch grid, from the cache."""
    if (grid_h, grid_w) not in self._rope_cache:                   # first call for this grid
        cos, sin = rope_tables(grid_h, grid_w, self.config.head_dim, self.config.rope_theta)
        self._rope_cache[(grid_h, grid_w)] = (mx.array(cos), mx.array(sin))
    return self._rope_cache[(grid_h, grid_w)]
  • The key is the patch grid (Hp, Wp), not the input resolution and not the batch size. A batch of 8 and a batch of 1 at 224 px use the same entry.
  • The first forward pass for a grid calls rope_tables on the CPU and converts the two NumPy arrays to mx.array. Later forward passes for the grid reuse the arrays.
  • The 12 configurations of the parity tests have 6 patch grids. So the cache holds at most 6 entries, 1.49 MB in all (Table 2). The cache has no size limit. A video at one input resolution uses one entry.
  • The attribute name starts with "_". MLX does not treat such an attribute as a parameter. So load_weights(strict=True), set_dtype and nn.quantize do not see the tables. T19 checks it: after a forward pass, the small model still has 40 parameters (2 blocks × 17 + 4 + 2).
  • The tables enter each block as inputs, not as constants. So mx.compile in Step 6 can take them as inputs of the compiled function.

Hugging Face caches less. An lru_cache with 32 entries keeps the patch-center coordinates (get_patches_center_coordinates). Hugging Face computes the angles, cos and sin again in every forward pass.

10 Two official tables: Hugging Face and Meta

Two official codes make the RoPE tables, and they do not agree:

  • Hugging Face computes the frequencies 100−k/16 in fp32 in the code. The frequencies are a buffer of the module, not part of the weights file. The key map raises UnknownWeightError for rope_embeddings.inv_freq (test T1).
  • The Meta code keeps the periods 100k/16 in the Meta checkpoint (rope_embed.periods). The checkpoint stores them in bf16, with 8 significant bits. bf16 rounds the Meta periods, for example 1.33352 to 1.33594 (k = 1). The Meta code then divides by the rounded periods in fp32: θ = 2π · c / pbf16.

The angle difference for one pair is 2π · |c| · |1/pbf16 − 1/pk|. The relative rounding error of a period is at most 1.91e-3 for every k (the bf16 bound is 2−9 = 1.95e-3). The angle difference also grows with the frequency, so it is largest for the fast pairs. Figure 4 shows the difference for c = 1. The periods 1 (k = 0) and 10 (k = 8) are exact in bf16.

The largest |c| of a grid is (n − 1)/n on its longer axis (Table 2). So the largest angle difference grows with the grid, from 0.00791 rad at 14 × 14 to 0.00825 rad at 32 × 32. T9 measured these angle differences (Table 6). A target of 1e-6 against the Meta tables must fail: the cos difference is up to 0.0082.

Its angles differ from the Hugging Face angles by up to 0.0079 rad at 224 px and 0.0083 rad at 512 px.

11 RoPE-box jittering: training only

In training, DINOv3 changes the RoPE coordinates at random: RoPE-box jittering. In the Hugging Face config of all six model sizes, pos_embed_rescale is 2.0, and pos_embed_jitter and pos_embed_shift are None. With rescale 2.0, each forward pass multiplies all coordinates by one random factor s, log-uniform between 1/2 and 2. The box becomes [−s, s]. Hugging Face applies it only in train mode:

# transformers 5.22.1, DINOv3ViTRopePositionEmbedding.forward (Apache-2.0), shortened
patch_coords = get_patches_center_coordinates(num_patches_h, num_patches_w, dtype=torch.float32, device=device)
if self.training:
    patch_coords = augment_patches_center_coordinates(patch_coords, shift=..., jitter=..., rescale=...)
  • The reference output comes from eval mode, without jittering. The small model of the part tests also runs in eval mode (tests/small_model.py).
  • Step 4 leaves RoPE-box jittering out. MlxBackbone has the flag rope_box_jitter = False (line 334). No code reads it yet.
  • The flag is separate from the train mode of nn.Module. A call of model.train() in MLX does not turn on jittering. In Hugging Face, model.train() does turn it on.
  • Step 8 decides if LoRA fine-tuning uses it (risk R17 of explore.html). With jittering on, the tables change in each iteration, so the cache by patch grid cannot hold them. The factor s multiplies the coordinates before the angles: between line 142 and line 143 of rope_tables.

The paired ratio is the throughput of mlx divided by the throughput of torch-mps in the same round, median of 3 rounds; RoPE is one part of it.

The table difference is 1 or 2 units in the last place of fp32 (1.19e-7 is one unit at 1.0). The operations and their order are the same as in Hugging Face. So the probable cause is the fp32 power, cos and sin functions of NumPy and torch. These functions can round differently. We did not find which function differs. The rotation has no such function: the same products and sums in the same order give the same bits.

13 Surprises

  1. Two official RoPE tables exist. The Meta checkpoint stores the periods in bf16. Its angles differ from the Hugging Face angles by up to 0.0079 rad at 224 px and 0.0083 rad at 512 px. The largest difference comes from k = 1, not from the slowest pair. Table 1 of 01-prior-ports.html said "same angles" (Section 10).
  2. mx.fast.rope has the right layout and still cannot do it. It supports the half-split layout. But it has one position for each token, integer offsets only, and no exception for the prefix tokens. An exact form needs two calls, gathers and a join (Section 7).
  3. The tables are not bit-equal, but the rotation is. The same fp32 operations in the same order give tables 1.19e-7 away from Hugging Face on all six grids. The rotation with the same tables gives a difference of exactly 0.
  4. Five rows replace a split and a join. cos 1 and sin 0 leave the prefix tokens unchanged, without a rounding. The cost is 5 extra rows of an element-wise operation (Section 6).
  5. Hugging Face and Meta treat half precision differently. Hugging Face casts the tables down to the dtype of the pixels and rotates in that dtype. Meta casts q and k up to fp32. The port follows Meta (Section 8).
  6. model.train() changes the positions in Hugging Face. Train mode turns on RoPE-box jittering, with a random box from [−0.5, 0.5] to [−2, 2]. A fine-tuning run in train mode sees other angles than the reference output. The MLX flag is separate from the train mode (Section 11).
  7. The fastest pair repeats inside one image. Its period (1) is half the box. At 224 px, patches 7 rows apart get the same angle in pair 0. The 15 slower pairs tell them apart (Section 4).
