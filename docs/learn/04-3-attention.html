1 Why this explainer

The attention is the only part of a block that mixes information between tokens. Step 4 ports it to MLX in the class Attention of src/dinov3_mlx/mlx_model.py, lines 227 to 268. The class is short. Most of the work happens in one MLX call: mx.fast.scaled_dot_product_attention. On the GPU, with 201 or more queries, this call starts the full-attention kernel of MLX. The full-attention kernel is one fused GPU kernel: it computes the scores, the softmax and the weighted sum of the values, and never writes the full score matrix to memory. For 8 or fewer queries, MLX starts a different kernel, the vector kernel (Section 6.3).

This explainer shows what the class does, what the full-attention kernel does inside, how close the result is to the Hugging Face module and to NumPy float64, and why the fp32 dtype mode of mlx runs with TF32 off. It also shows why the attention cost grows with the square of the token count.

The measured values come from four places: the test report of the Step 4 build of 2026-11-07 (tests/fixtures/generated/mlx/report.jsonl, which git ignores), results/parity-mlx.md, results/bench-mlx-port.jsonl and the targets of specs/04-mlx-port/plan.html. The build ran every mlx test on the GPU with TF32 off, except the TF32-on half of the TF32 probe (Section 8.2). For this page, nobody loaded a model and nobody ran a GPU computation. The NumPy emulations of Sections 6 and 8 ran on the CPU with NumPy 2.5.4.

Results in short. The full-attention kernel differs from a NumPy float64 formula by at most 7.8e-7 at 201 tokens and 1.3e-6 at 1,029 tokens (target ≤ 5e-6, AC8). The Attention module differs from the Hugging Face module by at most 4.5e-6 (target ≤ 1e-5). The TF32 probe gives 7.8e-7 with TF32 off and 7.2e-4 with TF32 on: 919 times more.

2 The attention in one block

Each token gives three vectors: a query q, a key k and a value v. A score is the dot product of one query and one key. For each query, a softmax over its scores with all keys gives one weight for each key. The output of the query is the weighted sum of all values. DINOv3 uses no mask: every token sees every token, the prefix tokens included. With the scale s = 1 / √64 = 0.125, one head computes:

a = softmax(q kᵀ · s) v        q, k, v: (T, 64) for one head; q kᵀ: (T, T) scores

ViT-S/16 has 6 heads of 64 values each. Block.__call__ (line 316) calls the attention on the output of norm1. LayerScale and the residual add come after it (04-4-layerscale.html):

316        x = self.layer_scale1(self.attention(self.norm1(x), cos, sin)) + x

Figure 1 shows the path through the attention for one image at 224 × 224 px. The grid has 14 × 14 = 196 patches, so the sequence has T = 5 + 196 = 201 tokens.

3 The four projections

Lines 235 to 238 make four nn.Linear(384, 384) modules. Their names are the names of the Hugging Face tensors, for example layer.3.attention.q_proj.weight. nn.Linear of MLX stores its weight as (out, in), as the safetensors file does. So the key map passes these weights without a change (04-1-patch-embedding.html). The key map accepts a block tensor only if the name after layer.{i}. is a parameter name of the MLX block. block_parameter_names (mlx_weights.py, lines 48 to 74) gets these names from one small Block with every bias on, so the weights and biases of the four projections pass. Hugging Face builds the same four nn.Linear modules in DINOv3ViTAttention.__init__ (lines 295 to 299 of modeling_dinov3_vit.py).

Line 234 computes the scale from the head dimension: 384 / 6 = 64, and 64−0.5 = 0.125. The value comes from the config, not from a constant. ViT-7B/16 has a head dimension of 128 and a scale of 0.0884 (Step 5).

3.1 Why k has no bias

Two facts explain it.

  1. Softmax ignores a k bias without RoPE. A bias b on every key adds q · b to each score of one query: q · (kj + b) = q · kj + q · b. The term q · b is the same for all keys j of that query. A softmax does not change when all values of its row get the same addend. So the k bias has no effect on the output. With RoPE, the term q · b changes from patch key to patch key, so a k bias would change the output. The term is the same only for the 5 prefix keys.
  2. DINOv3 trains with the k bias masked. The official code computes q, k and v with one linear layer qkv with 3 × D outputs. Its class LinearKMaskedBias multiplies the bias by a mask. init_weights_vit sets the mask to 0 for the outputs D to 2 D − 1, the k part. The hub backbones set mask_k_bias=True. So the trained model has no k bias, and the Hugging Face config says key_bias false.

Line 236 reads the flag from the config. A model size with a k bias would get one without a code change: map_key accepts attention.k_proj.bias, because block_parameter_names builds its block with every bias on. If a weights file has a k bias but its config says key_bias false, load_weights(strict=True) stops the load.

4 The split into heads and the merge

Attention.qkv (lines 240 to 250) applies the three projections and splits each result into heads. The inner function heads (line 248) does two operations:

  1. reshape(b, t, 6, -1) cuts the 384 channels of each token into 6 groups of 64. Channel c goes to head c // 64, position c % 64.
  2. transpose(0, 2, 1, 3) moves the head axis in front of the token axis: (B, T, 6, 64) becomes (B, 6, T, 64). This is the layout [B, N_q, T_q, D] that the docstring of mx.fast.scaled_dot_product_attention asks for.

Attention.output (lines 252 to 255) does the inverse. It transposes (B, 6, T, 64) back to (B, T, 6, 64), reshapes it to (B, T, 384) and applies o_proj. Head h again holds the channels 64 h to 64 h + 63. o_proj is the only operation that mixes the 6 heads.

Hugging Face does the same with view(batch_size, patches, num_heads, head_dim).transpose(1, 2) (lines 316 to 318), a transpose(1, 2) after the torch SDPA (line 184 of integrations/sdpa_attention.py) and reshape(batch_size, patches, -1) (line 338). The channel order must be the same, because the weights of o_proj expect it. The part tests qkv_proj and o_proj check the order. They measured 5.0e-6 and 4.3e-6 (target ≤ 1e-5, Section 7). A wrong order would miss these targets by far.

Why two methods and not one __call__? The methods give the part tests the cut points of block_parts of Step 3. The part qkv_proj ends after the split. The part o_proj starts at the merge. _mlx_parts in tests/test_mlx_parts.py (lines 87 to 104) uses attention.qkv, attention.scale and attention.output. Step 6 uses the same cut points for the block profile of mlx. Step 6 can also join the three projections into one fused qkv matmul in mlx_weights (Table 5 of the plan). A fused qkv module in the MLX block changes the names of block_parameter_names with it. Then map_key needs a rule for the names q_proj, k_proj and v_proj of the weights file: today it rejects a block name that is not a parameter of the MLX block, for example attention.qkv.weight (test_map_key_rejects_a_block_name_that_is_not_a_parameter).

5 RoPE on q and k

Line 266 rotates q and k with the RoPE tables of the patch grid. v gets no rotation. 04-2-rope.html explains the tables and the rotation. Three facts matter for the attention:

  • Only q and k. A rotation by the angle of position i on q and by the angle of position j on k gives a score that depends on the difference of the two angles. So the score sees the relative position of the two patches. The values v carry content, not position.
  • No split. Hugging Face splits q and k into the prefix tokens and the patch tokens, rotates the patch tokens and joins the pieces again (apply_rotary_pos_emb, lines 265 to 273). The MLX tables have 5 identity rows (cos 1, sin 0) on top. So apply_rope rotates all 201 rows, and the prefix tokens come out unchanged: x · 1 + r · 0 = x. The part test rope measured a largest difference of 0 (target ≤ 2e-6).
  • fp32. apply_rope casts q and k to fp32, rotates them and casts back. In the fp32 dtype mode these casts change nothing. They matter for fp16 and bf16 in Step 5.

6 The full-attention kernel

6.1 The call

267         a = mx.fast.scaled_dot_product_attention(q, k, v, scale=self.scale, mask=None)

The call takes q, k and v with the shape (B, 6, T, 64) and returns a with the same shape. scale=0.125 replaces the 1 / √64 of the formula. mask=None lets every query see every key. The call has no dropout argument; DINOv3 uses no attention dropout at inference. The docstring of mlx 0.32.4 says: "The softmax operation is performed in float32 regardless of the input precision." So Step 5 gets an fp32 softmax for fp16 and bf16 inputs without a cast in our code.

There is no explicit attention formula in src/ (decision D5 of explore.html). An explicit formula would need the full score matrix in memory and three operations. The call also has a VJP, which the LoRA training of Step 8 needs.

6.3 How the kernel applies the scale

The formula computes exp(0.125 · s) for each score s. The kernel computes 2(0.125 · log2(e)) · s. In exact math the two are equal. In fp32 they round differently:

  • The factor. M_LOG2E_F is log2(e) in fp32: 1.44269502, 1.9e-8 below the exact value. The product 0.125 × 1.44269502 = 0.18033688 is exact in fp32, because 0.125 is a power of two.
  • The scaled score. A multiplication by 0.125 is exact. A multiplication by 0.18033688 is not: each scaled score rounds once, with a relative error of at most 6e-8. This multiplication is in fp32 for every input dtype.
  • The exponential. The kernel uses fast::exp2. On the GPU, exp2 is the native operation; an exp needs a multiplication by log2(e) first. The kernel puts this multiplication into the scale, so each score gets one multiplication, not two.
  • Scores, not queries. The docstring calls the argument the "Scale for queries". The full-attention kernel multiplies the fp32 scores, after Q Kᵀ. Only the vector kernel for 8 or fewer queries multiplies the queries (sdpa_vector.h, line 86), and so does the CPU fallback. DINOv3 at 224 px and more has 201 or more tokens, so the full-attention kernel runs.

How much does the exp2 order cost? Table 3 gives an emulation in NumPy fp32 on the CPU, with the seed and the shapes of test_mlx_sdpa_float64. It computes the scores, the scale, the exponential, the row sum and P v in fp32, without tiles, in the two orders. Both orders divide by the row sum after P v, as the kernel does. The exp2 order adds about 5 % to 14 % to the largest difference. The values measured on the GPU are 4 % to 10 % above the exp2 emulation. So the kernel error is the normal fp32 error of this computation.

8 TF32

8.1 What TF32 is

TF32 is a matmul mode. It keeps the sign and the 8-bit exponent of fp32, but only 10 of the 23 mantissa bits of each input. The products and the sums stay in fp32. Its unit roundoff is 2−11 = 4.9e-4 with round to nearest; fp32 has 2−24 = 6e-8. Figure 3 shows the bits of the value 0.7.

mlx 0.32.4 turns TF32 on by default. mlx/utils.h reads the variable once, into a static value, with the default 1:

225 inline bool enable_tf32() {
226   static bool enable_tf32_ = get_var("MLX_ENABLE_TF32", 1);
227   return enable_tf32_;
228 }

With TF32 on, mlx 0.32.4 can run fp32 matmuls on the Neural Accelerators with relaxed precision (Table 14 of explore.html). An error message in libmlx.dylib lists the head dimensions of the attention kernels, adds head dimension 512 on GPUs with Neural Accelerators and says "float32 also requires TF32". This suggests that the head-dimension-512 attention kernel of the Neural Accelerators takes fp32 inputs only with TF32 on. The message says nothing about head dimension 64. We did not measure the full-attention kernel with TF32 on.

8.2 The TF32 probe

test_mlx_tf32_probe (T24, tests/test_mlx_environment.py, lines 115 to 133) starts two subprocesses, one after the other: one with MLX_ENABLE_TF32=0, one with =1. A new process is necessary, because MLX reads the variable only once. Each subprocess runs this code, the string TF32_PROBE (lines 57 to 71):

A match to 0.012 % does not prove the rule of the hardware, but it is a strong hint.

8.3 Why the fp32 dtype mode runs with TF32 off

  • The fp32 thresholds are 0.9999 for the frame embedding, the patch mean and the patch 1st percentile. On torch-mps, matmuls with a 10-bit mantissa (fp16-autocast) gave a worst patch 1st percentile of 0.999781 over five model sizes (Table 3 of 02-tokens-and-outputs.html). TF32 also keeps 10 mantissa bits.
  • The part targets would fail. The plan estimates that a matmul with TF32 on misses each matmul target of its Table 7 (≤ 1e-5 to ≤ 2e-5) by a factor of about 100. The probe supports this estimate: TF32 on gives 919 times the error of TF32 off.
  • fp32 must mean fp32 arithmetic. Then mlx and torch-mps compare at the same precision. A faster fp32 mode with TF32 on can come in Step 6, as a separate dtype mode with its own thresholds (ADR 0005, docs/adr/0005-fp32-on-mlx-runs-with-tf32-off.md).

The cost is speed. The Step 4 benchmark has no worker with TF32 on, so this cost is not measured yet.

  • Before the first use. MLX reads MLX_ENABLE_TF32 once. So tests/conftest.py sets the value before its first import of mlx, and the benchmark driver puts it into the environment of each mlx worker subprocess. The code in src/ does not change the environment.
  • tf32_enabled reads the environment as MLX does: no variable gives True; otherwise the leading integer decides. "1" gives True; "0", "no" and "" give False. test_tf32_enabled_reads_the_environment_as_mlx_does checks four values. T21 checks that the test process has "0".
  • TF32ModeError: load_mlx_backbone compares the requested state (tf32=False by default) with tf32_enabled(). On a mismatch it raises before the memory check and before any file read (T6, test_load_mlx_backbone_refuses_tf32_mismatch). The check applies only to the fp32 dtype mode, because TF32 changes only fp32 matmuls.
  • Limit. The check sees the environment, not the static value inside MLX. A process that changes the variable after its first mlx matmul defeats the check. The probe measures the real effect.

9 The attention cost grows with N²

A grid of N patches gives T = 5 + N tokens. Each head computes T × T scores. For large grids T is almost N, so the score count grows with N². The four projections grow only with T. 03-where-the-compute-goes.html derives the FLOPs: 4 B T² D for sdpa, against 8 B T D² for the four projections and 4 B T D F for the MLP of ViT-S/16 (F = 1,536). The Step 4 benchmark measures the whole backbone at 224 px, not the attention alone. The benchmark compares mlx (the full-attention kernel, TF32 off) with torch-mps without torch.compile (the SDPA of torch), in fp32, for the frame embedding. The median paired ratio is 1.39 at batch size 8 (847 against 611 images per second). It is 3.12 at batch size 1 (357 against 114). These are the medians of the three rounds of the build in results/bench-mlx-port.jsonl. At 224 px sdpa has only 8 % of the FLOPs, so these ratios say little about the kernel alone.

11 Surprises

  1. The kernel does not scale by 0.125. It multiplies the fp32 scores by 0.125 × log2(e) = 0.18033688 and uses exp2. A multiplication by 0.125 is exact; this one rounds each score once. In the NumPy emulation the exp2 order adds 5 % to 14 % to the largest difference. The measured error (7.8e-7 and 1.34e-6) stays 3.7 to 6.4 times below the target.
  2. "Scale for queries" scales the scores. The docstring calls the argument the scale for the queries. The full-attention kernel applies it to the scores, after Q Kᵀ. Only the vector kernel for 8 or fewer queries and the CPU fallback scale the queries. So the rounding depends on the token count and on the device.
  3. MLX turns TF32 on by default. An fp32 mx.array matmul is not fp32 arithmetic unless MLX_ENABLE_TF32=0 is in the environment before the first use of mlx. MLX reads the value once, so a change later in the same process has no effect.
  4. TF32 on is 7 times worse than expected, and it agrees with truncation. The probe gave 7.2e-4, not about 1e-4. A truncation of both inputs to 10 mantissa bits gives 7.167e-4, 0.012 % from the measured 7.168e-4. Round to nearest gives only 2.6e-4.
  5. TF32 off is exactly fp32. The GPU probe with TF32 off and a NumPy fp32 matmul on the CPU give the same largest relative difference, 7.795913575388104e-7. The plan expected about 1e-7; its estimate was low by a factor of about 8.
  6. The missing k bias is a training choice. The official DINOv3 code trains with one qkv bias and masks its k third to zero (LinearKMaskedBias). So the Hugging Face weights have no k_proj.bias, and the MLX k_proj has none either.
  7. Twelve blocks grow the error only a little. Each SDPA call has an error of about 1e-6. In the chain, 1 − cos goes from 3.0e-11 in hidden state 1 to 1.1e-10 in hidden state 11, far below the fp32 threshold of 1e-4. All 12 configurations reach parity 1.000000.
