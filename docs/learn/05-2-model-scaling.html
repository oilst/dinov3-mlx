1 Why this explainer

Step 4 ported ViT-S/16 to MLX in one dtype mode, fp32. Step 5 extends the port to all six model sizes and to five dtype modes. Three explainers describe Step 5 (Table 1 of specs/05-all-sizes/plan.html). 05-1 explains SwiGLU. 05-3 explains the numeric range of the tokens. This page explains three parts:

  • The scaling of the model family. What changes in the tensors from ViT-S/16 to ViT-7B/16, and why ViT-7B/16 needs no special code (Section 2).
  • The dtype modes. Each dtype mode is a pair of dtypes: the matmul dtype and the stream dtype. The casts in Embeddings and Block give each part its dtype (Sections 3 to 5).
  • The load and the run rule. The loader casts and evaluates one tensor at a time. A guard refuses every load of ViT-7B/16 with fp32 weights, on both backends (Sections 6 to 8).
  • The streamed reference (path D4-Y). The user said yes to a streamed fp32 reference of ViT-7B/16. It holds the fp32 weights of one block at a time on torch-cpu and gives the reference output of ViT-7B/16 (Sections 8.1 to 8.9).

Section 9 gives the paired ratios of the small benchmark at the priority configuration P2 in each dtype mode.

The result in five numbers:

  • The key map covers all six model sizes: 0 unknown names, 0 missing names and 0 shape differences (acceptance criterion AC12).

2 What changes from ViT-S/16 to ViT-7B/16

All six model sizes use the same naming scheme for their tensors. The SwiGLU model sizes add gate_proj, and ViT-7B/16 has no q and v biases. The parameter count grows from 21.6 million to 6.7 billion: about 311 times (our computation). But only two numbers set the shape of a tensor: the embedding dimension D and the hidden width FF of the feed-forward network.

  • The number of blocks sets the number of tensors, not their shapes.
  • The number of heads sets only the reshape inside Attention. No weight has a head axis: q_proj, k_proj, v_proj and o_proj are all (D, D).
  • SwiGLU adds one tensor pair to each block: mlp.gate_proj with the shape (FF, D) (05-1).

3 Five dtype modes: two dtypes each

In Step 4, MLX_DTYPE_MODES mapped each dtype mode to one dtype: {"fp32": mx.float32}. One dtype cannot describe an autocast mode. There the matmuls run in fp16 or bf16, but the residual stream, the layer norms and LayerScale stay in fp32. So Step 5 gives each dtype mode two dtypes (D2 of explore.html):

3.1 On mlx, the autocast modes have half-precision weights

The word "autocast" means one thing on both backends: the matmuls run in fp16 or bf16, and the residual stream stays in fp32. The weights differ. On torch, the weights stay in fp32, and torch.autocast casts each weight at each matmul. On mlx, the load casts the weight of each matmul once, to the matmul dtype (GLOSSARY, "Autocast mode"). The matmul gets the same rounded weight on both backends. bytes_per_weight, which the first fix session added to bench.py, writes this difference down in one place:

Four measured or computed consequences:

  • The need of the memory check. An autocast mode on mlx has the need of the cast mode: 6.02 GB for ViT-H+/16, against 8.03 GB in fp32 (Table 6).
  • The run rule. ViT-7B/16 loads on mlx in fp16-autocast and bf16-autocast: 2 bytes for each weight. On torch, the run rule refuses both modes: 4 bytes for each weight (Section 8). The official precision of DINOv3 is bf16 autocast with RoPE in fp32 (finding 5 of explore.html). In this repo, only mlx runs ViT-7B/16 in this precision.
  • The peak memory at P2. The mlx worker of ViT-H+/16 needs 3.44 GB in fp16-autocast and in fp16-cast. The torch-mps worker needs 5.00 GB in fp16-autocast and 4.31 GB in fp16-cast (Table 13).
  • The load peak. ViT-H+/16 in an autocast mode: 1,701.3 MB; in a cast mode: 1,700.8 MB. The 0.5 MB are the 254,720 values of the stream parameters, which stay in fp32 (our computation: 2 more bytes for each value).

The Close stage records this choice in ADR 0007 (Section 9 of plan.html).

The backbone keeps the two dtypes of its dtype mode as a plain attribute dtypes in Embeddings, in each Block and in MlxBackbone. The casts read this attribute, never the dtype of a weight. Figure 2 shows where each cast sits.

  • Line 407. The branch output is in the matmul dtype. layer_scale1 multiplies it by λ in the stream dtype. In an autocast mode, half × fp32 gives fp32 by type promotion, so the residual add stays in fp32. In fp32 and in a cast mode, all three have one dtype.

  • RoPE stays in fp32. apply_rope (lines 201 and 202) casts q and k to fp32, rotates them with the fp32 tables and casts the result back to the matmul dtype (04-2). 6 The load: one tensor at a time

6.1 Why the Step 4 loader cannot load ViT-7B/16

All files store fp32. So a load in fp16 or bf16 reads fp32 and casts. The Step 4 loader built all casts lazily and evaluated them in one call:

# src/dinov3_apple/mlx_weights.py at commit ae76e6e (Step 4), the end of load_mlx_backbone

This Mac crashed from out-of-memory before. So D5 asks for a loader that keeps the peak low by itself.

12 Surprises

  1. Only D and FF change the tensor shapes. From 21.6 million to 6.7 billion parameters, every tensor shape is a product of D, FF and fixed numbers. The number of blocks changes the count of the tensors, and the number of heads only a reshape. So one key map and one module tree serve all six model sizes.
  2. ViT-7B/16 is different in three ways, and needs no special code. Its head dimension is 128 (RoPE gets 32 frequencies), it has no q and v biases, and its weights are in six files with an index. The config and mx.load of every file handle all three.
  3. A lazy cast of all tensors would hold both copies. The Step 4 loader would hold about 40.3 GB for ViT-7B/16 in bf16 (an estimate): the 26.86 GB of fp32 sources and the 13.43 GB of casts. That is twice the need of 20.12 GB and more than the 38.7 GB of free memory before the measured load. The Step 5 loader measured a load peak of 13.5 GB (13,532,676,096 bytes): the casts plus one fp32 source tensor.
  4. On mlx, the autocast modes have half-precision weights. The load casts each matmul weight once. So ViT-7B/16 runs on mlx in bf16-autocast, the official precision of DINOv3, while the run rule refuses it on torch. At P2 the mlx autocast worker needs 3.44 GB, the same as the cast worker; the torch-mps autocast worker needs 5.00 GB.
  5. The cast-mode paired ratio is about 1, and its sign is not stable. Build: 1.028 (fp16-cast) and 1.039 (bf16-cast). Re-run with the same code: 0.968 and 0.973. The run-to-run spread is about 20 % in throughput. So no claim that mlx wins in the cast modes. In fp32 (1.094 to 1.118) and in the autocast modes (1.096 to 1.159), mlx is ahead in both runs.
  6. The half SDPA kernel is not fp32 inside. On this Mac, MLX runs a kernel that computes Q · KT and P · V with the hardware matrix operation and relaxed precision: about 11 bits at one internal step. 48 to 57 % of the fp16 outputs and 10.5 to 13.1 % of the bf16 outputs differ from the float64 result rounded once. No parity result changes.
  7. "At most one fp32 source tensor is alive" was not exact. The loader references at most one fp32 source; MLX can release it after the next read. ViT-S/16 in bf16-cast measured 1,536 bytes above the exact bound: one fp32 bias. mx.synchronize() closes the gap but makes the load 8.2 to 17.7 % slower, so the code stays.
  8. A loader that evaluates nothing passed every load-peak check. Before the fix of F1, the checks had only an upper bound. A load peak of about 0 bytes passed. Now the bytes of the mapped tensors are the lower bound. In bf16-cast, each measured load peak lies 0.6 to 2.0 percentage points of its target above it; in fp32, the load peak equals the lower bound within 0.8 MB.
  9. Streaming changes no bit. The streamed path loads the weights block by block and runs the 12 configurations block by block. Against the full-model reference files of five model sizes, its largest difference is exactly 0.0, for the tokens and for the hidden states (Table 9). The same classes, the same attention and batch size 1 give the same operations on the same inputs.
  10. A block built alone uses the eager attention. The full model of Step 2 used "sdpa". A DINOv3ViTLayer built from a plain config uses the eager attention, and the eager attention gives other bits: mutation D3 makes 7 tests red. So OuterParts.from_shards sets attn_implementation explicitly.
  11. The "load" of a block takes almost no time. safetensors maps the shards, and the pages of a tensor enter memory at its first use. So load_time_s of the ViT-7B/16 reference run is 0.33 s, in a run time of 118.74 s. The disk reads count as run time, and the resident pages count in the peak.
  12. The peak is 2.6 times one block. The largest block and the outer parts hold 0.68 GB in fp32; the peak was 1.75 GB (our computation of the ratio). The process before the run, the mapped pages and the states of the 12 configurations add the rest. It is still 6.5 % of the fp32 weights of the whole model.
  13. The largest model has a small fp32 token range. ViT-7B/16 reaches 13,537.4 in fp32: 20.7 % of the fp16 maximum. ViT-L/16 reaches 157,130.4 and ViT-H+/16 131,447.7: above the fp16 maximum (results/token-range-mlx.md, Table 3).
  14. Round 1 of fp32 favours torch-mps in both runs. The fp32 paired ratio of round 1 is 0.908 (build) and 0.860 (re-run), because torch-mps ran fp32 faster in round 1 than in rounds 2 and 3. The median of three rounds hides this; one round alone would give the opposite answer.
