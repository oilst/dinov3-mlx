1 Why this explainer

The largest fp16 value is 65,504. A larger value becomes infinite (inf). Some register tokens of DINOv3 go above this value inside the backbone (02, Section 5). So the dtype mode decides if a model size gives a finite output. Step 5 records the token range: the largest absolute value in the token sequence before block 1 and after each block. It also records the largest value of three tensors inside each block: the attention branch output, the feed-forward hidden values and the feed-forward branch output. The record covers 6 model sizes, the 5 dtype modes and the 12 configurations of each model size, on mlx.

This page explains the code of the record, the code that turns an fp16 overflow into an expected failure, and the measured values. The values come from results/token-range-mlx.md (test W7, 2026-11-07, mlx 0.32.4), from specs/05-all-sizes/verify.html and from explore.html. The values after one block come from the token-range lines in tests/fixtures/generated/parity/mlx.jsonl, which git ignores; results/token-range-mlx.md is made from the same lines. The fp32 values of ViT-7B/16 come from its streamed reference file on torch-cpu (path D4-Y, Section 8). The agent that wrote this page ran no test, no model and no GPU work. It read the stored reference files and the token-range lines with NumPy for Sections 8, 10 and 12.

The result in five numbers:

  • A register token of ViT-L/16 reaches 157,130 in fp32 (iss-kibo-lab, 224 × 224 px, after block 23). That is 239.9 % of the fp16 maximum. Over the 12 configurations the largest value is 158,433.
  • ViT-H+/16 goes above 65,504 only when the short side of the input is 224 px: 116,642 to 149,750. At 448 and 512 px it stays at 52,206 to 59,863.
  • The largest finite fp16 value is 59,776: 91.3 % of the fp16 maximum (ViT-H+/16, fp16-cast, iss-conference at 448 × 448 px).
  • In fp16-autocast the largest fp16 tensor value is 52,128: 79.6 % of the fp16 maximum (the feed-forward branch output of ViT-L/16 in block 1).
  • ViT-7B/16 reaches only 13,537.4 in fp32 (streamed reference, iss-kibo-lab at 224 × 224 px, after block 40) and at most 13,582 in the four half dtype modes: 20.7 % of the fp16 maximum. No ViT-7B/16 pair joined the list of expected failures.

2 fp16, bf16 and the dtype of each tensor

fp16 and bf16 both use 16 bits. They split the bits in a different way:

  • fp16 has more significant bits but a small range. The largest finite value is 65,504. A matmul output or a sum above it becomes inf. The next layer norm or softmax then gives NaN (Section 3.3 of explore.html).
  • bf16 has the range of fp32, so it does not overflow. But it has only 8 significant bits. Near 131,072 the spacing of bf16 values is 1,024 (02, Section 6).

So the fp16 overflow is a question of where a dtype mode keeps fp16. Each dtype mode of mlx is a pair of dtypes: the matmul dtype and the stream dtype (05-2). Table 2 gives the dtype of the four tensors of the token range, from Table 3 of the plan.

Table 2. The dtype of each tensor of the token range. "half" is fp16 or bf16. So in fp16-cast all four tensors must stay below 65,504. In fp16-autocast only the three branch tensors must stay below it; the token sequence is fp32.

The attention inside the branch has one measured difference to the plan. Table 3 of the plan says that the half SDPA kernel computes the scores, the softmax and P · V in fp32. On this Mac (M5 Max, mlx 0.32.4) it does not. MLX uses another kernel when the inputs are half, the head dimension is 64 or 128 and the sequence has more than 8 tokens. This kernel has the option relaxed_precision. It computes with about 11 bits of internal precision (finding F3 of verify.html; 05-2 explains it). This changes the rounding of the attention branch output, not its range. An analysis of the fp16 overflow must not assume an fp32 P · V.

3 The token range of one block

run_mlx_token_range runs image 0 of a pixel batch block by block. In each block it makes the same calls as Block.__call__, in the same order. It keeps only the largest absolute values, not the tensors. Figure 1 shows one block.

3.1 TokenRange

# src/dinov3_apple/mlx_model.py, lines 511 to 549
@dataclass(frozen=True)
class TokenRange:
    """The largest absolute values of one configuration, block by block (D6). Report only.

    Attributes:
        tokens: (L + 1,) fp32: the token sequence before block 1 and after each block.
        tokens_where: (L + 1,): the token index of each value of tokens. 0 is the CLS token; 1 to 4
            are the register tokens.
        tokens_finite: (L + 1,): True if every value of the token sequence is finite.
        attention: (L,) fp32: the attention branch output before LayerScale.
        ff_hidden: (L,) fp32: the feed-forward hidden values.
        ff_out: (L,) fp32: the feed-forward branch output before LayerScale.
        last_state: (5 + N, D) fp32: the token sequence after the last block.
    """

    tokens: np.ndarray
    tokens_where: np.ndarray
    tokens_finite: np.ndarray
    attention: np.ndarray
    ff_hidden: np.ndarray
    ff_out: np.ndarray
    last_state: np.ndarray

    @property
    def finite(self) -> bool:
        """True if every token sequence and every branch value is finite."""
        values = (self.tokens, self.attention, self.ff_hidden, self.ff_out)
        return bool(self.tokens_finite.all() and all(np.isfinite(v).all() for v in values))

    def report_values(self) -> dict[str, list]:
        """Return all fields except last_state as lists, for one JSON line."""
        return {
            "tokens": self.tokens.tolist(),
            "tokens_where": self.tokens_where.tolist(),
            "tokens_finite": self.tokens_finite.tolist(),
            "attention": self.attention.tolist(),
            "ff_hidden": self.ff_hidden.tolist(),
            "ff_out": self.ff_out.tolist(),
        }
  • Lines 526 to 528. The token fields have L + 1 values: index 0 is the token sequence before block 1, index i the sequence after block i. This is the numbering of the hidden states of Step 2. The three branch fields have L values: index i − 1 belongs to block i.
  • Line 527, tokens_where. The token index of the largest value: 0 is the CLS token, 1 to 4 are the register tokens R1 to R4, 5 and up are the patch tokens. scripts/token_range_table.py prints it as "R2" or "patch 622".
  • Lines 534 to 538, finite. False if one token sequence has one non-finite value, or if one recorded value is inf or NaN. W7 writes the status "measured" or "non-finite" from it. Before the fix of finding F6, no test checked this property. Now test_token_range_finite_sees_each_inf puts an inf into each field and checks that finite becomes False.
  • Lines 540 to 549, report_values. The values of one JSON line. last_state stays out: it has (5 + N) × D values, and only T26 uses it.

3.2 The two helpers

# src/dinov3_apple/mlx_model.py, lines 552 to 559
def _largest(t: mx.array) -> mx.array:
    return mx.abs(t.astype(mx.float32)).max()  # inf stays inf


def _token_values(x: mx.array) -> tuple[mx.array, mx.array, mx.array]:
    """The largest absolute value of a token sequence (1, T, D), its token and the finite flag."""
    magnitude = mx.abs(x[0].astype(mx.float32)).max(axis=-1)
    return magnitude.max(), mx.argmax(magnitude), mx.isfinite(x).all()
  • Line 553. The cast to fp32 comes first, so the record has one dtype in all five dtype modes. The cast does not change a value: fp32 holds each fp16 and each bf16 value exactly. An inf stays inf after the cast and after mx.abs. A NaN gives a NaN maximum.
  • Line 558. magnitude holds the largest |value| of each of the T tokens of image 0. Its maximum is the value of tokens, and its argmax is the value of tokens_where.
  • Line 559. mx.isfinite(x).all() checks every value of the sequence, not only the largest. The three results stay lazy MLX scalars until line 589 evaluates them.
  • After a NaN. When the sequence holds a NaN, the maximum is NaN and argmax gives 0. So after a NaN, tokens_where holds 0, and this 0 does not mean the CLS token. The lines of ViT-L/16 in fp16-cast show it: R2 (index 2) after block 1, where the value is inf, then 0 after block 2, where it is NaN.

3.3 run_mlx_token_range

# src/dinov3_apple/mlx_model.py, lines 562 to 602 (docstring shortened)
def run_mlx_token_range(model: MlxBackbone, pixels: np.ndarray) -> TokenRange:
    """Run image 0 block by block and keep only the largest absolute values (D6). Report only.

    The calls and their order are the calls of Block.__call__, so the last token sequence equals
    the last state of run_mlx_hidden_states. The function evaluates one block at a time.
    ...
    """
    x = model.embeddings(mx.array(pixels[:1]))
    p = model.config.patch_size
    cos, sin = model.rope(pixels.shape[2] // p, pixels.shape[3] // p)
    states = [_token_values(x)]
    mx.eval(x, states[-1])
    branches = []
    for block in model.layer:
        a = block.attention_branch(x, cos, sin)
        x = block.layer_scale1(a) + x
        h = block.ff_hidden(x)
        f = block.mlp.down_proj(h)
        x = block.layer_scale2(f) + x
        states.append(_token_values(x))
        branches.append((_largest(a), _largest(h), _largest(f)))
        mx.eval(x, states[-1], branches[-1])  # one block at a time
    largest, where, finite = (np.array([s[i].item() for s in states]) for i in range(3))
    attention, ff_hidden, ff_out = (
        np.array([b[i].item() for b in branches], np.float32) for i in range(3)
    )
    return TokenRange(
        tokens=largest.astype(np.float32),
        tokens_where=where.astype(np.int64),
        tokens_finite=finite.astype(bool),
        attention=attention,
        ff_hidden=ff_hidden,
        ff_out=ff_out,
        last_state=np.array(x[0].astype(mx.float32)),
    )
  • Line 575. pixels[:1] keeps image 0. The function does not cast the fp32 pixels: Embeddings.__call__ casts them to the matmul dtype (line 256), and it returns the token sequence in the stream dtype (Section 4).
  • Line 577. The RoPE tables of the patch grid come from the cache of the backbone (04-2).
  • Lines 582 to 586. Block.__call__ has two lines: x = self.layer_scale1(self.attention_branch(x, cos, sin)) + x and return self.layer_scale2(self.mlp.down_proj(self.ff_hidden(x))) + x. The five lines here are the same calls in the same order, with a name for each intermediate tensor. Step 5 added attention_branch and ff_hidden to Block for this reason (05-1, 05-2). So MLX builds the same graph, and T26 finds the same bits as run_mlx_hidden_states.
  • Line 585. f is the feed-forward branch output before LayerScale. Block.ff_hidden gives h, the input of down_proj: the GELU output of an MLP or silu(gate) · up of SwiGLU.
  • Line 589. MLX is lazy. Without this line, the graph of all L blocks would run at the first .item() call, and MLX would keep the tensors of all blocks for it. With this line, each block runs on an evaluated x, and MLX can free a, h and f of the block. ViT-7B/16 has 40 blocks.
  • Lines 590 to 593. .item() moves each evaluated scalar to Python. The branch fields become fp32 NumPy arrays.
  • Line 601. last_state is the token sequence after the last block, without the final layer norm, in fp32.

Why a new function, and not run_mlx_hidden_states with a maximum on top? run_mlx_hidden_states returns the token sequence only. It cannot give the three branch tensors, and the fp16 tensors of fp16-autocast are branch tensors (Table 2). It also returns all L + 1 states: for ViT-7B/16 at 512 × 512 px this is 41 × 1,029 × 4,096 fp32 values, about 0.69 GB (our computation). run_mlx_token_range keeps 6 values for each block.

4 The change in run_mlx_hidden_states

run_mlx_hidden_states came in Step 4 (04-5, Section 5). Step 5 changed one line of code and the "Returns" line of the docstring:

# Step 4, commit ea82d58
x = model.embeddings(mx.array(pixels[:1]).astype(model.norm.weight.dtype))

# Step 5, src/dinov3_apple/mlx_model.py, lines 487 to 508 (docstring shortened)
def run_mlx_hidden_states(model: MlxBackbone, pixels: np.ndarray) -> np.ndarray:
    """Return the token sequence before block 1 and after each block, before the final layer norm.
    ...
    Returns:
        The hidden states with shape (L + 1, 1 + 4 + N, D), cast to fp32.
    """
    x = model.embeddings(mx.array(pixels[:1]))  # the model casts the fp32 pixels
    p = model.config.patch_size
    cos, sin = model.rope(pixels.shape[2] // p, pixels.shape[3] // p)
    states = [x[0]]
    for block in model.layer:
        x = block(x, cos, sin)
        states.append(x[0])
    hidden = mx.stack(states).astype(mx.float32)
    mx.eval(hidden)
    return np.array(hidden)
  • Line 499. Step 4 read a dtype from a weight: the weight of the final layer norm. Step 4 had only fp32, so this gave fp32. In an autocast mode this weight has the stream dtype fp32, but the patch embedding needs the matmul dtype. Now Embeddings casts the pixels with its plain attribute dtypes (line 256), and run_mlx, run_mlx_hidden_states and run_mlx_token_range give it fp32 pixels. Finding F1 of specs/04-mlx-port/verify.html showed why a dtype from a weight is a risk: nn.quantize packs a weight into uint32.
  • Line 504. The line did not change, but Block.__call__ did: it now calls attention_branch and ff_hidden. So this loop and the loop of run_mlx_token_range run the same methods.
  • Line 506 and the docstring. In a half dtype mode the states are fp16 or bf16. astype(mx.float32) is necessary because NumPy has no bf16 dtype. The docstring now says "cast to fp32", not "in fp32": the values keep their half precision.

Two tests tie the two functions together. T26 (test_token_range_matches_hidden_states) runs both functions on the small models vits16 and vits16plus in the five dtype modes. Each token value equals the largest |value| of its hidden state. last_state equals the last hidden state. The three branch fields equal the maxima of the method outputs in the forward pass of run_mlx_hidden_states. W8 (test_mlx_token_range_matches_stored) compares the fp32 token range with the stored hidden states of Step 2, iss-kibo-lab at 224 × 224 px.

What the record shows:

  • A register token holds the largest value. In every finite row of Table 3 the token is R1, R2 or R3. In ViT-7B/16, R2 holds the largest value after every block, in all four dtype modes and in the fp32 hidden states of the streamed reference.
  • The dtype modes agree where the values are finite. At the same configuration, the finite values of the dtype modes differ by less than 2 %. The fp16-cast cell of ViT-H+/16 is lower only because it covers the 448 and 512 px configurations. At these configurations, fp32 and fp16-cast differ by less than 0.4 %. The large values are a property of the weights, not of the dtype mode.
  • The large values come from the feed-forward branch. The attention branch output stays at or below 60.7 in the five students and reaches 209.4 in ViT-7B/16 (block 1). The feed-forward branch output reaches 52,128 in ViT-L/16 (block 1) and 12,506 in ViT-H+/16 (block 23). The feed-forward hidden values of ViT-S+/16 reach 7,272 (block 3).
  • bf16 rounds the large values to its spacing. In bf16-cast, the largest value of ViT-L/16 is 157,696.0 in 10 configurations and 156,672.0 in 2. The two values are one bf16 spacing (1,024) apart.
  • W8 agrees with Step 2. In fp32, the token range of iss-kibo-lab at 224 × 224 px differs from the stored hidden states by at most 3.0e-7 to 2.5e-6 (relative), depending on the model size. The fp32 value of ViT-L/16 there is 157,130.5, the value of Step 2.

6 LayerScale makes a branch output large

Each branch of a block ends with LayerScale and the residual add: x + λ ⊙ branch output. λ has one learned factor for each channel. The factors change from block to block and from channel to channel (04-4, Figure 2). |λ| reaches 62 in ViT-H+/16, 51 in ViT-L/16 and 25 in ViT-7B/16 (risk R20 of explore.html). So a branch output that fits in fp16 can give a residual value far above 65,504.

Block 1 of ViT-L/16 shows it. Before block 1, the largest token value is only 15.2. The largest feed-forward branch output of block 1 is 51,716 (fp32, iss-kibo-lab at 224 × 224 px). After block 1, the register token R2 holds 155,923: three times as large. Figure 3 follows this value in the two fp16 dtype modes.

  • The overflow of ViT-L/16 does not depend on the image. In all 12 configurations, the feed-forward branch output of block 1 is 51,691 to 52,117 (fp32), and R2 holds 155,848 to 157,132 after block 1. So fp16-cast fails at every input resolution, as on torch-mps.
  • fp16-autocast needs only the branch output in fp16. Its largest fp16 value over all model sizes is this branch output of ViT-L/16: 52,128 (forest/448x448, block 1), 79.6 % of 65,504 (Section 8).
  • Small λ values lose precision in fp16-cast. 0.1 to 0.5 % of the λ values are below the smallest normal fp16 value, 6.1e-5. The smallest λ is 3.6e-8 (ViT-L/16). explore.html rates the effect small (risk R28). The autocast modes keep λ in fp32.

def stored_range(hidden: np.ndarray) -> dict:

def check_finite(
    tokens: np.ndarray, model_size: str, dtype_mode: str, note: Callable[[], None]
) -> None:
    """Record and xfail an expected fp16 overflow. Fail any other non-finite output (way M2).

    Args:
        tokens: The output of the backend under test.
        model_size: A key of MODEL_IDS.
        dtype_mode: A key of THRESHOLDS.
        note: Writes the result line with the status "non-finite".
    """

10 After the final layer norm

The large values stay inside the backbone. For all six model sizes in fp32 on torch-cpu, no output value after the final layer norm is above 18. The largest output values over the 12 configurations are 9.2 (ViT-S/16), 11.0 (ViT-S+/16), 17.9 (ViT-B/16), 15.7 (ViT-L/16), 12.3 (ViT-H+/16) and 7.3 (ViT-7B/16) (Table 2 of 02). The value of ViT-7B/16 comes from the tokens of its streamed reference file: 5.4 to 7.3 over the 12 configurations, the largest at iss-kibo-lab/224x400.

  • The layer norm divides each token by its own standard deviation over the D channels. The large values sit in 3 to 14 channels of one register token. So the large channels set the standard deviation of that token, and the normalized values are small. For any token, a normalized value is at most √(D − 1) in size before the learned scale (our derivation).
  • The frame embedding and the patch embeddings do not include the register tokens. But the attention of each block reads the register tokens. So an inf or a NaN in one register token reaches the outputs in the next block.
  • In ViT-S/16 to ViT-H+/16, the largest output value is in a register token. In ViT-7B/16 it is in a patch token: 7.3, against at most 4.8 in a register token and 0.73 in the CLS token (our read of the 12 configurations). So the patch embeddings of ViT-7B/16 hold its largest output values, and these stay at or below 7.3.
  • So fp16 is a risk only inside the backbone. For all six model sizes on the 12 configurations, a head after the backbone sees values below 18.

12 Surprises

  1. ViT-L/16 overflows in block 1, for every image. A register token of ViT-L/16 reaches 157,130 in fp32. The value is already 155,848 to 157,132 after block 1, in all 12 configurations. The feed-forward branch output of block 1 is nearly the same for each input: 51,691 to 52,117.
  2. The overflow of ViT-H+/16 depends on the input resolution. The same block 23 gives 116,368 to 149,432 with a 224 px short side and 38,304 to 48,818 at 448 and 512 px. The cause is a feed-forward branch output of about half the size. The record does not show why.
  3. |λ| reaches 62. So a branch output that fits in fp16 can give a residual value far above 65,504. In block 1 of ViT-L/16 the residual value is three times the largest branch output. fp16-autocast works only because λ and the residual add stay in fp32.
  4. The finite fp16 values come close to the limit. The fp16-autocast branch output of ViT-L/16 reaches 79.6 % of 65,504. The finite fp16-cast configuration iss-conference/448x448 of ViT-H+/16 reaches 91.3 %.
  5. The teacher has small register values. ViT-7B/16 reaches 13,537.4 in fp32 and 13,582 in the half dtype modes: 20.7 % of the fp16 maximum, less than ViT-B/16 (22.8 %). After block 1, its value grows a little in each of the other 39 blocks. ViT-S/16, ViT-S+/16, ViT-B/16 and ViT-H+/16 have later jumps. ViT-L/16 jumps only in block 1.
  6. No measured output value is above 18. For all six model sizes in fp32 on torch-cpu, no output value after the final layer norm is above 18. The values of 150,000 inside the backbone do not reach the outputs. ViT-7B/16 has the smallest: 7.3, from its streamed reference, in a patch token, not in a register token.
  7. The patch tokens of ViT-7B/16 come close to its register value. After block 40, its largest patch value is 7,600: 56 % of the value of R2, in the same channel, 1557. This channel holds −7,600 to −4,225 in every patch token: a feature-dimension outlier in all tokens, the second kind of Appendix A.2 of the DINOv3 paper (02, Section 5). In ViT-S/16 to ViT-H+/16 the largest patch value is 1.7 % (ViT-L/16) to 25.1 % (ViT-S/16) of the largest value (Table 2 of 02). One block makes the difference: after block 39 the largest patch value of ViT-7B/16 is 3,867 (our read of the stored hidden states).
  8. The attention branch never makes the large values. Its output stays at or below 60.7 in the students and 209.4 in ViT-7B/16. All large values come from the feed-forward branch.
  9. bf16 shows its spacing. In bf16-cast, the largest value of ViT-L/16 is 157,696 or 156,672 in all 12 configurations: one bf16 spacing (1,024) apart.
  10. A test that could not fail. At first, no test checked the branch values or TokenRange.finite. Three mutations stayed green (finding F6). The fix session added the checks.
