1 Why this explainer

Step 2 makes the reference output: the output of the Hugging Face backbone on torch-cpu in fp32. Each model size gets one reference file with 12 configurations: 3 test images at 4 input resolutions. Every later step compares its output with these files. So we must know exactly which tokens the backbone gives and which slices of them are the two outputs.

This explainer shows the path from an image file to the frame embedding and the patch embeddings. It also shows a property of DINOv3 that the probe of specs/02-reference/explore.html found and that Step 2 measured for five model sizes: one register token holds very large values inside the backbone. These values decide where fp16 and bf16 can run.

The values in Sections 5 and 6 come from the stored reference files of ViT-S/16, ViT-S+/16, ViT-B/16, ViT-L/16 and ViT-H+/16. In Step 2, ViT-7B/16 had no reference file: its memory check failed (36.5 GB needed, 23.2 GB available), and the user deferred it. Step 5 added a streamed fp32 reference of ViT-7B/16 on 2026-11-07: the fp32 weights of one block at a time, 4.82 GB need (path D4-Y, 05-3, Section 8). Figure 2 (a) and Tables 2 and 5 use it.

2 From image file to pixels

The backbone takes a normalized fp32 tensor with shape (1, 3, H, W). H and W are multiples of 16. src/dinov3_mlx/preprocess.py makes this tensor in four steps:

  1. load_image decodes the file with Pillow to an (h, w, 3) uint8 RGB array.
  2. preprocess divides the pixels by 255.
  3. It resizes the float pixels to (H, W) with a bilinear filter and antialiasing.
  4. It subtracts the ImageNet mean and divides by the ImageNet standard deviation of each color channel.
def preprocess(image: np.ndarray, size: tuple[int, int]) -> torch.Tensor:
    pixels = torch.from_numpy(image).permute(2, 0, 1).unsqueeze(0).to(torch.float64) / 255.0
    resized = F.interpolate(pixels, size=size, mode="bilinear", antialias=True)  # float pixels
    mean = IMAGENET_MEAN.to(torch.float64).view(1, 3, 1, 1)  # (0.485, 0.456, 0.406)
    std = IMAGENET_STD.to(torch.float64).view(1, 3, 1, 1)    # (0.229, 0.224, 0.225)
    return ((resized - mean) / std).to(torch.float32)          # fp64 math, fp32 result

The Hugging Face image processor does the same math in fp32. Our version does it in fp64 and casts the result to fp32. On the test images, the fp32 resize of torch was up to 2.25e-5 away from an fp64 resize. A Pillow float resize (mode F) was within 9e-8. With the fp64 version, a second implementation of the resize can agree with the stored pixels to 1e-7. The stored pixels differ from the Hugging Face image processor by up to about 2e-5. A resize of 8-bit pixels differs by up to 0.004 and drops the patch minimum of ViT-H+/16 to 0.93 (Step 1).

scripts/make_reference.py runs preprocess once and writes the result to inputs.safetensors. Every backend reads these stored pixels. So a parity test measures only the backbone. A separate test compares preprocess with the stored pixels (largest difference 0.0).

own_aspect_size(height, width, short_side=224) gives the input resolution that keeps the aspect ratio of an image. The short side becomes 224 px. The long side is rounded to the nearest multiple of 16.

3 The token sequence

The patch embedding cuts the image into patches of 16 × 16 px and maps each patch to one patch token. Then the backbone puts 5 learned tokens in front: the CLS token at position 0 and the 4 register tokens at positions 1 to 4. These 5 tokens are the prefix tokens. RoPE rotates only the patch tokens. Each block reads and writes the full sequence.

The patch tokens come in row-major order. The patch in row r and column c of a grid with W/16 columns is at sequence position 5 + r · (W/16) + c. For the input of 224 × 400 px, the grid has 14 rows and 25 columns, and the sequence has 5 + 350 = 355 tokens.

4 The final layer norm and the two outputs

After the last block, the final layer norm normalizes each token over its D channels and applies a learned scale and shift. The Hugging Face model returns the normalized sequence as last_hidden_state. Its pooler_output is row 0 of it. The frame embedding is row 0. The patch embeddings are rows 5 to 5 + N − 1, as a grid. The register tokens are not part of either output.

NUM_PREFIX_TOKENS = 5  # the CLS token and the 4 register tokens

def split_tokens(tokens: np.ndarray, height: int, width: int) -> tuple[np.ndarray, np.ndarray]:
    frame = tokens[..., 0, :]                    # the CLS token after the final layer norm
    patches = tokens[..., NUM_PREFIX_TOKENS:, :] # rows 1 to 4 (register tokens) are dropped
    grid = (height // PATCH_SIZE, width // PATCH_SIZE)
    return frame, patches.reshape(*tokens.shape[:-2], *grid, tokens.shape[-1])

The "..." in the slices keeps a batch axis when there is one. A test builds a synthetic sequence in which row i holds the value i. Then it checks that the frame embedding is row 0, that the first patch embedding is row 5, and that the patch below it is row 5 + W/16.

Each reference file stores all tokens after the final layer norm, (1 + 4 + N, D) for each configuration, so later steps can compare any slice. For one configuration (iss-kibo-lab/224x224) it also stores the hidden states: the sequence before block 1 and after each block, before the final layer norm, with shape (L + 1, 201, D). Step 4 uses them to find the first block that differs. Section 5 uses them for the register values.

Five facts follow from the data:

  • Few channels. The large values sit in 3 to 14 channels of one register token. In the channel with the largest value, the patch tokens hold only 26 to 221 (median). The norm of that register token is 14 times (ViT-S/16) to 206 times (ViT-L/16) the median norm of a patch token.
  • Steps, not growth. The value jumps in a few blocks and then stays almost constant. The residual connections carry it from block to block. ViT-B/16 jumps after block 3 (9,606) and after block 11 (14,926).
  • ViT-L/16 from block 1. Its register token R2 holds 155,923 after block 1 already and keeps about this value to the last block.
  • ViT-H+/16 from block 23. Its largest value goes from 3,703 after block 22 to 131,121 after block 23. At 448 px the same jump reaches about 59,900 (probe, iss-conference), below the fp16 maximum.
  • The final layer norm removes them. After the final layer norm, no output value is above 18. The register tokens are dropped anyway, but the other tokens saw the large values through the attention in every block.

The DINOv3 paper (Appendix A.1) explains why the registers exist. Without them, a large ViT puts tokens with a very high norm into some patches of low-information regions, for example the sky. These tokens carry the internal communication between the patches and the CLS token. Darcet et al. (2024) added register tokens to take over this role, and DINOv3 uses 4 of them. Our data shows the result: the high norm is in one register token, not in the patch tokens. Appendix A.2 of the paper also describes feature-dimension outliers in all tokens and recommends the final layer norm for the outputs. Our largest values sit in one register token only, so they match the first kind. ViT-7B/16 also shows the second kind after its last block: channel 1557 holds −7,600 to −4,225 in every patch token, and the largest value of R2 is in the same channel (our read of the streamed reference file).

6 Half precision and the large values

The parity tests run torch-mps in five dtype modes. In cast mode, the weights, the inputs and the residual stream are in the half-precision dtype. In autocast mode, the weights and the residual stream stay in fp32, and torch.autocast runs the matrix products in the half-precision dtype.

fp16. The largest fp16 value is 65,504. A larger value becomes infinite, and the next layer norm or softmax gives NaN. In fp16-cast mode, ViT-L/16 gives NaN in all 12 configurations, because its register value is above the fp16 maximum from block 1 on. ViT-H+/16 gives NaN in the 6 configurations with a short side of 224 px, and finite outputs at 448 and 512 px. The tests record each case as an expected failure. fp16-autocast keeps the residual stream in fp32. All its configurations give finite outputs and pass.

bf16. bf16 has the range of fp32, so it does not overflow. But it has only 8 significant bits. Near 131,072 the spacing of bf16 values is 1,024. The parity tests found 5 bf16 configurations below the first proposal of thresholds (0.999, 0.999 and 0.99). A probe ran the same configurations on torch-cpu in bf16 and got the same values, for example frame 0.998498 on torch-cpu and 0.998365 on torch-mps (ViT-S+/16, bf16-autocast, iss-kibo-lab at 224 × 400 px). So the cause is bf16 arithmetic, not the backend.

ViT-H+/16 at 224 px is sensitive to its input. In fp32, with only the stored pixels rounded to bf16, its patch 1st percentile is 0.9925 and its patch minimum 0.968 (iss-conference). At 448 px the same change gives 0.9999. In bf16-cast mode, the patch tokens move away from fp32 block by block after block 23, where the register value jumps: their 1st percentile goes from 0.994 to 0.953 at block 31. RoPE tables in fp32 and a final layer norm in fp32 did not fix this (patch 1st percentile 0.972 and 0.969).

On 2026-11-06 the user gave bf16 its own thresholds (Section 7). Step 5 must handle both effects in MLX: an fp32 residual stream, or another way to keep the register values out of fp16.

7 The parity metric

measure_parity(reference, output) compares two token sequences of shape (1 + 4 + N, D). It computes the cosine similarity of each pair of rows in fp64. In fp64, two equal fp32 vectors give 1.0 within a few units of 1e-16. In fp32 the same vectors can give 0.9999996.

def measure_parity(reference: np.ndarray, output: np.ndarray) -> Parity:
    ref, out = reference.astype(np.float64), output.astype(np.float64)
    cos = (ref * out).sum(-1) / (np.linalg.norm(ref, axis=-1) * np.linalg.norm(out, axis=-1))
    cos = np.minimum(cos, 1.0)
    patches = cos[NUM_PREFIX_TOKENS:]               # the register rows are not used
    return Parity(frame=float(cos[0]), patch_mean=float(patches.mean()),
                  patch_p01=float(np.quantile(patches, 0.01)), patch_min=float(patches.min()))

Example (Table 10 of docs/plan.html): the reference (1, 2, 2) and the output (1, 2, 2.1) give 9.2 / (3 × 3.0676) = 0.9997. This fails the fp32 threshold and passes the fp16 and the bf16 threshold.

The 1st percentile replaces the minimum as the patch threshold. One sensitive patch sets the minimum: ViT-H+/16 in bf16-cast mode has a patch minimum of 0.845 at 224 px, and its 1st percentile is 0.969. With linear interpolation, the 1st percentile of 196 patches lies between the 2nd and the 3rd lowest value. An error in one row of patches (14 of 196, 7 %) still fails.

8 The code of Step 2

8.1 src/dinov3_mlx/hub.py

  • CONVERTED_DIR is the folder of the converted weights, ~/.cache/dinov3-mlx/converted. scripts/convert_meta_checkpoint.py now imports it from here.
  • weights_dir(model_size, cache_dir=None, converted_dir=CONVERTED_DIR) returns the folder with config.json and the safetensors files. It takes the Hugging Face cache first, but only when every shard of the index is there. Else it takes the converted folder. Else it raises WeightsNotFoundError. The tests use a temporary cache folder, also one with a missing shard.

8.2 src/dinov3_mlx/memory.py

  • available_memory_bytes() reads vm_stat. It counts the free, speculative and purgeable pages, plus the inactive pages up to the number of file-backed pages, times the page size. macOS can drop file-backed pages at once; the other inactive pages hold app memory that macOS must compress or swap first. (Changed after Verify, finding F6. The Step 2 runs used free plus all inactive pages.)
  • check_free_memory(required_bytes, label) logs one line ("memory check: ViT-S/16 torch-mps fp16-cast: needs 4.1 GB, 21.0 GB available, ok") and raises InsufficientMemoryError when the memory does not fit. It returns the available bytes. GB is 1e9, the unit of the log line.

8.3 src/dinov3_mlx/preprocess.py and outputs.py

  • IMAGENET_MEAN, IMAGENET_STD, PATCH_SIZE, own_aspect_size, load_image and preprocess: Section 2.
  • NUM_PREFIX_TOKENS and split_tokens: Section 4.

8.4 src/dinov3_mlx/parity.py

  • Parity holds the four measures. THRESHOLDS maps each dtype mode to a Parity with the limits; its patch_min is −1 because the minimum is report only. measure_parity: Section 7. The module uses NumPy only, so the MLX tests of Steps 4 and 5 can use it without torch.

8.5 src/dinov3_mlx/reference.py

  • DtypeMode holds the dtype of the weights and the dtype of autocast (or None). DTYPE_MODES maps the five names of Table 3 to it.
  • Configuration is one test image at one input resolution. Its id is the key in the stored files, for example forest/224x304. It also gives image_path and num_patches. configurations() returns the 12 configurations of Table 1 in a fixed order.
  • model_slug gives the part of the Hugging Face id between dinov3- and -pretrain, and reference_path gives reference-{slug}.safetensors in REFERENCE_DIR.
  • parameter_count sums the tensor sizes from the safetensors headers without a load. required_load_bytes gives the memory check of a load: LOAD_RATIO (1.2) × the weight bytes in the load dtype + LOAD_RESERVE_BYTES (4 GB).
  • load_torch_backbone(model_size, device, dtype_mode) runs the memory check, then loads DINOv3ViTModel from weights_dir in the weight dtype of the dtype mode, and moves it to the device.
  • run_torch(model, pixels, dtype_mode) runs the backbone on stored pixels and returns all tokens after the final layer norm as fp32, shape (B, 1 + 4 + N, D). run_torch_hidden_states returns the (L + 1, 1 + 4 + N, D) hidden states.
  • read_inputs and read_reference read the stored files with safetensors in NumPy mode. read_reference also returns the JSON metadata. REQUIRED_METADATA lists its fields: versions, SHA-256 of the test images and of the weight files, preprocessing settings, weight source, attention implementation, run time, peak memory and date. REPO_ROOT, IMAGES_DIR, INPUTS_FILE, TEST_IMAGES, SQUARE_SIZES and HIDDEN_STATES_CONFIG give the paths and the names. REFERENCE_DIR is tests/fixtures/generated/reference/, which git ignores.
@torch.inference_mode()
def run_torch(model: DINOv3ViTModel, pixels: np.ndarray, dtype_mode: str) -> np.ndarray:
    mode = DTYPE_MODES[dtype_mode]
    device = _device_type(model)
    tensor = torch.from_numpy(pixels).to(device=device, dtype=mode.weights)  # cast mode: fp16 or bf16
    if mode.autocast is None:
        output = model(pixel_values=tensor)
    else:
        with torch.autocast(device_type=device, dtype=mode.autocast):        # autocast mode
            output = model(pixel_values=tensor)
    return output.last_hidden_state.float().cpu().numpy()

8.6 The scripts and the tests

  • scripts/make_test_images.py downloads the three photos from Wikimedia Commons, checks the SHA-1 of each against the Commons API, crops, resizes and writes SOURCES.md.
  • scripts/make_reference.py writes the stored pixels. Then it starts one subprocess for each model size, smallest first, after a memory check. It learns the load ratio from the peak memory of model sizes with at least 1 GB of fp32 weights. ViT-L/16 gave 1.21, so the check for ViT-7B/16 asked for 36.5 GB.
  • scripts/parity_table.py turns the JSON lines of the parity tests into results/parity-torch-mps.md.
  • tests/conftest.py sets the MPS watermarks before torch is imported, keeps one model in memory at a time, logs each memory check and records every measured, non-finite or skipped configuration.

9 Surprises

  1. ViT-L/16 overflows in fp16 at every input resolution. explore.html expected the fp16 overflow only for ViT-H+/16. ViT-L/16 has a register value above 155,000 from block 1 on, so fp16-cast mode gives NaN in all 12 configurations.
  2. Every model size has large register values. ViT-B/16 reaches 23 % of the fp16 maximum, ViT-S/16 only 2.6 %. The largest values do not grow with the model size: ViT-L/16 is above ViT-H+/16.
  3. The fp32 resize of torch is not exact. The antialiased fp32 resize is up to 2.25e-5 away from the fp64 resize; Pillow in mode F is within 9e-8. We now resize in fp64.
  4. The bf16 failures are not a torch-mps defect. torch-cpu in bf16 gives the same parity. For ViT-H+/16 at 224 px, a rounding of the input pixels alone moves some patch embeddings to a cosine of 0.968.
  5. One ViT-S+/16 input is special. Only iss-kibo-lab at 224 × 400 px fails the first bf16 proposal for ViT-S+/16. On this input, bf16 autocast is worse than bf16 cast (frame 0.9984 and 0.9994), on both backends. Its register values are normal.
  6. Batches change nothing. A batch of 8 gives the same output as 8 runs with batch size 1 on torch-mps in every dtype mode (parity 1.000000).
  7. Free memory is less than it looks. memory_pressure showed 60 % free memory, but the memory compressor held 20 GB. vm_stat gave 21 to 23 GB of free and inactive pages, too little for ViT-7B/16 in fp32. Only about 7 GB of that needs no compression or swap.
