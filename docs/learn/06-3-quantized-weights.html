1 Why this explainer

Step 6 adds quantized weights to the MLX backbone. The weights of the nn.Linear modules of the blocks become 8-bit or 4-bit integers. Each group of 64 weights of one row gets one scale and one offset. This is the affine format of MLX (D14 of specs/06-speed/plan.html). The loader quantizes each block weight directly after it reads the weight from the file (path L2, D17). The benchmark matrix has quantized rows for ViT-H+/16 and ViT-7B/16 in fp16-autocast and bf16-autocast (D15, D22).

This page covers the functions of row 06-3-quantized-weights.html in Table 5 of specs/06-speed/plan.html. Table 1 below lists them. Each section quotes the code with its line numbers in commit 2567808. Each quote is an exact copy. A quote that leaves out lines says "shortened" in its first line. 06-2 explains quantized_weight_bytes, BenchConfig.bits and the quantized rows of the benchmark driver. 06-1 explains compile_backbone, which runs after the load.

The agent that wrote this page ran no test, no model and no GPU job. It read the values from the committed result files of Section 12 with a small CPU-only Python script. Values that the agent computed from these files (ratios, shares, the bytes of one module) carry the mark "our computation".

The result in three numbers:

  • Parity. 8 bits pass the thresholds of their dtype mode (THRESHOLDS[mode]) in 72 of 72 test configurations. 4 bits pass in 0 of 72 (results/parity-mlx.md, Table 7).
  • Memory. The load peak of ViT-7B/16 falls from 13.53 GB (fp16 or bf16 weights) to 7.33 GB (8 bits) and 3.98 GB (4 bits) (results/speed-matrix.jsonl).
  • Time. At P2, quantized ViT-H+/16 gives 0.874 to 0.884 (8 bits) and 0.924 to 0.935 (4 bits) of the unquantized throughput (change ratio C5, results/speedup-table.md, Table 4). Quantized weights save memory, not time.

In this page, 1 GB is 109 bytes, as in the result files.

2 The affine format in one picture

Figure 1 follows one row of one block weight. up_proj of ViT-H+/16 maps 1,280 values to 5,120 values. MLX stores its weight as a (5120, 1280) matrix, with one row for each output value. mx.quantize cuts each row into groups of 64 weights. Each group gets its own scale and its own offset.

The affine format has four rules (MLX 0.32.4, docstring of mx.quantize):

  1. α is the largest and β is the smallest of the 64 weights of one group.
  2. The scale is s = (α − β) / (2b − 1), with b = 8 or 4.
  3. Each weight w becomes the integer q = round((w − β) / s), from 0 to 2b − 1.
  4. The matmul uses ŵ = s · q + β in place of w. The rounding error |w − ŵ| is at most s / 2.

For one group, the 4-bit scale is (28 − 1) / (24 − 1) = 255 / 15 = 17 times the 8-bit scale (our computation). So the largest rounding error at 4 bits is also 17 times the largest rounding error at 8 bits. Section 9 shows the effect on the parity. The docstring names the integer q "ŵ". This page uses ŵ for the value s · q + β.

The kernel differs in two details. The four rules come from the docstring. The Metal kernel affine_quantize of MLX 0.32.4 (mlx/backend/metal/kernels/quantized.h in the installed package) does two things differently. First, β is the end of the range with the larger magnitude. If that end is the largest weight, the scale is negative, and level 0 is the largest weight. Second, the kernel changes s a little, so that the weight 0 falls exactly on a level. Thus the factor 17 and the bound s / 2 are true only approximately for the kernel. The kernel also computes q with the fp32 value of s, and then it stores s in the dtype of the input (our reading of the kernel source).

The scale and the offset get the dtype of the input of mx.quantize (the table of modes in the same docstring). The loader casts each weight to the matmul dtype before mx.quantize. So the scales are fp16 in fp16-autocast and bf16 in bf16-autocast. Section 9 shows that bf16-autocast loses more parity than fp16-autocast at 8 bits, and how the scale dtype can cause a part of this loss.

  • Line 46. docs/plan.html names 8 and 4 bits only (D14, option D of explore.html). load_mlx_backbone raises ValueError for any other value, for example 6 (T50).

4 Which modules get quantized weights

nn.quantize(model, class_predicate=…) visits each leaf module of the tree (model.leaf_modules()). It calls the predicate with the path and the module. If the predicate returns a dict, nn.quantize calls module.to_quantized(**dict), and nn.Linear.to_quantized returns an nn.QuantizedLinear. If the predicate returns False, the module stays (MLX 0.32.4, python/mlx/nn/layers/quantized.py). The plan read the MLX source to confirm the dict form (Section 3.5 of the plan).

# src/dinov3_apple/mlx_weights.py, lines 209 to 228
def block_linear_predicate(
    bits: int, group_size: int = GROUP_SIZE
) -> Callable[[str, nn.Module], dict | bool]:
    """Return the class predicate of nn.quantize for the block nn.Linear modules (D16).

    The patch embedding keeps the matmul dtype: it is the most sensitive part (probe Q5) and the
    path of F1 of Step 4. The predicate returns the parameters of each module, so a later mixed
    row (other bits for one module group) changes only this function.

    Args:
        bits: 8 or 4.
        group_size: The number of weights of one row that share one scale and one offset.
    """

    def predicate(path: str, module: nn.Module) -> dict | bool:
        if isinstance(module, nn.Linear) and path.startswith("layer."):
            return {"group_size": group_size, "bits": bits}
        return False

    return predicate
  • Line 224, first condition. The module must be an nn.Linear. The layer norms and LayerScale stay as they are.
  • Line 224, second condition. The path must start with "layer.". The blocks of MlxBackbone live in the list layer, so their paths are layer.0.attention.q_proj to layer.{L − 1}.mlp.down_proj, the Hugging Face names. Each SwiGLU block has 7 such modules: q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj and down_proj. T44 checks 7 · L quantized modules for a SwiGLU small model and 6 · L for an MLP small model.
  • The patch embedding stays in the matmul dtype (D16). It is an nn.Linear too (04-1), but its path is embeddings.patch_embeddings. D16 gives three reasons. It is the most sensitive part: in probe Q5 the patch embedding alone at 4 bits gave a lower patch 1st percentile than all block weights at 4 bits together (Section 2.6 of explore.html). It holds a small share of the weights: the blocks hold 98.3 % to 99.9 % of all parameters. And a quantized patch embedding is the path of the fault F1 of Step 4 (04-1, Section 6). T44 checks that the predicate returns False for embeddings.patch_embeddings.
  • Line 225, a dict and not True. With True, nn.quantize would take group_size and bits from its own arguments. The dict carries them per module. The mode stays the MLX default "affine". The docstring names the reason: a later mixed row, for example other bits for one module group, changes only this function. Probe Q5 found that the tested mixed rows also fail at 4 bits (Section 9).

5 The names of a quantized module

linear_parameter_names tells mlx_weights which tensors get the matmul dtype. All other tensors get the stream dtype (05-2). In Step 5 the function found the modules with isinstance(module, nn.Linear). nn.quantize replaces each block nn.Linear by an nn.QuantizedLinear. In MLX 0.32.4, nn.QuantizedLinear is a subclass of nn.Module, not of nn.Linear. So the Step 5 form misses every quantized module (F1 of the plan). Step 6 changes one line:

# src/dinov3_apple/mlx_model.py, lines 525 to 548
def linear_parameter_names(model: nn.Module) -> frozenset[str]:
    """Return the names of the parameters of each nn.Linear and nn.QuantizedLinear module: the
    matmul dtype (D2).

    nn.QuantizedLinear is not a subclass of nn.Linear (F1 of specs/06-speed/plan.html): its
    weight, scales, biases (the offsets) and bias count too. The names come from named_modules()
    and isinstance, not from name suffixes. All other parameters get the stream dtype.
    """
    return frozenset(
        f"{name}.{leaf}"
        for name, module in model.named_modules()
        if isinstance(module, nn.Linear | nn.QuantizedLinear)
        for leaf in module.parameters()
    )


def quantized_weight_names(model: nn.Module) -> frozenset[str]:
    """Return the names of the weight of each nn.QuantizedLinear module: the tensors that the
    quantized load quantizes (D17 of specs/06-speed/plan.html)."""
    return frozenset(
        f"{name}.weight"
        for name, module in model.named_modules()
        if isinstance(module, nn.QuantizedLinear)
    )
  • Line 536. isinstance accepts the union type nn.Linear | nn.QuantizedLinear. The patch embedding stays an nn.Linear, so its weight and bias stay in the set.
  • Line 537. module.parameters() of an nn.QuantizedLinear has the keys weight, scales and biases, plus bias if the module has a bias. T43 checks this on the small model vits16plus: the names of each quantized module equal its parameters, and bias is there only where the config has a bias (the small configs have no k_proj bias).
  • What line 536 prevents. Without it, the file tensor layer.0.attention.q_proj.weight is not in linear. mlx_weights then casts it to the stream dtype, which is fp32 in the autocast modes. mx.quantize then gives fp32 scales and offsets, and the bias stays fp32 too. The strict load accepts all of it, because it checks no dtype (Section 6). The plan gives the cost: fp32 scales cost up to 6 times the dense time (D15, option E, Section 3.5 of the plan).
  • Lines 541 to 548. quantized_weight_names gives only the .weight names of the quantized modules. The loader quantizes exactly these tensors. T43 checks 14 names for vits16plus (2 blocks × 7 modules), and that the patch embedding weight is in linear but not in quantized. For ViT-H+/16 the set has 224 names (Table 3).
  • The module tree, not name suffixes. Both functions read the type of each module. A rule on the parts of a name cannot tell the two meanings of "bias" apart (the note below).

Two parameters with almost the same name. In an nn.QuantizedLinear, biases holds the offsets β of the groups: shape (5120, 20) for up_proj of ViT-H+/16. bias holds the additive bias of the module from the Hugging Face file: shape (5120). The forward pass of the module calls mx.quantized_matmul with the packed weight, the scales and the offsets, and then adds bias if the module has one (MLX 0.32.4, QuantizedLinear.__call__). This page says "offset" for β and "bias" for the additive bias, as GLOSSARY.md does.

6 The loader

Figure 2 shows the order of the actions of load_mlx_backbone with bits. The numbers are those of the action list of Section 3.5 of the plan. The run rule, the check of the bits and the memory check come before any file read.

# src/dinov3_apple/mlx_weights.py, lines 244 to 251 and 282 to 329 (shortened: the docstring, lines 252 to 281, is left out)
def load_mlx_backbone(
    model_size: str,
    dtype_mode: str = "fp32",
    tf32: bool = False,
    ratio: float = LOAD_RATIO,
    bits: int | None = None,
    group_size: int = GROUP_SIZE,
) -> MlxBackbone:
    ⋮
    dtypes = MLX_DTYPE_MODES[dtype_mode]
    label = f"{model_size} mlx {dtype_mode}" + (f" {bits}-bit" if bits else "")
    check_run_rule(model_size, dtypes.matmul.size, label)
    if bits is not None:
        if bits not in QUANTIZED_BITS:
            raise ValueError(f"bits must be one of {QUANTIZED_BITS}, not {bits}")
        if dtype_mode not in QUANTIZED_MODES:
            raise ValueError(f"quantized bits load in {QUANTIZED_MODES} only, not in {dtype_mode}")
    if dtypes.matmul == mx.float32 and tf32_enabled() != tf32:
        raise TF32ModeError(f"set MLX_ENABLE_TF32={int(tf32)} before the first use of mlx")
    need = required_mlx_load_bytes(model_size, dtype_mode, ratio, bits)
    check_free_memory(need, label)
    mx.set_memory_limit(need)  # only a guideline (R13 of Step 4): the loop keeps the peak low
    folder = weights_dir(model_size)
    config = MlxConfig.from_hf(json.loads((folder / "config.json").read_text()))
    model = MlxBackbone(config, dtype_mode)  # the random init stays lazy and is never computed
    if bits is not None:
        nn.quantize(model, class_predicate=block_linear_predicate(bits, group_size))
    linear = linear_parameter_names(model)  # nn.Linear and nn.QuantizedLinear (F1)
    quantized = quantized_weight_names(model)  # the .weight of each QuantizedLinear
    placeholder_skeleton(model)  # no lazy random weight of the whole model is left (R50)
    tensors: dict[str, mx.array] = {}
    for file in sorted(folder.glob("*.safetensors")):
        tensors |= mx.load(str(file))  # lazy; a str, not a Path (R18)
    active_before = mx.get_active_memory()
    mx.reset_peak_memory()
    pairs = []
    for key, array in mlx_weights(tensors, dtypes, linear):
        if key in quantized:
            weight, scales, biases = mx.quantize(array, group_size, bits)
            mx.eval(weight, scales, biases)  # one source, its cast and its quantized output
            stem = key.removesuffix(".weight")
            pairs += [(key, weight), (f"{stem}.scales", scales), (f"{stem}.biases", biases)]
            continue
        mx.eval(array)  # reads one tensor from its file and casts it
        pairs.append((key, array))
    model.load_weights(pairs, strict=True)
    del pairs
    mx.clear_cache()  # the freed fp32 buffers leave the MLX cache
    model.load_report = LoadReport(
        need_bytes=need,
        peak_bytes=mx.get_peak_memory() - active_before,
        cache_bytes=mx.get_cache_memory(),
        footprint_bytes=read_footprint().current_bytes,
        bits=bits,

    record_load_peak(label, model.load_report.peak_bytes, model.load_report.cache_bytes)

  • Line 284. check_run_rule gets the size of the matmul dtype: 2 bytes in both autocast modes. So ViT-7B/16 loads with bits. In fp32 the run rule stops ViT-7B/16 before any file read (ADR 0008).
  • Lines 285 to 289. bits must be in QUANTIZED_BITS, and the dtype mode must be in QUANTIZED_MODES: fp16-autocast or bf16-autocast. Else the loader raises ValueError before any file read (T50). D15, option C chose the two autocast modes. In fp32 the scales would be fp32 (D15, option E). No decision covers the cast modes.
  • Line 292. The need uses the quantized bytes (Section 8).
  • Line 297. The skeleton holds random weights. nn.Linear makes them with mx.random.uniform in fp32. MLX computes lazily, so these weights do not take memory yet.
  • Lines 298 and 299. nn.quantize replaces the block nn.Linear modules (Section 4). The new modules still reference the lazy random weights (Section 7).
  • Lines 300 and 301. The two name sets come from the tree after nn.quantize. The order is necessary: before nn.quantize the tree has no nn.QuantizedLinear, and quantized would be empty.
  • Line 302. The placeholders replace every parameter (Section 7). The unquantized load (bits=None) runs this line too.
  • Lines 303 to 307. mx.load opens each safetensors file lazily: it reads no tensor yet. The loader reads the active memory and resets the MLX peak. So the load peak counts only the work of the loop.
  • Lines 309 to 317. This loop is path L2. mlx_weights pops one fp32 tensor and maps its key. It casts the tensor to the matmul dtype if the name is in linear, else to the stream dtype (05-2). So each block weight arrives in the matmul dtype. For a block weight, mx.quantize gives three arrays: the packed weight (uint32), the scales and the offsets (both in the matmul dtype). mx.eval computes the three together. For a short time, the fp32 source, its cast and the three outputs exist together, for this one tensor only. The file has no tensors with the names .scales and .biases: lines 313 and 314 make these names from the stem of the weight name.
  • Line 318. load_weights(strict=True) checks that each name of the skeleton gets an array with the same shape, and that no other name comes in. The MLX cache after the load is 0 bytes in every quantized load of the matrix (load_report_cache_bytes in results/speed-matrix.jsonl).
  • Lines 321 to 328. The load report gets the field bits (Section 8).

In both autocast modes and at both bit widths, every parameter of L2 must equal the parameter of L1 bit for bit, with the same dtype. 7 The placeholder skeleton

The skeleton of ViT-7B/16 holds random fp32 weights for the whole model: 4 bytes × 6,716,035,072 parameters = 26.9 GB (our computation; the plan says "about 27 GB"). They stay lazy, so they take no memory. But one mx.eval of the skeleton computes them. That breaks ADR 0008 on a Mac that crashed from out-of-memory before (risk R50 of the plan).

nn.quantize does not remove the hazard. In MLX 0.32.4, nn.Linear.to_quantized calls QuantizedLinear.from_linear. from_linear makes a new nn.QuantizedLinear. Its constructor makes and quantizes a second random fp32 weight. Then from_linear sets the weight, the scales and the offsets to mx.quantize of the random weight of the old nn.Linear. All of it stays lazy. So after line 299 the packed weight of each quantized module is a lazy graph that still references the full random fp32 weight of its nn.Linear.

# src/dinov3_apple/mlx_weights.py, lines 231 to 241
def placeholder_skeleton(model: nn.Module) -> None:
    """Replace each parameter of a model before a load by a zero-stride placeholder (R50).

    The placeholder has the shape and the dtype of the parameter, so load_weights(strict=True)
    checks the same names and shapes. An evaluated placeholder holds one value. So an mx.eval of
    the skeleton, by mistake, allocates bytes, not the random fp32 weights of the whole model
    (about 27 GB for ViT-7B/16, against ADR 0008).
    """
    model.update(
        tree_map(lambda p: mx.broadcast_to(mx.zeros((), p.dtype), p.shape), model.parameters())
    )
  • Line 240. tree_map visits each parameter p. mx.zeros((), p.dtype) is one zero value. mx.broadcast_to gives it the shape of p with stride 0. An evaluated placeholder holds one value: 4 bytes or less.
  • Line 239. model.update replaces the parameters. The lazy random arrays lose their last reference, and MLX never computes them.
  • The dtype of a placeholder. The placeholder keeps the dtype of p. The placeholder of a packed weight is uint32. The placeholder of scales is fp32, because the random source of the skeleton is fp32. The loaded scales are fp16 or bf16. The strict load accepts this change, because it checks no dtype. T47 checks the dtypes after the load: each scales, biases and bias has the matmul dtype, each packed weight is uint32, and the patch embedding weight has the matmul dtype (risk R46).
  • The order: first nn.quantize, then the placeholders. The plan sets this order (Figure 2 of the plan). With the opposite order, nn.quantize would make each packed weight, scale and offset as a lazy mx.quantize output of a placeholder. These outputs are full-size arrays, not zero-stride views. So an mx.eval by mistake would again allocate memory for each quantized module (our reading of the MLX code).
  • T45. The test uses a small model with the shape of ViT-7B/16 at embedding dimension 1,024 and 8 blocks. After nn.quantize and placeholder_skeleton, an mx.eval of all parameters may grow the active memory by at most 1 MB. The control is the unquantized skeleton of the same config in the fp32 dtype mode, without placeholders. It must grow by at least 0.9 × its fp32 bytes; the plan expects about 335 MB (Table 21 of the plan). So the test shows that it can see the hazard.

Every 4-bit row of Table 5 fails all three thresholds. The frame value alone fails every 4-bit row: 0.861780 to 0.993235 in the tests, and 0.992172 to 0.994344 in the 72 quantized 4-bit rows of the speedup table (image 0, results/speedup-table.md, Table 3). The frame thresholds are 0.999 (fp16) and 0.998 (bf16). Three facts explain the result:

  1. The thresholds are made for half-precision rounding. The frame may lose 0.001 of cosine in fp16 and 0.002 in bf16 (1 − threshold). The 8-bit rows use at most 60.8 % (fp16) and 75.8 % (bf16) of this budget, both in ViT-S/16 (our computation from Table 5).
  2. 4 bits round 17 times coarser (Section 2). For a small error, 1 − cos grows with the square of the error. So 17 times the error gives about 17² = 289 times the loss. In the fp16-autocast rows of Table 5, the 4-bit frame loss is 205 to 278 times the 8-bit frame loss. In the bf16-autocast rows it is 64 to 105 times, because the bf16 rounding adds a loss that does not depend on the bits (our computation and our estimate).
  3. So the 4-bit loss is far above the budget. The 4-bit frame loss is 3.4 (ViT-7B/16, bf16-autocast) to 138 (ViT-S/16, fp16-autocast) times the frame budget (our computation). No 4-bit row can pass.

Over the three model sizes of Table 5, the loss at 4 bits falls with the model size. The 4-bit frame value is 0.86 for ViT-S/16, 0.987 for ViT-H+/16 and 0.993 for ViT-7B/16 (Table 5). But even ViT-7B/16 stays far below the frame threshold.

No single weak module group causes the failure. Probe Q5 (ViT-H+/16, bf16-autocast) quantized one module group at a time to 4 bits: q, k, v and o; gate and up; down. Each group alone failed. Rows with all blocks at 4 bits and some modules at 8 bits failed too. The patch embedding alone at 4 bits was worse than all blocks at 4 bits (Section 2.6 of explore.html). D16 keeps the patch embedding unquantized, so the 4-bit rows of Step 6 lose parity only in the blocks.

At 8 bits, bf16-autocast loses more than fp16-autocast. Against its own unquantized output, the patch 1st percentile of ViT-H+/16 is 0.998775 in fp16-autocast and 0.995660 in bf16-autocast (Table 5). Over the three model sizes, the bf16 loss (1 − value) is 2.1 to 5.6 times the fp16 loss at 8 bits, but 0.92 to 1.00 times at 4 bits (our computation from the last column of Table 5).

The rounding of the scale can cause a part of this loss (our reading of the kernel source, Section 2). The kernel computes q with the fp32 scale. Then it stores the scale in the matmul dtype. The rounding error of the stored scale moves ŵ by up to q times that error. bf16 keeps 8 significant bits, fp16 keeps 11. At 8 bits q goes up to 255, so the bf16 rounding of s can move ŵ by up to about one step s. The fp16 rounding moves ŵ by up to about s / 8. At 4 bits q goes up to 15 only, so this error stays small against the 17 times larger step. The quantized matmul also rounds ŵ = s · q + β to the matmul dtype before the multiply-adds. Step 6 did not measure these roundings one by one.

The 8-bit margin is small for ViT-S/16. Its bf16-autocast frame value 0.998484 is only 0.000484 above the threshold 0.998. ViT-S/16 has no quantized rows in the benchmark matrix (QUANTIZED_MODEL_SIZES), only in the tests.

10.1 Why fewer bytes do not give more speed

A matmul of an (M, K) input with a (K, N) weight does 2 · M · K · N FLOPs and reads K · N weights. Each weight serves M rows. Here M is the number of tokens in the batch. One image has T = 5 + (side / 16)² tokens (Section 2 of the plan). So M = 201 at 224 px and batch size 1, and M = 8 × 1,029 = 8,232 at P2 (our computation). With so many rows for each weight, the GPU spends its time on the multiply-adds, not on the reads of the weights (our reading). Fewer weight bytes then save little time. The quantized matmul also does extra work: it unpacks each integer from its uint32 word and computes s · q + β before the multiply-adds. Section 2 of the plan states the result: on this Mac, the quantized matmul does not win at the token counts of DINOv3.

A quantized weight saves time when the matmul waits for the weight bytes, for example in a language model that makes one token at a time (M = 1). The benchmark matrix never runs with so few tokens: one image at 224 px already has 201 tokens. Even there, ViT-7B/16 at 8 bits is slower than with bf16 weights (0.931, Table 7).

4 bits are faster than 8 bits in C5 (0.924 to 0.935 against 0.874 to 0.884), but slower than the unquantized weights. Step 6 did not measure the reason.

The quantized rows stay inside the mission rule "speedup above 1" (answer 5 in Table 2 of the plan). Of the 72 valid 8-bit rows, 16 have the verdict "above 1" (2 of them inside the noise) and 56 "not above 1" (results/speedup-table.md, Table 3). verify.html gives the reason for each row that is not above 1 or not valid (AC10 of the plan), for example "quantized weights save memory, not time".

The gain of quantized weights is memory. At 8 bits the weights take 53 % of the fp16 bytes, and all 72 rows keep the parity of their dtype mode. For ViT-7B/16, the MLX peak falls from 13.61 to 14.85 GB to 7.55 to 8.49 GB in the rows of Table 7.

11 Surprises

  • nn.QuantizedLinear is not an nn.Linear. In MLX 0.32.4 it is a subclass of nn.Module only. So every isinstance(module, nn.Linear) check misses the quantized modules. linear_parameter_names now accepts both types (F1, T43). Without the change, the block weights get the stream dtype (fp32 in the autocast modes), and the scales become fp32.
  • biases (the offsets) and bias are two parameters. MLX names the offsets β of the groups biases, shape (N, K / 64). The additive bias of the module stays bias, shape (N). A quantized module with a bias has four parameters: weight, scales, biases and bias. A rule on the parts of a name cannot tell them apart; the code reads the module tree.
  • The strict load checks no dtype. load_weights(strict=True) checks names, the array type and shapes. The placeholder of each scale is fp32, and the loaded scale is fp16 or bf16; the load accepts it. A wrong cast would pass the same way. T47 checks the dtypes (R46).
  • The lazy skeleton holds random fp32 weights of the whole model. For ViT-7B/16 that is 26.9 GB. nn.quantize keeps them referenced, through the lazy mx.quantize of each nn.Linear weight. One mx.eval of the skeleton would compute them. placeholder_skeleton after nn.quantize drops all of them; T45 limits the evaluation of the skeleton to 1 MB (R50).
  • 4 bits fail in every row. 0 of 72 test configurations pass THRESHOLDS[mode] (results/parity-mlx.md, Table 7), and 0 of 72 quantized 4-bit rows of the speedup table are valid. The frame value alone fails each row: 4 bits round 17 times coarser than 8 bits, and the loss grows with the square of the error.
  • The patch embedding alone at 4 bits is the worst part. In probe Q5 (ViT-H+/16) it gave a lower patch 1st percentile than all block weights at 4 bits together. But it holds only 0.12 % of the parameters of ViT-H+/16: 1,280 × 768 + 1,280 = 984,320 of 840,592,640 (our computation). D16 keeps it in the matmul dtype. Each module group of the blocks alone at 4 bits fails too.
  • Quantized weights save memory, not time. At P2 the throughput ratio is 0.874 to 0.884 at 8 bits and 0.924 to 0.935 at 4 bits (C5). The MLX peak falls by the saving of weight bytes. In the benchmark matrix each weight serves at least 201 tokens, so the matmul does not wait for the weight bytes (our reading).
  • 4 bits are faster than 8 bits. In C5 the 4-bit ratio is 0.05 higher than the 8-bit ratio in both dtype modes (our computation). Both stay below 1. Step 6 did not measure the reason.
  • The quantization in the loader costs little load time. ViT-7B/16 loads in 1.19 to 1.42 s at 4 bits and in 1.38 to 1.82 s with fp16 or bf16 weights. ViT-H+/16 loads in 0.32 to 0.34 s at 8 bits and in 0.30 to 0.32 s with fp16 or bf16 weights (results/speed-matrix.jsonl). Step 6 did not measure where the load time goes.
  • The kernel does not follow the docstring exactly. The docstring of mx.quantize takes the smallest weight as the offset. The Metal kernel of MLX 0.32.4 takes the end of the range with the larger magnitude, can use a negative scale, and moves the levels so that 0 falls on a level. It also stores the scale in the matmul dtype after it computed q with the fp32 scale (our reading of the kernel source, Section 2).
