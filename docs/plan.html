Summary

We want fast DINOv3 frame embeddings and patch embeddings on Apple silicon. We also want to understand DINOv3 in detail. This report is the plan for both goals. On 2026-11-06 the user made three decisions. The repo is public, MLX is the fast backend, and all benchmarks run on one Apple M5 Max with 64 GB of unified memory.

The plan has nine steps, from Step 0 to Step 8. Steps 1 to 3 build the reference outputs, the parity tests and the baseline on PyTorch. Steps 4 to 6 port all six ViT model sizes to MLX and make them fast. Step 7 publishes the first release. Step 8 makes our reference fine-tuning setup fast in MLX. Then it compares DoRA and other adapters with LoRA.

Each step follows a spec loop. An agent writes the options and the plan as HTML files, and the user approves them. A new session builds from these files. A separate agent then verifies the result against numbered acceptance criteria. Each step also writes an explainer for the DINOv3 part that it touched. So our understanding of DINOv3 grows with the code.

This report has no measured results. The speed goal stays a hypothesis until Step 3 measures the baseline. Two public MLX ports of DINOv3 exist, so Step 1 must show what this repo adds. The DINOv3 License covers derivative works of the DINOv3 code. So the repo license needs a decision before the first push.

Section 2 defines the terms, and Section 3 gives the goals, the decisions and the prior work. Section 4 explains DINOv3. Sections 5 and 6 describe the spec workflow and the steps. Section 7 defines the tests and the benchmarks, and Section 8 describes the fine-tuning step. Sections 9 and 10 list the risks, the open decisions and the sources.

DINOv3 in detail

This section explains DINOv3 from the input image to the two outputs, and then the training method. We took each fact from the official code, the Hugging Face code or the paper. The explainers of Steps 2 to 8 go deeper into each part.

The forward pass

The backbone computes the two outputs in these steps.

  1. Normalize the image with the ImageNet mean and standard deviation.
  2. Cut the image into patches of 16 × 16 pixels.
  3. Map each patch to a patch token with a 16 × 16 convolution with stride 16.
  4. Put the CLS token and the 4 register tokens in front of the patch tokens.
  5. Compute the RoPE tables from the patch grid.
  6. Send the token sequence through the L blocks.
  7. Apply the final layer norm to all tokens.
  8. Take the CLS token as the frame embedding.
  9. Take the patch tokens as the patch embeddings.

The ImageNet mean is (0.485, 0.456, 0.406) and the standard deviation is (0.229, 0.224, 0.225). These values apply to the LVD-1689M weights. The backbone also has a mask token. Only the iBOT loss in training uses it.

The feed-forward size is the length of the inner vector of the feed-forward network. For SwiGLU, the code takes two thirds of D times the feed-forward ratio. Then it rounds up to a multiple of 8, or 64 for ViT-7B/16.

All six model sizes share the patch size 16, the 4 register tokens, LayerScale, RoPE and layer norms with eps 1e-5. The key projection has no bias. The query and value projections have biases in five model sizes. ViT-7B/16 has no query bias and no value bias. ViT-7B/16 has one more layer norm for local crops, and only training uses it. DINOv3 also has four ConvNeXt backbones, but they are not in the scope of this repo.

Inside a block

Each block changes the token sequence in two residual branches. The equations below use LN for a layer norm and ⊙ for the product per channel.

block input    x, with T = 1 + 4 + N tokens of D values each
attention      x ← x + γ1 ⊙ Attention(LN1(x))
feed-forward   x ← x + γ2 ⊙ FFN(LN2(x))
MLP            FFN(x) = down(GELU(up(x)))
SwiGLU         FFN(x) = down(SiLU(gate(x)) ⊙ up(x))

γ1 and γ2 are the LayerScale factors. The names up, down and gate follow the Hugging Face layers up_proj, down_proj and gate_proj. The attention computes queries, keys and values with the separate layers q_proj, k_proj and v_proj. It rotates the queries and keys of the patch tokens with RoPE. Then it applies scaled dot-product attention and the output layer o_proj.

RoPE

RoPE gives each patch token its position. The tables depend on the patch grid, so each input resolution needs its own tables. The base is a set value of 100 for all model sizes. The official code makes the tables in these steps.

  1. Place each patch at the center of its grid cell, separately for rows and columns.
  2. Map the coordinates from the range 0 to 1 to the range −1 to 1.
  3. Make d/4 periods per axis, where d is the head dimension.
  4. Compute one angle for each coordinate and each period.
  5. Rotate the queries and keys of the patch tokens with the cosine and sine of the angles.
coordinate   c  = 2 · (i + 0.5) / n − 1      i = row or column index, n = grid size
period       pk = base ^ (4k / d)             k = 0 … d/4 − 1
angle        θ  = 2π · c / pk
rotation     q′ = q ⊙ cos θ + rotate_half(q) ⊙ sin θ      the same for k

The CLS token and the register tokens get no rotation. The official code computes RoPE in fp32 and casts the result back to the dtype of the queries and keys. In training, RoPE-box jittering scales the coordinate box by a random factor from 0.5 to 2. Inference uses the factor 1.

How DINOv3 learned its features

The training method explains why the patch embeddings are good. It also shows what fine-tuning can damage. Table 6 gives the training stages that the paper describes.

Training stageWhat the paper describes
DataLVD-1689M: 1,689 million images that Meta selected from a pool of about 17 billion web images.
PretrainingThe teacher trains for 1M iterations with a constant learning rate, weight decay and EMA momentum. Each image gives 2 global crops of 256 px and 8 local crops of 112 px. A batch has 4096 images.
RefinementAfter 1M iterations, the training adds Gram anchoring. The Gram teacher gets new weights every 10k iterations. Its input has twice the resolution, and the training downsamples its output by a factor of 2.
High-resolution adaptation10k more iterations with global crops of 512 and 768 px and local crops from 112 to 336 px, with Gram anchoring.
DistillationThe students learn from the frozen teacher in parallel: 1M iterations, then 250k iterations of cosine learning-rate cooldown, then high-resolution adaptation without Gram anchoring.

Table 6. Training stages of DINOv3, from the paper.

pretraining   L_Pre  = L_DINO + L_iBOT + w_K · L_KoLeo
Gram loss     L_Gram = ‖ X_S · X_Sᵀ − X_G · X_Gᵀ ‖²_F
refinement    L_Ref  = w_D · L_DINO + L_iBOT + w_DK · L_KoLeo + w_Gram · L_Gram

X_S and X_G hold the L2-normalized patch embeddings of the online network and of the Gram teacher, one row per patch. The paper sets w_K to 0.1. It computes the KoLeo term on small batches of 16 samples. It replaces the centering of DINO with Sinkhorn-Knopp in the DINO loss and the iBOT loss.

Gram anchoring matters for Step 8. Fine-tuning can also change the patch embeddings in ways that hurt dense tasks. A Gram anchoring term against the frozen backbone is one candidate in Step 8b.

Parity

Unit: none, from −1 to 1. Higher is better.

Parity measures how close an output vector is to the vector of the reference output. The value 1 means the same direction.

We compute the parity in these steps.

  1. Compute the output on the backend under test.
  2. Load the reference output for the same image, model size and input resolution.
  3. Cast both outputs to fp64.
  4. Compute the cosine similarity for each pair of vectors.
  5. For patch embeddings, take the mean, the 1st percentile and the minimum over all patches. The minimum is report only.
cosine   cos(a, b) = (a · b) / (‖a‖ · ‖b‖)

Our production use cases set two priority configurations. The first is ViT-S/16 with frame embeddings. The second is ViT-H+/16 and ViT-S/16 with patch embeddings at 512 px.

Benchmark procedure

The harness measures one configuration in these steps.

  1. Start a new subprocess for the configuration.
  2. Check the free memory, and record a skip if the configuration does not fit.
  3. Load the model and record the load time.
  4. Run the warm-up batches.
  5. Run the timed batches, and synchronize the backend after each batch.
  6. Record the throughput, the latency and the peak memory.
  7. Write one JSON line with the configuration, the results, the versions and the machine.
throughput   images per second = batch size · timed batches / timed seconds

Unit of the throughput: images per second. Higher is better. Unit of the peak memory: GB. Lower is better. We set the numbers of warm-up batches (5) and timed batches (30). Step 3 can change them with a reason. torch-mps synchronizes with torch.mps.synchronize(). mlx synchronizes with mx.eval.

Fine-tuning

This section describes Step 8, the last step. Step 8a makes the reference fine-tuning setup fast in MLX. Step 8b compares better adapters on the same task.

Step 8a. Make the reference fine-tuning setup fast

  1. Choose a public dataset that resembles our task, and check its license.
  2. Train the reference fine-tuning setup in PyTorch with PEFT on this dataset.
  3. Record the task quality, the training throughput and the peak memory.
  4. Implement LoRA layers for the MLX backbone.
  5. Train the same setup in MLX with the same seed and data order.
  6. Compile the training step with mx.compile.
  7. Test bf16 weights for the frozen backbone with fp32 adapters.
  8. Embed each unique frame once when sequences share frames.
  9. Test gradient checkpointing for larger batches and 512 px inputs.

Our production prediction code already embeds each unique frame once. Action 8 tests the same idea in training. Step 8a ends when MLX reaches the task quality of the PyTorch run within a tolerance that plan.html sets. MLX must also have a higher training throughput.

We also run four experiments that come from the DINOv3 design.

  • Target modules: q_proj and v_proj, all four attention layers, and all linear layers.
  • Rank: 2, 4, 8 and 16.
  • Adapters in the last blocks only, which makes the backward pass shorter.
  • A Gram anchoring term that keeps the Gram matrix of the patch embeddings close to that of the frozen backbone.

We measure the task quality, the training throughput, the peak memory and the number of trainable parameters. The private evaluation on production data stays outside this repo. Step 8b ends when Table 13 has measured values for each adapter on the public dataset.
